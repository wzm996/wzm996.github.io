<blockquote>
<p>很多团队一开始用定时任务都很顺手：<code>@Scheduled</code> 一贴，需求就上线了。但线上一跑几天，任务开始延迟、堆积、超时，最后大家才发现：不是“定时任务不准”，而是你根本没看见它背后的线程池、执行时长和排队情况。</p>

<h1 id="先说结论：定时任务变慢，往往不是“调度器坏了”"><a href="#先说结论：定时任务变慢，往往不是“调度器坏了”" class="headerlink" title="先说结论：定时任务变慢，往往不是“调度器坏了”"></a>先说结论：定时任务变慢，往往不是“调度器坏了”</h1>
<p>在 Java 服务里，定时任务“越跑越慢”最常见的根因，不是框架 bug，而是下面这几类问题叠在一起：</p>
<ul>
<li><strong>任务执行时间超过调度周期</strong>，导致下一轮开始排队；</li>
<li><strong>线程池配置过小</strong>，多个任务互相阻塞；</li>
<li><strong>把 IO 型任务、重计算任务、远程调用任务混在同一个调度线程池</strong>；</li>
<li><strong>没有暴露调度指标</strong>，直到 SLA 报警才发现问题；</li>
<li><strong>错误使用 fixedRate / fixedDelay</strong>，让“节拍”和“实际耗时”打架。</li>
</ul>
<p>这篇文章不讲空话，直接用一个可复现的小实验把问题跑出来，再演示怎么观察、怎么验证、怎么改。</p>

<h1 id="几个关键名词，先说人话版"><a href="#几个关键名词，先说人话版" class="headerlink" title="几个关键名词，先说人话版"></a>几个关键名词，先说人话版</h1>
<p><strong>fixedRate</strong>：按“理想节拍”触发任务，比如你要求每 5 秒执行一次，它会尽量按这个频率发车，不管上一班是不是已经很挤了。</p>
<p><strong>fixedDelay</strong>：上一轮任务彻底执行完之后，再等固定时长再执行下一轮。它更像“上一个人忙完，再叫下一个”。</p>
<p><strong>ScheduledThreadPoolExecutor</strong>：JDK 自带的定时任务线程池。说白了，它就是负责“按时间点投递任务 + 用几个工作线程执行任务”的调度器。</p>
<p><strong>Micrometer</strong>：Java 生态里很常见的指标埋点库。它是啥？它就是把执行次数、耗时、失败次数这种数据标准化暴露出来，方便接 Prometheus、Grafana。</p>
<p><strong>JFR（Java Flight Recorder）</strong>：JDK 自带的低开销诊断工具。简单说，它像一个黑匣子，能记录线程、锁、方法热点、GC 等事件，适合线上排障。</p>
<p><strong>async-profiler</strong>：一款很常用的 Java 性能采样工具。它解决的是“CPU 时间到底花在哪儿了”的问题，常用来生成火焰图。</p>

<h1 id="为什么定时任务会堆积：本质是供需失衡"><a href="#为什么定时任务会堆积：本质是供需失衡" class="headerlink" title="为什么定时任务会堆积：本质是供需失衡"></a>为什么定时任务会堆积：本质是供需失衡</h1>
<p>先把模型简化一下。假设有一个任务，每 <strong>5 秒</strong> 调度一次，但它实际执行要 <strong>8 秒</strong>。如果线程池里只有 <strong>1 个线程</strong>，那结果其实很明确：</p>
<ul>
<li>第 1 次：0 秒开始，8 秒结束；</li>
<li>第 2 次：理论上 5 秒就该开始，但线程还在忙，只能排队；</li>
<li>第 3 次：理论上 10 秒开始，但前面的还没完全消化；</li>
<li>系统看起来就像“越来越慢”。</li>
</ul>
<p>这里最容易误解的一点是：<strong>慢的不是“某一次调度”，而是系统开始产生持续性的调度延迟（schedule lag）</strong>。也就是“任务本来该在 T 时刻开始，结果真正开始已经是 T+N 秒了”。</p>
<p>工程上真正该盯的，不只是“单次执行耗时”，还要盯：</p>
<ul>
<li><strong>调度延迟</strong>：任务真正开始时间 - 计划开始时间；</li>
<li><strong>执行耗时</strong>：从 run 开始到结束；</li>
<li><strong>队列堆积</strong>：当前有多少待执行任务；</li>
<li><strong>线程池活跃度</strong>：活跃线程数 / 线程池大小；</li>
<li><strong>失败率</strong>：失败重试是否进一步放大了负载。</li>
</ul>

<h1 id="可复现实验：用一个小程序把“越跑越慢”跑出来"><a href="#可复现实验：用一个小程序把“越跑越慢”跑出来" class="headerlink" title="可复现实验：用一个小程序把“越跑越慢”跑出来"></a>可复现实验：用一个小程序把“越跑越慢”跑出来</h1>
<p>下面这个例子故意制造问题：两个固定频率任务共享同一个只有 1 个线程的调度池，其中一个任务每次执行 8 秒，但调度周期只有 5 秒。</p>

```java
import java.time.Duration;
import java.time.Instant;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;

public class SchedulerLagDemo {

    private static final AtomicLong expectedFast = new AtomicLong(System.currentTimeMillis());
    private static final AtomicLong expectedSlow = new AtomicLong(System.currentTimeMillis());

    public static void main(String[] args) {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);

        scheduler.scheduleAtFixedRate(() -> runTask("fast-task", expectedFast, 5000, 2000),
                0, 5, TimeUnit.SECONDS);

        scheduler.scheduleAtFixedRate(() -> runTask("slow-task", expectedSlow, 5000, 8000),
                0, 5, TimeUnit.SECONDS);
    }

    private static void runTask(String taskName, AtomicLong expected, long periodMs, long workMs) {
        long now = System.currentTimeMillis();
        long shouldStart = expected.getAndAdd(periodMs);
        long lag = Math.max(0, now - shouldStart);

        Instant begin = Instant.now();
        System.out.printf("[%s] begin=%s lag=%dms work=%dms%n", taskName, begin, lag, workMs);

        try {
            Thread.sleep(workMs);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        Instant end = Instant.now();
        System.out.printf("[%s] end=%s duration=%dms%n", taskName, end,
                Duration.between(begin, end).toMillis());
    }
}
```

<p>编译并运行：</p>

```bash
javac SchedulerLagDemo.java
java SchedulerLagDemo
```

<p>你大概率会看到类似输出：</p>

```text
[fast-task] begin=2026-04-11T10:00:00 lag=0ms work=2000ms
[fast-task] end=2026-04-11T10:00:02 duration=2001ms
[slow-task] begin=2026-04-11T10:00:02 lag=2002ms work=8000ms
[slow-task] end=2026-04-11T10:00:10 duration=8001ms
[fast-task] begin=2026-04-11T10:00:10 lag=5001ms work=2000ms
[fast-task] end=2026-04-11T10:00:12 duration=2001ms
[slow-task] begin=2026-04-11T10:00:12 lag=7004ms work=8000ms
```

<p>这就说明问题已经出来了：<strong>不是任务执行函数本身越来越慢，而是它开始执行得越来越晚</strong>。</p>

<h2 id="如何验证结论"><a href="#如何验证结论" class="headerlink" title="如何验证结论"></a>如何验证结论</h2>
<ul>
<li>把线程池大小从 <code>1</code> 改成 <code>2</code>，重新运行，看 lag 是否显著下降；</li>
<li>把 slow-task 的执行时间从 <code>8000ms</code> 改成 <code>3000ms</code>，看调度是否恢复稳定；</li>
<li>把 <code>scheduleAtFixedRate</code> 改成 <code>scheduleWithFixedDelay</code>，观察系统不再堆积，但吞吐节拍下降。</li>
</ul>

<h1 id="fixedRate-vs-fixedDelay：别把两个语义混着用"><a href="#fixedRate-vs-fixedDelay：别把两个语义混着用" class="headerlink" title="fixedRate vs fixedDelay：别把两个语义混着用"></a>fixedRate vs fixedDelay：别把两个语义混着用</h1>
<p>这俩名字大家都眼熟，但线上问题很多就是从这里开始的。</p>

| 模式 | 语义 | 适合场景 | 风险 |
| --- | --- | --- | --- |
| fixedRate | 尽量按固定节拍触发 | 指标采集、心跳上报、轻量级周期任务 | 任务变慢时容易出现调度延迟积累 |
| fixedDelay | 上次执行完成后再等待固定时长 | 扫描任务、批处理、补偿任务 | 节拍不稳定，实际执行频率可能下降 |

<p>如果你的任务包含以下特征，优先考虑 <strong>fixedDelay</strong>：</p>
<ul>
<li>依赖下游接口，耗时波动大；</li>
<li>任务不可重入，不适合并发执行；</li>
<li>任务本身就是“扫一遍、处理一批、再等一会儿”。</li>
</ul>
<p>如果你必须使用 <strong>fixedRate</strong>，那至少要把这几个问题先想清楚：</p>
<ul>
<li>任务最坏耗时是多少？</li>
<li>线程池峰值并发需要多少？</li>
<li>任务是否允许跳过、降频或者合并？</li>
<li>超时后是失败退出，还是把线程一直占住？</li>
</ul>

<h1 id="Spring-Boot-里最容易踩的坑：默认调度器常常不够用"><a href="#Spring-Boot-里最容易踩的坑：默认调度器常常不够用" class="headerlink" title="Spring Boot 里最容易踩的坑：默认调度器常常不够用"></a>Spring Boot 里最容易踩的坑：默认调度器常常不够用</h1>
<p>很多 Java 项目里，定时任务是这么写出来的：</p>

```java
@Component
public class ReportJob {

    @Scheduled(fixedRate = 5000)
    public void syncReport() {
        // 查数据库、调 RPC、拼报表、发消息
    }
}
```

<p>看起来没问题，但如果你没有显式配置调度线程池，就很容易在项目演进后出事。尤其是下面几种情况：</p>
<ul>
<li>一个服务里挂了十几个 <code>@Scheduled</code>；</li>
<li>有的任务会访问数据库，有的任务会调用外部 HTTP 接口；</li>
<li>某个任务偶发慢查询或下游超时，直接把调度线程拖住；</li>
<li>本来只是“后台小任务”，后面慢慢长成“半个批处理系统”。</li>
</ul>

<p>更稳妥的做法，是显式给出调度线程池配置，并把不同类型任务隔离开。</p>

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskScheduler;

@Configuration
public class SchedulerConfig {

    @Bean
    public ThreadPoolTaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(4);
        scheduler.setThreadNamePrefix("schedule-worker-");
        scheduler.setAwaitTerminationSeconds(30);
        scheduler.setWaitForTasksToCompleteOnShutdown(true);
        scheduler.setRemoveOnCancelPolicy(true);
        return scheduler;
    }
}
```

<p>上面几个参数第一次见也别慌：</p>
<ul>
<li><strong>poolSize</strong>：调度线程池大小，简单理解就是“同时最多有几个任务在跑”；</li>
<li><strong>setWaitForTasksToCompleteOnShutdown</strong>：服务关闭时是否等待任务执行完，适合需要优雅停机的任务；</li>
<li><strong>setRemoveOnCancelPolicy</strong>：取消的任务尽快从队列里移除，避免队列里堆无效任务。</li>
</ul>

<h1 id="只调线程数还不够：得把调度指标暴露出来"><a href="#只调线程数还不够：得把调度指标暴露出来" class="headerlink" title="只调线程数还不够：得把调度指标暴露出来"></a>只调线程数还不够：得把调度指标暴露出来</h1>
<p>很多线上事故的真实问题，不是“不会改”，而是<strong>出问题前根本没看到</strong>。所以建议至少暴露三类指标：</p>
<ul>
<li>任务执行耗时（timer）</li>
<li>任务执行次数 / 失败次数（counter）</li>
<li>调度延迟、线程池活跃数、队列长度（gauge）</li>
</ul>

<p>下面给一个基于 Micrometer 的简单埋点示例：</p>

```java
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;

import java.util.concurrent.ScheduledThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class InstrumentedScheduler {

    private final ScheduledThreadPoolExecutor executor;
    private final Timer durationTimer;
    private final Counter failureCounter;

    public InstrumentedScheduler(MeterRegistry registry) {
        this.executor = new ScheduledThreadPoolExecutor(4);
        this.durationTimer = Timer.builder("scheduler.task.duration")
                .tag("task", "order-sync")
                .publishPercentiles(0.5, 0.95, 0.99)
                .register(registry);
        this.failureCounter = Counter.builder("scheduler.task.failure")
                .tag("task", "order-sync")
                .register(registry);

        Gauge.builder("scheduler.queue.size", executor, e -> e.getQueue().size())
                .register(registry);
        Gauge.builder("scheduler.active.count", executor, ScheduledThreadPoolExecutor::getActiveCount)
                .register(registry);
    }

    public void start() {
        executor.scheduleAtFixedRate(() -> {
            Timer.Sample sample = Timer.start();
            try {
                // do work
                TimeUnit.MILLISECONDS.sleep(300);
                sample.stop(durationTimer);
            } catch (Exception e) {
                failureCounter.increment();
                sample.stop(durationTimer);
                throw new RuntimeException(e);
            }
        }, 0, 5, TimeUnit.SECONDS);
    }
}
```

<p>如果你把这些指标接到 Prometheus + Grafana，至少要看下面几个图：</p>
<ul>
<li><strong>P50 / P95 / P99 执行耗时</strong>；</li>
<li><strong>失败次数</strong>；</li>
<li><strong>线程池 active 数</strong>；</li>
<li><strong>队列长度</strong>；</li>
<li><strong>调度延迟</strong>（如果你自己埋了这个指标）。</li>
</ul>

<h2 id="一个很实用的判断标准"><a href="#一个很实用的判断标准" class="headerlink" title="一个很实用的判断标准"></a>一个很实用的判断标准</h2>
<p>如果你看到下面这组现象，基本可以判定任务已经在“慢性堆积”：</p>
<ul>
<li>P95/P99 执行耗时抬升；</li>
<li>队列长度持续不回落；</li>
<li>active thread 长时间贴着 poolSize；</li>
<li>下游超时增多；</li>
<li>同一时间窗口里，业务侧感知到“任务结果越来越晚到账”。</li>
</ul>

<h1 id="优化前后怎么比：别只看平均值"><a href="#优化前后怎么比：别只看平均值" class="headerlink" title="优化前后怎么比：别只看平均值"></a>优化前后怎么比：别只看平均值</h1>
<p>平均值很好看，但很容易骗人。调度任务这类问题，建议至少对比下面几个指标：</p>

| 指标 | 优化前 | 优化后 | 说明 |
| --- | ---: | ---: | --- |
| 线程池大小 | 1 | 4 | 提高并发能力，但不是万能药 |
| 平均执行耗时 | 2.7s | 2.4s | 平均值变化可能不大 |
| P95 执行耗时 | 8.3s | 3.1s | 尾延迟改善通常更关键 |
| P99 执行耗时 | 12.6s | 4.8s | 是否还有极端阻塞 |
| 队列峰值 | 37 | 3 | 是否仍持续堆积 |
| 调度延迟峰值 | 18.4s | 1.2s | 用户真正感知到的是这个 |

<p>注意，这里我故意把“平均执行耗时”放在前面，就是想强调：<strong>平均值没那么重要，尾延迟和堆积才重要</strong>。线上定时任务最怕的是“平时还行，偶发很炸”。</p>

<h1 id="JFR-怎么抓：低开销看线程和热点"><a href="#JFR-怎么抓：低开销看线程和热点" class="headerlink" title="JFR 怎么抓：低开销看线程和热点"></a>JFR 怎么抓：低开销看线程和热点</h1>
<p>如果你怀疑任务执行真的变慢了，而不是单纯排队，可以直接抓一段 JFR。</p>

```bash
jcmd <pid> JFR.start name=scheduler-lag settings=profile duration=3m filename=/tmp/scheduler-lag.jfr
```

<p>这个命令的意思很简单：</p>
<ul>
<li><code>jcmd</code>：JDK 自带诊断命令；</li>
<li><code>settings=profile</code>：用偏分析型的事件配置；</li>
<li><code>duration=3m</code>：录 3 分钟就停；</li>
<li><code>filename=...</code>：把结果写到文件里。</li>
</ul>

<p>验证方式：</p>
<ul>
<li>用 JDK Mission Control 打开 <code>/tmp/scheduler-lag.jfr</code>；</li>
<li>重点看 <strong>Threads</strong>、<strong>Method Profiling</strong>、<strong>Locks</strong>、<strong>Socket I/O</strong>；</li>
<li>如果你发现大量时间耗在 <code>java.net.SocketInputStream</code>，说明可能是下游调用慢；</li>
<li>如果大量时间耗在锁等待，说明可能是任务内部竞争，不只是线程池配置问题。</li>
</ul>

<h1 id="async-profiler-怎么抓：看火焰图最直观"><a href="#async-profiler-怎么抓：看火焰图最直观" class="headerlink" title="async-profiler 怎么抓：看火焰图最直观"></a>async-profiler 怎么抓：看火焰图最直观</h1>
<p>如果你的机器上已经装了 async-profiler，可以这样抓 CPU 采样：</p>

```bash
./profiler.sh -d 60 -e cpu -f /tmp/scheduler-cpu.html <pid>
```

<p>这里的意思也不复杂：</p>
<ul>
<li><code>-d 60</code>：采样 60 秒；</li>
<li><code>-e cpu</code>：采 CPU 热点；</li>
<li><code>-f</code>：输出成 HTML 火焰图。</li>
</ul>

<p>验证方式：</p>
<ul>
<li>打开 <code>/tmp/scheduler-cpu.html</code>；</li>
<li>如果热点集中在 JSON 序列化、数据库结果处理、加解密等 CPU 密集操作，说明任务逻辑本身就该拆或限流；</li>
<li>如果 CPU 很空，但任务还是慢，多半是 IO 阻塞、锁竞争或者外部依赖拖慢。</li>
</ul>

<h1 id="常见坑：不是把线程池调大就完了"><a href="#常见坑：不是把线程池调大就完了" class="headerlink" title="常见坑：不是把线程池调大就完了"></a>常见坑：不是把线程池调大就完了</h1>
<ul>
<li><strong>坑 1：把所有任务都扔一个池子里</strong><br>轻任务、重任务、IO 任务、补偿任务，混在一起最容易互相伤害。更合理的做法是按任务类型拆池。</li>
<li><strong>坑 2：没有超时控制</strong><br>如果任务里有 RPC、HTTP、数据库调用，但没有超时，线程被卡住时你连止损都做不到。</li>
<li><strong>坑 3：失败后立即重试</strong><br>本来就慢了，你还叠加重试，等于自己给自己加压。</li>
<li><strong>坑 4：把 fixedRate 用在长任务上</strong><br>固定节拍很美好，但前提是你真有能力维持节拍。</li>
<li><strong>坑 5：只看接口 RT，不看后台任务</strong><br>很多系统前台接口正常，但后台任务已经烂了。等数据延迟、报表延迟、状态同步延迟出现时，问题其实已经积了很久。</li>
</ul>

<h1 id="更靠谱的治理思路"><a href="#更靠谱的治理思路" class="headerlink" title="更靠谱的治理思路"></a>更靠谱的治理思路</h1>
<ol>
<li><strong>先区分任务类型</strong>：CPU 密集、IO 密集、补偿型、扫描型不要混用一个线程池；</li>
<li><strong>为每类任务定义 SLO</strong>：比如 99% 的任务 10 秒内完成，调度延迟不超过 3 秒；</li>
<li><strong>默认暴露耗时、失败、队列、活跃线程指标</strong>；</li>
<li><strong>出现抖动时先看调度延迟，再看执行耗时</strong>；</li>
<li><strong>对长任务做拆分、分片、幂等和限流</strong>；</li>
<li><strong>必要时从本地定时任务升级到专业调度系统</strong>，比如 XXL-JOB、Quartz、K8s CronJob，别让一个 Spring 服务偷偷长成任务平台。</li>
</ol>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>
<ul>
<li>定时任务“越跑越慢”，很多时候慢的是<strong>开始执行的时机</strong>，不是代码本身；</li>
<li><strong>fixedRate</strong> 和 <strong>fixedDelay</strong> 的语义差异，决定了系统是否容易堆积；</li>
<li>线程池大小重要，但更重要的是<strong>任务隔离 + 指标暴露 + 超时治理</strong>；</li>
<li>排障时不要只看平均值，要重点看 <strong>P95/P99、队列峰值、调度延迟</strong>；</li>
<li>JFR 和 async-profiler 都值得常备，前者适合低开销全局观察，后者适合看热点和火焰图。</li>
</ul>
