<blockquote><p>Java 21 正式发布的虚拟线程（Virtual Threads，Project Loom）被称为"Java 并发编程史上最重要的里程碑之一"。它号称能轻松创建百万级并发线程，让同步代码写出异步的吞吐量。但虚拟线程到底是什么？和传统线程池比到底快多少？有哪些坑？本文从原理讲到 Spring Boot 压测实战，给你一份"能不能上生产"的决策依据。</p></blockquote>

<h1>一、背景：为什么需要虚拟线程</h1>

<p>在聊虚拟线程之前，先回顾一下我们每天在用的<strong>平台线程（Platform Thread）</strong>——也就是传统的 <code>new Thread()</code> 或线程池里的线程。</p>

<p>平台线程有一个根本性的限制：<strong>它是 OS 线程的包装</strong>。每个平台线程底层对应一个操作系统内核线程，而 OS 线程是昂贵的资源：</p>

<ul>
<li>默认栈大小约 1MB（<code>-Xss</code> 控制），1 万个线程 ≈ 10GB 内存</li>
<li>OS 线程调度涉及内核态/用户态切换，上下文切换开销大</li>
<li>线程数受限于 CPU 核数和内存，一般几百个就是上限</li>
</ul>

<p>所以我们在写 Web 服务时，不得不使用<strong>线程池</strong>来限制并发数。Tomcat 默认 200 工作线程，一旦线程都在等 IO（数据库查询、RPC 调用），新请求就只能排队——这就是<strong>"线程池饥饿"</strong>问题。</p>

<p>历史上我们尝试过各种方案绕开这个限制：</p>

<table>
<thead>
<tr><th>方案</th><th>思路</th><th>代价</th></tr>
</thead>
<tbody>
<tr><td>异步编程（Reactor/Mono）</td><td>用事件循环替代多线程</td><td>学习曲线陡峭；调试困难；代码变成"回调地狱"</td></tr>
<tr><td>响应式框架（WebFlux）</td><td>Netty 事件驱动</td><td>生态兼容性差（JDBC 不友好）；团队改造成本高</td></tr>
<tr><td>增加机器</td><td>水平扩展</td><td>钱能解决的问题不是问题，但浪费钱</td></tr>
</tbody>
</table>

<p><strong>虚拟线程的思路完全不同</strong>：它不试图让你换编程模型，而是让"线程"这个概念本身变得极其廉价。</p>

<hr>

<h1>二、核心概念：虚拟线程是什么</h1>

<h2>2.1 定义</h2>

<p><strong>虚拟线程（Virtual Thread）</strong>是一种由 JVM 用户态调度而非 OS 内核调度的轻量级线程实现。它是 <code>java.lang.Thread</code> 的一个子类，API 上和普通线程完全一样，但：</p>

<ul>
<li>创建成本极低：不需要分配 OS 栈，初始栈只有几 KB（按需增长）</li>
<li>可以轻松创建<strong>百万级</strong>虚拟线程</li>
<li>由 JVM 的 <strong>ForkJoinPool</strong>（工作窃取调度器）调度到少量平台线程上执行</li>
</ul>

<p>打个比方：平台线程就像"正式员工"，数量有限、薪资高昂；虚拟线程就像"临时工"，数量可以很多，干活的还是那几个正式员工（载体线程/Carrier Thread），但调度更灵活。</p>

<h2>2.2 关键机制：Mount / Unmount（挂载/卸载）</h2>

<p>当虚拟线程执行到阻塞操作（I/O、<code>Thread.sleep()</code>、<code>synchronized</code> 以外的锁等待）时，JVM 会自动将它从当前平台线程上<strong>卸载（Unmount）</strong>，释放平台线程去执行其他虚拟线程。当阻塞操作完成后，虚拟线程会被重新<strong>挂载（Mount）</strong>到某个平台线程继续执行。</p>

<p>这个过程对开发者<strong>完全透明</strong>——你写的代码看起来就是普通的同步调用。</p>

<pre><code class="language-java">// 创建并启动一个虚拟线程
Thread.ofVirtual().start(() -> {
    // 这里做任何阻塞操作都没问题
    HttpClient client = HttpClient.newHttpClient();
    String response = client.send(HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/data"))
        .build(), HttpResponse.BodyHandlers.ofString()).body();
    System.out.println(response);
});

// 或者用 ExecutorService（推荐方式）
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> doSomethingBlocking());
}
</code></pre>

<h2>2.3 虚拟线程 vs 平台线程 vs 协程</h2>

<table>
<thead>
<tr><th>维度</th><th>平台线程</th><th>虚拟线程</th><th>Kotlin 协程</th></tr>
</thead>
<tbody>
<tr><td>调度者</td><td>OS 内核</td><td>JVM ForkJoinPool</td><td>用户态调度器</td></tr>
<tr><td>创建成本</td><td>高（~10万 ns）</td><td>极低（~200 ns）</td><td>极低</td></tr>
<tr><td>栈内存</td><td>固定 ~1MB</td><td>按需增长 ~几KB</td><td>按需增长</td></tr>
<tr><td>最大数量</td><td>数百~数千</td><td>百万级</td><td>百万级</td></tr>
<tr><td>阻塞处理</td><td>占用 OS 线程</td><td>自动卸载/重挂载</td><td>suspend/resume</td></tr>
<tr><td>编程模型</td><td>同步</td><td>同步（不变！）</td><td>需 async/await</td></tr>
<tr><td>JDK 版本</td><td>全版本</td><td>JDK 19 预览 / 21 正式</td><td>需 Kotlin 运行时</td></tr>
</tbody>
</table>

<h1>三、Spring Boot 中启用虚拟线程</h1>

<p>好消息是：Spring Boot 3.2+ 已经原生支持虚拟线程，开启只需要一行配置。</p>

<h2>3.1 前置条件</h2>

<ul>
<li>JDK 21+</li>
<li>Spring Boot 3.2+</li>
<li>Tomcat 作为嵌入式容器（默认即是）</li>
</ul>

<h2>3.2 开启方式</h2>

<p>在 <code>application.yml</code> 中添加：</p>

<pre><code class="language-yaml">spring:
  threads:
    virtual:
      enabled: true
</code></pre>

<p>就这么简单。Spring 会自动将 Tomcat 的请求处理线程替换为虚拟线程。</p>

<p><strong>注：</strong>如果你用的是 Undertow 或 Jetty，目前（截至 2026 年）对虚拟线程的支持不如 Tomcat 成熟，建议先用 Tomcat。</p>

<h2>3.3 验证是否生效</h2>

<pre><code class="language-java">@RestController
public class DebugController {

    @GetMapping("/thread-info")
    public Map&lt;String, Object&gt; threadInfo() {
        Thread t = Thread.currentThread();
        return Map.of(
            "name", t.getName(),
            "isVirtual", t.isVirtual(),
            "class", t.getClass().getName()
        );
    }
}
</code></pre>

<p>访问 <code>/thread-info</code>，如果 <code>"isVirtual": true</code>，说明虚拟线程已生效。</p>

    int result = 0;

    }
    // 模拟 20ms IO 等待
    Thread.sleep(20);

<h2>4.4 结果分析</h2>

<p>关键发现：</p>

<ol>
<li><strong>IO 密集型场景提升巨大</strong>：吞吐翻倍，P99 延迟减半。原因很简单——虚拟线程消除了线程池排队瓶颈。200 个平台线程全部阻塞时，新请求只能排队；而虚拟线程可以创建数十万个，几乎不会排队。</li>

<li><strong>CPU 密集型提升有限</strong>：因为瓶颈在 CPU 而非线程数。虚拟线程不是银弹，它解决的是<strong>线程等待利用率</strong>问题，不是计算能力问题。</li>

<li><strong>尾延迟改善显著</strong>：P99 的降幅远大于平均延迟。这是因为虚拟线程消除了"长尾请求占着线程不放"的问题。</li>
</ol>

<h1>五、生产环境踩坑指南</h1>

<p>虚拟线程虽好，但直接上线会踩坑。以下是社区已经趟过的雷区。</p>

<h2>5.1 坑 #1：synchronized 导致线程钉住（Pinned Thread）</h2>

<p><strong>这是最常见也最致命的坑。</strong></p>

<p>虚拟线程在遇到 <code>synchronized</code> 块或方法时<strong>无法卸载</strong>——它会"钉"在当前平台线程上，直到退出 synchronized 块。这意味着如果一个虚拟线程持有了 synchronized 锁并且在里面做了阻塞操作，它背后的那个平台线程就被白白占住了。</p>

<pre><code class="language-java">// ❌ 危险！synchronized 会导致 Pin
public synchronized void dangerousMethod() throws InterruptedException {
    Thread.sleep(1000); // 虚拟线程被钉住 1 秒，平台线程无法服务其他虚拟线程
}

// ✅ 改用 ReentrantLock（支持虚拟线程卸载）
private final ReentrantLock lock = new ReentrantLock();

public void safeMethod() throws InterruptedException {
    lock.lock();
    try {
        Thread.sleep(1000); // 虚拟线程正常卸载，不占用平台线程
    } finally {
        lock.unlock();
    }
}
</code></pre>

<p><strong>如何检测 Pin 问题</strong>：JDK 提供了 JVM 参数：</p>

<pre><code class="language-bash">-Djdk.tracePinnedThreads=short   # 打印简短 pin 堆栈
-Djdk.tracePinnedThreads=full    # 打印完整 pin 堆栈（推荐排查时使用）
</code></pre>

<p>开启后，当虚拟线程被钉住超过一定阈值时，控制台会输出堆栈信息，帮你定位是哪段 synchronized 代码导致的。</p>

<h2>5.2 坑 #2：连接池成为新瓶颈</h2>

<p>用了虚拟线程后，线程不再是瓶颈了，但<strong>数据库连接池</strong>可能成为新的瓶颈。</p>

<p>传统模式下，200 个线程 × 每个线程需要一个 DB 连接 → 连接池设 20 就够了（大部分线程在排队）。虚拟线程模式下，同时可能有数千个请求在跑，每个都需要 DB 连接 → 连接池瞬间打满。</p>

<p><strong>解决方案</strong>：</p>

<ul>
<li>适当增大连接池大小（HikariCP 从 20 调到 50~100，视 DB 承受力而定）</li>
<li>考虑引入 <code>virtual-per-task</code> 模式的连接获取策略</li>
<li>监控连接池等待指标（<code>HikariPool-xx - Pool Wait</code> 是关键指标）</li>
</ul>

<p>参考数据（来源 InfoQ 2025）：HikariCP 从 20 调到 50 后，虚拟线程模式下的 JDBC 场景吞吐从 624 req/s 提升到 1,539 req/s（+147%）。</p>

<h2>5.3 坑 #3：ThreadLocal 内存爆炸</h2>

<p>虚拟线程可以创建百万级，如果你的代码在每个请求的 ThreadLocal 里放了哪怕 1KB 数据，100 万个虚拟线程 = 1GB 仅用于 ThreadLocal。</p>

<pre><code class="language-java">// ⚠️ 危险：大量虚拟线程 + 大 ThreadLocal = OOM
private static final ThreadLocal&lt;byte[]&gt; data = 
    ThreadLocal.withInitial(() -> new byte[1024]); // 每个虚拟线程 1KB
</code></pre>

<p><strong>解决方案</strong>：</p>

<ul>
<li>审查所有 ThreadLocal 用法，评估虚拟线程规模下的内存影响</li>
<li>JDK 21+ 引入了 <code>ScopedValue</code>（预览特性），作为 ThreadLocal 在虚拟线程时代的替代品</li>
<li>优先使用 <code>TransmittableThreadLocal</code>（阿里开源）或框架自带上下文传递机制</li>
</ul>

<h2>5.4 坑 #4：线程名/线程 ID 不再有用</h2>

<p>调试时我们习惯通过线程名或线程 ID 来追踪请求。但虚拟线程的 ID 可能复用（垃圾回收后），而且数量太多导致日志里线程信息几乎没有意义。</p>

<p><strong>建议</strong>：</p>

<ul>
<li>用 MDC（Mapped Diagnostic Context）传递请求 ID，而不是依赖线程名</li>
<li>日志中记录 <code>requestId</code> 而非 <code>threadName</code></li>
<li>APM 工具（SkyWalking、Jaeger）用 TraceId 关联，天然不受影响</li>
</ul>

<h2>5.5 坑 #5：旧版库兼容性问题</h2>

<p>一些使用了以下模式的库可能在虚拟线程下行为异常：</p>

<ul>
<li><code>Thread.currentThread().stop()</code> / <code>suspend()</code> / <code>resume()</code>（已废弃，但在老代码里可能出现）</li>
<li>依赖线程 ID 做缓存 key 的代码</li>
<li>在 <code>static</code> 块或类初始化中使用 <code>Thread.sleep()</code> 的（会导致 ClassLoader 死锁）</li>
</ul>

<p><strong>建议</strong>：升级到最新版本的常用库（Netty 4.1.x 后续版本、OkHttp 4.x+、Spring Framework 6.1+），它们大多已适配虚拟线程。</p>

<h1>六、什么时候该用 / 不该用虚拟线程</h1>

<h2>✅ 推荐使用的场景</h2>

<ul>
<li><strong>IO 密集型 Web 服务</strong>：大量 HTTP 调用、数据库查询、文件读写</li>
<li><strong>需要简化并发代码</strong>：不想引入 Reactive 编程模型</li>
<li><strong>遗留系统改造</strong>：已有同步代码想提升吞吐，不想重写成异步</li>
<li><strong>任务批处理</strong>：需要同时发起大量独立请求（如爬虫、数据聚合）</li>
</ul>

<h2>❌ 不推荐（或需谨慎）的场景</h2>

<ul>
<li><strong>CPU 密集型计算</strong>：虚拟线程不会带来提升，反而增加调度开销</li>
<li><strong>大量使用 synchronized 的遗留代码</strong>：Pin 问题严重，收益打折扣</li>
<li><strong>连接池受限且无法扩容</strong>：如共享数据库连接数有硬上限</li>
<li><strong>对延迟极度敏感的场景</strong>：虚拟线程的 mount/unmount 本身有纳秒级开销（通常可忽略，但极端场景需实测）</li>
</ul>

<h2>📊 决策流程</h2>

<pre><code>你的服务主要是 IO 密集型吗？
├─ 否 → 虚拟线程帮助有限，优先优化算法/SQL/缓存
│
└─ 是 → 能否升级到 JDK 21 + Spring Boot 3.2+？
          ├─ 不能 → 先解决升级障碍
          │
          └─ 能 → 代码中有大量 synchronized 吗？
                    ├─ 是 → 先重构为 ReentrantLock
                    │
                    └─ 否 → 数据库连接池可以适当扩大吗？
                              ├─ 不能 → 评估连接池瓶颈影响
                              │
                              └─ 能 → ✅ 可以试点虚拟线程！
                                        建议：先在非核心服务灰度验证
</code></pre>

<h1>七、总结</h1>

<p>虚拟线程是 Java 并发编程的一次范式转移。它不是要取代线程池或异步编程，而是给了我们一个新的选择：<strong>用最简单的同步代码，获得接近异步的吞吐量</strong>。</p>

<p>核心要点回顾：</p>

<ol>
<li><strong>原理</strong>：JVM 用户态调度的轻量级线程，自动 mount/unmount，对开发者透明</li>
<li><strong>开启</strong>：Spring Boot 3.2+ 只需 <code>spring.threads.virtual.enabled=true</code></li>
<li><strong>性能</strong>：IO 密集场景吞吐可翻倍，P99 延迟降低 50%+；CPU 密集场景提升有限</li>
<li><strong>避坑</strong>：避免 synchronized（用 ReentrantLock）、注意连接池新瓶颈、警惕 ThreadLocal 内存膨胀</li>
<li><strong>决策</strong>：IO 密集 + 可升级 JDK → 强烈建议试点；CPU 密集 → 收益有限</li>
</ol>

<p>对于正在使用 Java 8/11 的团队，我的建议是：<strong>将 JDK 21 + 虚拟线程纳入下一个技术升级周期的评估清单</strong>。迁移成本其实很低（一行配置），但收益可能超出预期。</p>
