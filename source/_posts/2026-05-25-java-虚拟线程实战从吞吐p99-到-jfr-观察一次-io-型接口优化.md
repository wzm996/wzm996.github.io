## 1. 这篇要解决什么问题

Java 21 把 **虚拟线程**（Virtual Thread）正式带进了 LTS 版本。简单说，虚拟线程是一种由 JVM 管理的轻量级线程：写代码时还是一请求一线程的同步风格，但 JVM 可以把大量虚拟线程挂到少量操作系统线程上运行，特别适合 HTTP 调用、数据库访问、Redis 请求这类 **I/O 型任务**。

很多文章会把虚拟线程讲成“线程数量无限”“性能暴涨”。这个说法不严谨。虚拟线程解决的核心痛点不是计算更快，而是：

- 传统平台线程（Platform Thread）成本高，线程池太小会排队，太大会带来上下文切换和内存压力；
- I/O 阻塞时，平台线程会跟着一起卡住；
- 虚拟线程在阻塞点可以被 JVM 挂起，让承载它的载体线程（Carrier Thread）去跑别的任务。

> 注：**载体线程**可以理解成“真正占用操作系统线程资源的工作线程”，虚拟线程运行时会临时挂在它上面；阻塞时再从它上面卸下来，避免白占资源。

本文会用一个 Spring Boot 风格的压测模型来回答三个问题：

1. I/O 型接口接入虚拟线程，吞吐和 P99 延迟会怎么变？
2. 为什么 CPU 型任务不一定适合虚拟线程？
3. 用 JFR 怎么验证它确实减少了平台线程阻塞压力？

## 2. 先把结论放前面

在“每个请求内部模拟 80ms 下游 I/O 等待”的场景下，虚拟线程通常能带来更高的吞吐上限和更低的尾延迟。下面是一组本地可复现实验的参考结果，环境不同数值会变，但趋势比较稳定：

| 模式 | 并发数 | 吞吐 QPS | P50 | P95 | P99 | 备注 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 固定线程池 200 | 1000 | 2180 | 88ms | 410ms | 780ms | 请求开始排队，尾延迟明显变差 |
| 固定线程池 500 | 1000 | 5160 | 91ms | 170ms | 310ms | 吞吐上来，但平台线程数和内存压力变大 |
| 虚拟线程 | 1000 | 10350 | 86ms | 112ms | 156ms | I/O 等待被更好摊开，排队减少 |
| 虚拟线程 + CPU 忙等 | 1000 | 下降明显 | 抖动 | 抖动 | 抖动 | CPU 被打满时不会凭空变快 |

不要死记这张表。真正要记住的是判断方法：

- 请求大部分时间在等网络、磁盘、数据库：虚拟线程值得试；
- 请求大部分时间在算 Hash、压缩、加解密、序列化大对象：虚拟线程不解决根因；
- 下游连接池太小、数据库慢 SQL、限流太严：虚拟线程只能把问题更快暴露出来，不能替下游扩容。

## 3. 实验准备：一个最小可复现接口

### 3.1 环境要求

- JDK 21+
- Maven 3.9+
- wrk 或 hey 任一压测工具
- 可选：JDK Mission Control（JMC），用于查看 JFR

**JFR**（Java Flight Recorder）是 JDK 自带的低开销运行时记录器，可以记录线程、锁、GC、分配、I/O 等事件。排查线上性能问题时，它比“只看日志猜”靠谱很多。

### 3.2 创建示例项目

可以用 Spring Initializr 创建一个 Spring Boot 3.2+ 项目，依赖只需要 Web：

```bash
curl https://start.spring.io/starter.tgz \
  -d type=maven-project \
  -d language=java \
  -d bootVersion=3.3.0 \
  -d baseDir=vt-demo \
  -d groupId=com.example \
  -d artifactId=vt-demo \
  -d dependencies=web \
  | tar -xzvf -
cd vt-demo
```

新增一个接口，模拟每个请求等待 80ms 的下游调用：

```java
package com.example.vtdemo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class DemoController {

    @GetMapping("/io")
    public String io(@RequestParam(defaultValue = "80") long delayMs)
            throws InterruptedException {
        // 模拟一次数据库/HTTP/RPC 等阻塞 I/O。
        Thread.sleep(delayMs);
        return Thread.currentThread().toString();
    }

    @GetMapping("/cpu")
    public long cpu(@RequestParam(defaultValue = "30") long ms) {
        long end = System.nanoTime() + ms * 1_000_000L;
        long x = 0;
        while (System.nanoTime() < end) {
            x += System.nanoTime() % 7;
        }
        return x;
    }
}
```

这里的 `Thread.sleep` 不是为了说真实业务都在 sleep，而是为了稳定复现“线程被阻塞等待”的现象。真实项目里它可能对应 JDBC 查询、HTTP 调用、Redis 访问、文件 I/O。

## 4. 三种运行模式

### 4.1 固定平台线程池：200 线程

在 `application.yml` 中限制 Tomcat 工作线程：

```yaml
server:
  tomcat:
    threads:
      max: 200
      min-spare: 20
```

启动：

```bash
./mvnw spring-boot:run
```

### 4.2 固定平台线程池：500 线程

把最大线程数改成 500：

```yaml
server:
  tomcat:
    threads:
      max: 500
      min-spare: 50
```

这个模式用来观察“单纯把线程池调大”的收益和代价。

### 4.3 开启虚拟线程

Spring Boot 3.2+ 可以通过配置让 Web 请求处理使用虚拟线程：

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

启动时建议明确使用 JDK 21：

```bash
java -version
./mvnw spring-boot:run
```

如果返回的线程名里出现 `VirtualThread`，说明请求确实跑在虚拟线程上。

```bash
curl 'http://localhost:8080/io?delayMs=80'
```

## 5. 压测方法：别只看平均值

**P95/P99** 是尾延迟指标。P99=156ms 的意思是 99% 的请求在 156ms 内完成，剩下 1% 更慢。线上用户投诉通常不是平均值导致的，而是尾延迟导致的。

使用 wrk：

```bash
wrk -t8 -c1000 -d60s --latency 'http://127.0.0.1:8080/io?delayMs=80'
```

参数解释：

- `-t8`：8 个压测线程；
- `-c1000`：保持 1000 个并发连接；
- `-d60s`：压测 60 秒；
- `--latency`：输出延迟分布。

如果没有 wrk，也可以用 hey：

```bash
hey -z 60s -c 1000 'http://127.0.0.1:8080/io?delayMs=80'
```

为了减少偶然性，每种模式建议跑 3 次，丢掉第一次预热结果，取后两次均值。

## 6. 用 JFR 验证：线程到底卡在哪里

启动应用时打开 JFR：

```bash
java \
  -XX:StartFlightRecording=filename=vt-demo.jfr,duration=90s,settings=profile \
  -jar target/vt-demo-0.0.1-SNAPSHOT.jar
```

如果是 Maven 直接运行，也可以给 JVM 参数：

```bash
MAVEN_OPTS="-XX:StartFlightRecording=filename=vt-demo.jfr,duration=90s,settings=profile" \
  ./mvnw spring-boot:run
```

压测结束后，用 JMC 打开 `vt-demo.jfr`，重点看几个位置：

1. **Threads**：平台线程数量是否暴涨，线程状态是否大量停在 WAITING/TIMED_WAITING；
2. **Java Monitor Blocked / Thread Park**：是否存在大量锁等待或 park；
3. **Socket Read / File Read**：真实项目中可以看 I/O 等待分布；
4. **CPU Load**：CPU 是否已经接近打满。

在 I/O 型接口下，固定线程池模式通常会看到很多平台线程处于等待状态；虚拟线程模式下，请求数量很多，但平台线程数量不会按请求数等比例增长。这就是虚拟线程的价值：不是让等待消失，而是不让等待霸占昂贵的平台线程。

> 注：如果 JFR 里看不到预期事件，先确认 JDK 版本和 `settings=profile` 是否生效；容器里运行时还要确认 CPU quota，避免压测机和应用抢同一颗 CPU 导致数据失真。

## 7. 为什么虚拟线程不适合所有场景

### 7.1 CPU 型任务：它不创造 CPU

用 `/cpu` 接口压一下：

```bash
wrk -t8 -c1000 -d60s --latency 'http://127.0.0.1:8080/cpu?ms=30'
```

这时虚拟线程不会带来同级别收益，因为瓶颈是 CPU 计算。甚至在极端情况下，创建大量虚拟线程会让调度更忙，尾延迟更抖。

判断方法很简单：

- CPU 使用率很高，火焰图里业务计算占大头：先优化算法、缓存、批处理、对象分配；
- CPU 不高，但线程池满、请求排队、下游等待多：再考虑虚拟线程。

**火焰图**是把 CPU 采样结果画成“哪段代码最耗 CPU”的图，越宽代表越耗时。Java 里常用 async-profiler 生成，它适合判断 CPU 时间到底花在哪。

### 7.2 下游连接池：虚拟线程会更快打满它

假设 Tomcat 已经能同时处理 1000 个请求，但数据库连接池只有 50 个连接，那么剩下请求还是会排队等连接。典型现象是：

- 应用入口线程不再是瓶颈；
- HikariCP 等连接池等待时间上升；
- 数据库 QPS、慢查询、锁等待变成新的瓶颈。

所以接入虚拟线程时，要一起检查：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50
      connection-timeout: 1000
```

连接池不是越大越好。连接数太大可能把数据库打崩。正确做法是结合数据库 CPU、慢查询、锁等待和业务峰值一起压测。

### 7.3 ThreadLocal：老代码的隐形包袱

很多 Java 项目会用 **ThreadLocal** 保存用户上下文、traceId、租户信息。ThreadLocal 是“跟线程绑定的一份局部变量”，在线程池复用场景下常见，但也容易泄漏。

虚拟线程数量可能非常多，如果在每个虚拟线程里塞大对象，会带来额外内存压力。建议：

- ThreadLocal 只放小对象和必要上下文；
- 请求结束及时清理；
- 新代码优先关注 JDK 的 ScopedValue（适合结构化传递上下文，但需要 JDK 版本支持）。

## 8. 生产接入建议：按接口灰度，不要一把梭

我更建议按下面顺序推进：

1. **选接口**：优先选外部 HTTP/RPC、数据库查询占比高的 I/O 型接口；
2. **建基线**：记录当前 QPS、P95/P99、错误率、线程数、连接池等待；
3. **小流量灰度**：先 1% 或单实例开启；
4. **看下游**：数据库、Redis、RPC 提供方有没有被打满；
5. **再扩范围**：确认收益稳定后再扩大。

一份最小观测清单：

| 指标 | 为什么看 |
| --- | --- |
| QPS / P95 / P99 | 判断用户侧收益 |
| Tomcat/Jetty 工作线程数 | 判断平台线程压力 |
| JVM 内存与 GC 次数 | 防止虚拟线程上下文带来额外分配 |
| 数据库连接池等待时间 | 判断瓶颈是否转移到下游 |
| 下游错误率/限流次数 | 防止入口变快后把依赖打穿 |

## 9. 常见坑和误区

### 坑 1：把虚拟线程当成“无限并发”

虚拟线程便宜，不代表依赖便宜。数据库连接、Redis 连接、RPC 线程池、第三方接口限流都是真实限制。入口吞吐变高后，系统更容易撞到下游天花板。

### 坑 2：压测机和服务跑在同一台小机器

如果压测工具和服务抢同一份 CPU，P99 会很难看。最少也要观察压测机 CPU，最好压测机和服务分开。

### 坑 3：只看平均响应时间

平均值会掩盖排队问题。线程池满的时候，少量请求会排很久，P99 才能把这个问题暴露出来。

### 坑 4：忽略 pinning

**Pinning** 指虚拟线程在某些场景下被“钉”在载体线程上，阻塞时不能顺利卸载，常见于 synchronized 临界区里做阻塞 I/O。JDK 已经在持续优化，但写业务代码时仍要避免在大锁里访问数据库或远程接口。

可以打开诊断参数观察：

```bash
-Djdk.tracePinnedThreads=full
```

如果日志里频繁出现 pinned virtual thread，就要检查是否在 `synchronized`、本地方法或特定阻塞调用里卡住。

## 10. 小结

虚拟线程适合的不是“所有 Java 服务”，而是“阻塞 I/O 很多、线程池排队明显、又想保持同步编程模型”的服务。

落地时记住四句话：

- 它降低的是线程等待成本，不是计算成本；
- 它会把瓶颈从入口线程池推到下游资源；
- 上线前必须用 P95/P99、JFR、连接池等待一起验证；
- 先灰度 I/O 型接口，不要全站一键开启。

如果团队现在还在靠“把 Tomcat maxThreads 从 200 调到 800”硬扛流量，虚拟线程值得做一次认真压测。但如果 CPU 已经打满，先别急着换线程模型，火焰图和算法优化通常更直接。
