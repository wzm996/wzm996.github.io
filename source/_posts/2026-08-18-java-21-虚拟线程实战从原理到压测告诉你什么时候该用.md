<blockquote><p>虚拟线程（Virtual Thread）是 JDK 21 正式发布的轻量级线程实现，由 JVM 而非操作系统内核管理。它解决了 Java 长期以来"高并发靠线程池"的痛点，让"每个请求一个线程"的直观模型重新变得可行。但虚拟线程不是银弹——本文从原理、代码、压测数据三个层面，帮你搞清楚它到底适合什么场景、什么时候该用、哪些坑要避开。</p></blockquote>

<!-- more -->

<h1 id="背景：为什么需要虚拟线程"><a href="#背景：为什么需要虚拟线程" class="headerlink" title="背景：为什么需要虚拟线程"></a>背景：为什么需要虚拟线程</h1>

<p>写 Java Web 服务的人应该都经历过这个经典问题：<strong>线程不够用了</strong>。</p>

<p>传统的 <strong>平台线程（Platform Thread）</strong>——也就是我们平时说的 Thread——是操作系统内核线程的包装。创建一个平台线程大约需要 1MB 栈内存（默认），而且调度权在 OS 手里。一台 8 核机器就算把线程数撑到 2000，大部分时间线程都在等 I/O（数据库查询、RPC 调用、读文件），真正跑 CPU 的没几个。</p>

<p>于是大家开始用<strong>线程池</strong>（ThreadPoolExecutor）来限制线程数，又引入了<strong>异步编程</strong>（CompletableFuture、Reactive 等）来提高吞吐。但异步代码写起来痛苦，调试更痛苦——这就是过去十来年 Java 并发编程的困境。</p>

<p><strong>虚拟线程</strong>（Project Loom 的核心产出）就是要打破这个困局：</p>
<ul>
<li>由 JVM 调度，不绑定 OS 线程</li>
<li>创建成本极低，一个 JVM 里轻松创建 <strong>百万级</strong>虚拟线程</li>
<li>阻塞操作（I/O、sleep 等）会自动让出底层载体线程（Carrier Thread），不浪费资源</li>
<li>API 兼容 Thread，学习成本几乎为零</li>
</ul>

<h1 id="核心原理：虚拟线程是怎么工作的"><a href="#核心原理：虚拟线程是怎么工作的" class="headerlink" title="核心原理：虚拟线程是怎么工作的"></a>核心原理：虚拟线程是怎么工作的</h1>

<h2 id="Mount-Unmount-机制"><a id="Mount-Unmount-机制" href="#Mount-Unmount-机制" class="headerlink" title="Mount/Unmount 机制"></a>Mount/Unmount 机制</h2>

<p>虚拟线程的核心设计思想跟<strong>虚拟内存</strong>非常像：OS 用有限的物理内存模拟出巨大的虚拟地址空间；JVM 用少量的平台线程（叫作 <strong>载体线程</strong>，Carrier Thread）模拟出大量的虚拟线程。</p>

<p>运行时的关键流程：</p>
<figure class="highlight plain">
<table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br></pre></td><td class="code"><pre><span class="line">sequenceDiagram</span><br><span class="line">    participant VT as 虚拟线程</span><br><span class="line">    participant CT as 载体线程(ForkJoinPool)</span><br><span class="line">    VT->>CT: Mount(挂载): 虚拟线程运行在载体上</span><br><span class="line">    Note over VT,CT: 遇到阻塞操作(sleep/IO/blocking queue)</span><br><span class="line">    CT-->>VT: Unmount(卸载): 虚拟线程让出载体,载体去跑其他VT</span><br><span class="line">    Note over VT,CT: 阻塞操作完成</span><br><span class="line">    CT->>VT: 重新Mount到任意空闲载体继续执行</span><br></pre></td></table></figure>

<p><strong>关键点</strong>：阻塞不再 = 浪费。虚拟线程遇到阻塞时自动卸载，载体线程立刻可以干别的。等阻塞结束了，调度器会把虚拟线程重新挂到某个空闲载体上继续跑。</p>

<h2 id="载体线程池：ForkJoinPool"><a id="载体线程池：ForkJoinPool" href="#载体线程池：ForkJoinPool" class="headerlink" title="载体线程池：ForkJoinPool"></a>载体线程池：ForkJoinPool</h2>

<p>默认情况下，虚拟线程的载体线程池是一个 <strong>ForkJoinPool</strong>（commonPool 的变种），大小等于 CPU 核心数。这意味着：</p>
<ul>
<li>你的 8 核机器默认只有 ~8 个载体线程在真正跑任务</li>
<li>但可以有成千上万虚拟线程同时"活跃"（大部分在等待 I/O）</li>
<li>CPU 密集型任务不会因为虚拟线程变多而加速——载体数就那么多</li>
</ul>

<pre><code>注：可以通过 jdk.virtualThreadScheduler.parallelism 参数调整载体线程数，
     但通常不需要动它。
</code></pre>

<h2 id="坑-1：不要用-synchronized-做虚拟线程之间的互斥"><a id="坑-1：不要用-synchronized-做虚拟线程之间的互斥" href="#坑-1：不要用-synchronized-做虚拟线程之间的互斥" class="headerlink" title="坑 1：不要用 synchronized 做虚拟线程之间的互斥"></a>坑 1：不要用 synchronized 做虚拟线程之间的互斥</h2>

<p>这是虚拟线程的头号陷阱。<strong>synchronized</strong> 会导致虚拟线程无法被卸载（pin），也就是虚拟线程会一直占着载体线程不放，退化为普通阻塞行为。</p>

<p><strong>❌ 错误做法</strong>：</p>
<figure class="highlight java">
<table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br></pre></td><td class="code"><pre><span class="line">private final Object lock = new Object();</span><br><span class="line">void bad() {</span><br><span class="line">    synchronized (lock) {       // ← 虚拟线程会被 pin！</span><br><span class="line">        Thread.sleep(1000);     //   这 1 秒内载体线程被白白占用</span><br><span class="line">    }</span><br><span class="line">}</span><br></pre></td></table></figure>

<h2 id="坑-2：虚拟线程不适合-CPU-密集型任务"><a id="坑-2：虚拟线程不适合-CPU-密集型任务" href="#坑-2：虚拟线程不适合-CPU-密集型任务" class="headerlink" title="坑 2：虚拟线程不适合 CPU 密集型任务"></a>坑 2：虚拟线程不适合 CPU 密集型任务</h2>

<p>虚拟线程解决的是<strong>并发度</strong>问题，不是<strong>并行计算</strong>问题。载体线程数 ≈ CPU 核心数，CPU 密集型任务用虚拟线程不会更快，反而因为调度开销可能略慢。</p>

<p><strong>判断标准</strong>：如果你的任务大部分时间在等 I/O（DB、RPC、文件、网络），用虚拟线程；如果在疯狂算数（图像处理、加密、ML 推理），还是用传统线程池或 ForkJoinPool。</p>

<h2 id="坑-3：不要池化虚拟线程"><a id="坑-3：不要池化虚拟线程" href="#坑-3：不要池化虚拟线程" class="headerlink" title="坑 3：不要池化虚拟线程"></a>坑 3：不要池化虚拟线程</h2>

<p>很多人看到线程就想到线程池——<strong>虚拟线程不要池化</strong>。它的设计哲学就是"用完即弃"：</p>
<ul>
<li>创建虚拟线程的开销 ≈ 创建一个普通对象（纳秒级）</li>
<li>池化反而增加复杂度和调度延迟</li>
<li>官方 API 名字就叫 <code>newVirtualThreadPerTaskExecutor()</code>——每次新建</li>
</ul>

<h2 id="坑-4：ThreadLocal-可能变成内存泄漏的新源头"><a id="坑-4：ThreadLocal-可能变成内存泄漏的新源头" href="#坑-4：ThreadLocal-可能变成内存泄漏的新源头" class="headerlink" title="坑 4：ThreadLocal 可能变成内存泄漏的新源头"></a>坑 4：ThreadLocal 可能变成内存泄漏的新源头</h2>

<p>以前线程池只有几百个线程，ThreadLocal 泄漏问题还不算太夸张。现在虚拟线程一创建就是几十万个，如果每个虚拟线程都往 ThreadLocal 塞东西且不清理……OOM 就在门口等着了。</p>

<p><strong>建议</strong>：</p>
<ul>
<li>审查现有代码中的 ThreadLocal 使用</li>
<li>优先使用 <strong>ScopedValue</strong>（JDK 21 预览，JDK 23 正式）替代 ThreadLocal 来在线程间传递上下文</li>
<li>如果必须用 ThreadLocal，确保在 finally 中 remove</li>
</ul>

<h2 id="坑-5：连接池仍然是必需的"><a id="坑-5：连接池仍然是必需的" href="#坑-5：连接池仍然是必需的" class="headerlink" title="坑 5：连接池仍然是必需的"></a>坑 5：连接池仍然是必需的</h2>

<p>虚拟线程再多，数据库连接数还是有限制的（MySQL 默认 max_connections=151）。你不可能开一万个虚拟线程就真的一万并发查库——<strong>连接池还是要配好</strong>（HikariCP 照样用）。虚拟线程解决的是"等待查询结果时线程不被浪费"，不是"凭空变出更多连接"。</p>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>

<p>虚拟线程是 Java 并发史上最重要的演进之一。它不是要取代所有现有的并发工具，而是给了我们一个新的选择：</p>

<ul>
<li><strong>适合</strong>：I/O 密集型高并发服务（Web 后端、微服务网关、API 网关、爬虫等）</li>
<li><strong>不适合</strong>：CPU 密集型计算（用 ForkJoinPool / 传统线程池）、对延迟极其敏感的超低延迟系统（考虑响应式）</li>
<li><strong>迁移成本</strong>：Spring Boot 3.2+ 只需一行配置；自研框架需将线程池替换为 <code>newVirtualThreadPerTaskExecutor()</code></li>
<li><strong>最大风险</strong>：synchronized 导致的 pin 问题、ThreadLocal 内存膨胀、连接池配置不当</li>
</ul>

<p>如果你正在维护一个 Spring Boot 微服务，日常 QPS 上千、大量时间花在等数据库和 RPC 上——<strong>现在就是尝试虚拟线程的最佳时机</strong>。JDK 21 已经是成熟的 LTS 版本，Spring Boot 3.x 对虚拟线程的支持也相当完善。先在非核心服务试点，收集压测数据和 GC 指标，再逐步推广。</p>
