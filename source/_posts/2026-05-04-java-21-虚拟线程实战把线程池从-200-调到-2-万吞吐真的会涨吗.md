<blockquote>
<p><strong>虚拟线程</strong>不是“线程池调大一点”的语法糖，它本质上是在 JVM 里把大量阻塞型任务的调度成本做薄了。对 IO 密集型服务来说，它经常能显著提升并发承载能力；但一旦你把它用在长时间占用 CPU、或者在 synchronized 里做阻塞调用，收益就会迅速缩水，甚至出现新的性能坑。</p>
</blockquote>

<!-- more -->

<h1 id="为什么想写这篇"><a href="#为什么想写这篇" class="headerlink" title="为什么想写这篇"></a>为什么想写这篇</h1><p>很多 Java 同学第一次看到 <strong>Virtual Thread（虚拟线程）</strong> 时，直觉都是：这不就是“线程更便宜”吗？这个理解不算错，但太粗了。真正落到工程里，大家关心的不是概念本身，而是三个更实际的问题：</p>
<ul>
<li>到底什么场景值得上？</li>
<li>吞吐、延迟、线程数会变化多少？</li>
<li>有哪些一开始不明显、线上却很容易踩的坑？</li>
</ul>
<p>这篇文章不打算泛泛讲 Loom 的设计史，而是直接从一个 <strong>可复现实验</strong> 出发：做一个典型的“外部调用 + 等待返回”的 IO 密集型服务，对比 <strong>固定线程池</strong> 和 <strong>虚拟线程 per task</strong> 两种实现，看看吞吐、延迟、线程占用和 JFR 观测结果到底有什么差异。</p>

<h1 id="先说结论"><a href="#先说结论" class="headerlink" title="先说结论"></a>先说结论</h1><ul>
<li>如果你的任务大部分时间都在 <strong>等待网络、磁盘、数据库、RPC</strong>，虚拟线程通常值得试。</li>
<li>如果你的任务大部分时间都在 <strong>跑 CPU 计算</strong>，虚拟线程不会凭空让 CPU 变快。</li>
<li>虚拟线程最怕两类问题：<strong>pinning（载体线程被“钉住”）</strong> 和 <strong>误把它当无限资源</strong>。</li>
<li>验证虚拟线程别只看 QPS，至少还要一起看 <strong>P95/P99</strong>、线程数、JFR 事件、GC 和连接池等待。</li>
</ul>

<h1 id="几个新名词先讲人话"><a href="#几个新名词先讲人话" class="headerlink" title="几个新名词先讲人话"></a>几个新名词先讲人话</h1><p>先把几个容易劝退人的词，用人话解释一下：</p>
<ul>
<li><strong>虚拟线程（Virtual Thread）</strong>：JVM 提供的一种超轻量线程。它看起来像普通线程，写法也很像，但调度更便宜，适合“一堆任务都在等”的场景。</li>
<li><strong>平台线程（Platform Thread）</strong>：传统 Java 线程，本质上和操作系统线程一一对应，数量多了以后内存和调度开销都更明显。</li>
<li><strong>载体线程（Carrier Thread）</strong>：JVM 真正拿去执行虚拟线程的底层工作线程。可以把它理解成“虚拟线程最终还是要骑在几匹真马上跑”。</li>
<li><strong>Pinning</strong>：虚拟线程本来该在阻塞时把载体线程让出来，但某些情况下让不出来，导致底层平台线程被占住。这就像本来是共享单车，结果有人把车锁自己家门口了。</li>
<li><strong>JFR（Java Flight Recorder）</strong>：JDK 自带的低开销诊断工具，能录线程、锁、分配、GC、方法热点等事件。线上排查性能问题时非常常用。</li>
</ul>

<h1 id="实验目标与环境"><a href="#实验目标与环境" class="headerlink" title="实验目标与环境"></a>实验目标与环境</h1><p>我们做一个最小但足够真实的实验：</p>
<ul>
<li>服务端暴露一个 HTTP 接口 `/work`</li>
<li>每次请求内部会模拟一次 <strong>80ms 外部 IO 等待</strong></li>
<li>分别用两种方式处理请求：
  <ul>
    <li>固定线程池：`Executors.newFixedThreadPool(200)`</li>
    <li>虚拟线程：`Executors.newVirtualThreadPerTaskExecutor()`</li>
  </ul>
</li>
<li>用 wrk 压测 60 秒，对比吞吐、延迟和线程状态</li>
</ul>

<p>实验环境如下：</p>
<ul>
<li>JDK：OpenJDK 21</li>
<li>机器：4 vCPU / 8 GB RAM</li>
<li>OS：Linux</li>
<li>压测工具：wrk 4.x</li>
<li>JFR：JDK 自带</li>
</ul>

<h1 id="示例代码"><a href="#示例代码" class="headerlink" title="示例代码"></a>示例代码</h1><p>为了把重点放在线程模型上，这里直接用 JDK 自带的 `HttpServer` 起一个最小服务，不引 Spring Boot。你要迁移到 Spring MVC / WebFlux 也不难，核心观察点是一样的。</p>

<h2 id="1-服务端代码"><a href="#1-服务端代码" class="headerlink" title="1. 服务端代码"></a>1. 服务端代码</h2><pre><code class="language-java">import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpServer;

import java.io.IOException;
import java.io.OutputStream;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class VirtualThreadDemo {

    public static void main(String[] args) throws Exception {
        String mode = System.getProperty("mode", "vt"); // vt | fixed
        int port = Integer.getInteger("port", 8080);

        ExecutorService executor = switch (mode) {
            case "fixed" -&gt; Executors.newFixedThreadPool(200);
            case "vt" -&gt; Executors.newVirtualThreadPerTaskExecutor();
            default -&gt; throw new IllegalArgumentException("unknown mode: " + mode);
        };

        HttpServer server = HttpServer.create(new InetSocketAddress(port), 0);
        server.createContext("/work", new IoBoundHandler());
        server.setExecutor(executor);
        server.start();

        System.out.println("started on port=" + port + ", mode=" + mode);
    }

    static class IoBoundHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange exchange) throws IOException {
            try {
                // 模拟一次外部 IO，例如 RPC / DB / HTTP 调用
                Thread.sleep(Duration.ofMillis(80));
                byte[] body = "OK".getBytes(StandardCharsets.UTF_8);
                exchange.sendResponseHeaders(200, body.length);
                try (OutputStream os = exchange.getResponseBody()) {
                    os.write(body);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                exchange.sendResponseHeaders(500, 0);
                exchange.close();
            }
        }
    }
}
</code></pre>

<h2 id="2-编译与启动"><a href="#2-编译与启动" class="headerlink" title="2. 编译与启动"></a>2. 编译与启动</h2><pre><code class="language-bash">javac VirtualThreadDemo.java

# 固定线程池版本
java -XX:StartFlightRecording=filename=fixed.jfr,dumponexit=true \
     -Djdk.tracePinnedThreads=full \
     -Dmode=fixed VirtualThreadDemo

# 虚拟线程版本
java -XX:StartFlightRecording=filename=vt.jfr,dumponexit=true \
     -Djdk.tracePinnedThreads=full \
     -Dmode=vt VirtualThreadDemo
</code></pre>

<p>这里有两个参数值得单独说一句：</p>
<ul>
<li><strong>`-XX:StartFlightRecording`</strong>：启动时就开始录 JFR，省得问题来了才临时抓。</li>
<li><strong>`-Djdk.tracePinnedThreads=full`</strong>：如果虚拟线程发生 pinning，JVM 会把堆栈打印出来，方便你定位是哪段代码把载体线程钉住了。</li>
</ul>

<h2 id="3-压测命令"><a href="#3-压测命令" class="headerlink" title="3. 压测命令"></a>3. 压测命令</h2><pre><code class="language-bash">wrk -t8 -c2000 -d60s http://127.0.0.1:8080/work
</code></pre>

<p><strong>并发连接数（`-c`）</strong> 就是同时挂在服务上的连接数量。这里故意打到 2000，是为了逼出“请求很多，但每个请求大部分时间都在等”的效果。</p>

<p>这组数据背后的逻辑并不神秘：</p>
<ul>
<li>固定线程池只有 200 个工作线程，而每个请求都要等 80ms，所以很快就把池子占满了，后续请求只能排队。</li>
<li>虚拟线程版本虽然也在 `sleep`，但阻塞期间底层载体线程可以去跑别的任务，所以整体并发承载能力高很多。</li>
</ul>

<p>换句话说，虚拟线程不是把单个请求变快了，而是 <strong>让等待中的请求不再重度占用昂贵的平台线程</strong>，所以系统能更从容地接住更多并发。</p>

<h1 id="如何验证这些结论不是“嘴上说说”"><a href="#如何验证这些结论不是“嘴上说说”" class="headerlink" title="如何验证这些结论不是“嘴上说说”"></a>如何验证这些结论不是“嘴上说说”</h1>

<h2 id="验证-1：看线程数量与状态"><a href="#验证-1：看线程数量与状态" class="headerlink" title="验证 1：看线程数量与状态"></a>验证 1：看线程数量与状态</h2><pre><code class="language-bash">jcmd $(pgrep -f VirtualThreadDemo | head -n1) Thread.print &gt; thread_dump.txt
</code></pre>

<p>你会看到两种现象：</p>
<ul>
<li>固定线程池版本里，工作线程很快大量处于 `TIMED_WAITING`，池子大小就是硬上限。</li>
<li>虚拟线程版本里，虚拟线程数量会很多，但平台线程数量通常比较克制，不会跟着线性膨胀。</li>
</ul>

<h2 id="验证-2：看-JFR-里的调度与阻塞"><a href="#验证-2：看-JFR-里的调度与阻塞" class="headerlink" title="验证 2：看 JFR 里的调度与阻塞"></a>验证 2：看 JFR 里的调度与阻塞</h2><p>用 JDK Mission Control 打开 `fixed.jfr` 和 `vt.jfr`，重点看以下几个面板：</p>
<ul>
<li><strong>Threads</strong>：观察线程数量、状态分布、上下文切换趋势。</li>
<li><strong>Java Monitor Blocked</strong>：看有没有锁竞争。</li>
<li><strong>Socket Read / File Read / Thread Sleep</strong>：看阻塞时间主要花在哪。</li>
<li><strong>Virtual Threads</strong>（JDK 21+ 相关事件）：看虚拟线程创建、挂起、恢复是否异常密集。</li>
</ul>

<p>在这组实验里，虚拟线程版本通常会表现出两个很明显的特征：</p>
<ol>
<li>平台线程数量远低于任务数量；</li>
<li>等待事件很多，但并没有把底层工作线程全部锁死。</li>
</ol>

<h2 id="验证-3：看-GC-和内存是否失控"><a href="#验证-3：看-GC-和内存是否失控" class="headerlink" title="验证 3：看 GC 和内存是否失控"></a>验证 3：看 GC 和内存是否失控</h2><pre><code class="language-bash">jstat -gcutil $(pgrep -f VirtualThreadDemo | head -n1) 1s 10
</code></pre>

<p>很多人一看到“2 万线程”就会条件反射觉得内存爆炸。虚拟线程之所以有讨论价值，正是因为它的栈和调度模型比平台线程轻得多。但注意，这不等于零成本：如果你的每个任务都挂着大对象、ThreadLocal、数据库连接、MDC，上来几万并发一样会把堆和外部资源拖爆。</p>

<h1 id="为什么吞吐会涨这么多"><a href="#为什么吞吐会涨这么多" class="headerlink" title="为什么吞吐会涨这么多"></a>为什么吞吐会涨这么多</h1><p>这个问题可以从“资源浪费”角度来理解。</p>

<p>固定线程池方案里，200 个平台线程就像 200 个正式工。每个人接到单子后，哪怕只是傻等下游服务返回，也得一直占着工位。请求一多，外面只能排队。</p>

<p>虚拟线程方案里，JVM 会在合适的阻塞点把任务挂起，把底下的工位腾出来给别的任务继续干。所以它更像“接单的人很多，但真正需要占工位的时候才去占”。对于 IO 密集型业务，这种模型天然更划算。</p>

<h1 id="但别高兴太早：3-个最常见的坑"><a href="#但别高兴太早：3-个最常见的坑" class="headerlink" title="但别高兴太早：3 个最常见的坑"></a>但别高兴太早：3 个最常见的坑</h1>

<h2 id="坑-1：把虚拟线程用在-CPU-密集型任务上"><a href="#坑-1：把虚拟线程用在-CPU-密集型任务上" class="headerlink" title="坑 1：把虚拟线程用在 CPU 密集型任务上"></a>坑 1：把虚拟线程用在 CPU 密集型任务上</h2><p>如果你的任务主要是在做 JSON 大对象序列化、压缩、加解密、规则计算、图像处理，那瓶颈本来就在 CPU，不在“线程贵不贵”。这时候你把线程从 200 开到 2 万，通常只会让调度更乱、上下文切换更多、延迟抖得更厉害。</p>

<p><strong>一句话判断：</strong>任务是不是“经常在等”？如果不是，就别指望虚拟线程带来魔法。</p>

<h2 id="坑-2：在-synchronized-里做阻塞调用，触发-pinning"><a href="#坑-2：在-synchronized-里做阻塞调用，触发-pinning" class="headerlink" title="坑 2：在 synchronized 里做阻塞调用，触发 pinning"></a>坑 2：在 synchronized 里做阻塞调用，触发 pinning</h2><p>看一个非常典型、也非常容易在线上偷偷出现的写法：</p>
<pre><code class="language-java">private final Object lock = new Object();

public void badCase() throws InterruptedException {
    synchronized (lock) {
        Thread.sleep(200); // 或者 JDBC / HTTP / RPC 阻塞调用
    }
}
</code></pre>

<p>问题在于：虚拟线程如果在某些受限上下文里阻塞，可能没法优雅地“卸载”自己，于是载体线程也跟着被占住。你本来想省线程，结果又回到了“真线程被堵住”的老路上。</p>

<p><strong>怎么查？</strong></p>
<ul>
<li>启动时加 `-Djdk.tracePinnedThreads=full`</li>
<li>看日志里有没有 pinned thread 堆栈</li>
<li>JFR 里看虚拟线程相关事件和 monitor blocking</li>
</ul>

<p><strong>怎么改？</strong> 能不用粗粒度 `synchronized` 就别用；需要锁时优先缩小临界区，避免在锁里做网络、磁盘、数据库等阻塞操作。</p>

<h2 id="坑-3：线程变便宜了，就误以为“下游也扛得住”"><a href="#坑-3：线程变便宜了，就误以为“下游也扛得住”" class="headerlink" title="坑 3：线程变便宜了，就误以为“下游也扛得住”"></a>坑 3：线程变便宜了，就误以为“下游也扛得住”</h2><p>这是最常见的工程误区。虚拟线程只能解决 <strong>你自己这层的并发调度成本</strong>，但数据库连接池、Redis 连接、下游 HTTP 客户端连接池、第三方 API 限流，这些一个都不会自动变大。</p>

<p>举个很现实的例子：</p>
<ul>
<li>应用层你能轻松挂 5000 个虚拟线程；</li>
<li>但 HikariCP 最大连接数还是 50；</li>
<li>结果就是 4950 个请求都在等连接。</li>
</ul>

<p>所以把虚拟线程引进生产之前，至少一起复核这些参数：</p>
<ul>
<li>数据库连接池大小</li>
<li>HTTP 客户端最大并发 / 每主机连接数</li>
<li>线程上下文（MDC、ThreadLocal）传播策略</li>
<li>限流、熔断、超时配置</li>
</ul>

<h1 id="成本与延迟的取舍：该怎么看"><a href="#成本与延迟的取舍：该怎么看" class="headerlink" title="成本与延迟的取舍：该怎么看"></a>成本与延迟的取舍：该怎么看</h1><p>虚拟线程的价值不只是“跑得更快”，还包括 <strong>用更少的平台线程承接更多等待型任务</strong>。这通常意味着两类收益：</p>
<ul>
<li><strong>延迟收益</strong>：排队更少，P95/P99 往往更好看；</li>
<li><strong>资源收益</strong>：不需要为大量阻塞请求预留同等数量的平台线程栈空间和调度成本。</li>
</ul>

<p>但成本也不是没有：</p>
<ul>
<li>排障门槛会上升一些，团队得学会看 JFR、看 pinning、看 ThreadLocal 传播。</li>
<li>如果代码里有很多历史锁用法、老 JDBC 驱动、奇怪的同步块，迁移成本会高于 demo。</li>
</ul>

<p>所以更现实的决策方式不是“全量改不改”，而是：</p>
<ol>
<li>先挑一个 <strong>IO 密集、路径清晰、指标明确</strong> 的接口做试点；</li>
<li>压测对比 QPS / P95 / P99 / 线程数 / JFR；</li>
<li>确认没有 pinning、没有把连接池和下游打爆，再逐步扩大范围。</li>
</ol>

<h1 id="如果你用的是-Spring-Boot，可以怎么落地"><a href="#如果你用的是-Spring-Boot，可以怎么落地" class="headerlink" title="如果你用的是 Spring Boot，可以怎么落地"></a>如果你用的是 Spring Boot，可以怎么落地</h1><p>如果是 Spring Boot 3.2+，很多场景已经能比较顺滑地接入虚拟线程。例如异步任务执行器、部分 servlet 容器线程模型、应用内部并发编排，都可以逐步尝试。</p>

<p>一个常见的最小配置思路是：</p>
<pre><code class="language-java">@Bean
ExecutorService applicationTaskExecutor() {
    return Executors.newVirtualThreadPerTaskExecutor();
}
</code></pre>

<p>但别一上来就全局替换。更稳的做法是：</p>
<ul>
<li>先替换内部的阻塞型并发任务</li>
<li>观察日志、JFR、线程 dump</li>
<li>再考虑扩大到更多请求链路</li>
</ul>

<td>虚拟线程保留同步直觉；响应式更强调背压和异步数据流</td>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1><ul>
<li><strong>虚拟线程最适合 IO 密集型业务</strong>，尤其是“请求很多，但大部分时间在等”的服务。</li>
<li><strong>它优化的是并发承载方式，不是 CPU 计算速度</strong>。</li>
<li><strong>做性能结论要拿证据说话</strong>：至少一起看 QPS、P95/P99、线程状态、JFR 和连接池等待。</li>
<li><strong>上线前重点排查 pinning、ThreadLocal、下游连接池</strong>，这三类问题最容易让收益打折。</li>
</ul>

<p>如果你最近正好在做 Java 21 升级，这个方向很值得拿一个接口试一试。它不是银弹，但在合适场景下，的确是那种“改动不算大，收益却挺实在”的优化项。</p>
