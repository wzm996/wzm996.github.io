<h1 id="背景：为什么默认配置会害了你"><a href="#背景：为什么默认配置会害了你" class="headerlink" title="背景：为什么默认配置会害了你"></a>背景：为什么默认配置会害了你？</h1>

<p>先说一个真实场景：</p>

<ul>
<li>你的 Spring Boot 服务刚上线，QPS 50，一切正常</li>
<li>业务增长到 QPS 500，开始偶尔报 <code>HikariPool-1 - Connection is not available, request timed out after 30000ms</code></li>
<li>你把 <code>maximum-pool-size</code> 从 10 改成 100，好了两天</li>
<li>然后数据库 CPU 飙到 95%，DBA 找上门了</li>
</ul>

<p>这个故事的教训是：<strong>连接池大小不是拍脑袋决定的，它和你的 CPU 核数、数据库能承受的并发连接数、业务 SQL 的平均执行时间都强相关</strong>。用默认配置等于把一辆跑车当自行车骑——能用，但远没发挥出应有的性能。</p>

<p><strong>HikariCP</strong>（日语"光"的意思）：目前业界最快的 JDBC 连接池，Spring Boot 2.x/3.x 的默认连接池。它的设计目标是<strong>极低开销 + 极简配置</strong>，代码量比其他连接池少一个数量级，但"极简"不意味着"不用调"——恰恰因为默认值偏保守，生产环境几乎一定需要 tuning。</p>

<p><strong>Micrometer</strong>：Spring Boot 内置的监控门面库，可以把 HikariCP 的运行指标（活跃连接数、空闲连接数、等待线程数等）暴露给 Prometheus/Grafana/JMX。<strong>没有监控的调优等于盲人摸象</strong>，所以本文把监控作为调优的一等公民来对待。</p>

<p>本文实验环境：</p>

<pre><code class="language-text">JDK: 17 (LTS)
Spring Boot: 3.2.x
HikariCP: 5.1.0（Spring Boot 3.2 内置版本）
数据库: MySQL 8.0.x / InnoDB
压测工具: Apache JMeter 5.6
监控: Spring Boot Actuator + Micrometer (Prometheus 格式)
机器配置: 4C8G（应用服务器）+ 4C16G（数据库）
</code></pre>

<p>其中最需要盯的两个是 <strong>pending</strong>（有线程在排队等连接）和 <strong>timeout_total</strong>（有人等不到连接直接失败了）。一旦这两个指标不为零，说明连接池已经成为瓶颈了。</p>

<h1 id="核心参数逐个讲：每个值背后的逻辑"><a href="#核心参数逐个讲：每个值背后的逻辑" class="headerlink" title="核心参数逐个讲：每个值背后的逻辑"></a>核心参数逐个讲：每个值背后的逻辑</h1>

<p>HikariCP 的参数不多，但每个都值得理解。下面按<strong>重要性从高到低</strong>排列：</p>

<h2 id="1-maximum-pool-size-最重要的参数没有之一"><a href="#1-maximum-pool-size-最重要的参数没有之一" class="headerlink" title="1. maximum-pool-size（最重要的参数，没有之一）"></a>1. <code>maximum-pool-size</code>（最重要的参数，没有之一）</h2>

<p><strong>控制连接池里最多能有多少个连接</strong>。这个值直接决定了你的应用能同时支撑多少数据库并发请求。</p>

<p>官方给出的经验公式（来自 HikariCP Wiki 的 <a href="https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing">About Pool Sizing</a>）：</p>

<pre><code class="language-text">connections = ((core_count * 2) + effective_spindle_count)
</code></pre>

<ul>
<li><code>core_count</code>：数据库服务器的 CPU 核心数</li>
<li><code>effective_spindle_count</code>：有效磁盘 spindle 数（SSD 通常算 1~3，机械硬盘按实际盘数）</li>
</ul>

<p>举个例子：你的数据库服务器是 4 核 SSD，那公式给出的是 <code>(4 × 2) + 1 = 9</code>，取整 <strong>10 个连接</strong>就够了。</p>

<p><strong>等等，这也太少了吧？</strong>对，这就是 HikariCP 的核心理念：<strong>连接池应该小而忙，而不是大而闲</strong>。原因很简单——数据库连接本身是重量级资源（每个连接占用 DB 端内存 + 一个线程），开太多反而会增加上下文切换和锁竞争。</p>

<blockquote>
<p><strong>注：</strong>上面公式适用于"纯 OLTP 场景"（SQL 执行快、事务短）。如果你的业务有大量长时间运行的查询（报表、大批量 ETL），公式需要适当放大。下文压测部分会给出不同场景的建议值。</p>
</blockquote>

<h2 id="2-minimum-idle-不是越多越好"><a href="#2-minimum-idle-不是越多越好" class="headerlink" title="2. minimum-idle（不是越多越好）"></a>2. <code>minimum-idle</code>（不是越多越好）</h2>

<p><strong>连接池里保底的空闲连接数</strong>。HikariCP 会在后台维护至少这么多个空闲连接，保证突发流量来了不用临时创建。</p>

<p>Spring Boot 3.2.x（HikariCP 5.x）默认值是 <strong>2</strong>。对于大多数场景够用了。如果你有非常规律的流量波峰（比如每天 10:00 准时来一波），可以适当提高到 <code>maximum-pool-size</code> 的 30%~50%。</p>

<p><strong>但不要设得太大</strong>——空闲连接虽然不干活，但也要占数据库端的内存和文件描述符。</p>

<h2 id="3-connection-timeout-等不及就报错"><a href="#3-connection-timeout-等不及就报错" class="headerlink" title="3. connection-timeout（等不及就报错）"></a>3. <code>connection-timeout</code>（等不及就报错）</h2>

<p><strong>线程从连接池获取连接的最大等待时间（毫秒）</strong>。默认 30 秒。</p>

<p>这个值的设置原则：<strong>应该略大于你接口允许的最大 RT</strong>。如果你的 API 超时设为 3 秒，那 <code>connection-timeout</code> 设 30 秒就没有意义——调用方早就超时放弃了，这边还在傻等连接。</p>

<p>建议：线上服务一般设 <code>3000~10000ms</code>（3~10 秒），配合快速失败策略。</p>

<h2 id="4-idle-timeout-多余连接何时回收"><a href="#4-idle-timeout-多余连接何时回收" class="headerlink" title="4. idle-timeout（多余连接何时回收）"></a>4. <code>idle-timeout</code>（多余连接何时回收）</h2>

<p><strong>一个空闲连接在被回收前可以存活多久（毫秒）</strong>。默认 600 秒（10 分钟）。</p>

<p>只有当连接数超过 <code>minimum-idle</code> 时，超出部分的空闲连接才会受此规则约束。这个参数一般不需要改，除非你的数据库防火墙会在 N 分钟后主动断开空闲连接（比如 AWS RDS 的 idle timeout 是 10 分钟），这时要把 HikariCP 的 <code>idle-timeout</code> 设得比数据库端短一些。</p>

<h2 id="5-max-lifetime-连接的寿命上限"><a href="#5-max-lifetime-连接的寿命上限" class="headerlink" title="5. max-lifetime（连接的寿命上限）"></a>5. <code>max-lifetime</code>（连接的寿命上限）</h2>

<p><strong>一个连接从创建出来，不管用没用过，最长能活多久（毫秒）</strong>。默认 30 分钟。</p>

<p>为什么要设这个？因为数据库端可能会有一些"半死不活"的状态（网络设备中间断开了 TCP、数据库做了 failover 等），连接池这边不知道，还以为连接是好的。<code>max-lifetime</code> 强制定期刷新连接，避免用到"僵尸连接"。</p>

<p><strong>重要：</strong>HikariCP 会把这个值随机浮动 ±5%，避免所有连接同时被回收导致雪崩。</p>

<blockquote>
<p><strong>注：</strong>MySQL 的 <code>wait_timeout</code> 默认是 8 小时（28800 秒），所以 HikariCP 默认的 30 分钟 <code>max-lifetime</code> 完全能覆盖。但如果你改过 MySQL 的 <code>wait_timeout</code>（比如改成 60 秒省资源），一定要确保 HikariCP 的 <code>max-lifetime</code> &lt; MySQL 的 <code>wait_timeout</code>，否则你会遇到经典的 "The last packet successfully received from the server was X milliseconds ago" 错误。</p>
</blockquote>

<h2 id="6-leak-detection-threshold-连接泄漏的照妖镜"><a href="#6-leak-detection-threshold-连接泄漏的照妖镜" class="headerlink" title="6. leak-detection-threshold（连接泄漏的照妖镜）"></a>6. <code>leak-detection-threshold</code>（连接泄漏的照妖镜）</h2>

<p><strong>一个连接被借出去超过多少毫秒还没归还，就怀疑它泄漏了</strong>。默认关闭（0）。</p>

<p>这是<strong>开发/测试环境必开</strong>的神器。一旦有代码忘了 close 连接（或者事务没正确提交/回滚），HikariCP 会打一条 WARN 日志告诉你哪行代码借的连接没还：</p>

<pre><code class="language-text">WARNING - Connection leak detection triggered for connection org.jdbc.hikari.pool.ProxyConnection@5a9a, 
stack trace follows:
    com.example.myapp.UserService.getUser(UserService.java:42)
    ...
</code></pre>

<p><strong>生产环境建议也开着</strong>，阈值可以设宽松一点（比如 30~60 秒）。性能开销极小（只在借用连接时记录时间戳 + 归还时比较），但能帮你提前发现致命 bug。</p>

<h1 id="压测实战：默认配置-vs-调优配置"><a href="#压测实战：默认配置-vs-调优配置" class="headerlink" title="压测实战：默认配置 vs 调优配置"></a>压测实战：默认配置 vs 调优配置</h1>

<p>光说不练假把式。下面我们用一套可复现的压测方案，对比 Spring Boot 默认配置和经过计算的调优配置之间的性能差异。</p>

<h2 id="实验准备"><a href="#实验准备" class="headerlink" title="实验准备"></a>实验准备</h2>

<p><strong>测试应用</strong>：一个简单的 Spring Boot REST 接口，查一次 MySQL 再返回：</p>

<pre><code class="language-java">@RestController
@RequestMapping("/api/user")
public class UserController {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @GetMapping("/{id}")
    public Map&lt;String, Object&gt; getUser(@PathVariable Long id) {
        return jdbcTemplate.queryForMap(
            "SELECT id, username, email, created_at FROM users WHERE id = ?", id);
    }
}
</code></pre>

<p><strong>表结构 &amp; 数据量</strong>：<code>users</code> 表 10 万条记录，<code>id</code> 有主键索引。</p>

<p><strong>JMeter 压测配置</strong>：</p>

<ul>
<li>线程数：50 / 100 / 200 / 500（四组梯度）</li>
<li>Ramp-up：30 秒（线程逐步启动）</li>
<li>持续时间：120 秒（稳定期采集数据）</li>
<li>测试模式：循环调用 <code>GET /api/user/{randomId}</code></li>
</ul>

<h2 id="配置组-a-spring-boot-默认配置"><a href="#配置组-a-spring-boot-默认配置" class="headerlink" title="配置组 A：Spring Boot 默认配置"></a>配置组 A：Spring Boot 默认配置</h2>

<pre><code class="language-yaml">spring:
  datasource:
    hikari:
      maximum-pool-size: 10       # HikariCP 5.x 默认值
      minimum-idle: 10            # HikariCP 5.x 默认值
      connection-timeout: 30000   # 30s
      idle-timeout: 600000        # 10min
      max-lifetime: 1800000       # 30min
      leak-detection-threshold: 0 # 关闭
</code></pre>

<h2 id="配置组-b-调优后的配置"><a href="#配置组-b-调优后的配置" class="headerlink" title="配置组 B：调优后的配置"></a>配置组 B：调优后的配置</h2>

<pre><code class="language-yaml">spring:
  datasource:
    hikari:
      maximum-pool-size: 10       # 公式：(4核×2) + SSD(2) = 10
      minimum-idle: 3             # 保底 3 个即可，不需要 10 个常驻
      connection-timeout: 5000    # 5s，匹配 API 超时策略
      idle-timeout: 300000        # 5min，更快回收多余连接
      max-lifetime: 900000        # 15min，更积极的刷新策略
      leak-detection-threshold: 30000 # 30s 泄漏检测
      pool-name: BizHikariPool    # 自定义名称，方便日志排查
</code></pre>

<h1 id="连接泄漏：怎么发现怎么防"><a href="#连接泄漏：怎么发现怎么防" class="headerlink" title="连接泄漏：怎么发现怎么防"></a>连接泄漏：怎么发现，怎么防？</h1>

<p>连接泄漏是连接池场景下最常见也最危险的问题之一。它的典型症状是：<strong>运行一段时间后，连接池里的连接越来越少，最终全部耗尽，新请求全部超时</strong>。</p>

<h2 id="常见泄漏场景"><a href="#常见泄漏场景" class="headerlink" title="常见泄漏场景"></a>常见泄漏场景</h2>

<pre><code class="language-java">// ❌ 场景 1：手动获取连接但忘记关闭
@Autowired
private DataSource dataSource;

public void badMethod() throws SQLException {
    Connection conn = dataSource.getConnection();
    // 用完没调 conn.close()！
    // 如果抛异常，更不可能 close 了
}

// ❌ 场景 2：Spring 管理的事务中手动操作 Connection
@Transactional
public void alsoBad() {
    // Transactional 会从池里拿连接，
    // 如果里面又手动 dataSource.getConnection() 且不关，就多占了一个
}

// ✅ 正确做法：交给框架管理
@Transactional
public void goodMethod(UserDTO dto) {
    userMapper.insert(dto);  // MyBatis/Spring 自动管理连接生命周期
}
</code></pre>

<h2 id="开启-leak-detection"><a href="#开启-leak-detection" class="headerlink" title="开启 leak-detection"></a>开启 leak-detection</h2>

<p>调优不是一劳永逸的——随着业务变化，今天的最优配置明天可能就是瓶颈。你需要一套持续监控方案。</p>

<h2 id="step-1-开启-actuator-端点"><a href="#step-1-开启-actuator-端点" class="headerlink" title="Step 1：开启 Actuator 端点"></a>Step 1：开启 Actuator 端点</h2>

<h2 id="step-2-grafana-dashboard-推荐模板"><a href="#step-2-grafana-dashboard-推荐模板" class="headerlink" title="Step 2：Grafana Dashboard（推荐模板）"></a>Step 2：Grafana Dashboard（推荐模板）</h2>

<p>Grafana 官方模板库中有现成的 HikariCP Dashboard（ID: <strong>5887</strong>），导入后可以直接看到：</p>

<ul>
<li><strong>Connections Usage</strong>：Active / Idle / Total 的时序图</li>
<li><strong>Connection Wait Time</strong>：获取连接的等待时间分布（P50/P95/P99）</li>
<li><strong>Pending Threads</strong>：排队等连接的线程数（告警重点）</li>
<li><strong>Connection Creation Rate</strong>：新建连接速率（过高说明池太小或连接频繁被回收）</li>
</ul>

<p>推荐的 Grafana 告警规则：</p>

<pre><code class="language-text"># 告警 1：有线程在等连接（说明池可能不够）
ALERT HikariCPPendingThreads
  IF hikaricp_connections_pending > 0
  FOR 2m
  LABELS { severity = warning }
  ANNOTATIONS {
    summary = "HikariCP 有线程等待连接",
    description = "{{$labels.pool}} 中有 {{$value}} 个线程正在等待连接"
  }

# 告警 2：连接获取超时（严重！）
ALERT HikariCPConnectionTimeout
  IF increase(hikaricp_connections_timeout_total[5m]) > 0
  FOR 1m
  LABELS { severity = critical }
  ANNOTATIONS {
    summary = "HikariCP 连接获取超时",
    description = "过去 5 分钟发生 {{$value}} 次连接获取超时"
  }

# 告警 3：连接利用率过高
ALERT HikariCPUHighUtilization
  IF hikaricp_connections_active / hikaricp_connections_max > 0.85
  FOR 5m
  LABELS { severity = warning }
  ANNOTATIONS {
    summary = "HikariCP 连接利用率过高",
    description = "{{$labels.pool}} 利用率达到 {{ $value | humanizePercentage }}"
  }
</code></pre>

<h2 id="step-3-快速自检命令"><a href="#step-3-快速自检命令" class="headerlink" title="Step 3：快速自检命令"></a>Step 3：快速自检命令</h2>

</code></pre>

<h1 id="常见坑与误区"><a href="#常见坑与误区" class="headerlink" title="常见坑与误区"></a>常见坑与误区</h1>

<h3 id="坑-1-越大越好综合症"><a href="#坑-1-越大越好综合症" class="headerlink" title="坑 1：「越大越好」综合症"></a>坑 1：「越大越好」综合症</h3>

<p><strong>现象</strong>：一看到连接超时就把 <code>maximum-pool-size</code> 从 10 改到 200。</p>

<p><strong>后果</strong>：数据库端瞬间多出 190 个连接，每个连接占用 ~10MB 内存，再加上 190 个线程的上下文切换，数据库 CPU 直接爆炸。而且连接多了意味着锁竞争加剧（MySQL 的内部锁、InnoDB 的行锁队列），<strong>吞吐量反而下降</strong>。</p>

<p><strong>正解</strong>：先用公式算基准值，再用压测数据微调。连接池利用率长期低于 50% 说明设大了，高于 90% 说明可能小了。</p>

<h3 id="坑-2-忽略-mysql-的-wait-timeout"><a href="#坑-2-忽略-mysql-的-wait-timeout" class="headerlink" title="坑 2：忽略 MySQL 的 wait_timeout"></a>坑 2：忽略 MySQL 的 <code>wait_timeout</code></h3>

<p><strong>现象</strong>：凌晨低峰期过后，早上的第一批请求全部报 " Communications link failure " 或 " The last packet successfully received... "。</p>

<p><strong>原因</strong>：MySQL 在夜间把空闲连接踢掉了（<code>wait_timeout</code> 到期），但 HikariCP 这边还认为这些连接是活的。早上第一个请求拿到一个"死连接"，直接报错。</p>

<p><strong>正解</strong>：确保 <code>max-lifetime &lt; MySQL wait_timeout</code>。MySQL 默认 <code>wait_timeout=28800</code>（8 小时），HikariCP 默认 <code>max-lifetime=1800000</code>（30 分钟），通常没问题。但如果运维改过 MySQL 的 <code>wait_timeout</code>（有些云厂商默认 600 秒），一定要同步调整 HikariCP。</p>

<h3 id="坑-3-多数据源共用默认配置"><a href="#坑-3-多数据源共用默认配置" class="headerlink" title="坑 3：多数据源共用默认配置"></a>坑 3：多数据源共用默认配置</h3>

<p><strong>现象</strong>：主库连接池经常不够用，但从库连接池常年空闲。</p>

<p><strong>原因</strong>：主库承担写操作 + 大部分读操作，连接消耗大；从库只承接少量读请求。两个库用一样的 <code>maximum-pool-size=10</code> 显然不合理。</p>

<p><strong>正解</strong>：根据各数据源的实际负载分别配置：</p>

<pre><code class="language-yaml">spring:
  datasource:
    master:          # 主库
      hikari:
        maximum-pool-size: 15
        pool-name: MasterPool
    replica:         # 从库
      hikari:
        maximum-pool-size: 5
        pool-name: ReplicaPool
</code></pre>

<h3 id="坑-4-只看-qps-不看-p99"><a href="#坑-4-只看-qps-不看-p99" class="headerlink" title="坑 4：只看 QPS 不看 P99"></a>坑 4：只看 QPS 不看 P99</h3>

<p><strong>现象</strong>：压测报告上 QPS 很漂亮，但线上用户反馈"偶尔很慢"。</p>

<p><strong>原因</strong>：平均值掩盖了长尾问题。连接池的场景下，只要有一小段时间连接被打满，排队等待的请求就会产生极高的 P99/P999。上文压测数据显示：200 线程下默认配置的 P99 达到了 <strong>1020ms</strong>（超过 1 秒！），但 P50 只有 89ms——只看中位数完全发现不了问题。</p>

<p><strong>正解</strong>：压测报告必须包含 P50 / P95 / P99 三个分位值，线上监控要对 P99 设告警阈值。</p>

<h3 id="坑-5-连接池调优后没做回归"><a href="#坑-5-连接池调优后没做回归" class="headerlink" title="坑 5：连接池调优后没做回归"></a>坑 5：连接池调优后没做回归</h3>

<p><strong>现象</strong>：改了个参数上线，当天晚上又出了新问题。</p>

<p><strong>原因</strong>：连接池和应用是耦合的——改了连接池大小会影响线程池行为、数据库负载、甚至 GC 压力。任何参数变更都应该在预发环境做完整的回归压测。</p>

<p><strong>正解</strong>：建立"参数变更清单"流程：改参数 → 预发压测 → 对比 QPS/P99/错误率/DB CPU → 灰度发布 → 全量观察 24 小时。</p>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>

<p>本文从 HikariCP 的核心参数出发，讲了连接池调优的完整链路：</p>

<ul>
<li><strong><code>maximum-pool-size</code></strong> 是最重要的参数，用官方公式 <code>connections = (core_count × 2) + spindle_count</code> 算基准值，再根据实际 workload 微调</li>
<li><strong><code>minimum-idle</code></strong> 不宜过大，2~5 个足够应对大多数突发流量</li>
<li><strong><code>connection-timeout</code></strong> 要和 API 超时策略匹配，建议 3~10 秒</li>
<li><strong><code>leak-detection-threshold</strong></strong> 必须开（开发和生产都要），性能开销极小但能救命</li>
<li><strong>监控是调优的前提</strong>：通过 Actuator + Prometheus + Grafana 建立 <code>pending</code>、<code>timeout_total</code>、<code>active/max</code> 三个指标的告警</li>
<li><strong>压测必须看 P99</strong>：我们的实验显示，调优后高并发下 P99 改善了 62%（1020ms → 385ms）</li>
</ul>

<p>最后送一句话：<strong>连接池没有银弹配置，只有适合你当前业务的配置</strong>。公式给你起点，压测给你信心，监控给你安全感——三者缺一不可。</p>
