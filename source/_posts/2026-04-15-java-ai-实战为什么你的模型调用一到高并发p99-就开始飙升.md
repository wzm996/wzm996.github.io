<blockquote>
<p>很多 Java 项目接大模型接口时，单次调用明明没问题，一上并发就开始出现 <strong>P99 延迟飙升</strong>、<strong>超时</strong>、<strong>线程堆积</strong>。问题往往不在模型本身，而是在客户端连接复用、超时参数、流式消费以及限流策略这几个看起来“不起眼”的地方。</p>
</blockquote>

<!-- more -->

<h1 id="背景-为什么这类问题在-Java-项目里特别常见"><a href="#背景-为什么这类问题在-Java-项目里特别常见" class="headerlink" title="背景-为什么这类问题在 Java 项目里特别常见"></a>背景：为什么这类问题在 Java 项目里特别常见</h1>
<p>这两年很多 Java 服务开始接入 <strong>LLM（Large Language Model，大语言模型）</strong>。说白了，它就是一个“你给提示词，它给文本结果”的推理服务，通常通过 HTTP API 调用。</p>
<p>问题是，很多团队在做第一版接入时，关注点都放在了 <strong>Prompt</strong>、模型选型、RAG 效果这些“业务层”的东西上，却把最底下的 <strong>HTTP 客户端性能</strong> 当成了默认没问题。结果就是：</p>
<ul>
<li>本地联调一切正常；</li>
<li>压到几十上百并发后，接口开始慢；</li>
<li>P50 看起来还能接受，但 <strong>P95/P99</strong> 明显炸掉；</li>
<li>线程池满了、连接池不够、请求排队，最后大家开始怀疑是模型服务不稳定。</li>
</ul>
<p>这篇文章不聊玄学，专门聊一个很落地的问题：<strong>Java 调大模型接口时，为什么高并发下 P99 会飙升，以及怎么系统性排查和优化。</strong></p>

<h1 id="先说结论：真正容易出问题的不是模型，而是调用链"><a href="#先说结论：真正容易出问题的不是模型，而是调用链" class="headerlink" title="先说结论：真正容易出问题的不是模型，而是调用链"></a>先说结论：真正容易出问题的不是模型，而是调用链</h1>
<p>在工程里，一次模型调用的总耗时，通常可以拆成下面几段：</p>
<ol>
<li><strong>获取连接</strong>：有没有可复用连接，需不需要新建 TCP / TLS；</li>
<li><strong>发送请求</strong>：请求体是不是过大，JSON 序列化有没有额外开销；</li>
<li><strong>模型排队与推理</strong>：模型服务端是否限流、排队、冷启动；</li>
<li><strong>接收响应</strong>：是一次性返回，还是流式返回；</li>
<li><strong>业务后处理</strong>：解析 JSON、写数据库、打日志、落缓存。</li>
</ol>
<p>只要其中一段在高并发下放大，最终的 P99 就会很难看。尤其是下面这 4 个点，最容易把 Java 项目拖慢：</p>
<ul>
<li><strong>连接没有复用</strong>，导致频繁建连；</li>
<li><strong>连接池太小</strong>，请求在客户端排队；</li>
<li><strong>超时配置混乱</strong>，失败请求拖太久才释放资源；</li>
<li><strong>流式响应消费不及时</strong>，把连接长时间占住。</li>
</ul>

<h1 id="一个最小可复现案例：同样的模型接口，为什么参数一改吞吐就掉"><a href="#一个最小可复现案例：同样的模型接口，为什么参数一改吞吐就掉" class="headerlink" title="一个最小可复现案例：同样的模型接口，为什么参数一改吞吐就掉"></a>一个最小可复现案例：同样的模型接口，为什么参数一改吞吐就掉</h1>
<p>为了把问题讲清楚，我们用一个最小 Demo 来模拟“Java 服务调用外部模型网关”。示例基于 Spring Boot 3 + Java 21。</p>
<p><strong>JFR（Java Flight Recorder）</strong> 是 JDK 自带的低开销诊断工具，可以理解成 JVM 的“黑匣子”，用来抓线程、锁、GC、方法热点这些运行时信息。后面我们会用它来验证瓶颈到底卡在哪。</p>

<h2 id="1-控制器代码"><a href="#1-控制器代码" class="headerlink" title="1. 控制器代码"></a>1. 控制器代码</h2>
<pre><code class="language-java">@RestController
@RequestMapping("/ai")
public class AiController {

    private final AiGatewayClient aiGatewayClient;

    public AiController(AiGatewayClient aiGatewayClient) {
        this.aiGatewayClient = aiGatewayClient;
    }

    @GetMapping("/summary")
    public Map&lt;String, Object&gt; summary(@RequestParam(defaultValue = "1000") int size) {
        String prompt = "请用 200 字总结以下文本：" + "A".repeat(size);
        long begin = System.currentTimeMillis();
        String result = aiGatewayClient.chat(prompt);
        long cost = System.currentTimeMillis() - begin;
        return Map.of(
                "costMs", cost,
                "length", result.length(),
                "result", result
        );
    }
}
</code></pre>

<h2 id="2-一个故意写得不够好的客户端版本"><a href="#2-一个故意写得不够好的客户端版本" class="headerlink" title="2. 一个故意写得不够好的客户端版本"></a>2. 一个故意写得不够好的客户端版本</h2>
<p>先看一个线上特别常见的“能跑但不抗压”的写法：</p>
<pre><code class="language-java">@Component
public class AiGatewayClient {

    private final ObjectMapper objectMapper = new ObjectMapper();

    public String chat(String prompt) {
        try {
            HttpClient client = HttpClient.newBuilder()
                    .connectTimeout(Duration.ofSeconds(10))
                    .build();

            String body = objectMapper.writeValueAsString(Map.of(
                    "model", "gpt-4o-mini",
                    "input", prompt
            ));

            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create("http://127.0.0.1:18080/mock-llm/chat"))
                    .timeout(Duration.ofSeconds(60))
                    .header("Content-Type", "application/json")
                    .POST(HttpRequest.BodyPublishers.ofString(body))
                    .build();

            HttpResponse&lt;String&gt; response = client.send(request, HttpResponse.BodyHandlers.ofString());
            return response.body();
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}
</code></pre>
<p>这段代码最大的问题不是“语法丑”，而是它在 <strong>每次请求都 new 一个 HttpClient</strong>。这意味着连接复用、TLS 会话复用、底层连接池这些能力基本都浪费掉了。</p>
<p>如果你的模型服务在公网，或者前面还有 API Gateway / WAF / 反向代理，这类重复建连带来的额外耗时会被进一步放大。</p>

<h2 id="3-改成可复用客户端版本"><a href="#3-改成可复用客户端版本" class="headerlink" title="3. 改成可复用客户端版本"></a>3. 改成可复用客户端版本</h2>
<pre><code class="language-java">@Configuration
public class AiClientConfig {

    @Bean
    public HttpClient httpClient() {
        ExecutorService executor = Executors.newFixedThreadPool(64);
        return HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(3))
                .executor(executor)
                .version(HttpClient.Version.HTTP_1_1)
                .build();
    }
}
</code></pre>

<pre><code class="language-java">@Component
public class AiGatewayClient {

    private final HttpClient httpClient;
    private final ObjectMapper objectMapper;

    public AiGatewayClient(HttpClient httpClient, ObjectMapper objectMapper) {
        this.httpClient = httpClient;
        this.objectMapper = objectMapper;
    }

    public String chat(String prompt) {
        try {
            String body = objectMapper.writeValueAsString(Map.of(
                    "model", "gpt-4o-mini",
                    "input", prompt
            ));

            HttpRequest request = HttpRequest.newBuilder()
                    .uri(URI.create("http://127.0.0.1:18080/mock-llm/chat"))
                    .timeout(Duration.ofSeconds(20))
                    .header("Content-Type", "application/json")
                    .POST(HttpRequest.BodyPublishers.ofString(body))
                    .build();

            HttpResponse&lt;String&gt; response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
            if (response.statusCode() &gt;= 400) {
                throw new IllegalStateException("bad response: " + response.statusCode());
            }
            return response.body();
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}
</code></pre>

<p>注意，这还不是“最优解”，但至少从“一次请求一个客户端”的坑里爬出来了。</p>

<h1 id="怎么压：用-wrk-先把问题打出来"><a href="#怎么压：用-wrk-先把问题打出来" class="headerlink" title="怎么压：用 wrk 先把问题打出来"></a>怎么压：用 wrk 先把问题打出来</h1>
<p><strong>wrk</strong> 是一个常用 HTTP 压测工具，特点是轻量、快，适合先把接口的吞吐和延迟曲线打出来。你可以把它理解成“先用它探探服务到底扛不扛揍”。</p>
<p>先启动一个模拟模型服务的 Mock Server。这里可以直接用 WireMock、MockWebServer，或者自己写个简单 Controller，在服务端随机 sleep 200~800ms，模拟模型推理时间：</p>
<pre><code class="language-java">@RestController
@RequestMapping("/mock-llm")
public class MockLlmController {

    private final Random random = new Random();

    @PostMapping("/chat")
    public String chat(@RequestBody String body) throws Exception {
        Thread.sleep(200 + random.nextInt(600));
        return "这是模型返回的摘要结果";
    }
}
</code></pre>

<p>然后压测业务接口：</p>
<pre><code class="language-bash">wrk -t4 -c32 -d60s 'http://127.0.0.1:8080/ai/summary?size=1500'
wrk -t8 -c64 -d60s 'http://127.0.0.1:8080/ai/summary?size=3000'
</code></pre>

<p>如果你想更贴近真实流量，可以分三组场景压：</p>
<ul>
<li><strong>短 Prompt</strong>：size=500</li>
<li><strong>中 Prompt</strong>：size=1500</li>
<li><strong>长 Prompt</strong>：size=5000</li>
</ul>
<p>这样可以顺便观察：<strong>输入 token 增大后，到底是模型变慢，还是你自己的序列化、网络、连接占用时间变长。</strong></p>

<h1 id="用-JFR-抓一次，你就知道时间花到哪了"><a href="#用-JFR-抓一次，你就知道时间花到哪了" class="headerlink" title="用 JFR 抓一次，你就知道时间花到哪了"></a>用 JFR 抓一次，你就知道时间花到哪了</h1>
<p>很多性能问题靠猜是猜不准的。最稳的方式，是边压边采样。</p>

<h2 id="1-启动时打开-JFR"><a href="#1-启动时打开-JFR" class="headerlink" title="1. 启动时打开 JFR"></a>1. 启动时打开 JFR</h2>
<pre><code class="language-bash">java \
  -XX:StartFlightRecording=filename=llm-client.jfr,duration=120s,settings=profile \
  -jar target/demo.jar
</code></pre>

<p>这里的 <strong>profile</strong> 是 JFR 的采样配置，偏向性能分析；<strong>duration=120s</strong> 表示采 120 秒，刚好覆盖一轮压测。</p>

<h2 id="2-压测期间观察什么"><a href="#2-压测期间观察什么" class="headerlink" title="2. 压测期间观察什么"></a>2. 压测期间观察什么</h2>
<p>把 JFR 文件用 JDK Mission Control 打开，优先看这几块：</p>
<ul>
<li><strong>Socket Read</strong>：是不是大量时间都在等下游返回；</li>
<li><strong>Java Monitor Blocked</strong>：是不是有对象锁竞争；</li>
<li><strong>Thread Dump</strong>：业务线程是不是都堵在 send()/read() 上；</li>
<li><strong>Garbage Collections</strong>：GC 暂停有没有明显抬高尾延迟；</li>
<li><strong>Method Profiling</strong>：JSON 序列化、日志打印、字符串拼接是否过重。</li>
</ul>

<p>如果你看到绝大部分线程都挂在网络 I/O 上，那通常说明瓶颈更偏向 <strong>下游慢 / 连接占用长 / 客户端并发策略不合适</strong>。如果你看到 GC 次数特别频繁，那就要怀疑是不是请求体、响应体、日志对象创建过多，导致年轻代回收太勤。</p>

<h2 id="3-GC-日志顺手也开上"><a href="#3-GC-日志顺手也开上" class="headerlink" title="3. GC 日志顺手也开上"></a>3. GC 日志顺手也开上</h2>
<pre><code class="language-bash">java \
  -Xlog:gc*:file=gc.log:time,level,tags \
  -XX:StartFlightRecording=filename=llm-client.jfr,duration=120s,settings=profile \
  -jar target/demo.jar
</code></pre>

<p>GC 日志不是为了“看一眼安心”，而是为了确认尾延迟尖峰时，JVM 有没有一起抖一下。模型调用这种 I/O 密集型场景，GC 不一定是主因，但它经常是“放大器”。</p>

<h1 id="真正有效的优化，不是一个参数，而是一组取舍"><a href="#真正有效的优化，不是一个参数，而是一组取舍" class="headerlink" title="真正有效的优化，不是一个参数，而是一组取舍"></a>真正有效的优化，不是一个参数，而是一组取舍</h1>
<p>很多人喜欢问：“连接池应该调多少？” 这种问题没有万能答案。因为模型调用的性能，实际上是 <strong>吞吐、尾延迟、成本、失败率</strong> 四件事的平衡。</p>

<h2 id="1-连接复用：第一优先级"><a href="#1-连接复用：第一优先级" class="headerlink" title="1. 连接复用：第一优先级"></a>1. 连接复用：第一优先级</h2>
<p>不管你用的是 JDK HttpClient、OkHttp 还是 Apache HttpClient，第一原则都一样：<strong>客户端对象要复用</strong>。</p>
<p>原因很简单：</p>
<ul>
<li>减少 TCP 三次握手和 TLS 握手开销；</li>
<li>降低连接建立阶段的抖动；</li>
<li>避免在高并发下把大量时间浪费在建连上。</li>
</ul>

<h2 id="2-限流：不要把下游当无限吞吐机"><a href="#2-限流：不要把下游当无限吞吐机" class="headerlink" title="2. 限流：不要把下游当无限吞吐机"></a>2. 限流：不要把下游当无限吞吐机</h2>
<p><strong>限流</strong> 就是主动控制同时打到下游的请求数量，避免把外部模型服务、网关、或者你自己的线程池一把打爆。</p>
<p>最简单的方式可以直接上 <strong>Semaphore</strong>：</p>
<pre><code class="language-java">@Component
public class AiGatewayClient {

    private final Semaphore semaphore = new Semaphore(24);

    public String chat(String prompt) {
        boolean acquired = false;
        try {
            acquired = semaphore.tryAcquire(200, TimeUnit.MILLISECONDS);
            if (!acquired) {
                throw new IllegalStateException("LLM downstream busy");
            }
            // do http call
            return "ok";
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        } finally {
            if (acquired) {
                semaphore.release();
            }
        }
    }
}
</code></pre>

<p>这会让吞吐看起来“没那么猛”，但通常能明显改善 P99。原因也不复杂：<strong>少一点无意义排队，往往比盲目堆并发更划算。</strong></p>

<h2 id="3-超时配置：别让失败请求拖 60 秒才死"><a href="#3-超时配置：别让失败请求拖 60 秒才死" class="headerlink" title="3. 超时配置：别让失败请求拖 60 秒才死"></a>3. 超时配置：别让失败请求拖 60 秒才死</h2>
<p>模型调用常见的超时至少有三层：</p>
<ul>
<li><strong>连接超时</strong>：连不上多快失败；</li>
<li><strong>读取超时/请求超时</strong>：对方一直不回，多久放弃；</li>
<li><strong>业务超时</strong>：从网关到应用整体最多接受多久。</li>
</ul>
<p>如果你把请求超时统一拍成 60 秒，表面上是“更稳”，实际上常常是在制造资源滞留。失败请求不及时释放，连接、线程、队列都会一起堆。</p>

<h2 id="4-流式返回不是白嫖，它会占着连接更久"><a href="#4-流式返回不是白嫖，它会占着连接更久" class="headerlink" title="4. 流式返回不是白嫖，它会占着连接更久"></a>4. 流式返回不是白嫖，它会占着连接更久</h2>
<p><strong>流式返回（streaming）</strong> 指的是模型一边生成 token，一边把内容逐段推回来。它的好处是首字更快，用户体感更好；坏处是连接会被占用更久。</p>
<p>这就带来一个很现实的 trade-off：</p>

<table>
<thead>
<tr>
<th style="text-align:center">策略</th>
<th style="text-align:center">首字延迟</th>
<th style="text-align:center">总连接占用</th>
<th style="text-align:center">适用场景</th>
</tr>
</thead>
<tbody>
<tr>
<td style="text-align:center">一次性返回</td>
<td style="text-align:center">偏慢</td>
<td style="text-align:center">偏短</td>
<td style="text-align:center">批处理、离线任务</td>
</tr>
<tr>
<td style="text-align:center">流式返回</td>
<td style="text-align:center">更快</td>
<td style="text-align:center">偏长</td>
<td style="text-align:center">聊天、Copilot、问答</td>
</tr>
</tbody>
</table>

<p>如果你的服务主打“对话体验”，流式通常值得；如果你的服务主要是后台摘要、批量改写、标签生成，那很多时候非流式更容易把整体吞吐做稳。</p>

<h2 id="5-成本-延迟一起看，别只看模型单价"><a href="#5-成本-延迟一起看，别只看模型单价" class="headerlink" title="5. 成本 / 延迟一起看，别只看模型单价"></a>5. 成本 / 延迟一起看，别只看模型单价</h2>
<p>做模型接入时，很多团队只盯着“哪个模型便宜”，但真正影响系统成本的，往往是：</p>
<ul>
<li>是否因为超时重试导致 <strong>重复计费</strong>；</li>
<li>是否因为长 Prompt 导致 <strong>token 成本</strong> 上升；</li>
<li>是否因为流式占连接太久，逼着你把实例数扩上去；</li>
<li>是否因为 P99 太高，最终需要增加缓存或异步化改造。</li>
</ul>
<p>所以一个比较靠谱的评估方式是同时看：</p>
<ul>
<li><strong>平均每次调用成本</strong>；</li>
<li><strong>P95 / P99</strong>；</li>
<li><strong>超时率 / 重试率</strong>；</li>
<li><strong>单位实例吞吐</strong>。</li>
</ul>
<p>这才是工程视角，而不是只看单个模型报价表。</p>

<h1 id="如何验证你的优化到底有没有效果"><a href="#如何验证你的优化到底有没有效果" class="headerlink" title="如何验证你的优化到底有没有效果"></a>如何验证你的优化到底有没有效果</h1>
<p>别靠感觉。按下面这个顺序做验证：</p>
<ol>
<li>固定一个 Mock LLM 延迟分布，比如 200~800ms；</li>
<li>先压“每次 new HttpClient”的版本，记录吞吐和 P95/P99；</li>
<li>改成“复用客户端”，重新压；</li>
<li>再加并发闸门（Semaphore / Bulkhead），继续压；</li>
<li>同时采 JFR 和 GC 日志，对比线程等待和 GC 情况；</li>
<li>最后再把 Mock 换成真实模型网关做小流量验证。</li>
</ol>

<p>如果优化有效，你通常会看到下面几个信号：</p>
<ul>
<li>P99 明显下降，尖刺减少；</li>
<li>超时率下降；</li>
<li>线程堆积减轻；</li>
<li>实例 CPU 不一定大幅下降，但 <strong>吞吐更稳定</strong>；</li>
<li>在同样并发下，错误率更低。</li>
</ul>

<h1 id="常见坑-误区：很多团队都踩过"><a href="#常见坑-误区：很多团队都踩过" class="headerlink" title="常见坑 / 误区：很多团队都踩过"></a>常见坑 / 误区：很多团队都踩过</h1>
<h2 id="1-把慢都归因给模型"><a href="#1-把慢都归因给模型" class="headerlink" title="1. 把慢都归因给模型"></a>1. 把慢都归因给模型</h2>
<p>模型确实可能慢，但你得先确认是不是客户端排队、连接复用失败、线程池打满，别一上来就甩锅给下游。</p>

<h2 id="2-平均耗时好看，就觉得服务稳定"><a href="#2-平均耗时好看，就觉得服务稳定" class="headerlink" title="2. 平均耗时好看，就觉得服务稳定"></a>2. 平均耗时好看，就觉得服务稳定</h2>
<p>模型调用的体验问题，十有八九出在尾延迟。只看平均值，很容易把偶发长尾给藏掉。</p>

<h2 id="3-无脑加线程池大小"><a href="#3-无脑加线程池大小" class="headerlink" title="3. 无脑加线程池大小"></a>3. 无脑加线程池大小</h2>
<p>线程变多，不等于吞吐一定更高。I/O 密集型场景下，如果下游本来就慢，你只是把排队从一个地方挪到另一个地方。</p>

<h2 id="4-把日志打得像流水账"><a href="#4-把日志打得像流水账" class="headerlink" title="4. 把日志打得像流水账"></a>4. 把日志打得像流水账</h2>
<p>模型请求体、响应体通常都不小。高并发下 full body 日志非常容易把 CPU、磁盘 I/O、对象分配一起拉高。生产环境建议做采样日志和字段脱敏，不要把每个 token 都完整刷出来。</p>

<h2 id="5-重试策略没边界"><a href="#5-重试策略没边界" class="headerlink" title="5. 重试策略没边界"></a>5. 重试策略没边界</h2>
<p>LLM 调用超时后直接重试，看起来合理，但如果没有总超时、没有退避策略、没有幂等保护，很容易把下游打成雪崩。</p>

<h1 id="更适合生产环境的一套建议"><a href="#更适合生产环境的一套建议" class="headerlink" title="更适合生产环境的一套建议"></a>更适合生产环境的一套建议</h1>
<blockquote>
<p>如果你要在 Java 服务里稳定接入大模型，我更推荐把它当成“一个慢而贵的外部依赖”来治理，而不是把它当普通 HTTP 接口随便调用。</p>
</blockquote>

<ul>
<li><strong>客户端单例复用</strong>；</li>
<li><strong>设置清晰的 connect/read/business timeout</strong>；</li>
<li><strong>对下游做并发闸门</strong>；</li>
<li><strong>按场景决定是否流式返回</strong>；</li>
<li><strong>观测指标至少补齐 QPS、P95/P99、超时率、重试率</strong>；</li>
<li><strong>压测时同时抓 JFR / GC 日志</strong>；</li>
<li><strong>把成本、延迟、稳定性一起纳入评估</strong>。</li>
</ul>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>
<p>回到文章标题那个问题：<strong>为什么你的模型调用一到高并发，P99 就开始飙升？</strong></p>
<p>大概率不是一个单点问题，而是下面几件事叠在一起：</p>
<ul>
<li>连接没有复用；</li>
<li>下游响应慢，连接占用时间长；</li>
<li>客户端没有限流，导致本地排队；</li>
<li>超时策略太松，失败请求迟迟不释放；</li>
<li>GC、日志、对象分配在高并发下继续放大尾延迟。</li>
</ul>
<p>真正靠谱的优化路径也很明确：<strong>先压测，后观测，再调参，最后拿真实流量验证。</strong> 别靠拍脑袋，也别一看到慢就只会换更贵的模型。</p>
