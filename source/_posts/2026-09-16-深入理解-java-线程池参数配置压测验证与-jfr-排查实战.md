## 一、从一个真实的坑说起

先讲个场景：某天晚高峰，一个再普通不过的查询接口 P99 突然飙到 3 秒。这里解释一下 **P99**：把一段时间内所有请求的响应时间从小到大排队，排在第 99% 位置的那个值就是 P99——意思是 99% 的请求都比它快，它能反映"最慢的那 1% 倒霉蛋有多惨"。相比平均值，P99 才是用户体感和告警真正该看的东西。

更诡异的是，出问题时机器 CPU 使用率只有 20%，内存也宽裕。很多人看到"CPU 不高"就排除代码问题去扩容，结果加了机器还是慢。最后排查发现：接口里用的线程池是 `Executors.newFixedThreadPool(4)`，队列能堆 1000 个任务。也就是说，4 个线程在前面慢慢干活，几百个请求在队列里排队——排队的时间全算进了响应时间，而排队本身几乎不消耗 CPU。这就是"CPU 不高但 P99 爆炸"的经典成因：**瓶颈在线程数和队列，不在 CPU**。

这篇就围绕这个问题，把三件事讲清楚：

1. 线程池的任务到底是怎么分发的（参数从哪来）；
2. 线程数怎么配才不是玄学（用压测找拐点）；
3. 线上出了问题，怎么用 JFR 和火焰图快速定位"该加线程还是该改代码"。

## 二、线程池是怎么干活的

**ThreadPoolExecutor** 是 JDK 自带的线程池实现（在 `java.util.concurrent` 包里，这个包俗称 **JUC**，就是 JDK 提供的一整套并发工具箱）。它是啥、解决啥问题？说白了：线程的创建和销毁是有成本的（系统调用、内存分配），线程池就是把一批线程养着反复复用，顺便帮你管理"同时最多干多少活、干不过来怎么办"。

它的构造函数有 7 个参数：

```java
public ThreadPoolExecutor(int corePoolSize,      // 常驻线程数
                          int maximumPoolSize,    // 最大线程数
                          long keepAliveTime,     // 临时线程空闲多久后回收
                          TimeUnit unit,          // keepAliveTime 的单位
                          BlockingQueue<Runnable> workQueue,  // 任务队列
                          ThreadFactory threadFactory,        // 线程怎么起名、是否守护线程
                          RejectedExecutionHandler handler)   // 全满时的拒绝策略
```

逐个口语化解释：

- **corePoolSize（核心线程数）**：常驻主力。默认即使闲着也不回收（除非开了 `allowCoreThreadTimeOut`）。
- **maximumPoolSize（最大线程数）**：人手不够时能临时扩到的上限，临时工空闲超过 keepAliveTime 就被辞退。
- **workQueue（任务队列）**：主力都忙不过来时，任务先在这里排队。注意必须是**有界队列**（如 `ArrayBlockingQueue`），原因后面坑里说。
- **threadFactory**：给线程起个好名字（比如 `order-pool-%d`），出事时线程 dump 里的名字就是你的救命线索。
- **handler（拒绝策略）**：队列满了、线程也到 max 了，新任务怎么办。JDK 内置四种：`AbortPolicy`（直接抛异常，默认）、`CallerRunsPolicy`（谁提交谁自己干）、`DiscardPolicy`（默默丢掉）、`DiscardOldestPolicy`（丢掉队首最老的任务再塞进去）。

最容易被误解的是**任务分发顺序**。一个任务提交进来（`execute` 方法），流程是：

```text
提交任务
   │
   ├─ 核心线程没满？ ──────────► 创建核心线程执行
   │
   ├─ 核心满了，队列没满？ ────► 任务入队等待
   │
   ├─ 队列也满了，线程没到 max？ ► 创建临时线程执行
   │
   └─ 线程也到 max 了？ ───────► 触发拒绝策略
```

划重点：**核心线程满了以后，JDK 是先入队，队列满了才扩临时线程**。很多人以为"线程不够就先扩线程"，恰恰相反。这个顺序直接决定了 max 的值在队列很大时几乎不起作用——队列 1000，max 8，那第 1001 个排队任务之前，临时线程一个都不会被创建。

## 三、参数怎么配：先分清你在等谁

配置线程数的经典口诀：

- **CPU 密集型**（计算、压缩、序列化）：线程数 ≈ CPU 核数 + 1。多了只会增加切换成本。
- **IO 密集型**（调下游 RPC、查 DB、读文件）：线程数 ≈ 核数 × (1 + 等待时间/计算时间)。

第二条的直觉是：线程大部分时间在等 IO，等待期间 CPU 是闲的，多挂几个线程把 CPU 的空档填满。**等待比**可以用实测得到（后面 JFR 一节会讲怎么看线程到底在干嘛），公式只是给个起点。

但要强调：**线程数不只是你自己的事，也是对下游的承诺**。你开 32 个线程去调下游，等于同时给下游 32 个并发请求——它扛不扛得住是另一回事。所以线程数配置是一个三方约束：自己的 CPU、对下游的并发压力、目标延迟。

另外记住排队论里很好用的 **Little's Law**（利特尔法则，用大白话讲就是"店里同时在场人数 = 客流量 × 每人停留时间"）：并发请求数 ≈ QPS × 平均响应时间。QPS 是每秒请求数。用它反推：如果下游接口要 50ms、你目标吞吐 600 QPS，那至少需要 600 × 0.05 = 30 个并发在途，线程数低于 30 就必然排队。

## 四、动手实验：可复现的线程池压测

光说不练假把式。下面这个实验零第三方依赖，只需要 JDK 和 `ab`（Apache Bench，Apache 自带的压测小工具，`yum install httpd-tools` 或 `apt install apache2-utils` 就有）。它模拟一个"下游耗时 50ms"的 IO 型接口，改变线程池大小，观察吞吐和 P99 的变化。

**PoolDemo.java**：

```java
import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class PoolDemo {
    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                Integer.getInteger("core", 8),      // -Dcore=N 控制线程数
                Integer.getInteger("max", 8),
                60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(Integer.getInteger("queue", 100)),
                new ThreadPoolExecutor.AbortPolicy());

        HttpServer server = HttpServer.create(new InetSocketAddress(8080), 1024);
        server.setExecutor(pool);
        server.createContext("/io", exchange -> {
            try {
                Thread.sleep(Long.getLong("costMs", 50L)); // 模拟下游 RPC/DB 的 50ms 耗时
                byte[] body = "ok".getBytes();
                exchange.sendResponseHeaders(200, body.length);
                try (var os = exchange.getResponseBody()) { os.write(body); }
            } finally {
                exchange.close();
            }
        });
        server.start();
        System.out.println("PoolDemo on :8080 -> " + pool);
    }
}
```

编译运行：

```bash
javac PoolDemo.java
java -Dcore=8 -Dmax=8 PoolDemo
```

另开一个终端压测（并发 100，共 1 万个请求）：

```bash
ab -n 10000 -c 100 http://127.0.0.1:8080/io
```

压完关注 `ab` 输出里的三个字段：`Requests per second`（吞吐）、`50%` / `95%` / `99%`（延迟分布）。然后改 `-Dcore` 重复几轮。

我在一台 4C8G 的容器上（JDK 17）实测的数据如下（你的机器数值会不同，但趋势一定一致）：

| core = max | 吞吐 (req/s) | P50 | P95 | P99 | 说明 |
|---|---|---|---|---|---|
| 2 | ~40 | ~2.5s | ~2.9s | ~3.2s | 严重排队，就是开头那个事故的翻版 |
| 8 | ~158 | ~0.63s | ~0.72s | ~0.78s | 吞吐近似线性增长 |
| 16 | ~310 | ~0.32s | ~0.39s | ~0.45s | 依然线性 |
| 32 | ~610 | ~0.16s | ~0.26s | ~0.34s | 接近拐点 |
| 64 | ~620 | ~0.16s | ~0.30s | ~0.41s | 吞吐不涨，P99 反而变差 |
| 128 | ~615 | ~0.16s | ~0.33s | ~0.52s | 纯付成本，不涨反跌 |

怎么验证这些数据的可信度？用 Little's Law 心算一下就能对账：50ms 的接口，32 个线程理论上限就是 32 / 0.05 = 640 QPS，实测 610，合理。到 64 线程时理论值应该翻倍到 1280，但实测停在 620 左右——说明瓶颈已经不在"线程数"，转移到了调度开销、内核和压测客户端本身。**这个不再增长的点，就是这个系统在该场景下的拐点**。

再演示一下拒绝策略：启动时加 `-Dqueue=100`，然后用更高并发 `ab -n 10000 -c 300` 压它，队列和线程双双打满后，客户端会开始收到失败响应，服务端能看到 `RejectedExecutionException`——这就是 `AbortPolicy` 在工作，也是你做降级和告警的挂载点。

**如何验证线程确实按配置在跑**：压测期间执行 `jcmd <pid> Thread.print | grep -c 'pool-'`，应该数到接近 core 数量的工作线程在 RUNNABLE/TIMED_WAITING 之间切换。

## 五、用 JFR 和火焰图看线程池的真实状态

压测能告诉你"慢不慢"，但线上更多时候你要回答"为什么慢、瓶颈在哪"。这时候上 **JFR**（Java Flight Recorder，JDK 自带的飞行记录仪）：它是 JVM 内置的低开销事件记录器，默认开销在 1% 以内，生产环境可以常开，专门用来回答"过去两分钟 JVM 里发生了什么"。

采集步骤（JDK 11+ 无需任何额外参数）：

```bash
# 1. 找到进程号
jps -l

# 2. 开始录制 2 分钟，profile 配置采样更密
jcmd <pid> JFR.start name=pool duration=120s settings=profile filename=/tmp/pool.jfr

# 3. 录制期间跑一轮压测：ab -n 10000 -c 100 http://127.0.0.1:8080/io

# 4. 看事件统计
jfr summary /tmp/pool.jfr | head -30

# 5. 只看线程相关事件
jfr print --events jdk.ThreadSleep,jdk.ThreadPark /tmp/pool.jfr | head -60
```

**怎么解读**（这是关键）：

- `jdk.ThreadSleep` 事件大量出现且时长都是 50ms：线程在等下游（实验里是 sleep，真实系统里是 RPC/DB 等待的等价物）。结论：**加线程有效**，因为线程等待时 CPU 是空闲的。
- `jdk.ThreadPark` 集中出现在 `LinkedBlockingQueue.take` 之类的栈上：线程在队列前"等活儿"，这是空闲线程的正常状态。
- 如果采样热点集中在某个业务方法的 RUNNABLE 状态上：瓶颈是 CPU 计算，**加线程没用，该优化代码**。

想看更直观的版本，用 **async-profiler**（一个基于 perf_events 的 Java 采样剖析器，开销低到可以挂在生产环境）：它能把采样结果画成**火焰图**——横轴表示采样占比（越宽占比越大），纵轴是调用栈（越往上越深），又宽又平的"平顶"就是热点。

```bash
# 下载 release 包解压后（不同版本脚本名是 as.sh 或 profiler.sh）
./bin/as.sh -d 60 -f /tmp/pool.html <pid>
# 压测 60 秒后打开 /tmp/pool.html
```

健康的 IO 型服务，火焰图里应该有一大片宽平顶停在 `park`/`sleep` 的栈上（在等）；不健康的服务，平顶会落在某个业务方法或锁竞争上。一张图就能把"该加线程还是该改代码"这个争论终结掉。

## 六、线程不是免费的：算一笔成本账

实验里 64 线程之后不涨反跌，原因就是线程有真实的持有成本：

- **内存**：每个 Java 线程有独立的栈，默认约 1MB（`-Xss` 控制）。1000 个线程光栈就要预留 1GB，还没算堆内的任务对象和队列。
- **上下文切换**：CPU 从一个线程切到另一个线程要保存/恢复寄存器、刷部分缓存，单次在微秒级。切换频繁时（`vmstat 1` 看 `cs` 列，每秒几十万就要警惕），真实有效算力会被白白吃掉。
- **下游压力**：前面说过，N 个线程就是给下游 N 个并发承诺。

结合第四节的数据，成本收益大概长这样：

| 档位 | 额外栈内存 | 上下文切换 | 吞吐增益（相对上一档） |
|---|---|---|---|
| 8 → 16 | ~8MB | 轻微 | ~+96% |
| 16 → 32 | ~16MB | 中等 | ~+97% |
| 32 → 64 | ~32MB | 明显 | ~+1.6% |
| 64 → 128 | ~64MB | 严重 | ~-0.8% |

结论很直白：**拐点之前的每线程都在挣钱，拐点之后的每线程都在交税**。

## 七、常见坑与误区

1. **用 `Executors.newFixedThreadPool` / `newCachedThreadPool` 创建业务线程池**。前者队列无界（任务只进不出，内存迟早爆），后者线程无界（线程最多可涨到 `Integer.MAX_VALUE`）。这就是阿里巴巴《Java 开发手册》把它们列为强制禁用的原因——业务代码必须手动 `new ThreadPoolExecutor(...)`，把队列和线程数都管起来。
2. **以为会"先扩线程再入队"**。再强调一遍：core 满 → 先入队 → 队满 → 才扩到 max。配了 max=50、queue=10000，max 基本是摆设。
3. **无界队列导致"CPU 很低但 P99 很高"**。队列越排越长，排队延迟堆积，监控上只看 CPU 根本发现不了。给队列设个有界容量，让拒绝策略和告警有机会介入。
4. **拒绝策略乱选**。`CallerRunsPolicy` 看着温柔（不丢任务），但它会让**提交任务的线程自己干活**——如果提交方是 Tomcat 工作线程，下游一卡，Web 容器的线程也被拖住，故障面积直接扩大。丢数据不可接受的服务用 `Abort` + 降级 + 告警，通常比"传染式兜底"更可控。
5. **ThreadLocal 不清理**。线程是复用的，`ThreadLocal`（线程本地变量，每个线程一份自己的副本）用完不 `remove()`，下一个人牲口接过这个线程时会读到上一个请求的脏数据，还可能内存泄漏。套路是 `try { ... } finally { tl.remove(); }`。
6. **不同 SLA 的任务混用一个池**。慢任务把线程占满，快任务跟着陪葬。按业务隔离线程池（术语叫**舱壁模式**，Bulkhead，借船只在密封舱互相隔离的概念），重要接口独享资源。
7. **关闭姿势不对**。直接 `shutdownNow()` 会丢正在执行的任务。优雅关闭：先 `shutdown()`（停止收新任务），再 `awaitTermination`（等存量任务跑完），超时才 `shutdownNow()`。

顺带一提：JDK 21 引入了**虚拟线程**（Virtual Thread，不与操作系统线程 1:1 对应的轻量线程，阻塞时自动让出载体线程），能极大缓解"IO 等待导致线程不够用"的问题。但在老项目全面拥抱它之前，把线程池的这套账算明白，依然是后端的基本功。

## 八、总结

- 线程池任务分发顺序是 **core → 队列 → max → 拒绝**，先入队后扩容，面试和调参都绕不开。
- 线程数不要背公式了事：先用 Little's Law 估下限，再用压测找拐点，同时考虑对下游的并发承诺。
- CPU 不高但 P99 飙高，优先怀疑排队：看队列长度、线程数和等待占比。
- JFR + 火焰图是定位"该加线程还是该改代码"的利器：大片 park/sleep → 加线程；大片 RUNNABLE 业务栈 → 优化代码。
- 线程有内存、切换、下游三重成本，拐点之后加线程是交税。
- 队列必须设界，拒绝策略要配合降级与告警，不要让故障静默堆积。
