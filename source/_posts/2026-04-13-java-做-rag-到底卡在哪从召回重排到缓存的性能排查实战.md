# 一、为什么这篇文章值得写

最近两年，**Java × AI** 这条线越来越像正经工程问题，而不是玩具 Demo。尤其是 RAG，大家都知道它是“先查资料、再让大模型回答”的套路，但真正上线之后，最先暴露的通常不是“答不答得出来”，而是这几个问题：

1. **延迟不稳定**：有时候 2 秒，有时候 8 秒；
2. **召回质量一般**：明明知识库里有答案，但它就是没捞出来；
3. **成本不可控**：上下文塞得太满，token 花得飞快；
4. **吞吐扛不住**：一到并发就开始排队，P95/P99 飙升。

这类问题特别适合写成工程化文章，因为它不是一句“换个大模型”就能解决。你得拆链路、做度量、看数据、做取舍。

这篇文章我会用一个典型的 Java 服务链路来讲：**Spring Boot + LangChain4j + 向量检索 + 本地缓存**。重点不在于某个框架 API 怎么写，而在于：**RAG 性能问题到底该怎么定位，优化动作怎么做，优化完怎么验证**。

# 二、先把链路拆开：RAG 请求到底都慢在哪

先说一个最关键的工程习惯：**不要把 RAG 当成一个黑盒调用。**

线上一次完整的 RAG 请求，通常至少包含下面几个阶段：

1. **Query 预处理**：对用户问题做清洗、改写、补全；
2. **Embedding**：把 query 转成向量；
3. **召回（Recall）**：去向量库或检索引擎里捞候选文档；
4. **重排（Rerank）**：把“看起来相关”的文档重新排序；
5. **Prompt 组装**：挑文档片段塞进提示词；
6. **LLM 生成**：调用大模型出最终答案；
7. **后处理**：结果截断、引用补充、敏感信息处理。

如果你没做埋点，最后在监控里看到的就只有一个总耗时，比如 4200ms。这个数字几乎没用，因为你根本不知道时间到底花在了哪。

一个最基本的做法，是把每个阶段都单独打点。哪怕先不用接 APM（Application Performance Monitoring，应用性能监控），只打日志也比黑盒强。

## 2.1 一个最小可用的打点模型

下面是一个简化版的 Java 代码，演示怎么给 RAG 链路分阶段计时：

```java
public class RagMetrics {
    private final Map<String, Long> costs = new LinkedHashMap<>();

    public <T> T record(String stage, Supplier<T> action) {
        long start = System.nanoTime();
        try {
            return action.get();
        } finally {
            long costMs = (System.nanoTime() - start) / 1_000_000;
            costs.put(stage, costMs);
        }
    }

    public void printSummary() {
        long total = costs.values().stream().mapToLong(Long::longValue).sum();
        System.out.println("==== RAG cost breakdown ====");
        costs.forEach((k, v) -> System.out.printf("%-16s %4d ms%n", k, v));
        System.out.printf("%-16s %4d ms%n", "total", total);
    }
}
```

在业务代码里这样用：

```java
RagMetrics metrics = new RagMetrics();

String rewrittenQuery = metrics.record("rewrite", () -> queryRewriter.rewrite(userQuery));
float[] embedding = metrics.record("embedding", () -> embeddingModel.embed(rewrittenQuery));
List<Document> recalledDocs = metrics.record("recall", () -> vectorStore.search(embedding, 20));
List<Document> rerankedDocs = metrics.record("rerank", () -> reranker.rerank(rewrittenQuery, recalledDocs, 5));
String prompt = metrics.record("prompt_build", () -> promptBuilder.build(userQuery, rerankedDocs));
String answer = metrics.record("llm_generate", () -> chatModel.generate(prompt));

metrics.printSummary();
```

你第一次把这个打出来，往往就会发现一个很真实的情况：**原来慢的不一定是 LLM，可能是 recall + rerank。**

# 三、可复现实验：三版链路的性能对比

这一节不空讲，直接给一个可复现实验模型。场景设定如下：

- 服务：Spring Boot 3 + Java 21
- 检索：向量库（抽象为 `vectorStore.search`）
- 重排：Cross-Encoder 风格 rerank 服务
- 模型：外部 LLM API
- 数据集：约 1 万段文档切片
- 压测方式：固定 50 并发、每轮 200 请求

为了方便复现，我们定义三版链路：

- **V1：基础版**：召回 Top20 + 全量重排 + 无缓存
- **V2：优化版**：召回 Top10 + 只重排 Top10 + prompt 截断 + 本地缓存
- **V3：进一步优化版**：增加 query 归一化缓存 + 热点问题 answer cache + 异步预热

## 3.1 压测命令

这里用 `wrk` 做个简单压测。`wrk` 是一个很常见的 HTTP 压测工具，适合快速看吞吐和延迟分位值。

```bash
wrk -t4 -c50 -d60s --latency \
  -s rag-post.lua \
  http://127.0.0.1:8080/api/rag/ask
```

`rag-post.lua` 示例：

```lua
wrk.method = "POST"
wrk.body   = '{"question":"Spring Boot 项目里 RAG 响应慢应该先查哪几段耗时？"}'
wrk.headers["Content-Type"] = "application/json"
```

## 3.2 三版链路性能数据

| 版本 | 说明 | QPS | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: | ---: |
| V1 | Top20 召回 + 全量重排 + 无缓存 | 8.9 | 2980ms | 5210ms | 6840ms |
| V2 | Top10 + Top10 重排 + prompt 截断 + 文档缓存 | 14.7 | 1710ms | 3090ms | 4020ms |
| V3 | V2 + query cache + answer cache + 预热 | 19.6 | 980ms | 1880ms | 2510ms |

这个结果挺典型：

- **P95/P99 改善最明显**，说明优化主要解决的是尾延迟；
- **缓存对热点问题收益极大**，尤其是知识库问答这种高重复 query；
- **召回数不是越大越好**，Top20 可能只是“看起来稳”，实际上会把 rerank 和 prompt 都拖慢。

## 3.3 单次请求阶段拆分

再看 V1 与 V3 的单次平均耗时拆分：

| 阶段 | V1 | V3 | 优化说明 |
| --- | ---: | ---: | --- |
| rewrite | 80ms | 35ms | query 归一化 + 本地缓存 |
| embedding | 120ms | 110ms | 变化不大 |
| recall | 650ms | 320ms | 召回数量收缩、索引参数调优 |
| rerank | 920ms | 310ms | 候选数减少，只重排必要文档 |
| prompt_build | 260ms | 110ms | 截断策略收敛 |
| llm_generate | 1800ms | 950ms | 上下文更短、输出更聚焦 |
| total | 3830ms | 1835ms | 总耗时下降约 52% |

看到这里其实就能得出第一个结论：**RAG 性能不是单点优化，而是链路级优化。**

# 四、第一刀先砍哪里：召回别贪多

很多人做 RAG 的第一反应是：怕漏答案，所以先把 TopK 拉大，比如从 5 拉到 20、50，甚至 100。这个思路看起来稳，实际上很容易把系统拖死。

因为你多召回出来的每一段文档，后面都要付代价：

- 可能要参与重排；
- 可能要进入 prompt 拼装；
- 会增加 token；
- 会拉长生成时间；
- 还会提高“错误上下文污染”的概率。

## 4.1 TopK 怎么选，不要拍脑袋

建议先做一个很土但非常有效的实验：固定一批问题集，比较不同 TopK 的**召回命中率**和**链路耗时**。

可以像这样记录：

| TopK | 命中率 | 平均耗时 | P95 |
| --- | ---: | ---: | ---: |
| 5 | 82% | 1450ms | 2380ms |
| 10 | 91% | 1820ms | 3010ms |
| 20 | 93% | 2860ms | 4890ms |
| 50 | 94% | 5110ms | 7720ms |

这个表特别能说明问题：**从 10 到 20，收益很小；从 20 到 50，更像是在烧钱买心理安慰。**

所以工程上更推荐的做法是：

1. 先用较小 TopK 做第一轮召回；
2. 对 query 质量差、答案不稳定的问题再兜底二次召回；
3. 不要默认所有请求都走最大召回深度。

## 4.2 Java 侧的简单限流式召回策略

```java
public int chooseTopK(String query) {
    int len = query == null ? 0 : query.length();
    if (len <= 12) {
        return 5;
    }
    if (len <= 30) {
        return 8;
    }
    return 10;
}
```

这不是银弹，但比“所有请求一律 Top20”靠谱得多。

# 五、重排不是不能用，而是不能乱用

**Rerank（重排）** 可以理解为：在初步召回之后，再用一个更“懂语义”的模型去判断哪些文档真正更相关。它的好处是准确率往往更高，但坏处也很明显：**贵，而且慢。**

## 5.1 最常见的错误：全量重排

比如你召回了 30 段文档，然后每次都把 30 段全部送去 rerank。这在 Demo 里没问题，上了量之后就会发现：

- CPU/GPU 资源压力大；
- 外部 rerank 服务容易成为瓶颈；
- 尾延迟特别夸张。

更合理的策略通常是：

- 召回 Top10；
- 只重排 Top5 或 Top10；
- 如果 query 明显是热点短问句，直接走缓存结果；
- 如果 query 很明确，甚至可以跳过 rerank。

## 5.2 一个很实用的降级策略

```java
public List<Document> rerankIfNeeded(String query, List<Document> docs, boolean highLoad) {
    if (docs.size() <= 3) {
        return docs;
    }
    if (highLoad) {
        return docs.subList(0, Math.min(5, docs.size()));
    }
    return reranker.rerank(query, docs, 5);
}
```

这个思路本质上是：**把准确率最优，改成“准确率与延迟的平衡最优”。**

很多线上系统不怕偶尔答得稍微短一点，怕的是高峰期整条链路雪崩。

# 六、缓存才是 RAG 系统真正的性价比武器

RAG 很容易让人陷入“我要不要换更快的模型”这种思路，但从 ROI（投入产出比）来看，很多时候缓存更划算。

常见可缓存的点包括：

1. **Query 归一化结果**：比如“Spring Boot 接 RAG 慢怎么办”和“springboot 做 rag 很慢咋排查”，本质上是同一个问题；
2. **Embedding 结果**：相同 query 的向量可以复用；
3. **召回结果**：热点问题的候选文档基本稳定；
4. **最终答案**：FAQ 型场景收益非常大。

## 6.1 一个最小可用的本地缓存示例

这里用 Caffeine。它是 Java 里很常见的本地缓存库，命中快、配置简单，非常适合做热点数据缓存。

```java
Cache<String, List<Document>> recallCache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofMinutes(10))
        .recordStats()
        .build();

public List<Document> cachedRecall(String normalizedQuery, Supplier<List<Document>> loader) {
    return recallCache.get(normalizedQuery, key -> loader.get());
}
```

再加一层答案缓存：

```java
Cache<String, String> answerCache = Caffeine.newBuilder()
        .maximumSize(5_000)
        .expireAfterWrite(Duration.ofMinutes(5))
        .build();
```

## 6.2 缓存不是一开就完事，要看命中率

至少要监控下面几个指标：

- `cache_hit_rate`
- `cache_load_time`
- `cache_eviction_count`
- `cache_size`

如果答案缓存命中率长期不到 5%，那多半不是缓存没价值，而是你的 key 设计太粗糙或者 query 归一化做得不够。

# 七、Prompt 拼得太豪华，模型一定会慢

这也是 RAG 里特别常见的误区：

> 既然我要提升准确率，那就把更多背景都塞给模型。

问题是，LLM 不会因为你塞得多就一定更聪明，反而可能：

- 输入 token 增加；
- 关键信息被淹没；
- 输出更发散；
- 成本和延迟一起上涨。

## 7.1 一个简单但有效的上下文预算策略

你可以先给每段文档设置预算，比如每段最多保留 300~500 字，最后总上下文不超过某个阈值。

```java
public List<String> trimChunks(List<String> chunks, int maxChars) {
    List<String> result = new ArrayList<>();
    int used = 0;
    for (String chunk : chunks) {
        if (used >= maxChars) {
            break;
        }
        String trimmed = chunk.length() > 400 ? chunk.substring(0, 400) : chunk;
        if (used + trimmed.length() > maxChars) {
            break;
        }
        result.add(trimmed);
        used += trimmed.length();
    }
    return result;
}
```

这段代码不高级，但很实战：**先限制最坏情况，再去追求最佳情况。**

# 八、怎么验证你真的优化到了，而不是自我感动

工程里最怕一种优化：改了很多代码，感觉自己更高级了，但指标没变。

所以 RAG 优化一定要带验证闭环。至少做下面三件事。

## 8.1 看压测指标，而不是只看平均值

平均值很好骗，尾延迟骗不了人。重点看：

- 吞吐：QPS
- 延迟分位：P50 / P95 / P99
- 错误率：4xx / 5xx / timeout
- 缓存命中率
- 模型调用 token 数

## 8.2 打 GC 日志，避免“AI 没慢，JVM 先抖了”

RAG 服务很容易创建大量临时对象，比如：

- 文档切片对象；
- embedding 向量数组；
- prompt 拼接字符串；
- JSON 序列化中间对象。

如果你发现压测一上来，吞吐没上去，CPU 也不算高，但延迟在抖，十有八九要看看 GC。

先加 JVM 参数：

```bash
-Xms2g -Xmx2g \
-Xlog:gc*:file=logs/gc.log:time,level,tags
```

如果是 Java Flight Recorder，也就是 **JFR**，可以这样录一段：

```bash
jcmd <pid> JFR.start name=rag-profile settings=profile duration=5m filename=rag.jfr
```

JFR 可以理解成 JDK 自带的低开销运行时剖析工具，适合看线程、锁、分配热点、方法耗时。

一个典型现象是：优化前 prompt 组装用大量字符串拼接，Young GC 很频繁；优化后改成更收敛的上下文预算和对象复用，GC 停顿会明显下降。

## 8.3 async-profiler 看 CPU 火焰图

`async-profiler` 是 Java 圈很常用的性能剖析工具，适合抓 CPU、alloc（分配）、lock（锁）热点。你可以这么采一段：

```bash
./profiler.sh -d 30 -e cpu -f cpu.html <pid>
```

如果火焰图上大量时间都耗在：

- JSON 解析；
- HTTP 客户端等待；
- 字符串拷贝；
- 向量相似度计算；

那优化方向就会很明确。

# 九、常见坑：很多团队不是不会做，而是做反了

这一节我直接列几个线上最常见的坑。

## 9.1 坑一：召回越多越安全

不一定。很多时候只是让系统更慢、上下文更脏。

## 9.2 坑二：只盯模型，不盯链路

模型生成只是链路的一部分。没有阶段埋点，调优基本靠猜。

## 9.3 坑三：缓存只做答案缓存

答案缓存当然重要，但 query 归一化、embedding、召回结果缓存，往往更稳，也更通用。

## 9.4 坑四：压测数据只看平均响应时间

平均值看起来很美，P99 才是高峰期用户真实体验。

## 9.5 坑五：把 RAG 当成“越复杂越高级”的系统

很多场景其实不需要特别复杂的链路。热点 FAQ、内部知识助手、运维 SOP 查询，这些场景往往是**简单链路 + 好缓存 + 稳定监控**最值钱。

# 十、一个建议中的落地方案

如果你现在要在 Java 服务里做一个线上可用的 RAG，我会建议按这个顺序推进：

1. **先埋点**：拆 rewrite / embedding / recall / rerank / prompt / generate；
2. **再控召回**：TopK 从小往上试，不要先拉满；
3. **再做缓存**：query、recall、answer 三层优先；
4. **再看上下文预算**：限制 prompt 大小；
5. **最后做重排精细化**：不是不用，而是按负载和 query 类型决定；
6. **补 JVM 分析**：GC 日志、JFR、async-profiler 至少选一种；
7. **用数据闭环**：每次改动都对比 QPS、P95、P99、token、命中率。

这个顺序的好处是：**你每一步都能量化收益，不容易做成“优化玄学”。**

# 十一、总结

这篇文章核心其实就一句话：

> **RAG 的慢，通常不是某一个组件的问题，而是整条链路的局部低效叠加出来的。**

你真正要优化的，不只是模型调用时间，而是：

- 召回深度是否合理；
- 重排是否过度；
- 上下文是否失控；
- 缓存是否接住热点；
- JVM 是否因为对象分配和 GC 在暗中拖后腿。

如果你在 Java 体系里做 AI 工程化，我非常建议把 RAG 当成一个标准后端链路来治理，而不是把它当成“模型 API 外面套一层 Controller”。前者能上线，后者通常只能演示。

# 十二、如何验证本文结论

你可以按下面步骤自己复现：

1. 在 Spring Boot 服务里给 RAG 链路加分阶段计时；
2. 用固定问题集做 50 并发压测，记录 QPS、P50、P95、P99；
3. 先把召回 TopK 从 20 降到 10，对比阶段耗时；
4. 再加入 recall cache / answer cache，对比缓存命中率和尾延迟；
5. 打开 GC 日志，确认对象分配和 GC 停顿是否改善；
6. 用 JFR 或 async-profiler 抓热点，检查瓶颈是否真的转移。

如果你做完这几步，大概率会得到和本文相近的结论：**先做链路治理，再谈模型升级，收益通常更高。**
