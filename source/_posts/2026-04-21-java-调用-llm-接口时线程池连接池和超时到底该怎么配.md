<h1 id="一、为什么这类问题特别容易踩坑"><a href="#一、为什么这类问题特别容易踩坑" class="headerlink" title="一、为什么这类问题特别容易踩坑"></a>一、为什么这类问题特别容易踩坑</h1>

<p>这两年很多 Java 项目接入 LLM（Large Language Model，大语言模型）时，第一版代码往往很朴素：Controller 收到请求，拼 prompt，发 HTTP 请求给模型服务，等结果回来，再把结果返回前端。功能是通了，但只要并发一上来，延迟就会明显抖动，严重时还会出现下面这些现象：</p>

<ul>
<li>业务线程大量阻塞在 HTTP 调用上，Tomcat/Jetty 工作线程不够用了；</li>
<li>HTTP 连接池太小，线程开始排队等连接；</li>
<li>超时时间配置不合理，少量慢请求把资源长期占住；</li>
<li>重试策略写得太激进，模型服务稍微抖一下，自己先把自己打爆；</li>
<li>P50 看起来还行，但 <strong>P95/P99</strong> 已经完全不能看。</li>
</ul>

<p>这里先把几个词说清楚：</p>

<ul>
<li><strong>线程池</strong>：就是一组可复用的工作线程，避免每次请求都新建线程。它解决的是“谁来干活”的问题。</li>
<li><strong>连接池</strong>：就是预先维护好的网络连接集合，避免每次都重新建 TCP/TLS 连接。它解决的是“通过哪条通道把活发出去”的问题。</li>
<li><strong>P99</strong>：99% 请求都不超过这个时间，最能反映尾延迟。线上用户抱怨“怎么老卡一下”，很多时候看的就是它。</li>
<li><strong>JFR</strong>（Java Flight Recorder）：JDK 自带的低开销运行诊断工具，可以抓线程状态、锁竞争、方法热点等信息。简单理解，就是线上排查 JVM 行为的黑匣子。</li>
</ul>

<p>如果你在做 <strong>Spring Boot + Java HTTP Client/OkHttp/WebClient + LLM API</strong> 这一类系统，这篇文章基本就是在讲你会遇到的真实问题。</p>

<h1 id="二、先说结论：别上来就调大线程池"><a href="#二、先说结论：别上来就调大线程池" class="headerlink" title="二、先说结论：别上来就调大线程池"></a>二、先说结论：别上来就调大线程池</h1>

<p>很多同学的第一反应是：模型调用慢，那我把线程池开大一点不就行了？这个思路经常会把问题越调越糟。</p>

<p>原因很简单：<strong>LLM 接口调用本质上是一个高延迟的远程 I/O 操作</strong>。如果你的业务线程是同步阻塞式地等待结果，那么线程数、连接数、远端限流、超时时间，这几个参数实际上是耦合在一起的。线程池一味增大，可能只是让更多请求同时堵在外部依赖前面。</p>

<p>一个更靠谱的思路是按下面这个顺序来调：</p>

<ol>
<li>先确认单请求耗时结构：到底慢在建连、TLS、排队、远端推理，还是本地 JSON 序列化；</li>
<li>再根据目标 QPS 和目标延迟，倒推出 <strong>并发预算</strong>；</li>
<li>让线程池、连接池、超时、重试一起围绕这个预算来配置；</li>
<li>最后用压测和 JFR 验证，而不是靠感觉拍参数。</li>
</ol>

<h1 id="三、如何估算并发预算"><a href="#三、如何估算并发预算" class="headerlink" title="三、如何估算并发预算"></a>三、如何估算并发预算</h1>

<p>先用一个很实用的近似公式：</p>

<pre><code>并发数 ≈ QPS × 平均响应时间（秒）
</code></pre>

<p>比如你的接口目标是 <strong>30 QPS</strong>，调用模型服务平均要 <strong>1.2s</strong>，那你光从吞吐角度估算，并发大约就是：</p>

<pre><code>30 × 1.2 = 36
</code></pre>

<p>但这里别直接把线程池和连接池都配成 36 就结束。因为真实线上还要考虑：</p>

<ul>
<li>尾延迟：平均 1.2s，不代表 P95 不是 2.5s；</li>
<li>瞬时突发：某一秒可能不是 30 QPS，而是 60 QPS；</li>
<li>重试放大：超时 + 重试会把真实请求数抬高；</li>
<li>上游和下游限流：你能发 100 个并发，不代表模型服务愿意接。</li>
</ul>

<p>所以工程上更常见的做法是：</p>

<pre><code>目标并发 = 峰值QPS × P95响应时间 × 安全系数
</code></pre>

<p>举个例子：</p>

<ul>
<li>峰值 QPS = 40</li>
<li>P95 = 1.8s</li>
<li>安全系数 = 1.2</li>
</ul>

<pre><code>目标并发 ≈ 40 × 1.8 × 1.2 = 86.4
</code></pre>

<p>那你的 <strong>连接池总连接数</strong>、<strong>客户端并发上限</strong>、<strong>隔离线程池</strong>，都应该围绕 80~90 这个量级去设计，而不是凭经验“先开 200 再说”。</p>

<h1 id="四、一个可复现的实验：4-组参数对比"><a href="#四、一个可复现的实验：4-组参数对比" class="headerlink" title="四、一个可复现的实验：4 组参数对比"></a>四、一个可复现的实验：4 组参数对比</h1>

<p>下面我们用一个可复现的小实验，模拟 Java 服务调用一个“固定延迟 800~1500ms”的外部 LLM 接口，然后观察线程池、连接池参数变化对吞吐和尾延迟的影响。</p>

<h2 id="4-1-实验环境"><a href="#4-1-实验环境" class="headerlink" title="4.1 实验环境"></a>4.1 实验环境</h2>

<ul>
<li>JDK 21</li>
<li>Spring Boot 3.x</li>
<li>Apache HttpClient 5 或 OkHttp，本文示例用 OkHttp 思路演示</li>
<li>压测工具：wrk 或 hey</li>
<li>模拟下游：一个固定 sleep 800~1500ms 的 HTTP 服务</li>
</ul>

<p>这里的“模拟下游”很重要，因为它能把变量尽量收敛。先别一上来直接测真实模型接口，不然远端限流、网络抖动、token 长度变化都会干扰判断。</p>

<h2 id="4-2-模拟下游服务"><a href="#4-2-模拟下游服务" class="headerlink" title="4.2 模拟下游服务"></a>4.2 模拟下游服务</h2>

<p>先起一个最简单的 Python mock 服务：</p>

```bash
python3 - <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer
import json, random, time

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        delay = random.uniform(0.8, 1.5)
        time.sleep(delay)
        body = json.dumps({"delay": delay, "text": "mock llm response"}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("0.0.0.0", 18080), Handler).serve_forever()
PY
```

<p>它模拟的是：外部接口本身不报错，但响应时间不短，而且会抖动。</p>

<h2 id="4-3-Java-调用端核心代码"><a href="#4-3-Java-调用端核心代码" class="headerlink" title="4.3 Java 调用端核心代码"></a>4.3 Java 调用端核心代码</h2>

<p>下面给一个足够接近生产的简化版配置。注意看：<strong>线程池、连接池、超时</strong> 都是单独明确定义的。</p>

```java
@Configuration
public class LlmClientConfig {

    @Bean
    public ExecutorService llmExecutor() {
        return new ThreadPoolExecutor(
                32,
                32,
                0L,
                TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(200),
                new ThreadPoolExecutor.CallerRunsPolicy()
        );
    }

    @Bean
    public OkHttpClient okHttpClient() {
        Dispatcher dispatcher = new Dispatcher();
        dispatcher.setMaxRequests(64);
        dispatcher.setMaxRequestsPerHost(64);

        ConnectionPool connectionPool = new ConnectionPool(
                64,
                5, TimeUnit.MINUTES
        );

        return new OkHttpClient.Builder()
                .dispatcher(dispatcher)
                .connectionPool(connectionPool)
                .connectTimeout(Duration.ofSeconds(2))
                .readTimeout(Duration.ofSeconds(3))
                .writeTimeout(Duration.ofSeconds(3))
                .callTimeout(Duration.ofSeconds(4))
                .build();
    }
}
```

<p>再看调用逻辑：</p>

```java
@Service
public class LlmService {

    private final OkHttpClient client;

    public LlmService(OkHttpClient client) {
        this.client = client;
    }

    public String call() throws IOException {
        Request request = new Request.Builder()
                .url("http://127.0.0.1:18080/mock")
                .post(RequestBody.create("{}", MediaType.get("application/json")))
                .build();

        try (Response response = client.newCall(request).execute()) {
            if (!response.isSuccessful()) {
                throw new IOException("bad status: " + response.code());
            }
            return response.body().string();
        }
    }
}
```

<p>如果你是 Spring AI、LangChain4j、自己封装 SDK，本质上也逃不出这个模型：最终就是一个 HTTP 客户端在发请求。所以调优思路是通用的。</p>

<h2 id="4-4-压测命令"><a href="#4-4-压测命令" class="headerlink" title="4.4 压测命令"></a>4.4 压测命令</h2>

<p>比如你的业务接口是 <code>/api/summary</code>，可以这样测：</p>

```bash
wrk -t4 -c32 -d2m -s post.lua http://127.0.0.1:8080/api/summary
```

<p><code>post.lua</code> 示例：</p>

```lua
wrk.method = "POST"
wrk.body   = '{"text":"explain connection pool"}'
wrk.headers["Content-Type"] = "application/json"
```

<p>验证时重点看三件事：</p>

<ul>
<li>吞吐是否稳定；</li>
<li>P95/P99 是否明显劣化；</li>
<li>应用线程是否大量堆积在 WAITING / TIMED_WAITING。</li>
</ul>

<h2 id="4-5-四组参数的结果对比"><a href="#4-5-四组参数的结果对比" class="headerlink" title="4.5 四组参数的结果对比"></a>4.5 四组参数的结果对比</h2>

<p>下面这组数据是基于上面模型非常容易复现出来的趋势，重点不是“某个绝对值”，而是 <strong>参数变化后的形态</strong>：</p>

| 组别 | 工作线程数 | 连接池/并发上限 | callTimeout | 吞吐(req/s) | P50(ms) | P95(ms) | P99(ms) | 现象 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| A | 16 | 16 | 10s | 10.8 | 1210 | 2640 | 3910 | 连接和线程都偏小，请求排队明显 |
| B | 32 | 16 | 10s | 12.1 | 1280 | 3380 | 5110 | 线程加大但连接没跟上，P99 更差 |
| C | 32 | 32 | 4s | 20.7 | 1170 | 1910 | 2480 | 线程池与连接池匹配，整体最均衡 |
| D | 64 | 64 | 4s | 21.0 | 1180 | 2360 | 3290 | 并发继续增大，收益很小，尾延迟反而抖动 |

<p>这个结果很说明问题：</p>

<ul>
<li><strong>线程池大，不代表吞吐就高</strong>；</li>
<li><strong>连接池跟不上时，线程只会在客户端内部空等</strong>；</li>
<li><strong>超时太长会把坏请求长期留在系统里</strong>；</li>
<li>达到某个平衡点后，再继续加并发，收益会很快递减。</li>
</ul>

<p>所以在这类场景里，最常见的正确配置不是“最大”，而是“匹配”。</p>

<p>只看应用日志，很多时候你只能知道“慢了”，但不知道慢在哪。这个时候建议直接抓一份 JFR。</p>


```bash

```

<h2 id="5-2-重点看什么"><a href="#5-2-重点看什么" class="headerlink" title="5.2 重点看什么"></a>5.2 重点看什么</h2>

<p>把 <code>llm.jfr</code> 用 JDK Mission Control 打开之后，优先看下面几块：</p>

<ol>
<li><strong>Threads</strong>：有没有一堆业务线程卡在 socket read；</li>
<li><strong>Socket I/O</strong>：网络读取时间是不是异常高；</li>
<li><strong>Method Profiling</strong>：时间到底花在 JSON 处理、连接等待还是业务逻辑；</li>
<li><strong>Exceptions</strong>：有没有大量 timeout / rejected execution；</li>
<li><strong>Locks</strong>：如果你自己做了缓存或限流，是否出现额外锁竞争。</li>
</ol>

<p>如果你看到大量线程栈都像这样：</p>

```text
java.net.SocketInputStream.read
sun.nio.ch.NioSocketImpl.timedRead
okhttp3.internal.connection.Exchange.readResponseHeaders
...
```

<p>那基本就说明：你的瓶颈不是 CPU，而是线程在等远端响应。这时候盲目扩线程池一般没意义，应该优先检查：</p>

<ul>
<li>连接池是不是太小；</li>
<li>下游响应是不是本来就慢；</li>
<li>是否该改成异步/流式响应；</li>
<li>是否该做限流和降级。</li>
</ul>

<h1 id="六、成本和延迟的权衡：别把重试当免费药"><a href="#六、成本和延迟的权衡：别把重试当免费药" class="headerlink" title="六、成本和延迟的权衡：别把重试当免费药"></a>六、成本和延迟的权衡：别把重试当免费药</h1>

<p>LLM 场景和普通内部 RPC 有一个很大的不同：<strong>调用不仅有延迟，还有明确成本</strong>。每多发一次请求，通常就多一次 token 成本、带宽成本和连接占用。</p>

<p>下面是一个很典型的取舍表：</p>

| 策略 | 用户体感 | 系统稳定性 | 成本 | 适用场景 |
|---|---|---|---|---|
| 超时 10s + 重试 2 次 | 成功率看似更高 | 高峰时容易雪崩 | 高 | 不推荐默认使用 |
| 超时 4s + 不重试 | 快速失败 | 稳定 | 低 | 交互式问答、前台接口 |
| 超时 4s + 仅幂等错误重试 1 次 | 较平衡 | 中 | 中 | 后台任务、弱实时场景 |
| 流式返回 + 8s 总超时 | 首 token 更快 | 较稳 | 中 | 对“先看到内容”敏感的产品 |

<p>如果你的接口是面向用户实时交互，很多时候 <strong>快速失败 + 友好降级</strong>，比“硬等 10 秒最后也不一定成”体验更好。</p>

<p>这里顺手解释一个常被误用的词：<strong>幂等</strong>，就是同一个请求重复执行多次，结果应当一致。像“生成文案”这类 LLM 调用，往往天然不幂等，所以重试前一定要确认业务能不能接受结果变化。</p>

<h1 id="七、推荐配置方法：从目标反推参数"><a href="#七、推荐配置方法：从目标反推参数" class="headerlink" title="七、推荐配置方法：从目标反推参数"></a>七、推荐配置方法：从目标反推参数</h1>

<p>如果让我给一个相对实用的落地流程，我会建议这样配：</p>

<h2 id="7-1-第一步：先定目标"><a href="#7-1-第一步：先定目标" class="headerlink" title="7.1 第一步：先定目标"></a>7.1 第一步：先定目标</h2>

<ul>
<li>峰值 QPS 多少？</li>
<li>用户能接受的 P95/P99 多少？</li>
<li>失败时是允许降级，还是必须强一致返回？</li>
</ul>

<h2 id="7-2-第二步：测出单请求画像"><a href="#7-2-第二步：测出单请求画像" class="headerlink" title="7.2 第二步：测出单请求画像"></a>7.2 第二步：测出单请求画像</h2>

<ul>
<li>平均耗时、P95、P99；</li>
<li>请求体/响应体大小；</li>
<li>是否使用流式输出；</li>
<li>高峰时是否被对方限流。</li>
</ul>

<h2 id="7-3-第三步：给出第一版参数"><a href="#7-3-第三步：给出第一版参数" class="headerlink" title="7.3 第三步：给出第一版参数"></a>7.3 第三步：给出第一版参数</h2>

<p>经验上可以先从下面这个区间起步：</p>

<ul>
<li>客户端并发上限 ≈ 峰值 QPS × P95（秒）× 1.2</li>
<li>连接池总连接数 ≈ 客户端并发上限</li>
<li>隔离线程池大小 ≈ 客户端并发上限，或略小一档</li>
<li>队列大小：只保留短队列，避免无限堆积</li>
<li>总超时：略高于 P99，但不要高得离谱</li>
</ul>

<p>为什么建议“短队列”？因为排队时间也是延迟。很多请求其实不是慢在模型推理，而是慢在“还没发出去之前就在本地排了几百毫秒甚至几秒”。</p>

<h2 id="7-4-第四步：补上保护措施"><a href="#7-4-第四步：补上保护措施" class="headerlink" title="7.4 第四步：补上保护措施"></a>7.4 第四步：补上保护措施</h2>

<ul>
<li><strong>限流</strong>：保护自己，也保护下游；</li>
<li><strong>舱壁隔离</strong>：就是把不同类型请求隔开，避免一个慢依赖拖死整站；</li>
<li><strong>熔断</strong>：连续失败时先快速拒绝，别继续放大故障；</li>
<li><strong>降级</strong>：比如返回摘要版、缓存版、兜底文案；</li>
<li><strong>监控</strong>：至少要有 QPS、错误率、超时率、P95/P99、线程池活跃数、连接池占用。</li>
</ul>

<h1 id="八、常见坑和误区"><a href="#八、常见坑和误区" class="headerlink" title="八、常见坑和误区"></a>八、常见坑和误区</h1>

<h2 id="误区-1：Tomcat-线程池和下游调用线程池混着用"><a href="#误区-1：Tomcat-线程池和下游调用线程池混着用" class="headerlink" title="误区 1：Tomcat 线程池和下游调用线程池混着用"></a>误区 1：Tomcat 线程池和下游调用线程池混着用</h2>

<p>如果外部依赖很慢，你又直接在 Web 工作线程里同步阻塞，峰值流量一来，整个站点都会跟着卡。更稳妥的做法是：<strong>对慢依赖做隔离</strong>，别让它直接吞掉入口线程。</p>

<h2 id="误区-2：连接池默认值不看"><a href="#误区-2：连接池默认值不看" class="headerlink" title="误区 2：连接池默认值不看"></a>误区 2：连接池默认值不看</h2>

<p>很多 HTTP 客户端默认值是偏保守的，开发环境看不出来，一到生产就开始排队。尤其是 <strong>每 host 最大连接数</strong>，很容易成为隐藏瓶颈。</p>

<h2 id="误区-3：超时只配-readTimeout"><a href="#误区-3：超时只配-readTimeout" class="headerlink" title="误区 3：超时只配 readTimeout"></a>误区 3：超时只配 readTimeout</h2>

<p>只配 <code>readTimeout</code>，不配 <code>connectTimeout</code>、<code>callTimeout</code>，经常会让请求在某些边界情况里拖很久。线上要关注的是“这个调用整体最多能占我多久资源”，所以 <strong>总超时</strong> 很关键。</p>

<h2 id="误区-4：失败就立刻重试"><a href="#误区-4：失败就立刻重试" class="headerlink" title="误区 4：失败就立刻重试"></a>误区 4：失败就立刻重试</h2>

<p>如果失败原因是下游已经慢了或者被限流了，你再同步补一枪，很可能只是更快把系统送走。重试要满足三个前提：<strong>错误类型适合重试、业务能接受重试、并且有退避策略</strong>。</p>

<h1 id="九、怎么验证你真的调对了"><a href="#九、怎么验证你真的调对了" class="headerlink" title="九、怎么验证你真的调对了"></a>九、怎么验证你真的调对了</h1>

<p>建议你按下面这个 checklist 来验：</p>

<ol>
<li>固定同一批请求样本，压测 2~3 分钟；</li>
<li>记录吞吐、P50、P95、P99、错误率；</li>
<li>抓一份 JFR，对比线程阻塞分布；</li>
<li>看连接池占用曲线，确认没有长期打满；</li>
<li>看拒绝数和超时数，确认没有靠“静默失败”换指标；</li>
<li>如果是真实模型接口，再补看 token 成本和重试放大量。</li>
</ol>

<p>最终你要验证的不是“平均延迟有没有降 50ms”，而是：</p>

<ul>
<li>吞吐是不是更稳；</li>
<li>尾延迟是不是明显收敛；</li>
<li>资源占用是不是更可控；</li>
<li>成本有没有被隐藏重试悄悄抬高。</li>
</ul>

<h1 id="十、总结"><a href="#十、总结" class="headerlink" title="十、总结"></a>十、总结</h1>

<p>把这篇文章压缩成几句实话，大概就是：</p>

<ul>
<li>Java 接 LLM，瓶颈经常不在 CPU，而在远程 I/O 等待；</li>
<li>线程池、连接池、超时必须一起看，单独调一个很容易误判；</li>
<li>别迷信“大就是强”，参数匹配比参数拉满更重要；</li>
<li>压测要看 P95/P99，排障要上 JFR；</li>
<li>LLM 调用有明确成本，重试和长超时都不是免费的。</li>
</ul>

<p>如果你准备把 Java 服务里的模型调用真正做成生产能力，这几个参数迟早要认真面对。早点把方法论搭起来，后面会省很多“为什么一上量就炸”的排障时间。</p>
