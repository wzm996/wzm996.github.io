# 一、为什么线程池经常“看起来没问题，线上却出事”

很多 Java 服务的线程池参数，都是这么来的：

- `corePoolSize=8`，因为机器 8 核；
- `maximumPoolSize=16`，因为“留点弹性”；
- 队列设成 `1000`，因为“别太容易拒绝”；
- 拒绝策略用默认 `AbortPolicy`，因为“先跑起来再说”。

表面上看没毛病，压测一上来就容易出现几种经典事故：

1. **吞吐量没上去，响应时间先炸了**；
2. **CPU 不高，但请求越积越多**；
3. **线程数拉满后，GC 开始变频繁**；
4. **队列特别长，业务方还以为服务很稳，因为没有报错**。

这里的核心矛盾是：**线程池本质上是“并发控制器 + 背压阀门”**。如果你只把它当成“多开几个线程加速执行”的工具，那大概率会把系统调到一个“慢性雪崩”状态。

> 注：**背压（Backpressure）** 可以理解成“下游扛不住时，主动把压力往上游传回去”，而不是无脑把任务先堆起来。

这篇文章我会用一个简单但很贴近工程现场的实验来讲清楚：

- 线程池的关键参数各自影响什么；
- 为什么“大队列 + 大线程数”往往是个坑；
- 如何通过压测、JFR、GC 日志来判断瓶颈到底在哪；
- 一套相对靠谱的调参顺序是什么。

# 二、先把核心参数讲明白：别一上来就背公式

先看最常用的 `ThreadPoolExecutor`：

```java
new ThreadPoolExecutor(
    corePoolSize,
    maximumPoolSize,
    keepAliveTime,
    TimeUnit.SECONDS,
    workQueue,
    threadFactory,
    handler
);
```

几个关键参数，建议按下面的工程视角理解。

## 2.1 corePoolSize：常驻工位数

**corePoolSize** 是核心线程数，可以理解成“平时固定开的工位”。

- 任务来了，如果当前线程数还没到核心线程数，就直接新建线程执行；
- 到了核心线程数后，再来的任务通常先入队。

如果你的业务请求量比较稳定，核心线程数一般对应“常态流量下的并发处理能力”。

## 2.2 maximumPoolSize：极限扩容上限

**maximumPoolSize** 是线程池允许创建的最大线程数。

但注意，这个参数不是说“任务一多就立刻扩到最大值”。

典型流程是：

1. 先用核心线程处理；
2. 核心线程忙了，任务先入队；
3. 队列满了，才会继续创建非核心线程；
4. 到了最大线程数还扛不住，才触发拒绝策略。

这也是很多人误判线程池行为的原因：**你以为 maximumPoolSize 很重要，实际上如果队列很大，它可能长期根本没机会生效。**

## 2.3 workQueue：缓冲区，也是风险放大器

**workQueue** 是任务队列，本质上就是“处理不过来时，先攒着”。

它当然有价值，但队列不是越大越好：

- 队列大，短时间看起来更稳，因为不容易拒绝；
- 但队列大意味着请求等待时间被拉长；
- 如果任务对象本身占内存，长队列还会推高堆内存占用，增加 GC 压力。

很多线上问题不是“线程池立刻崩”，而是“队列偷偷变长，最终把延迟、内存、超时一起带崩”。

## 2.4 RejectedExecutionHandler：最后一道保险丝

**拒绝策略** 是线程池顶不住时的最后动作。常见的有：

- `AbortPolicy`：直接抛异常，最直白；
- `CallerRunsPolicy`：由提交任务的线程自己执行，相当于把压力反向传回调用方；
- `DiscardPolicy`：静默丢弃；
- `DiscardOldestPolicy`：丢弃队列中最老的任务。

工程上我最不喜欢 `DiscardPolicy`，因为它会制造一种很可怕的假象：**系统没报错，但业务结果悄悄没了。**

# 三、一个可复现实验：固定流量下，不同参数组合的差异

为了避免空谈，我们做一个小实验。场景设定如下：

- 一个简单 Java 程序，模拟 Web 服务收到任务；
- 每个任务执行 200ms，其中包含少量 CPU 计算 + 一次 `sleep` 模拟 IO 等待；
- 持续提交固定速率的请求；
- 记录吞吐、平均延迟、P95、P99、拒绝数、队列长度。

> 注：**P95/P99** 可以理解成“95%/99% 请求在这个耗时以内完成”，它比平均值更能反映线上用户的真实体感。

## 3.1 实验代码

下面这段代码可以直接保存成 `ThreadPoolTuningDemo.java` 运行。

```java
import java.time.Duration;
import java.time.Instant;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicLong;

public class ThreadPoolTuningDemo {

    static class Metrics {
        AtomicInteger submitted = new AtomicInteger();
        AtomicInteger completed = new AtomicInteger();
        AtomicInteger rejected = new AtomicInteger();
        AtomicLong totalLatencyMs = new AtomicLong();
        List<Long> latencies = Collections.synchronizedList(new ArrayList<>());
    }

    public static void main(String[] args) throws Exception {
        int core = Integer.parseInt(System.getProperty("core", "8"));
        int max = Integer.parseInt(System.getProperty("max", "8"));
        int queue = Integer.parseInt(System.getProperty("queue", "100"));
        int qps = Integer.parseInt(System.getProperty("qps", "120"));
        int durationSec = Integer.parseInt(System.getProperty("duration", "60"));
        String reject = System.getProperty("reject", "abort");

        Metrics metrics = new Metrics();
        ThreadPoolExecutor executor = new ThreadPoolExecutor(
                core,
                max,
                60,
                TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(queue),
                Executors.defaultThreadFactory(),
                rejectHandler(reject, metrics)
        );

        ScheduledExecutorService reporter = Executors.newSingleThreadScheduledExecutor();
        reporter.scheduleAtFixedRate(() -> {
            System.out.printf("[pool] active=%d pool=%d queue=%d completed=%d rejected=%d%n",
                    executor.getActiveCount(),
                    executor.getPoolSize(),
                    executor.getQueue().size(),
                    metrics.completed.get(),
                    metrics.rejected.get());
        }, 1, 1, TimeUnit.SECONDS);

        Instant end = Instant.now().plusSeconds(durationSec);
        long intervalNs = 1_000_000_000L / qps;
        long next = System.nanoTime();

        while (Instant.now().isBefore(end)) {
            next += intervalNs;
            metrics.submitted.incrementAndGet();
            long submitTime = System.nanoTime();
            try {
                executor.execute(() -> {
                    try {
                        busyCpu(5);
                        Thread.sleep(195);
                        long latencyMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - submitTime);
                        metrics.completed.incrementAndGet();
                        metrics.totalLatencyMs.addAndGet(latencyMs);
                        metrics.latencies.add(latencyMs);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
            } catch (RejectedExecutionException e) {
                metrics.rejected.incrementAndGet();
            }
            long waitNs = next - System.nanoTime();
            if (waitNs > 0) {
                LockSupport.parkNanos(waitNs);
            }
        }

        executor.shutdown();
        executor.awaitTermination(5, TimeUnit.MINUTES);
        reporter.shutdownNow();

        printSummary(metrics);
    }

    static void busyCpu(int ms) {
        long end = System.nanoTime() + ms * 1_000_000L;
        long x = 0;
        while (System.nanoTime() < end) {
            x += 1;
        }
        if (x == 42) {
            System.out.println("never");
        }
    }

    static RejectedExecutionHandler rejectHandler(String name, Metrics metrics) {
        return switch (name.toLowerCase()) {
            case "caller" -> (r, executor) -> {
                metrics.rejected.incrementAndGet();
                r.run();
            };
            case "discard" -> (r, executor) -> metrics.rejected.incrementAndGet();
            default -> new ThreadPoolExecutor.AbortPolicy();
        };
    }

    static void printSummary(Metrics metrics) {
        List<Long> list = new ArrayList<>(metrics.latencies);
        Collections.sort(list);
        long avg = metrics.completed.get() == 0 ? 0 : metrics.totalLatencyMs.get() / metrics.completed.get();
        long p95 = percentile(list, 95);
        long p99 = percentile(list, 99);
        System.out.println("========== summary ==========");
        System.out.printf("submitted=%d completed=%d rejected=%d avg=%dms p95=%dms p99=%dms%n",
                metrics.submitted.get(), metrics.completed.get(), metrics.rejected.get(), avg, p95, p99);
    }

    static long percentile(List<Long> list, int p) {
        if (list.isEmpty()) return 0;
        int idx = (int) Math.ceil(p / 100.0 * list.size()) - 1;
        return list.get(Math.max(0, Math.min(idx, list.size() - 1)));
    }
}
```

# 四、怎么验证结论：别只盯着吞吐，要一起看延迟、队列、GC

线程池调参最容易踩的坑，就是只看一个指标。

比如你只看 completed 数量，会以为系统挺健康；但如果 P99 已经从 220ms 飙到 4s，这个系统对用户来说已经很差了。

建议至少看下面几组指标：

- **吞吐量**：单位时间完成的任务数；
- **延迟**：平均值、P95、P99；
- **队列长度**：有没有持续堆积；
- **拒绝数**：是否开始触发保护；
- **GC 行为**：年轻代回收频率、停顿时间有没有明显上升；
- **JFR 线程视图**：线程是在跑 CPU，还是在等锁/等 IO。

## 4.1 一组典型结果怎么解读

下面给一组很典型、也很符合实际工程经验的结果示例：

| 实验组 | 参数组合 | 平均延迟 | P95 | P99 | 拒绝数 | 现象 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| A | core=8,max=8,queue=20 | 230ms | 310ms | 420ms | 少量 | 延迟稳定，有轻微拒绝，属于“及时失败” |
| B | core=8,max=8,queue=1000 | 1450ms | 3100ms | 4800ms | 0 | 看似没报错，实际大量请求在排队 |
| C | core=8,max=16,queue=20 | 210ms | 280ms | 360ms | 极少 | 扩容起效，延迟和吞吐都比较均衡 |

这个表最想说明一件事：

> **没有拒绝，不等于系统健康。**

实验组 B 最危险，因为它特别像很多线上系统的状态：监控里错误率不高，但用户已经明显感知到慢。根因不是线程不够，而是**队列把等待时间藏起来了**。

## 4.2 GC 日志怎么看

如果你打开了 GC 日志，可以先看两类信号：

1. 年轻代 GC 次数是否明显增加；
2. 停顿时间是否随着队列变长而上升。

简单粗暴一点，可以先这么看：

```bash
grep -E "Pause Young|Pause Full" gc-b.log | tail -n 20
```

如果大队列场景下任务对象、上下文对象在堆里积压得更多，就很容易看到更频繁的年轻代回收。

> 注：**GC（Garbage Collection）** 就是 JVM 自动回收不再使用对象的过程。对象分配太猛、存活时间变长，都会让 GC 压力变大。

## 4.3 JFR 怎么看线程到底卡在哪

JFR 文件可以用 JDK Mission Control 打开。重点看几个视图：

- **Threads**：线程状态分布，是否大量处于 `TIMED_WAITING` 或 `BLOCKED`；
- **Method Profiling**：热点方法都耗在哪；
- **Socket / File I/O**：如果你的任务依赖网络或磁盘，可以看到等待情况；
- **Allocation**：对象分配热点，辅助判断是不是队列堆积带来的内存压力。

如果你看到：

- CPU 很低；
- 大量线程在 `TIMED_WAITING`；
- 队列却一直很长；

那通常说明这是个 **IO 受限** 场景，继续加线程可能有帮助，但更应该回头看下游接口、连接池、超时配置。

如果你看到：

- CPU 已经接近打满；
- 热点方法集中在计算逻辑；
- 增加线程数后上下文切换更重；

那就是 **CPU 受限**，这时候盲目扩线程往往适得其反。

# 五、线程池参数到底怎么定：给一套实用调参顺序

我不太喜欢网上那种“一行公式走天下”的说法。线程池调参可以有经验公式，但最后一定要回到业务模型和实验数据。

下面这套顺序，比较适合日常工程实践。

## 5.1 第一步：先判断任务类型

先问自己：这个线程池里的任务，到底更像哪一类？

### CPU 密集型

比如：

- JSON 大对象序列化；
- 图像处理；
- 加解密；
- 规则计算。

这类任务通常线程数不要开太大，接近 CPU 核数就差不多了。线程一多，额外的上下文切换会把收益吃掉。

### IO 密集型

比如：

- 调数据库；
- 调下游 HTTP 服务；
- 读写磁盘；
- 远程 RPC。

这类任务线程数可以比 CPU 核数更大，因为很多时间线程其实在等外部资源返回。

但这里有个前提：**外部依赖本身要扛得住**。如果数据库连接池才 20，你把业务线程池加到 200，很多线程只会排队等连接。

## 5.2 第二步：先把队列收紧，再决定要不要扩线程

我的建议通常是：

- 不要先给一个超大队列；
- 先用较小队列观察系统在压力下的真实行为；
- 再决定是增加线程、优化下游，还是加背压。

原因很简单：**大队列会掩盖问题，小队列会暴露问题。**

线上系统更怕“慢性死亡”，不怕“可观测、可告警的及时失败”。

## 5.3 第三步：明确拒绝策略的业务语义

拒绝不是纯技术参数，它其实是业务决策。

- 核心链路、必须成功：要结合限流、降级、重试，不要只靠线程池硬扛；
- 非核心异步任务：可以丢，但必须可观测，最好落日志或指标；
- 希望自然限速：`CallerRunsPolicy` 往往比静默丢弃更靠谱。

`CallerRunsPolicy` 的好处是，它会把执行压力压回提交线程，调用方自然就慢下来，相当于形成一种很朴素但有效的背压。

## 5.4 第四步：把线程池监控补齐，不要把它当黑盒

至少建议暴露这些指标：

- 当前线程数；
- 活跃线程数；
- 队列长度；
- 已完成任务数；
- 拒绝次数；
- 任务执行时间分布。

如果你用的是 Spring Boot，可以把这些指标挂到 Micrometer，再接 Prometheus + Grafana 做可视化。

# 六、常见坑：这些问题我见得太多了

## 6.1 一个接口一个线程池，最后把机器切碎了

很多系统喜欢“每个业务都配自己的线程池”，看起来隔离了，实际上可能把机器资源切得过碎。

结果就是：

- 每个线程池都不够大；
- 线程总数却非常多；
- 上下文切换和调度开销一起上来。

隔离当然重要，但隔离的前提是你知道自己在隔离什么、成本是什么。

## 6.2 队列很长却没有任何告警

这是最危险的情况之一。

如果监控只看错误率，而不看队列长度和延迟分位数，你会在用户投诉前一直以为系统没事。

## 6.3 拒绝后又无脑重试，等于把故障放大两次

线程池已经拒绝，说明当前系统就在保护自己。你如果上游马上重试，相当于再补一刀。

正确姿势应该是：

- 重试要有退避；
- 明确哪些错误可以重试；
- 尽量在更上游做限流或熔断。

## 6.4 只调业务线程池，不看数据库/HTTP 连接池

线程池、连接池、下游超时，其实是一整套联动系统。

如果业务线程池加大了，但数据库连接池没变，最后只是更多线程一起堵在拿连接上。这个时候看线程池参数本身，已经看不出问题全貌了。

# 七、给一个落地建议：不同场景怎么选

这里给一个偏工程实践的简化建议，不是金科玉律，但大多数时候比“拍脑袋填数”靠谱。

| 场景 | 建议 |
| --- | --- |
| CPU 密集型任务 | `core ≈ CPU 核数`，`max` 不要比 `core` 大太多，队列适中偏小 |
| IO 密集型任务 | `core` 可从 `CPU 核数` 起步，`max` 适当放大，但要结合下游容量 |
| 延迟敏感接口 | 队列尽量小，优先暴露拒绝，避免长时间排队 |
| 异步削峰任务 | 可以适当放大队列，但必须设置监控和丢弃语义 |
| 不确定场景 | 先小队列 + 压测 + JFR/GC 观察，再逐步调整 |

如果非要浓缩成一句话，我的观点是：

> **先定背压策略，再定队列大小，最后才是线程数。**

因为线程池最终服务的是系统稳定性，不是单次压测里那一点看起来好看的吞吐数字。

# 八、一个 Spring Boot 配置示例

如果你在 Spring Boot 里自定义业务线程池，可以参考下面这种写法：

```java
@Bean("bizExecutor")
public ThreadPoolTaskExecutor bizExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(8);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(50);
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("biz-exec-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}
```

这个配置的重点不是数字本身，而是它表达了两个态度：

1. 队列不无限放大；
2. 出现拥塞时，把压力回传给调用方，而不是悄悄吞掉。

# 九、总结：线程池调参，别迷信公式，先让系统可观察

把今天这篇文章压缩成几个结论：

- **线程池不是加速器，而是并发控制器**；
- **大队列不等于稳定，很多时候只是把延迟藏起来了**；
- **没有拒绝不代表健康，要一起看 P95/P99、队列长度、GC 和 JFR**；
- **CPU 密集和 IO 密集的调法完全不同**；
- **先决定背压和失败策略，再讨论线程数和队列大小。**

如果你最近正好在排查“服务不报错但就是很慢”的问题，线程池和它背后的队列，几乎一定值得你先看一眼。
