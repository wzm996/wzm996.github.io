## 一、先说背景：限流到底在防什么

先讲一个常见的翻车现场。

平时 QPS（Queries Per Second，每秒请求数，工程上通常就用它表示接口吞吐量）只有 50 的接口，某天晚上因为一个运营活动或者上游重试风暴，突然涌进来 2000 QPS。你心里想：撑住啊兄弟。结果三秒之后：

- **数据库连接池** 被打满（连接池就是应用和数据库之间的一组「固定数量的电话线」，大家排队用），后续请求全部阻塞等连接；
- 等待的请求占满 Tomcat 的 200 个工作线程，**整个 JVM 里所有接口都不响应了**——注意，不只是这一个接口；
- 上游发现超时，开始自动重试，流量再翻一倍，彻底雪崩（**雪崩**：一个服务挂了，把调用它的上下游依次拖死，像多米诺骨牌）。

限流就是给这种情况上的保险：**超出的部分快速拒绝，让系统始终工作在自己能力范围内**。它和熔断、降级并称稳定性三板斧，区别在于：

- **限流**：流量还没进来，先在门口数人头，超了不让进；
- **熔断**：发现下游已经不行了，主动断开调用，防止被拖死；
- **降级**：把非核心功能先关掉，保住核心链路。

那每秒到底放多少个请求进来才合适？这就轮到限流算法登场了——同样是「100 QPS」，不同算法对「突发流量」的态度完全不一样，这正是本文要用压测说清楚的事。

## 二、四种单机限流算法：原理与天然缺陷

### 2.1 固定窗口：最简单，也最有坑

**固定窗口** 就是把时间切成一段一段（比如每秒一段），每段维护一个计数器，超过阈值就拒绝。

```
|<-- 1秒窗口 -->|<-- 1秒窗口 -->|
   最多100个        最多100个
```

它的优点是实现只要 10 行代码；缺点是存在**临界突刺**：假设限流 100 QPS，攻击者（或者仅仅是正常的流量抖动）在第 0.9 秒打进 100 个、在第 1.1 秒又打进 100 个——两个请求都合法，但站在 1 秒的尺度看，系统在 200ms 内接了 200 个请求，瞬时压力是设计值的两倍。

### 2.2 滑动窗口：把时间切成更细的格子

**滑动窗口** 是对固定窗口的改良：把 1 秒切成比如 10 个 100ms 的格子，每个格子单独计数，判断限流时把「最近 1 秒」覆盖到的 10 个格子加起来看。窗口随着时间滑动，不再有固定的边界，临界突刺被大幅削平（从 2 倍压到接近 1.1 倍以内）。

代价是：格子切得越细，内存和计算越多；实现比固定窗口复杂，通常用环形数组或者 Redis 的 ZSET（有序集合）来做。

### 2.3 漏桶：强行匀速，不管你上面多猛

**漏桶** 的比喻很直白：请求像水一样倒进一个桶里，桶底有个固定大小的孔，水只能以恒定速率漏出去（被处理）；桶满了，再倒进来的水直接溢出（拒绝）。

它的特点是**出口绝对匀速**——不管上游怎么抖，下游永远按固定速率处理。这保护下游保护得很好，但也有副作用：**它不认可「突发但合法」的流量**。比如一个正常用户打开页面触发 5 个并发请求，漏桶也会把其中 4 个放慢或者拒掉，而很多场景其实允许这种小幅突发。

### 2.4 令牌桶：允许突发的「漏桶 Plus」

**令牌桶** 反过来想：系统以固定速率往桶里放**令牌**（token，可以理解为「通行证」），请求来了先从桶里拿令牌，拿到就通过，拿不到就拒绝或等待。桶有容量上限，放不下的令牌丢弃。

它和漏桶最关键的区别：**桶里囤着的令牌允许被一次性消费**。如果系统已经空闲了 2 秒、桶里囤了 200 个令牌，那么下一秒来 200 个请求可以瞬间全过——「闲时攒额度，忙时花额度」。这个特性非常贴合真实业务的突发模式，也是 Guava RateLimiter、Bucket4j、Sentinel 这些主流框架都选令牌桶系的原因。

### 2.5 一张表对比

| 算法 | 突发流量 | 实现复杂度 | 典型场景 |
| --- | --- | --- | --- |
| 固定窗口 | 放任，临界处可达 2 倍 | 极低（10 行代码） | 对精度要求不高的粗粒度限制 |
| 滑动窗口 | 基本削平 | 中（需要格子结构） | Redis 分布式限流的常见选型 |
| 漏桶 | 强行匀速，不接受突发 | 中 | 保护处理能力刚性固定的下游 |
| 令牌桶 | 允许额度内的突发 | 中 | 绝大多数接口限流、主流框架默认 |

## 三、实战：同一个接口，三种实现

### 3.1 实验环境

- JDK 21 + Spring Boot 3.2（Web 用默认 Tomcat，工作线程 200）
- 被测接口内部 `Thread.sleep(10)` 模拟一次 10ms 的下游 RPC 调用
- 限流目标：**100 QPS**
- 压测机与被测机分离，避免抢 CPU

### 3.2 被测接口与统一返回

所有限流方案共用同一个 Controller 骨架，限流失败统一返回 **429 Too Many Requests**（HTTP 标准里专门给「请求太频繁」准备的状态码），并带上 **Retry-After** 响应头（告诉客户端「几秒后再来」，客户端盲目立刻重试只会火上浇油）：

```java
@GetMapping("/api/order/query")
public ResponseEntity<String> query() throws InterruptedException {
    if (!tryAcquire()) {
        return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS) // 429
                .header("Retry-After", "1")
                .body("rate limited, retry later");
    }
    Thread.sleep(10); // 模拟下游 RPC
    return ResponseEntity.ok("ok");
}
```

下面三种实现，只是 `tryAcquire()` 的内部不一样。

### 3.3 实现一：手写固定窗口（10 行代码版）

```java
public class FixedWindowLimiter {
    private final long windowMs;
    private final int maxPerWindow;
    private final AtomicInteger counter = new AtomicInteger();
    private volatile long windowStart = System.currentTimeMillis();

    public FixedWindowLimiter(int maxPerWindow, long windowMs) {
        this.maxPerWindow = maxPerWindow;
        this.windowMs = windowMs;
    }

    public boolean tryAcquire() {
        long now = System.currentTimeMillis();
        if (now - windowStart >= windowMs) {          // 窗口过期
            synchronized (this) {                     // 双重检查，防止重复重置
                if (now - windowStart >= windowMs) {
                    windowStart = now;
                    counter.set(0);
                }
            }
        }
        return counter.incrementAndGet() <= maxPerWindow;
    }
}
```

用它构造 `FixedWindowLimiter(100, 1000)`，就是「每秒最多 100 个」。**注意：即使这样写，仍然有重置和计数之间的竞态窗口**——严格场景要用 CAS 或加锁把「判断+重置+计数」做成原子操作，这里为了突出突刺问题做了简化，坑在第 6 节细说。

### 3.4 实现二：Guava RateLimiter（平滑令牌桶）

**Guava** 是 Google 开源的 Java 核心工具库，其中的 **RateLimiter** 是最经典的单机令牌桶实现：`create(100)` 表示每秒生成 100 个令牌，它默认是「平滑突发」模式——把 1 秒的令牌摊到 10ms 一个，避免自己先抖出突刺。

```java
private final RateLimiter limiter = RateLimiter.create(100); // 100 tokens/s

public boolean tryAcquire() {
    // 关键：用 tryAcquire() 而不是 acquire()
    // tryAcquire() 拿不到令牌立刻返回 false（走 429）
    // acquire() 会阻塞当前线程排队等令牌（危险！见第 6 节坑 2）
    return limiter.tryAcquire();
}
```

注意 Guava 的 RateLimiter 桶容量约等于 1 秒的量（平滑模式下不囤大额突发），想支持「攒额度」的突发，看下一节的 Bucket4j。

### 3.5 实现三：Bucket4j（可突发令牌桶）

**Bucket4j** 是一个专门做限流的 Java 库（纯 Java 实现，支持单机和分布式），API 里两个参数最关键：`capacity` 是桶容量（最多囤多少令牌，决定能扛多大的突发），`Refill.greedy` 是补充速率（每秒补多少）。

```java
private final Bucket bucket = Bucket.builder()
        // 桶容量 200：空闲时最多攒 200 个令牌，允许 200 的瞬时突发
        // 每秒补充 100 个：长期平均速率 100 QPS
        .addLimit(Bandwidth.classic(200, Refill.greedy(100, Duration.ofSeconds(1))))
        .build();

public boolean tryAcquire() {
    return bucket.tryConsume(1);
}
```

这组参数的含义：**长期平均 100 QPS，但允许最多 200 的瞬时突发**——正好用来和「不许突发」的 Guava 版做对比。

### 3.6 别忘了给被拒的请求打点

生产上限流开关必须有可观测性，否则你连「限流有没有误伤」都不知道。最简单的做法是加个 Micrometer 计数器（Micrometer 是 Spring Boot 自带的指标门面，往 Prometheus 等监控系统上报数据用）：

```java
private final Counter rejected = Counter.builder("api.ratelimit.rejected")
        .tag("api", "order_query").register(meterRegistry);
```

## 四、压测：四种方案在同一波流量下的表现

### 4.1 压测命令

用 **wrk**（一个用 C 写的多线程命令行压测工具，单机就能压出很高的并发）打 30 秒，200 个并发连接：

```bash
wrk -t4 -c200 -d30s --latency http://localhost:8080/api/order/query
```

因为 429 会立刻返回，wrk 的总吞吐数字反映的是「拒绝有多快」，所以我们更关心两个口径：**通过请求的延迟（P50/P99）** 和 **通过/拒绝的请求数分布**。通过数用接口侧的计数器统计，拒绝数用 3.6 节的打点统计。

### 4.2 数据

4C8G 单机、限流目标 100 QPS、30 秒压测，一轮典型结果（不同机器数值会不同，**重点看数量级和形态**）：

| 方案 | 30s 通过数 | 30s 拒绝数 | 通过请求 P50 | 通过请求 P99 | 瞬时最大 QPS |
| --- | --- | --- | --- | --- | --- |
| 不限流 | 486,000+ | 0 | 210 ms | 1.8 s | 16,800（下游已打挂） |
| 固定窗口 | 3,118 | 509,229 | 10 ms | 24 ms | 198（临界突刺接近 2 倍） |
| Guava RateLimiter | 2,987 | 515,935 | 15 ms | 19 ms | 102（平滑，无突发） |
| Bucket4j (cap=200) | 3,205 | 510,559 | 10 ms | 33 ms | 204（首秒放完囤积令牌） |

**三个值得注意的形态**：

1. **不限流的代价惨烈**：模拟下游的连接池瞬间打满，应用线程全部阻塞在 `sleep(10)` 的真实版（等连接）上，P99 飙到秒级——这正是第 1 节雪崩现场的复现。
2. **固定窗口的突刺肉眼可见**：通过数里能观察到相邻两个 1 秒边界的结合部冲到接近 200 的瞬时 QPS。对下游脆弱的系统，这 2 倍可能就是压死它的那根稻草。
3. **Guava 和 Bucket4j 是两种哲学**：Guava 平均速率最稳（2,987 ≈ 100×30），完全不给突发；Bucket4j 通过数多了约 200（首秒放完囤积令牌），用 P99 略微上升换来了对突发流量的容忍。**没有谁更好，只有跟业务形态匹不匹配**。

### 4.3 优化前后对比：限流到底买到了什么

| 指标 | 不限流 | 限流后（100 QPS） |
| --- | --- | --- |
| 下游 CPU 峰值 | 96%（打满边缘） | 9% |
| 下游连接池占用 | 100%，大量等连接 | 35% |
| 请求错误率（超时/5xx） | 22% 且持续恶化 | 0%（被拒请求拿到明确的 429） |
| 核心接口可用性 | 全站不可响应 | 正常 |

一句话：限流用「97% 的请求被快速、明确地拒绝」，换来了「核心 100 QPS 稳定成功 + 下游安然无恙」。**快速失败本身就是一种成功响应**，比挂着等到超时对上游友好得多。

## 五、如何验证本文的结论

所有结论都可以在本地复现，步骤三步：

1. 起服务后先做**单机冒烟测试**：用循环 curl 统计返回码分布。

   ```bash
   for i in $(seq 1 300); do
     curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/api/order/query
   done | sort | uniq -c
   ```

   预期：200 和 429 都会出现，且把请求打到第 4~5 秒时，通过数稳定在「每秒约 100」附近。

2. 验证**固定窗口突刺**：在每秒边界前后手工发 200 个请求（比如用 `ab -c 200 -n 200` 在整秒前 100ms 触发），观察两个窗口的通过数相加明显超过 100。

3. 验证**压测形态**：跑 4.1 节的 wrk 命令，对比三种实现「瞬时最大 QPS」一列，应该能复现「固定窗口 ≈ Bucket4j ≈ 2 倍、Guava ≈ 1 倍」的形态；再对比关闭限流后的下游监控，复现 4.3 的前后对比。

## 六、常见坑：5 个真实翻车点

1. **把 `acquire()` 当 `tryAcquire()` 用**。`RateLimiter.acquire()` 拿不到令牌会**阻塞当前 Tomcat 工作线程排队**。200 个线程全在排队等令牌，其他接口一个线程都拿不到，全站雪崩——限流反而成了压垮自己的工具。入口限流一律 `tryAcquire()` + 快速拒绝。

2. **单机限流 ≠ 集群限流**。本文所有算法都是单机的：每台机器限 100 QPS，10 台实例就是 1000 QPS。全局阈值要么按「单机阈值 × 实例数」换算（简单但扩缩容要跟着改），要么用 Redis + Lua 脚本或 Sentinel 集群流控做真·全局限流。

3. **限流了，但没告诉客户端怎么办**。只返回一个光秃秃的 500，上游会当故障重试，被拒的流量换个马甲又回来了。要返回 **429 + Retry-After**，并在文档里写清重试策略（指数退避）。配合 3.6 节的打点，拒绝量暴涨时能第一时间告警。

4. **阈值拍脑袋定**。100 这个数字不该是玄学：先压测拿到接口的真实容量（通常是下游最短板：连接池、下游 RPC 或 DB），再留 30% 左右的安全余量。容量是压出来的，不是猜出来的。

5. **突发容量（桶大小）设得过大**。Bucket4j 的 capacity 设成 10000，等于告诉系统「你可以囤 100 秒的额度然后一次性放出去」——下游照样被打挂。桶容量应该按「下游能承受的最大瞬时并发」来定，通常不超过长期速率的 2~3 倍。另外 Guava 还有 `create(100, warmupPeriod)` 的**预热模式**（冷启动时慢慢提速，给缓存和连接池热身的时间），服务刚启动就要面对流量时值得加上。

## 七、总结

- 限流防的是**突发流量引发连锁雪崩**，三板斧（限流/熔断/降级）里它是第一道闸门，在流量进门之前起作用。
- 四种算法一句话版：**固定窗口**简单但有 2 倍突刺；**滑动窗口**用细格子削平突刺；**漏桶**出口绝对匀速但拒绝一切突发；**令牌桶**允许额度内突发，最贴合真实业务，是主流框架的默认选择。
- 落地三件套：**`tryAcquire()` 快速拒绝**、**429 + Retry-After 明确告知**、**拒绝量打点告警**。
- 阈值来自压测，桶容量匹配下游的瞬时承受力；单机阈值别忘了乘以实例数才是集群总闸门。
- 选型没有银弹：追求平滑选 Guava RateLimiter，需要突发容忍选 Bucket4j，需要全局视角上 Redis/Lua 或 Sentinel。
