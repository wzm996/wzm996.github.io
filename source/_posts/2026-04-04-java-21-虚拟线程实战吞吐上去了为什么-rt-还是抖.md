<h1 id="为什么很多项目一上虚拟线程就误判“性能翻倍”"><a href="#为什么很多项目一上虚拟线程就误判“性能翻倍”" class="headerlink" title="为什么很多项目一上虚拟线程就误判“性能翻倍”"></a>为什么很多项目一上虚拟线程就误判“性能翻倍”？</h1>
<p>这两年只要聊 <strong>Java 21</strong>，<strong>虚拟线程（Virtual Threads）</strong> 基本是绕不过去的话题。它是 JDK 21 正式发布的一种轻量线程模型，本质上是把“一个任务一个线程”这件事做得更便宜，从而让高并发阻塞型程序不必死磕传统线程池大小。</p>
<p>但线上经常有两个很常见的误判：</p>
<blockquote>
<p>1、接口 TPS 变高了，于是以为系统瓶颈已经没了。<br>2、线程数上万了，于是以为可以不看连接池、不看锁、不看慢 SQL 了。</p>
</blockquote>
<p>这两个结论都不太对。虚拟线程解决的是 <strong>线程调度成本和线程占用成本</strong>，不是替你把数据库、网络、锁竞争、序列化这些瓶颈自动抹平。</p>
<p>所以这篇文章我想回答 4 个具体问题：</p>
<ul>
<li>虚拟线程到底适合什么场景？</li>
<li>为什么 TPS 上去了，P99 延迟可能还是不好看？</li>
<li>怎么用 <strong>JFR</strong> 去看虚拟线程到底卡在哪？</li>
<li>Spring Boot 项目接入虚拟线程时，最容易踩哪些坑？</li>
</ul>
<p><strong>JFR</strong> 全称是 <strong>Java Flight Recorder</strong>，你可以把它理解成 JVM 自带的低开销黑盒录制器，平时用来抓性能事件、线程状态、锁竞争、GC、方法热点，排查线上性能问题非常顺手。</p>

<h1 id="先说结论：虚拟线程提升的不是“单请求变快”，而是“并发承载能力变强”"><a href="#先说结论：虚拟线程提升的不是“单请求变快”，而 is=" class="headerlink" title="先说结论：虚拟线程提升的不是“单请求变快”，而是“并发承载能力变强”"></a>先说结论：虚拟线程提升的不是“单请求变快”，而是“并发承载能力变强”</h1>
<p>如果只记一句话，我更建议记这个：</p>
<pre><code>虚拟线程更像是在“阻塞很多、等待很多”的系统里，
把线程从稀缺资源变成相对便宜的资源。
它通常改善的是并发度、资源利用率和线程管理复杂度，
而不是把业务逻辑本身变快。
</code></pre><p>举个很接地气的例子：</p>
<ul>
<li>你的接口大部分时间都在等 MySQL / Redis / 下游 HTTP 返回</li>
<li>传统线程池配 200 个线程，峰值一来就排队</li>
<li>换成虚拟线程后，请求不容易卡在线程池入口</li>
<li>于是吞吐提升、超时变少、线程池调参负担也变小</li>
</ul>
<p>但如果：</p>
<ul>
<li>数据库连接池只有 30</li>
<li>某个同步块锁住了核心逻辑</li>
<li>JSON 序列化本身就很重</li>
<li>外部接口 P99 还是 800ms</li>
</ul>
<p>那虚拟线程只是让更多请求更快地 <strong>同时抵达瓶颈</strong>，它不会让瓶颈自己消失。</p>

<h1 id="实验设计：固定业务逻辑，对比平台线程池和虚拟线程"><a href="#实验设计：固定业务逻辑，对比平台线程池和虚拟线程" class="headerlink" title="实验设计：固定业务逻辑，对比平台线程池和虚拟线程"></a>实验设计：固定业务逻辑，对比平台线程池和虚拟线程</h1>
<p>为了避免空谈，我们做一个非常小但足够说明问题的实验。</p>
<p>实验目标：模拟一个典型的“阻塞型聚合接口”——每次请求都会等待两个下游调用，各自 sleep 一段时间，再做一点轻量 CPU 计算。</p>
<p>我们做两版实现：</p>
<ul>
<li><strong>版本 A：</strong> 固定大小平台线程池（platform thread pool）</li>
<li><strong>版本 B：</strong> 每个任务一个虚拟线程（virtual thread per task）</li>
</ul>
<p>说明一下，<strong>平台线程</strong> 就是你以前理解的普通操作系统线程；<strong>虚拟线程</strong> 是 JVM 调度的轻量线程，运行时会挂载到少量平台线程上执行。</p>

<ul>

<li>数据库连接池等待</li>
<li>热点锁竞争</li>
<li>大对象分配和序列化抖动</li>
<li>日志 IO 或同步刷盘</li>
</ul>

<p>这个现象很重要：<strong>虚拟线程把“线程入口排队”转成了“下游资源排队”</strong>。系统总吞吐可能没差太多，但尾延迟更难看了。</p>

<h1 id="怎么验证瓶颈到底在线程、锁还是连接池？先看 JFR"><a href="#怎么验证瓶颈到底在线程、锁还是连接池？先看 JFR" class="headerlink" title="怎么验证瓶颈到底在线程、锁还是连接池？先看 JFR"></a>怎么验证瓶颈到底在线程、锁还是连接池？先看 JFR</h1>
<p>很多同学一遇到虚拟线程性能问题，第一反应是先猜。其实最稳的办法还是抓证据。</p>
<p>启动时打开 JFR：</p>
<figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><span class="line">java -XX:StartFlightRecording=filename=app.jfr,dumponexit=true \</span><br><span class="line">     -jar demo.jar</span><br></pre></td></tr></table></figure>

<p>或者运行中抓一段：</p>
<figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><span class="line">jcmd &lt;pid&gt; JFR.start name=vt-demo settings=profile filename=vt-demo.jfr</span><br><span class="line">sleep 60</span><br><span class="line">jcmd &lt;pid&gt; JFR.stop name=vt-demo</span><br></pre></td></tr></table></figure>

<p>重点看这几类事件：</p>
<ul>
<li><strong>Java Monitor Blocked</strong>：看 <code>synchronized</code> 锁竞争</li>
<li><strong>Thread Park</strong>：看线程 park 等待是否异常增多</li>
<li><strong>Socket Read / Socket Write</strong>：看网络 IO 等待时间</li>
<li><strong>Execution Sample</strong>：看 CPU 真正热在哪个方法上</li>
<li><strong>Object Allocation in New TLAB / Outside TLAB</strong>：看对象分配抖不抖</li>
</ul>
<p><strong>TLAB</strong> 是 <strong>Thread Local Allocation Buffer</strong>，可以把它理解成“线程私有的一小块对象分配缓存”，对象先在这里分配会更快；如果频繁跑到 TLAB 外分配，通常说明分配压力不小。</p>

<h2 id="JFR 里怎么看“虚拟线程被 pin 住”"><a href="#JFR 里怎么看“虚拟线程被 pin 住”" class="headerlink" title="JFR 里怎么看“虚拟线程被 pin 住”"></a>JFR 里怎么看“虚拟线程被 pin 住”</h2>
<p>虚拟线程有个很经典的坑叫 <strong>pinning</strong>。中文通常会说“被钉住”。你可以把它理解成：本来虚拟线程遇到阻塞时，应该把底层平台线程让出来；但某些场景下它让不出来，结果 carrier thread 被长期占住。</p>
<p><strong>carrier thread</strong> 指的是承载虚拟线程执行的底层平台线程。虚拟线程最终还是要跑在它上面，只是平时可以灵活挂载和卸载。</p>
<p>常见触发场景：</p>
<ul>
<li>在 <code>synchronized</code> 代码块里做了长时间阻塞 IO</li>
<li>某些 native 调用阻塞时间过长</li>
<li>老旧三方库内部用了不友好的同步方式</li>
</ul>
<p>打开下面这个 JVM 参数可以直接把 pinning 打到日志里：</p>
<figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span></pre></td><td class="code"><pre><span class="line">-Djdk.tracePinnedThreads=full</span><br></pre></td></tr></table></figure>

<p>如果日志里频繁出现 pinned thread 警告，再结合 JFR 的 monitor blocked 和 stack trace，基本就能快速定位到哪段代码不适合继续这么写。</p>

<h1 id="Spring-Boot-里怎么接，才不容易翻车？"><a href="#Spring-Boot-里怎么接，才不容易翻车？" class="headerlink" title="Spring Boot 里怎么接，才不容易翻车？"></a>Spring Boot 里怎么接，才不容易翻车？</h1>
<p>如果你的应用是典型的 Web + DB + Redis + 调下游 HTTP 的阻塞型服务，虚拟线程是值得试的。但别一把梭，建议按下面这个顺序来。</p>

<h2 id="1-先选对场景：阻塞型 IO 服务收益最大"><a href="#1-先选对场景：阻塞型 IO 服务收益最大" class="headerlink" title="1-先选对场景：阻塞型 IO 服务收益最大"></a>1、先选对场景：阻塞型 IO 服务收益最大</h2>
<p>最适合的场景：</p>
<ul>
<li>接口大量时间在等待 DB / Redis / HTTP</li>
<li>以前线程池大小很难调，调大怕 OOM，调小又排队</li>
<li>业务代码同步写法很多，改响应式成本过高</li>
</ul>
<p>不一定适合的场景：</p>
<ul>
<li>纯 CPU 密集型计算</li>
<li>高锁竞争热点服务</li>
<li>下游资源特别小，但入口并发特别大</li>
</ul>

<h2 id="2-别只改线程池，不看连接池"><a href="#2-别只改线程池，不看连接池" class="headerlink" title="2、别只改线程池，不看连接池"></a>2、别只改线程池，不看连接池</h2>
<p>这是最容易翻车的一点。你把线程池从 200 个固定线程，换成“几乎想开多少开多少”的虚拟线程以后，数据库连接池、HTTP 连接池、下游限流阈值都要重新审视。</p>
<p>比如 HikariCP 可以重点看这些指标：</p>
<ul>
<li><code>active</code>：活跃连接数</li>
<li><code>pending</code>：等待连接的线程数</li>
<li><code>connectionTimeout</code>：拿连接超时阈值</li>
</ul>
<p>如果你发现换虚拟线程后 <code>pending</code> 激增，那不是虚拟线程有问题，而是你真正的瓶颈已经被它“照妖镜化”了。</p>

<h2 id="3-尽量少在 synchronized 里做慢操作"><a href="#3-尽量少在-synchronized-里做慢操作" class="headerlink" title="3、尽量少在 synchronized 里做慢操作"></a>3、尽量少在 <code>synchronized</code> 里做慢操作</h2>
<p>这条非常关键。以前平台线程时代，很多人也会在 <code>synchronized</code> 里顺手做点 IO，虽然不优雅，但勉强还能跑。到了虚拟线程时代，这种代码更容易制造 pinning。</p>
<p>更稳的做法是：</p>
<ul>
<li>缩小锁粒度</li>
<li>把慢 IO 移出同步块</li>
<li>优先考虑无锁结构、分段锁或者状态拆分</li>
</ul>

<h2 id="4-线程本地变量不是不能用，但别乱囤"><a href="#4-线程本地变量不是不能用，但别乱囤" class="headerlink" title="4、线程本地变量不是不能用，但别乱囤"></a>4、线程本地变量不是不能用，但别乱囤</h2>
<p><strong>ThreadLocal</strong> 在虚拟线程里不是完全不能用，但它的使用姿势必须更克制。因为虚拟线程数量可能非常多，如果你在线程本地变量里塞很重的对象，就很容易把内存占用搞大。</p>
<p>尤其是下面这些东西，别轻易往 ThreadLocal 里放：</p>
<ul>
<li>大缓存对象</li>
<li>大 JSON 缓冲区</li>
<li>数据库上下文大对象</li>
<li>不及时清理的用户态上下文</li>
</ul>

<h2 id="5-监控体系要跟着改"><a href="#5-监控体系要跟着改" class="headerlink" title="5、监控体系要跟着改"></a>5、监控体系要跟着改</h2>
<p>上虚拟线程以后，如果你还只盯着“线程池活跃线程数”，那监控视角已经落后了。更应该重点看：</p>
<ul>
<li>数据库连接池等待时间</li>
<li>下游 HTTP 客户端连接池和超时</li>
<li>锁竞争</li>
<li>GC 暂停与对象分配速率</li>
<li>P95 / P99，而不是只看平均值</li>
</ul>

<h2 id="步骤-4：看 JFR 是否出现这几类证据"><a href="#步骤-4：看-jfr-是否出现这几类证据" class="headerlink" title="步骤 4：看 JFR 是否出现这几类证据"></a>步骤 4：看 JFR 是否出现这几类证据</h2>
<ul>
<li>平台线程池版本：大量请求排队在线程池入口</li>
<li>虚拟线程版本：线程排队下降，但连接池等待或锁竞争上升</li>
<li>如存在 pinning：日志出现 pinned thread，JFR 中伴随 monitor/blocking 证据</li>
</ul>

<h2 id="如何验证结论"><a href="#如何验证结论" class="headerlink" title="如何验证结论"></a>如何验证结论</h2>
<blockquote>
<p>如果虚拟线程版本的 TPS 提升明显，但 P99 下降有限，且 JFR 显示主要等待时间落在 Socket Read、连接池等待、锁竞争上，而不是线程创建或线程池排队上，那么就可以验证本文核心结论：虚拟线程主要缓解线程资源瓶颈，而不是消除所有尾延迟来源。</p>
</blockquote>

<h1 id="常见坑与误区"><a href="#常见坑与误区" class="headerlink" title="常见坑与误区"></a>常见坑与误区</h1>
<h2 id="误区-1：虚拟线程等于响应式"><a href="#误区-1：虚拟线程等于响应式" class="headerlink" title="误区 1：虚拟线程等于响应式"></a>误区 1：虚拟线程等于响应式</h2>
<p>不是一回事。虚拟线程解决的是同步阻塞写法下的线程成本问题；响应式解决的是非阻塞事件驱动模型下的资源利用方式问题。两者有交集，但不是互相替代。</p>

<h2 id="误区-2：线程数可以无限开"><a href="#误区-2：线程数可以无限开" class="headerlink" title="误区 2：线程数可以无限开"></a>误区 2：线程数可以无限开</h2>
<p>虚拟线程很轻，但不是不要成本。任务对象、栈片段、上下文、调度、对象分配、监控链路都会有开销。更关键的是，下游资源永远不是无限的。</p>

<h2 id="误区-3：上了虚拟线程就不用做性能分析"><a href="#误区-3：上了虚拟线程就不用做性能分析" class="headerlink" title="误区 3：上了虚拟线程就不用做性能分析"></a>误区 3：上了虚拟线程就不用做性能分析</h2>
<p>恰恰相反。越是并发能力变强，越要更认真地看连接池、锁、GC、序列化和下游抖动，否则只是把问题从“线程不够”换成了“别的地方更挤”。</p>

<h2 id="误区-4：所有三方库都天然适配"><a href="#误区-4：所有三方库都天然适配" class="headerlink" title="误区 4：所有三方库都天然适配"></a>误区 4：所有三方库都天然适配</h2>
<p>别想太美。尤其是一些老旧 JDBC 驱动、HTTP 客户端、native 依赖或者重同步风格的库，最好都压测一下再说。能不能跑是一回事，跑起来尾延迟漂不漂亮又是另一回事。</p>

<h1 id="落地建议：怎么把虚拟线程安全地带到生产"><a href="#落地建议：怎么把虚拟线程安全地带到生产" class="headerlink" title="落地建议：怎么把虚拟线程安全地带到生产"></a>落地建议：怎么把虚拟线程安全地带到生产</h1>
<ol>
<li>先挑一个 <strong>阻塞型、链路短、指标清晰</strong> 的接口做灰度。</li>
<li>压测时一定同时看 <strong>TPS + P95/P99 + 连接池等待 + JFR</strong>。</li>
<li>如果 TPS 上去了但 P99 不动，先查下游资源，不要急着怪 JVM。</li>
<li>如果出现 pinning，优先排查 <code>synchronized</code> + 慢 IO 组合。</li>
<li>上线后把监控重心从“线程数”转到“资源等待与尾延迟”。</li>
</ol>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>
<ul>
<li><strong>虚拟线程最适合阻塞型 IO 服务</strong>，它解决的是线程资源贵、线程池难调的问题。</li>
<li><strong>TPS 提升不代表尾延迟自然变好</strong>，P99 往往取决于连接池、锁竞争、下游抖动和对象分配。</li>
<li><strong>JFR 是判断瓶颈位置的核心证据</strong>，别靠猜。</li>
<li><strong>线上接入要成套改</strong>：线程模型、连接池、监控、锁设计、三方库兼容性要一起看。</li>
</ul>
<p>一句人话总结就是：<strong>虚拟线程能让你“更从容地并发”，但不能替你“更聪明地设计系统”。</strong></p>
