<h1 id="为什么这个问题值得单独写一篇"><a href="#为什么这个问题值得单独写一篇" class="headerlink" title="为什么这个问题值得单独写一篇"></a>为什么这个问题值得单独写一篇</h1>
<p>做 Java 后端时，超时配置几乎天天见：调用第三方接口要配、服务间 HTTP 调用要配、数据库连接池要配、消息消费要配。可真到了线上，很多人对“超时”其实只有一个非常模糊的印象：反正别太大，也别太小。</p>
<p>问题就在这儿。<strong>超时不是一个孤立参数，它本质上是在定义资源最多被占用多久</strong>。你把超时从 500ms 改到 5s，改的不只是“等等看”，而是线程、连接、队列、重试窗口、用户体验和故障扩散半径。</p>
<p>这篇文章聚焦一个很典型的工程场景：<strong>Spring Boot 应用通过 HTTP 调用下游服务</strong>。我们会把问题拆成四层：</p>
<ul>
<li><strong>连接超时（connect timeout）</strong>：和对方建立 TCP 连接愿意等多久。</li>
<li><strong>读超时（read timeout）</strong>：连接已经建立好后，等对方返回数据愿意等多久。</li>
<li><strong>线程池与连接池容量</strong>：一次慢调用会把多少资源卡住。</li>
<li><strong>重试策略</strong>：本来一个慢请求，怎么被放大成雪崩。</li>
</ul>
<p>如果你最近碰到过这些现象，这篇会很对味：</p>
<ul>
<li>下游偶发超时，结果本服务 CPU 不高但 RT 飙升；</li>
<li>Tomcat 线程打满，接口全部排队；</li>
<li>监控里错误率不算高，但 P99 巨难看；</li>
<li>加了重试之后，系统反而更容易挂。</li>
</ul>

<h1 id="先把几个容易混的名词掰开"><a href="#先把几个容易混的名词掰开" class="headerlink" title="先把几个容易混的名词掰开"></a>先把几个容易混的名词掰开</h1>
<p>先说几个新名词，尽量口语一点：</p>
<ul>
<li><strong>P50 / P95 / P99</strong>：这是延迟分位数。比如 P99=1200ms，意思是 99% 的请求都在 1.2 秒内完成，但最慢那 1% 可能特别离谱。线上盯 P99，往往比盯平均值更有用。</li>
<li><strong>线程池</strong>：就是一组可以复用的工作线程。你可以把它理解成餐厅后厨的人手，超时越大，人手被一个慢单占住的时间就越久。</li>
<li><strong>连接池</strong>：提前准备好的连接集合，避免每次都重新建连接。常见于数据库、HTTP client 等。</li>
<li><strong>重试放大</strong>：原本只发 1 次请求，因为超时后自动重试 2~3 次，瞬间把下游流量扩大成 2 倍、3 倍甚至更高。</li>
<li><strong>Bulkhead（舱壁隔离）</strong>：就是把不同调用的资源隔开，别让一个慢下游把整个服务拖沉。名字来自船舱隔板，某一舱进水，不至于整艘船一起沉。</li>
</ul>

<h1 id="一个核心结论先摆出来"><a href="#一个核心结论先摆出来" class="headerlink" title="一个核心结论先摆出来"></a>一个核心结论先摆出来</h1>
<blockquote>
<p><strong>超时值不是“越大越稳”，而是“越大越容易把资源占死”</strong>。如果下游已经明显退化，过大的读超时 + 无脑重试，通常只会让本服务更慢、更堵、更难恢复。</p>
</blockquote>
<p>所以合理的超时设计，目标不是“尽量等成功”，而是：</p>
<ul>
<li>尽快识别无意义等待；</li>
<li>把失败控制在局部；</li>
<li>给系统留出自我恢复空间；</li>
<li>让上游能尽快降级、兜底或返回明确错误。</li>
</ul>

<h1 id="实验场景：用一个小服务把问题复现出来"><a href="#实验场景：用一个小服务把问题复现出来" class="headerlink" title="实验场景：用一个小服务把问题复现出来"></a>实验场景：用一个小服务把问题复现出来</h1>
<p>为了不空谈，我们做一个最小可复现实验：</p>
<ul>
<li><strong>caller-service</strong>：对外暴露 `/bench`，收到请求后去调用下游 `/sleep?ms=...`；</li>
<li><strong>downstream-service</strong>：收到请求后故意 sleep 一段时间再返回；</li>
<li>通过 ApacheBench（ab）压 200 个请求，看不同超时配置下的表现。</li>
</ul>
<p>这里用 <strong>ApacheBench</strong>，它是个很老但够用的 HTTP 压测工具，适合做这种快速对比实验。要更细的性能分析，也可以换 wrk、hey、JMeter。</p>

<h2 id="一、准备两个最小服务"><a href="#一、准备两个最小服务" class="headerlink" title="一、准备两个最小服务"></a>一、准备两个最小服务</h2>
<p><strong>downstream-service</strong>：</p>
<pre><code class="java">@RestController
public class SleepController {

    @GetMapping("/sleep")
    public Map&lt;String, Object&gt; sleep(@RequestParam(defaultValue = "100") long ms) throws Exception {
        Thread.sleep(ms);
        return Map.of(
                "ok", true,
                "sleepMs", ms,
                "thread", Thread.currentThread().getName()
        );
    }
}
</code></pre>
<p><strong>caller-service</strong>（为了演示，先直接用 RestTemplate）：</p>
<pre><code class="java">@Configuration
public class HttpClientConfig {

    @Bean
    public RestTemplate restTemplate() {
        var factory = new HttpComponentsClientHttpRequestFactory();
        factory.setConnectTimeout(200);
        factory.setReadTimeout(300);
        return new RestTemplate(factory);
    }
}
</code></pre>
<pre><code class="java">@RestController
@RequiredArgsConstructor
public class BenchController {

    private final RestTemplate restTemplate;

    @GetMapping("/bench")
    public String bench(@RequestParam(defaultValue = "100") long ms) {
        String url = "http://127.0.0.1:8081/sleep?ms=" + ms;
        return restTemplate.getForObject(url, String.class);
    }
}
</code></pre>
<p><strong>连接超时</strong> 和 <strong>读超时</strong> 第一次出现，顺手解释一下：</p>
<ul>
<li><strong>连接超时</strong>：TCP 三次握手迟迟建不起来时，最多等多久。比如目标地址写错、网络不可达、SYN 一直没回。</li>
<li><strong>读超时</strong>：连接已经建好了，但服务迟迟不回包时，最多等多久。比如下游线程池满了、SQL 慢了、接口卡住了。</li>
</ul>

<h2 id="二、启动服务"><a href="#二、启动服务" class="headerlink" title="二、启动服务"></a>二、启动服务</h2>
<pre><code class="bash"># terminal 1
cd downstream-service
./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8081

# terminal 2
cd caller-service
./mvnw spring-boot:run -Dspring-boot.run.arguments=--server.port=8080
</code></pre>

<pre><code class="bash">curl 'http://127.0.0.1:8080/bench?ms=100'

<p>预期：正常返回。</p>

<h2 id="怎么从容量角度理解这个结果"><a href="#怎么从容量角度理解这个结果" class="headerlink" title="怎么从容量角度理解这个结果"></a>怎么从容量角度理解这个结果</h2>
<p>这里有个很好用的粗估公式：</p>
<pre><code>系统内同时被占住的请求数 ≈ 到达速率 × 请求停留时间</code></pre>
<p>这其实就是 <strong>Little's Law</strong>（利特尔法则）的直觉版。它是排队论里一个很经典的关系，用来估算系统里平均有多少请求正在排队或处理中。</p>
<p>假设你的服务每秒进来 100 个请求：</p>
<ul>
<li>如果每个请求最多卡 300ms，那平均被占住的大概是 30 个；</li>
<li>如果每个请求最多卡 1500ms，那平均被占住的大概是 150 个。</li>
</ul>
<p>线程数没变、连接数没变，排队自然就出来了。<strong>很多“突然 RT 飙升”的根因，不是 CPU 打满，而是等待时间把资源池泡满了。</strong></p>

<h1 id="连接超时和读超时，到底该怎么分开配"><a href="#连接超时和读超时，到底该怎么分开配" class="headerlink" title="连接超时和读超时，到底该怎么分开配"></a>连接超时和读超时，到底该怎么分开配</h1>
<p>一个很常见的错误，是把 connect timeout 和 read timeout 都拍脑袋写成同一个值，比如都 3 秒。这样不能说一定错，但通常不够精细。</p>

<h2 id="1-连接超时一般应该更短"><a href="#1-连接超时一般应该更短" class="headerlink" title="1-连接超时一般应该更短"></a>1. 连接超时一般应该更短</h2>
<p>在同机房、同 VPC 或正常服务网格里，连一个健康下游，建连通常是毫秒级。如果 TCP 连不上，往往说明：</p>
<ul>
<li>地址不通；</li>
<li>DNS 解析错了；</li>
<li>防火墙/安全组拦了；</li>
<li>下游监听端口异常。</li>
</ul>
<p>这些问题，等 3 秒和等 300ms，很多时候结论是一样的：还是连不上。所以 <strong>连接超时应该偏短</strong>，尽快失败更合理。</p>

<h2 id="2-读超时应该来自-SLO-而不是心情"><a href="#2-读超时应该来自-SLO-而不是心情" class="headerlink" title="2-读超时应该来自 SLO 而不是心情"></a>2. 读超时应该来自 SLO，而不是心情</h2>
<p><strong>SLO</strong> 是 Service Level Objective，也就是服务目标，比如“99% 的请求在 300ms 内完成”。它不是玄学，是你给自己定的延迟和可用性承诺。</p>
<p>如果你的接口整体预算是 500ms，而这个下游只是其中一个依赖，那你就不能给它配 800ms 的读超时。否则即使它“按时返回”，整个链路也已经超预算了。</p>
<p>一个更靠谱的思路是：</p>
<ol>
<li>先定义入口接口的目标延迟，比如 P99 ≤ 800ms；</li>
<li>给每个下游分配时间预算，比如 A 服务 150ms，B 服务 200ms；</li>
<li>把超时值配成“略高于健康状态下的 P99，但低于整链路失控阈值”。</li>
</ol>
<p>说白了，<strong>读超时应该服务于整体延迟预算，而不是“希望这次也许能等回来”</strong>。</p>

<h1 id="重试为什么经常把系统救火变纵火"><a href="#重试为什么经常把系统救火变纵火" class="headerlink" title="重试为什么经常把系统救火变纵火"></a>重试为什么经常把系统救火变纵火</h1>
<p>很多团队加重试的初衷没问题：网络抖一下、偶发超时，重试一次也许就成功了。问题是，一旦你没有控制好边界，重试就是最典型的放大器。</p>
<p>举个很朴素的例子：</p>
<ul>
<li>原始流量：1000 QPS；</li>
<li>某下游开始变慢，30% 请求超时；</li>
<li>调用方每次失败重试 2 次。</li>
</ul>
<p>那下游实际承受的请求数，可能不再是 1000 QPS，而是接近：</p>
<pre><code>1000 + 300 * 2 = 1600 QPS</code></pre>
<p>如果多个服务层层重试，情况会更夸张。你会看到一种特别恶心的现象：<strong>本来只是局部退化，最后被重试打成全面雪崩</strong>。</p>

<h2 id="相对靠谱的重试原则"><a href="#相对靠谱的重试原则" class="headerlink" title="相对靠谱的重试原则"></a>相对靠谱的重试原则</h2>
<ul>
<li><strong>只对幂等操作重试</strong>。比如 GET、查询类接口。别对扣款、发券、下单这种有副作用的操作乱重试。</li>
<li><strong>优先重试连接失败、瞬时网络错误</strong>，少对明确的慢处理超时做高次数重试。</li>
<li><strong>重试次数要少</strong>。通常 1 次就已经很激进了，2 次往上要非常谨慎。</li>
<li><strong>加退避和抖动</strong>。也就是别所有请求都在 100ms 后齐刷刷再来一波。<strong>抖动（jitter）</strong> 就是在等待时间里加一点随机性，避免重试风暴同时砸下去。</li>
<li><strong>配合熔断和限流</strong>。下游持续异常时，早点短路，不要继续给它喂流量。</li>
</ul>

<h1 id="工程上更稳妥的落地方案"><a href="#工程上更稳妥的落地方案" class="headerlink" title="工程上更稳妥的落地方案"></a>工程上更稳妥的落地方案</h1>
<p>如果你在 Spring Boot 里做生产实践，我更建议把下面几件事一起做，而不是只改一个 timeout 参数。</p>

<h2 id="1-给不同下游单独配超时"><a href="#1-给不同下游单独配超时" class="headerlink" title="1-给不同下游单独配超时"></a>1. 给不同下游单独配超时</h2>
<p>支付、库存、画像、搜索，这些下游的重要性和耗时分布不一样，不应该共用一套默认超时。</p>
<pre><code class="yaml">clients:
  user-service:
    connect-timeout-ms: 100
    read-timeout-ms: 200
  report-service:
    connect-timeout-ms: 200
    read-timeout-ms: 800
</code></pre>
<p>快接口就用更紧的预算，慢接口要么异步化，要么单独隔离，不要一锅端。</p>

<h2 id="2-把线程池和下游调用隔离开"><a href="#2-把线程池和下游调用隔离开" class="headerlink" title="2-把线程池和下游调用隔离开"></a>2. 把线程池和下游调用隔离开</h2>
<p>如果一个高风险下游特别容易抖，最好别让它直接占满核心业务线程池。可以用独立线程池、Bulkhead、隔离舱模式来兜住。</p>
<p>比如用 Resilience4j：</p>
<pre><code class="java">BulkheadConfig bulkheadConfig = BulkheadConfig.custom()
        .maxConcurrentCalls(20)
        .maxWaitDuration(Duration.ofMillis(50))
        .build();
</code></pre>
<p>这段配置的意思很简单：最多允许 20 个并发调用继续执行，多出来的请求最多等 50ms，等不到就快速失败。它不是为了“多处理点”，而是为了<strong>别把所有资源都赔进去</strong>。</p>

<h2 id="3-监控别只看平均值"><a href="#3-监控别只看平均值" class="headerlink" title="3-监控别只看平均值"></a>3. 监控别只看平均值</h2>
<p>线上最容易误导人的指标之一就是平均 RT。平均值很容易被大量正常请求稀释。</p>
<p>更建议至少盯这些：</p>
<ul>
<li>成功率；</li>
<li>P50 / P95 / P99；</li>
<li>线程池 active / queue / reject；</li>
<li>HTTP client 连接池 leased / pending；</li>
<li>重试次数和熔断次数；</li>
<li>下游调用耗时分布。</li>
</ul>

<h2 id="4-出问题时，先抓线程栈，再谈调参"><a href="#4-出问题时，先抓线程栈，再谈调参" class="headerlink" title="4-出问题时，先抓线程栈，再谈调参"></a>4. 出问题时，先抓线程栈，再谈调参</h2>
<p>很多人一看到 timeout，就开始改参数。其实线上排查更靠谱的顺序通常是：</p>
<ol>
<li>看监控：是连接失败多，还是读超时多？</li>
<li>抓线程栈：线程是卡在 socket read、连接池等待、还是业务锁竞争？</li>
<li>看连接池状态：是不是 pending 很高？</li>
<li>再决定调 timeout、调线程池，还是做降级。</li>
</ol>
<p>线程栈可以先用：</p>
<pre><code class="bash">jcmd &lt;pid&gt; Thread.print &gt; /tmp/thread-dump.txt
</code></pre>
<p>如果你看到大量线程卡在 `java.net.SocketInputStream.socketRead0` 或 Apache HttpClient 的读路径上，基本就能确认：这不是 CPU 算不过来，而是在傻等下游。</p>

<h1 id="怎么验证你的结论不是拍脑袋"><a href="#怎么验证你的结论不是拍脑袋" class="headerlink" title="怎么验证你的结论不是拍脑袋"></a>怎么验证你的结论不是拍脑袋</h1>
<p>这一节很重要。工程文章最怕“感觉如此”。下面给一个最小验证闭环。</p>

<h2 id="验证项-1：超时是否真的生效"><a href="#验证项-1：超时是否真的生效" class="headerlink" title="验证项 1：超时是否真的生效"></a>验证项 1：超时是否真的生效</h2>
<pre><code class="bash">time curl -s -o /dev/null 'http://127.0.0.1:8080/bench?ms=1000'
</code></pre>
<p>如果 read timeout 配的是 300ms，那整个调用时间应该接近 300~400ms，而不是老老实实等满 1 秒。</p>

<h2 id="验证项-2：长超时会不会拖高尾延迟"><a href="#验证项-2：长超时会不会拖高尾延迟" class="headerlink" title="验证项 2：长超时会不会拖高尾延迟"></a>验证项 2：长超时会不会拖高尾延迟</h2>
<p>把 read timeout 从 300ms 改成 1500ms，重新跑：</p>
<pre><code class="bash">ab -n 500 -c 50 'http://127.0.0.1:8080/bench?ms=800'
</code></pre>
<p>对比两次结果中的 `Time per request`、百分位延迟以及错误率。你通常会看到：</p>
<ul>
<li>成功率升高；</li>
<li>P95 / P99 明显升高；</li>
<li>整体吞吐下降。</li>
</ul>

<h2 id="验证项-3：重试是否带来放大"><a href="#验证项-3：重试是否带来放大" class="headerlink" title="验证项 3：重试是否带来放大"></a>验证项 3：重试是否带来放大</h2>
<p>打开应用监控，观察两类指标：</p>
<ul>
<li>caller-service 对 downstream 的总请求数；</li>
<li>入口 `/bench` 的真实请求数。</li>
</ul>
<p>如果入口是 500 次，但下游收到 800 次、1000 次，那就是重试放大已经发生了。</p>

<h2 id="验证项-4：线程是否真的被占住"><a href="#验证项-4：线程是否真的被占住" class="headerlink" title="验证项 4：线程是否真的被占住"></a>验证项 4：线程是否真的被占住</h2>
<p>压测时执行：</p>
<pre><code class="bash">jcmd $(pgrep -f caller-service) Thread.print | grep -n 'socketRead0' -n
</code></pre>
<p>如果大量线程卡在读 socket，那就说明你的问题不是“代码慢”，而是“等待把线程泡住了”。</p>

<h1 id="常见坑与误区"><a href="#常见坑与误区" class="headerlink" title="常见坑与误区"></a>常见坑与误区</h1>
<ul>
<li><strong>误区 1：成功率高就是配置更优。</strong><br>不一定。成功率高但 P99 爆炸、线程池被占满，整体体验可能更差。</li>
<li><strong>误区 2：所有下游统一 3 秒超时最省事。</strong><br>省事通常也最粗暴。不同依赖必须按业务价值和延迟预算拆开配。</li>
<li><strong>误区 3：重试总能提升可用性。</strong><br>只有在短暂抖动、并且容量还没被打满时，重试才可能有正收益。</li>
<li><strong>误区 4：只调 HTTP timeout，不看连接池与线程池。</strong><br>超时本质上是资源占用时间参数，不结合资源池一起看，很容易头痛医头。</li>
<li><strong>误区 5：监控里平均值正常，就说明系统没事。</strong><br>线上很多事故，是 P99 先烂，平均值最后才跟着难看。</li>
</ul>

<h1 id="一套我更推荐的默认思路"><a href="#一套我更推荐的默认思路" class="headerlink" title="一套我更推荐的默认思路"></a>一套我更推荐的默认思路</h1>
<p>如果你问我一个没有绝对标准、但在大多数 Java 内部服务调用里还算靠谱的起手式，我会这样建议：</p>
<ul>
<li>连接超时：<strong>100ms ~ 300ms</strong> 起步；</li>
<li>读超时：依据接口 SLO 和下游 P99 来定，通常从 <strong>200ms ~ 1000ms</strong> 的业务区间里选，而不是统一拍 3 秒；</li>
<li>重试：默认<strong>关闭或最多 1 次</strong>，只对明确幂等、短暂网络抖动场景开启；</li>
<li>慢下游：单独线程池/舱壁隔离；</li>
<li>监控：必须有 P95/P99、连接池、线程池、重试次数。</li>
</ul>
<p>一句话总结就是：<strong>超时配置的本质，不是“给请求多一点机会”，而是“给系统设一道止损线”</strong>。</p>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>
<ul>
<li>连接超时解决的是“连不连得上”，通常应该比读超时更短；</li>
<li>读超时要从整条链路的延迟预算倒推，不要拍脑袋；</li>
<li>超时一旦变大，吞吐、尾延迟、线程占用都会受到影响；</li>
<li>重试是放大器，不是银弹；</li>
<li>排查超时问题时，线程栈、连接池和分位数监控，比“感觉”靠谱得多。</li>
</ul>
