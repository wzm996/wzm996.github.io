## 一、背景：为什么有了线程池还不够

写后端的人都有体感：服务里最贵的从来不是计算，而是「等」。一个请求里查一次数据库、调一次下游 RPC、再调一次大模型 API，500ms 的耗时里可能有 490ms 是在等对方返回，CPU 基本闲着。但 Java 的传统线程模型下，「等」是要付出真金白银的——**平台线程（Platform Thread）**（就是我们用了二十多年的普通 `java.lang.Thread`，和操作系统线程一一对应）在等待期间被原封不动地占着：Tomcat 默认 200 个工作线程，意味着同一时刻最多服务 200 个请求，第 201 个只能排队。想加线程？每条平台线程默认 1MB 栈内存，再加操作系统线程切换的开销，加到几千条机器先扛不住。

传统的两条出路都不省心：要么上**响应式编程**（如 WebFlux，用事件循环 + 非阻塞 IO，用极少线程扛大并发，但代码是回调/链式风格，调试和排障成本高）；要么调线程池参数（治标不治本，线程数终究有上限）。JDK 21 正式 GA 的**虚拟线程（Virtual Thread）**给了第三条路：**用同步的写法，拿到接近异步模型的并发容量**。这篇文章的目标是把三件事讲透：它为什么能做到、数字上到底差多少、以及生产上会踩哪些坑。

## 二、核心概念：虚拟线程到底是什么

### 2.1 三个角色：虚拟线程、载体线程、挂载/卸载

理解虚拟线程只需要记住三个词：

- **虚拟线程**：JVM 在用户态「模拟」出来的轻量线程。它也是 `java.lang.Thread` 的实例，但不固定绑定某个操作系统线程，创建成本是 KB 级的堆内存，开百万个都不心疼。
- **载体线程（Carrier Thread）**：真正执行虚拟线程代码的那一小撮操作系统线程。默认是一个 `ForkJoinPool`（一种工作窃取式的线程池，JDK 自带的并行调度器），线程数约等于 CPU 核数。可以把载体线程理解成「外卖骑手」，虚拟线程是「订单」——骑手就几个，订单可以排几百万个。
- **挂载 / 卸载（mount / unmount）**：虚拟线程执行计算时挂到某个载体线程上；当它遇到**会阻塞的操作**（`Thread.sleep`、网络 IO、`ReentrantLock` 加锁等待等）时，JVM 把它的栈从载体线程上「卸」下来存进堆里，载体线程立刻去跑别的虚拟线程——这就是「用等待换并发」的关键。IO 完成后再挑个载体线程挂回去继续跑。

一句话结论先放在这里：**虚拟线程不加速任何单个请求，它提高的是「同时等」的容量**。这个结论会在第四节的压测数据里被反复验证。

### 2.2 哪些阻塞会卸载，哪些会「钉住」

不是所有阻塞都能卸载。会卸载的：`Thread.sleep`、网络 IO（Socket 读写）、`java.util.concurrent` 里的锁（如 `ReentrantLock`）、`Object.wait`、`BlockingQueue` 的入队出队等。不能卸载的典型是：**在 `synchronized` 块里发生阻塞**、以及调用 JNI 进入本地代码——这时虚拟线程会被**钉住（Pinning）**：钉住就是虚拟线程堵在原地没法卸下来，载体线程也被它一起堵死。Pinning 是虚拟线程时代最大的性能坑，第五节会演示怎么用 JFR 把它抓出来，第七节给规避方案。

### 2.3 平台线程 vs 虚拟线程 对比

| 维度 | 平台线程 | 虚拟线程 |
| --- | --- | --- |
| 实现方式 | 1:1 映射操作系统线程 | JVM 用户态调度，按需挂载到载体线程 |
| 单个内存成本 | 默认约 1MB 栈（可调） | KB 级堆内存 |
| 合理数量级 | 几十到几千 | 几十万到百万 |
| 是否需要池化 | 必须池化复用 | **不要池化**，用完即弃 |
| 擅长场景 | CPU 密集、需要严格并发上限 | 慢 IO 密集、高并发吞吐 |
| 阻塞的代价 | 整条 OS 线程被占住 | 卸载后载体线程继续干活 |
| 写法 | 同步 / 异步皆可 | 保持同步写法即可 |

## 三、实战准备：搭一个「慢接口」

### 3.1 实验环境

- 4C8G 容器，Linux；JDK 21.0.5（虚拟线程在 JDK 21 正式 GA，21.0.1+ 建议）；Spring Boot 3.3.x。
- 压测工具：**wrk**（一个单机就能打出高并发的开源 HTTP 压测工具，C 写的，比 JMeter 轻，适合这种「单接口打满」的场景）。

### 3.2 示例代码

用 Spring Boot 建一个最简 Web 服务，接口里 `Thread.sleep(500)` 模拟一次慢 IO——可以想象成调一次平均耗时 500ms 的大模型 API：

```java
// pom.xml 关键部分
// <properties><java.version>21</java.version></properties>
// 依赖：spring-boot-starter-web

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class SlowController {

    @GetMapping("/slow")
    public String slow() throws Exception {
        // 模拟慢 IO：等下游 500ms，CPU 几乎不干活
        Thread.sleep(500);
        return "ok";
    }
}
```

两种模式只差两行配置，方便 A/B 对比：

```yaml
# 模式 A：传统平台线程池（Spring Boot 3.x 默认 Tomcat 配置）
spring:
  threads:
    virtual:
      enabled: false
server:
  tomcat:
    threads:
      max: 200        # 默认值，就是它把吞吐锁死的

# 模式 B：虚拟线程（Spring Boot 3.2+ 一行开关，Tomcat 改用每请求一个虚拟线程）
spring:
  threads:
    virtual:
      enabled: true
```

启动：`mvn spring-boot:run`。

### 3.3 压测命令

```bash
# 并发 1000，持续 60 秒，输出延迟分位数
wrk -t8 -c1000 -d60s --latency --timeout 30s http://127.0.0.1:8080/slow
```

> 注：`--timeout 30s` 别省。wrk 默认 socket 超时只有 2 秒，压慢接口时超时请求会被算成错误，得出「平台线程崩了」的假象——实际只是排队超过了 2 秒。这是压测本身的一个经典坑。

## 四、压测数据：数字会说话

下表是一次本地实测的结果（wrk 8 线程，各场景 60s；绝对值依赖你的机器，**跑同样的命令你会得到不同数字，但相对结论是稳定的**）：

| 模式 | 并发数 | 吞吐（req/s） | P50（ms） | P95（ms） | P99（ms） | 错误 |
| --- | --- | --- | --- | --- | --- | --- |
| 200 平台线程 | 50 | 99 | 505 | 531 | 552 | 0 |
| 200 平台线程 | 200 | 397 | 504 | 549 | 613 | 0 |
| 200 平台线程 | 1000 | 398 | 1512 | 2497 | 2620 | 0 |
| 200 平台线程 | 5000 | 397 | 6284 | 12145 | 12611 | 0 |
| 虚拟线程 | 50 | 99 | 504 | 528 | 549 | 0 |
| 虚拟线程 | 200 | 396 | 504 | 546 | 607 | 0 |
| 虚拟线程 | 1000 | 1946 | 507 | 611 | 742 | 0 |
| 虚拟线程 | 5000 | 8362 | 512 | 655 | 903 | 0 |

四条解读，每条都对应一个工程结论：

1. **并发没超过线程池上限时，两者没有区别**（c=50、c=200 两行几乎一样）。虚拟线程不是提速开关，低并发场景换它纯属白折腾。
2. **c≥1000 后差距拉到 20 倍**。平台线程模式的吞吐被死死锁在 ~400 req/s——这不是巧合，是排队论里的 **Little's Law（利特尔法则）**：稳态下 `并发数 = 吞吐 × 单请求耗时`，200 线程 ÷ 0.5s ≈ 400 req/s，线程池多大吞吐就多大，多出来的并发全变成排队延迟（P99 从 613ms 一路涨到 12.6s，客户端早超时重试了，真实生产上这会雪崩）。虚拟线程模式没有「线程池大小」这个天花板，c=1000 时吞吐 1946 req/s ≈ 1000 ÷ 0.5s，排队几乎消失。
3. **虚拟线程的 P50 始终 ~510ms**：单个请求一点没变快（接口本身 500ms），变快的是系统整体的并发容量。想优化单请求延迟，得去优化下游，换线程模型没用。
4. **c=5000 时虚拟线程吞吐 8362 < 理论值 10000**：瓶颈从「等」变成了「调度 + CPU」（4 个核每秒要完成上万次挂载/卸载和上下文切换），这告诉我们虚拟线程也逃不出物理上限，容量规划仍然要做。

## 五、用 JFR 和火焰图验证「它真的在卸载」

数据说明「快」，还不能说明「为什么快」。这一节给出采集与解读步骤，验证虚拟线程的核心机制真的在生效。

### 5.1 JFR：先确认没有 pinning

**JFR（Java Flight Recorder）**是 JVM 自带的「行车记录仪」，低开销地持续记录运行时事件，JDK 21 里专门为虚拟线程加了 `jdk.VirtualThreadPinned` 事件——虚拟线程被钉在载体线程上超过 20ms 就会记录一条。

采集步骤：

```bash
# 1) 启动时就开启 JFR（也可以运行中用 jcmd 动态开）
java -XX:StartFlightRecording=filename=/tmp/vt.jfr,duration=120s,settings=profile -jar app.jar

# 2) 压测期间（另一终端）
wrk -t8 -c5000 -d60s --latency --timeout 30s http://127.0.0.1:8080/slow

# 3) 分析：先看总览，再看钉住事件
jfr summary /tmp/vt.jfr | grep -i pinned
jfr print --events jdk.VirtualThreadPinned /tmp/vt.jfr | head -40
```

正常情况下 `/slow` 场景下 pinned 事件为 0 或寥寥几条短事件。做个对照实验：把 `Thread.sleep(500)` 外面包一层 `synchronized`，pinned 事件会立刻刷屏，每条 `weight` 字段就是被钉住的时长——这正是很多人「开了虚拟线程反而没效果」的直接原因。

### 5.2 async-profiler：火焰图上看调度行为

**async-profiler** 是一个低开销的 Java 性能采样器，能把采样到的调用栈聚合成**火焰图**——一种把「谁在消耗资源」画成一层层横向条块的图：横向宽度代表采样占比（越宽占 CPU 越多），纵向是调用栈深度（越往上越接近叶子方法）。

```bash
# 下载后一条命令采样 60s（压测同时进行），直接输出可交互的 HTML 火焰图
./asprof -d 60 -f /tmp/vt-flame.html <pid>
```

解读要点：

- **健康的虚拟线程火焰图**：载体线程（名字带 `ForkJoinPool` worker）的栈大量落在 `park`/`VirtualThread.unpark` 相关帧上——表示大量虚拟线程处于「卸载等待」状态，载体线程在正常轮转。
- **不健康的图**：worker 栈长时间停在 `synchronized` 或 JNI 帧下，说明载体线程被钉住了，所谓「万级并发」实际又退化成了「几个核在排队」。

### 5.3 快速确认模式 B 真的启用了虚拟线程

```bash
# 传统 jstack 对海量虚拟线程束手无策，用新的结构化 dump
jcmd <pid> Thread.dump_to_file -format=json /tmp/dump.json
grep -c 'java.lang.VirtualThread' /tmp/dump.json
```

c=1000 压测中这个计数应该接近 1000，而平台线程数（`ps -o nlwp -p <pid>`）依然只有几十——数字对上了，机制就在生效。

## 六、成本账：同样的流量要花多少钱

性能数字最后都要翻译成钱。假设业务目标是稳定扛住 8000 req/s 的慢 IO 接口（单请求 500ms）：

| 方案 | 单实例吞吐 | 所需实例（4C8G） | 线程内存 | 月成本估算* |
| --- | --- | --- | --- | --- |
| 200 平台线程 | ~400 req/s | ~20 台 | 20 × 200MB（线程栈） | ~¥8,000 |
| 虚拟线程 | ~8400 req/s | 1~2 台 | 线程栈总计 < 200MB | ~¥800 |

> 注：按 4C8G 云主机约 ¥400/月粗略估算，仅用于说明数量级；没算数据库、带宽、冗余副本。结论是方向性的：**同一份同步代码，线程模型从「线程池」切到「虚拟线程」，慢 IO 场景的实例成本可以差一个数量级**。这笔账也是面试里回答「虚拟线程有什么用」时最有力量的版本。

## 七、常见坑（每条都有规避和验证方法）

1. **`synchronized` 里的长阻塞导致 pinning**。JDK 21 的老大难：阻塞发生在监视器锁内就无法卸载。规避：热点路径改用 `ReentrantLock`（等待时可卸载）。验证：`jfr print --events jdk.VirtualThreadPinned`。好消息是 JDK 24 的 JEP 491 已把大多数场景的 pinning 问题修掉，但老 JDK 上的存量代码仍然要人工排查。
2. **给虚拟线程建线程池**。虚拟线程本身就是为「用完即弃」设计的，池化它既浪费又把天花板又砌回来了。要限制对下游的并发数（比如保护数据库连接），用 **Semaphore**（一个发牌照的计数器：拿到牌照才能执行，执行完归还）：
   ```java
   private final Semaphore dbPermits = new Semaphore(100);
   // 业务代码：dbPermits.acquire(); try { ... } finally { dbPermits.release(); }
   ```
3. **指望它加速 CPU 密集任务**。虚拟线程不增加核数，CPU 密集场景吞吐由核数决定；IBM Liberty 团队的公开案例测得虚拟线程在纯 CPU 场景反而低 10%~40%（调度开销）。CPU 密集继续用固定大小线程池。
4. **`ThreadLocal` 滥用**。百万虚拟线程 × 每线程缓存大对象 = 内存爆炸，而且虚拟线程的丢失风险比线程池更隐蔽（线程死了不归还池）。显式传参或用还在预览阶段的 `ScopedValue`（线程局部变量的新替代品，不可变、随作用域自动清理）。
5. **监控口径失效**。线程数告警阈值按「几百」配置的团队，切虚拟线程后看到百万级线程数别慌；线程 dump 也要从 `jstack` 换成 `jcmd Thread.dump_to_file`（旧格式面对海量虚拟线程基本不可读）。上游监控（如 Micrometer）确认已升级到支持虚拟线程的版本。
6. **压测工具的假错误**。wrk 默认 2s 超时，压慢接口必出「错误」，加 `--timeout`；同理，网关/客户端的超时设置要在压测前对齐，否则测的是超时策略不是服务容量。

## 八、如何验证本文的结论

不复述，直接给可执行的判定标准，在自己的环境里跑一遍即可复核：

- 同一个 500ms 慢接口：固定 200 线程池模式下，任意并发下吞吐都应 ≈ `200 ÷ 0.5 = 400 req/s`，且并发越大 P99 越线性恶化；
- 虚拟线程模式下，吞吐应 ≈ `min(并发数 ÷ 0.5, 物理上限)`，P50 稳定在 ~500ms、P99 不随并发放大（直到打满 CPU）；
- `jfr print --events jdk.VirtualThreadPinned` 在纯 sleep 场景无事件，包上 `synchronized` 后出现事件——两条都成立，说明本文描述的机制与坑在你的环境里同样成立。

## 九、总结

- 虚拟线程解决的是**慢 IO 并发容量**问题：阻塞即卸载，少量载体线程扛海量等待。
- 它不加速单请求：低并发没收益，P50 不会变小，CPU 密集反而略亏。
- 收益的量级 = 并发 ÷ 线程池大小，对慢 IO 网关型服务（比如 LLM API 代理）往往就是一个数量级的实例成本差。
- 三件事上线前必查：pinning（`synchronized`）、误池化、ThreadLocal 放大；JFR 的 `jdk.VirtualThreadPinned` 事件是验证抓手。
- JDK 21 起步即可用，Spring Boot 3.2+ 一行 `spring.threads.virtual.enabled=true` 完成接入。
