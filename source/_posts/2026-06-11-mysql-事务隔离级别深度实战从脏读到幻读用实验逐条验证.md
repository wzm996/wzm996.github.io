<h1 id="背景：为什么搞懂隔离级别这么难？"><a href="#背景：为什么搞懂隔离级别这么难？" class="headerlink" title="背景：为什么搞懂隔离级别这么难？"></a>背景：为什么搞懂隔离级别这么难？</h1>

<p>先说结论：<strong>大多数人对隔离级别的理解停留在"背八股文"阶段——知道有 4 种级别、知道各自防什么问题，但一旦线上出了诡异的数据不一致，根本不知道从哪下手排查</strong>。</p>

<p>你可能遇到过这种场景：</p>
<ul>
<li>A 事务刚插入一行数据，B 事务居然能读到（或者读不到）——到底算不算 bug？</li>
<li><code>UPDATE</code> 的时候报 <code>Lock wait timeout exceeded</code>，但你看代码里明明没显式加锁啊？</li>
<li>生产库从 <code>READ COMMITTED</code> 升到 <code>REPEATABLE READ</code>，结果死锁数量暴增——为什么？</li>
</ul>

<p>这些问题的根因都指向同一个东西：<strong>InnoDB 的并发控制机制</strong>。而要理解它，必须亲手做实验——光看文档是看不透的。</p>

<p><strong>MVCC</strong>（Multi-Version Concurrency Control，多版本并发控制）：InnoDB 实现的一种并发控制方案，核心思想是"读不加锁，通过维护数据的历史版本来实现一致性读"。每个事务看到的是自己启动时刻（或第一条 SQL 执行时刻）的数据快照，所以普通 SELECT 不会阻塞其他事务的写操作。<strong>但 MVCC 只对"快照读"生效，"当前读"还是要加锁的</strong>——这个区别是理解隔离级别的关键。</p>

<p><strong>当前读 vs 快照读</strong>：</p>
<ul>
<li><strong>快照读</strong>：普通的 <code>SELECT</code>（不加锁），读取的是 MVCC 快照版本</li>
<li><strong>当前读</strong>：<code>SELECT ... FOR UPDATE / FOR SHARE</code>、<code>INSERT/UPDATE/DELETE</code>，读取的是最新版本并加锁</li>
</ul>

<p>本文所有实验基于以下环境：</p>
<pre><code class="language-text">MySQL 8.0.x（5.7 大部分适用，RR 下 Gap Lock 行为略有差异）
引擎：InnoDB
字符集：utf8mb4
默认隔离级别：REPEATABLE-READ（MySQL 默认值）
</code></pre>

<p>注意上表里的"幻读"列——<strong>MySQL 的 REPEATABLE READ 对幻读的处理是个特殊存在</strong>。SQL 标准只要求 RR 防不可重复读，不要求防幻读；但 InnoDB 在 RR 下通过 MVCC + Next-Key Lock 做到了<strong>快照读防幻读 + 当前读也防幻读</strong>（大部分场景）。这也是为什么 MySQL 敢把 RR 当默认级别的原因。</p>

<h2 id="实验方法说明"><a href="#实验方法说明" class="headerlink" title="实验方法说明"></a>实验方法说明</h2>

<p>所有实验都需要<strong>两个 MySQL 客户端连接</strong>（模拟两个并发事务）。你可以用：</p>
<ul>
<li>两个终端窗口分别登录 mysql</li>
<li>或者用 Navicat/DBeaver 开两个查询窗口</li>
<li>或者用 Docker 起两个容器（不推荐，同一实例两个连接就够了）</li>
</ul>

<pre><code class="language-bash"># 终端 A（事务 A）
mysql -u root -p your_database

# 终端 B（事务 B）
mysql -u root -p your_database
</code></pre>

<p><strong>关键命令速查</strong>：</p>
<pre><code class="language-sql">-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置会话级隔离级别（推荐，不影响其他连接）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 手动开启事务（关闭自动提交）
SET autocommit = 0;
-- 或者
START TRANSACTION;

-- 提交 / 回滚
COMMIT;
ROLLBACK;

-- 查看当前锁等待情况（需 SUPER 权限）
SHOW ENGINE INNODB STATUS\G

-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS\G
-- 然后搜索 "LATEST DETECTED DEADLOCK" 段落
</code></pre>

<h1 id="实验一：READ-UNCOMMITTED——脏读复现"><a href="#实验一：READ-UNCOMMITTED——脏读复现" class="headerlink" title="实验一：READ UNCOMMITTED——脏读复现"></a>实验一：READ UNCOMMITTED —— 脏读复现</h1>

<p><strong>脏读</strong>（Dirty Read）：一个事务读到了另一个事务<strong>未提交</strong>的数据。如果那个事务回滚了，你读到的就是"脏数据"——从未真正持久化的垃圾数据。</p>

<h2 id="步骤"><a href="#步骤" class="headerlink" title="步骤"></a>步骤</h2>

<p>两个终端都执行：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET autocommit = 0;
</code></pre>

<p><strong>终端 A（事务 A）</strong>：</p>
<pre><code class="language-sql">-- 查看张三的余额
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 1000.00

-- 张三转账 500 给李四（未提交）
UPDATE account SET balance = balance - 500 WHERE name = '张三';
UPDATE account SET balance = balance + 500 WHERE name = '李四';
-- 注意：此时不要 COMMIT！
</code></pre>

<p><strong>终端 B（事务 B）</strong>：</p>
<pre><code class="language-sql">-- 在 A 未提交时，直接读取
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 500.00 ← 读到了未提交的数据！！！

SELECT * FROM account WHERE name = '李四';
-- 结果：balance = 2500.00 ← 同样是脏数据
</code></pre>

<p><strong>终端 A（回滚）</strong>：</p>
<pre><code class="language-sql">ROLLBACK;
</code></pre>

<p><strong>终端 B（再次读取）</strong>：</p>
<pre><code class="language-sql">SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 1000.00 ← 回到了原始值
</code></pre>

<h2 id="结论"><a href="#结论" class="headerlink" title="结论"></a>结论</h2>

<p>事务 B 在 A 回滚前读到的 500.00 就是<strong>脏数据</strong>——这笔转账最终没有生效，但 B 已经拿这个值去做后续计算了（比如放贷审批、库存扣减……后果不堪设想）。</p>

<p><strong>生产建议</strong>：除非你有极其特殊的业务场景（比如某些统计报表容忍脏读以换取极致性能），否则<strong>永远不要使用 READ UNCOMMITTED</strong>。Oracle 甚至压根不支持这个级别。</p>

<h1 id="实验二：READ-COMMITTED——不可重复读复现"><a href="#实验二：READ-COMMITTED——不可重复读复现" class="headerlink" title="实验二：READ COMMITTED——不可重复读复现"></a>实验二：READ COMMITTED —— 不可重复读复现</h2>

<p><strong>不可重复读</strong>（Non-Repeatable Read）：同一个事务内，两次读取同一行数据得到了不同的结果——因为另一个事务在你两次读取之间修改并提交了这行数据。</p>

<p>RC 是 Oracle、SQL Server、PostgreSQL 的默认级别，也是大多数应用的选择。</p>

<h2 id="步骤-1"><a href="#步骤-1" class="headerlink" title="步骤"></a>步骤</h2>

<p>两个终端都执行：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET autocommit = 0;
</code></pre>

<p><strong>终端 A（事务 A）</strong>：</p>
<pre><code class="language-sql">-- 第一次读取
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 1000.00
</code></pre>

<p><strong>终端 B（事务 B）</strong>：</p>
<pre><code class="language-sql">UPDATE account SET balance = 800 WHERE name = '张三';
COMMIT;  -- 注意：这次提交了！
</code></pre>

<p><strong>终端 A（第二次读取）</strong>：</p>
<pre><code class="language-sql">-- 同一个事务内，再次读取
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 800.00 ← 变了！！！
</code></pre>

<h2 id="发生了什么？"><a href="#发生了什么？" class="headerlink" title="发生了什么？"></a>发生了什么？</h2>

<p>在 RC 级别下，每次 <code>SELECT</code> 都会生成一个新的 Read View（读视图），所以每次 SELECT 都能看到别的事务最新提交的数据。<strong>这就是"不可重复读"的本质——你的事务没有自己的稳定快照</strong>。</p>

<p>对比一下后面 RR 的行为，你会明显感受到差异。</p>

<h2 id="什么时候不可重复读会成为问题？"><a href="#什么时候不可重复读会成为问题？" class="headerlink" title="什么时候不可重复读会成为问题？"></a>什么时候不可重复读会成为问题？</p>

<p>典型场景：<strong>"读取-修改-写回"（Read-Modify-Write）模式</strong>。</p>

<pre><code class="language-java">// Java 伪代码：银行扣款
BigDecimal balance = accountMapper.selectBalance("张三");  // 第一次读：1000
// ← 此时另一个事务把余额改成了 800 并提交
accountMapper.updateBalance("张三", balance.subtract(new BigDecimal(200)));  // 写回：800
// 问题：实际应该扣 200，变成了 1000 - 200 = 800（覆盖了别人的修改）
// 正确结果应该是：800 - 200 = 600
</code></pre>

<p>解决方案：<strong>用 <code>SELECT ... FOR UPDATE</code>（当前读）或 CAS（Compare-And-Swap）乐观锁</strong>。后文会详细讲。</p>

<h1 id="实验三：REPEATABLE-READ——MVCC-如何实现可重复读"><a href="#实验三：REPEATABLE-READ——MVCC-如何实现可重复读" class="headerlink" title="实验三：REPEATABLE READ —— MVCC 如何实现可重复读"></a>实验三：REPEATABLE READ —— MVCC 如何实现可重复读</h3>

<p>现在切换到 MySQL 的默认级别，看看同样操作会有什么不同。</p>

<h2 id="步骤-2"><a href="#步骤-2" class="headerlink" title="步骤"></a>步骤</h2>

<p>两个终端都执行：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET autocommit = 0;
</code></pre>

<p><strong>终端 A（事务 A）</strong>：</p>
<pre><code class="language-sql">-- 第一次读取
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 1000.00（假设前面 RC 实验已经 ROLLBACK 或重置了）
</code></pre>

<p><strong>终端 B（事务 B）</strong>：</p>
<pre><code class="language-sql">UPDATE account SET balance = 888 WHERE name = '张三';
COMMIT;
</code></pre>

<p><strong>终端 A（第二次读取）</strong>：</p>
<pre><code class="language-sql">-- 同一个事务内，再次读取
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 1000.00 ← 没变！MVCC 生效了！
</code></pre>

<p><strong>终端 A（提交后再读）</strong>：</p>
<pre><code class="language-sql">COMMIT;

-- 新事务中读取
SELECT * FROM account WHERE name = '张三';
-- 结果：balance = 888.00 ← 新事务看到了最新提交的数据
</code></pre>

<h2-id="MVCC-底层原理（通俗版）"><a href="#MVCC-底层原理（通俗版）" class="headerlink" title="MVCC 底层原理（通俗版）"></a>MVCC 底层原理（通俗版）</h2>

<p>InnoDB 的每一行数据除了用户定义的字段外，还隐藏了三个字段：</p>
<ul>
<li><code>DB_TRX_ID</code>：最近修改这行数据的事务 ID</li>
<li><code>DB_ROLL_PTR</code>：回滚指针，指向上一个版本的 undo log 记录</li>
<li><code>DB_ROW_ID</code>：隐藏主键（如果表没有主键，InnoDB 自动生成）</li>
</ul>

<p>当一个事务开始时，InnoDB 会创建一个 <strong>Read View</strong>（读视图），里面记录了：</p>
<ul>
<li><code>m_ids</code>：当前活跃（未提交）的事务 ID 列表</li>
<li><code>min_trx_id</code>：m_ids 里最小的事务 ID</li>
<li><code>max_trx_id</code>：下一个将要分配的事务 ID（即当前最大事务 ID + 1）</li>
<li><code>creator_trx_id</strong>：创建该 Read View 的事务自身 ID</li>
</ul>

<p>当事务 A 做 SELECT 时，判断某行数据是否可见的逻辑是：</p>
<ol>
<li>如果 <code>DB_TRX_ID == creator_trx_id</code> → 自己改的，可见</li>
<li>如果 <code>DB_TRX_ID &lt; min_trx_id</code> → 在 Read View 创建前就提交了，可见</li>
<li>如果 <code>DB_TRX_ID &gt;= max_trx_id</code> → 在 Read View 创建后才开始的，不可见</li>
<li>如果在 m_ids 里 → 还没提交，不可见（通过回滚指针找上一个版本）</li>
<li>如果不在 m_ids 里 → 已提交，可见</li>
</ol>

<p>这就是为什么在 RR 级别下，<strong>Read View 只在事务第一次 SELECT 时生成一次</strong>，之后所有 SELECT 都用同一个快照——从而实现了可重复读。而 RC 级别下，每条 SELECT 都会重新生成 Read View。</p>

<h1 id="实验四：幻读——Next-Key-Lock-如何封杀“幽灵行”"><a href="#实验四：幻读——Next-Key-Lock-如何封杀“幽灵行”" class="headerlink" title="实验四：幻读 —— Next-Key Lock 如何封杀“幽灵行”"></a>实验四：幻读 —— Next-Key Lock 如何封杀"幽灵行"</h1>

<p><strong>幻读</strong>（Phantom Read）：同一个事务内，两次范围查询得到的行数不同——因为另一个事务在你两次查询之间插入（或删除）了符合条件的新行。这些新行就像"幽灵"一样突然冒出来了。</p>

<p>幻读比不可重复读更隐蔽：你查的是一批数据，不是单行，所以一般的行级锁根本拦不住插入操作。</p>

<h2 id="快照读下的幻读（RR-其实防住了）"><a href="#快照读下的幻读（RR-其实防住了）" class="headerlink" title="快照读下的幻读（RR 其实防住了）"></a>快照读下的幻读（RR 其实防住了）</h2>

<p>两个终端都设为 RR：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET autocommit = 0;
</code></pre>

<p><strong>终端 A（事务 A）</strong>：</p>
<pre><code class="language-sql">-- 查询研发部的所有员工
SELECT * FROM salary WHERE dept = '研发部';
-- 结果：4 行（王五、赵六、吴十、冯十二）
</code></pre>

<p><strong>终端 B（事务 B）</strong>：</p>
<pre><code class="language-sql">-- 插入一个新的研发部员工
INSERT INTO salary (emp_name, dept, amount) VALUES ('新员工', '研发部', 20000);
COMMIT;
</code></pre>

<p><strong>终端 A（再次查询）</strong>：</p>
<pre><code class="language-sql">-- 同一个事务内，再次范围查询
SELECT * FROM salary WHERE dept = '研发部';
-- 结果：仍然是 4 行！← MVCC 快照读防住了幻读
</code></p>

<p>看起来很完美对吧？<strong>但这只是快照读的情况</strong>。如果我们用的是当前读呢？</p>

<h2 id="当前读下的幻读（Next-Key-Lock-登场）"><a href="#当前读下的幻读（Next-Key-Lock-登场）" class="headerlink" title="当前读下的幻读（Next-Key Lock 登场）"></a>当前读下的幻读（Next-Key Lock 登场）</h2>

<p>重新开始（确保数据干净）：</p>

<p><strong>终端 A（事务 A）</strong>：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET autocommit = 0;

-- 当前读：锁定所有研发部的记录
SELECT * FROM salary WHERE dept = '研发部' FOR UPDATE;
-- 结果：4 行被锁定
</code></pre>

<p><strong>终端 B（事务 B）</strong>：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET autocommit = 0;

-- 尝试插入新的研发部员工
INSERT INTO salary (emp_name, dept, amount) VALUES ('新员工', '研发部', 20000);
-- 结果：阻塞！！！（等待 A 释放锁）
</code></pre>

<p>如果 B 等待超过 <code>innodb_lock_wait_timeout</code>（默认 50 秒），会报错：</p>
<pre><code class="language-text">ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
</code></pre>

<p><strong>这说明什么？</strong>说明 <code>SELECT ... FOR UPDATE</code> 不只是锁定了已有的 4 行记录，还<strong>锁定了它们之间的间隙</strong>——让 B 无法在这个范围内插入新行。这就是 <strong>Next-Key Lock</strong>（Record Lock + Gap Lock）的威力。</p>

<h2 id="Next-Key-Lock-拆解"><a href="#Next-Key-Lock-拆解" class="headerlink" title="Next-Key Lock 拆解"></a>Next-Key Lock 拆解</h2>

<p>InnoDB 的锁按粒度分三种：</p>

<table>
<thead>
<tr>
<th>锁类型</th>
<th>作用对象</th>
<th>作用</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Record Lock</strong>（记录锁）</td>
<td>索引记录本身</td>
<td>锁住确切的某一行</td>
</tr>
<tr>
<td><strong>Gap Lock</strong>（间隙锁）</td>
<td>索引记录之间的间隙</td>
<td>锁住两行之间的"空隙"，防止 INSERT</td>
</tr>
<tr>
<td><strong>Next-Key Lock</strong></td>
<td>记录 + 左侧间隙</td>
<td>Record Lock + Gap Lock 的组合，左开右闭区间</td>
</tr>
</tbody>
</table>

<p>你可以用以下方式查看锁的情况：</p>
<pre><code class="language-sql">-- 在终端 A 执行 FOR UPDATE 后，另开终端 C 查看
SELECT 
  r.trx_id AS waiting_trx,
  r.trx_mysql_thread_id AS waiting_thread,
  r.trx_query AS waiting_query,
  b.trx_id AS blocking_trx,
  b.trx_mysql_thread_id AS blocking_thread,
  b.trx_query AS blocking_query
FROM information_schema.INNODB_LOCK_WAITS w
JOIN information_schema.INNODB_LOCKS r ON w.requested_lock_id = r.lock_id
JOIN information_schema.INNODB_LOCKS b ON w.blocking_lock_id = b.lock_id\G
</code></pre>

<p>或者在终端 A 执行 <code>SHOW ENGINE INNODB STATUS\G</code>，搜索 <code>TRANSACTIONS</code> 段落，可以看到类似这样的锁信息：</p>
<pre><code class="language-text">------- TRX HAS BEEN WAITING 5 SEC FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 60 page no 4 n bits 576 INDEX idx_dept_amount of table `test`.`salary` 
trx id 12345 lock_mode X locks gap before rec insert intention waiting
</code></pre>

<p>关键字解读：</p>
<ul>
<li><code>lock_mode X locks gap before rec insert intention waiting</code>：B 事务想插入意向插入锁（Insert Intention Lock），但在 Gap Lock 处被阻塞</li>
<li><code>insert intention</code>：这是插入操作的特有锁类型，表示"我想往某个间隙里插一条记录"</li>
</ul>

<h2 id="压测脚本（Java-JDBC）"><a href="#压测脚本（Java-JDBC）" class="headerlink" title="压测脚本（Java JDBC）"></a>压测脚本（Java JDBC）</h2>

<pre><code class="language-java">// BenchIsolationLevel.java — 简易压测
// 编译：javac BenchIsolationLevel.java
// 运行：java BenchIsolationLevel jdbc:mysql://localhost:3306/test user password

import java.sql.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class BenchIsolationLevel {
    static final int THREADS = 20;          // 并发线程数
    static final int OPS_PER_THREAD = 500; // 每线程操作数
    static final String ISOLATION = args.length > 2 ? args[2] : "REPEATABLE_READ";

    public static void main(String[] args) throws Exception {
        String url = args[0];
        String user = args[1];

        ExecutorService pool = Executors.newFixedThreadPool(THREADS);
        AtomicLong totalOps = new AtomicLong(0);
        AtomicLong totalMs = new AtomicLong(0);

        long start = System.nanoTime();

        for (int t = 0; t < THREADS; t++) {
            pool.submit(() -> {
                try (Connection conn = DriverManager.getConnection(url, user, "")) {
                    switch (ISOLATION) {
                        case "READ_UNCOMMITTED":
                            conn.setTransactionIsolation(Connection.TRANSACTION_READ_UNCOMMITTED); break;
                        case "READ_COMMITTED":
                            conn.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED); break;
                        case "REPEATABLE_READ":
                        default:
                            conn.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ); break;
                    }
                    conn.setAutoCommit(false);

                    PreparedStatement sel = conn.prepareStatement(
                        "SELECT * FROM bench WHERE val BETWEEN ? AND ?");
                    PreparedStatement upd = conn.prepareStatement(
                        "UPDATE bench SET val = val + 1 WHERE id = ?");

                    Random rnd = new Random();
                    for (int i = 0; i < OPS_PER_THREAD; i++) {
                        conn.beginTransaction();  // JDBC 没有 beginTxn，靠 setAutoCommit(false) + 首条 SQL 开始事务

                        int lo = rnd.nextInt(999);
                        sel.setInt(1, lo);
                        sel.setInt(2, lo + 20);
                        ResultSet rs = sel.executeQuery();
                        while (rs.next()) { /* read */ }

                        upd.setLong(1, 1L + rnd.nextInt(100000));
                        upd.executeUpdate();

                        conn.commit();
                        totalOps.incrementAndGet();
                    }
                } catch (Exception e) {
                    System.err.println("Error: " + e.getMessage());
                }
            });
        }

        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.MINUTES);
        long elapsed = (System.nanoTime() - start) / 1_000_000;

        System.out.println("=== " + ISOLATION + " ===");
        System.out.println("Threads: " + THREADS);
        System.out.println("Ops/thread: " + OPS_PER_THREAD);
        System.out.println("Total ops: " + totalOps.get());
        System.out.println("Elapsed: " + elapsed + "ms");
        System.out.printf("Throughput: %.0f ops/sec%n", totalOps.get() * 1000.0 / elapsed);
        System.out.printf("Avg latency: %.2f ms/op%n", (double)elapsed / totalOps.get());
    }
}
</code></pre>

<h1 id="实验六：死锁复现——Gap-Lock-的代价"><a href="#实验六：死锁复现——Gap-Lock-的代价" class="headerlink" title="实验六：死锁复现 —— Gap Lock 的代价"></a>实验六：死锁复现 —— Gap Lock 的代价</h1>

<p>RR 下的 Gap Lock 能防止幻读，但也有副作用：<strong>更容易死锁</strong>。下面是一个经典的死锁复现场景。</p>

<h2 id="步骤-3"><a href="#步骤-3" class="headerlink" title="步骤"></a>步骤</h2>

<p>确保在 RR 隔离级别下：</p>
<pre><code class="language-sql">SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET autocommit = 0;
</code></pre>

<p>假设 <code>salary</code> 表有以下数据（按 <code>idx_dept_amount</code> 索引排列）：</p>
<pre><code class="language-text">研发部 | 15000  (id=1)
研发部 | 16000  (id=6)
研发部 | 17000  (id=8)
研发部 | 18000  (id=2)
</code></pre>

<p><strong>终端 A（事务 A）</strong>：</p>
<pre><code class="language-sql">-- 插入新行（需要在研发部金额 16000~17000 之间的间隙加 Insert Intention Lock）
INSERT INTO salary (emp_name, dept, amount) VALUES ('A', '研发部', 16500);
-- 成功，暂不提交
</code></pre>

<p><strong>终端 B（事务 B）</strong>：</p>
<pre><code class="language-sql">-- 插入到同一个间隙
INSERT INTO salary (emp_name, dept, amount) VALUES ('B', '研发部', 16500);
-- 阻塞（等 A 的 Gap Lock）
</code></p>

<p><strong>终端 A（尝试插入 B 想要的位置附近）</strong>：</p>
<pre><code class="language-sql">-- A 尝试插入另一行，可能与 B 等待的间隙冲突
INSERT INTO salary (emp_name, dept, amount) VALUES ('C', '研发部', 16600);
-- 如果时机恰当，这里可能触发死锁检测
</code></pre>

<p>当死锁被检测到时，MySQL 会自动回滚其中一个事务：</p>
<pre><code class="language-text">ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
</code></pre>

<pre><code class="language-sql">SHOW ENGINE INNODB STATUS\G

<h2 id="如何减少死锁"><a href="#如何减少死锁" class="headerlink" title="如何减少死锁"></a>如何减少死锁</h2>

<ol>
<li><strong>统一访问顺序</strong>：所有事务按相同顺序访问表和索引（如总是按 id 升序）</li>
<li><strong>缩短事务长度</strong>：事务里尽量少做事，快速提交</li>
<li><strong>考虑降级到 RC</strong>：如果你的业务不需要防幻读，RC 下没有 Gap Lock，死锁概率大幅降低</li>
<li><strong>加合理的重试机制</strong>：捕获 <code>Deadlock found</code> 异常后自动重试（大多数 ORM 框架支持）</li>
</ol>

<h2 id="选型决策树"><a href="#选型决策树" class="headerlink" title="选型决策树"></a>选型决策树</h2>

<pre><code>你的业务是否需要"同一个事务内多次读取结果一致"？

<h1 id="常见坑与误区"><a href="#常见坑与误区" class="headerlink" title="常见坑与误区"></a>常见坑与误区</h1>

<h3 id="误区1：“RR-能完全防止幻读”"><a href="#误区1：“RR-能完全防止幻读”" class="headerlink" title="误区1：“RR 能完全防止幻读”"></a>误区 1："RR 能完全防止幻读"</h3>

<p><strong>真相</strong>：RR 的 MVCC 只能防止<strong>快照读</strong>的幻读。对于 <code>SELECT ... FOR UPDATE / LOCK IN SHARE MODE</code> 这种当前读，InnoDB 靠 Next-Key Lock 来防。但如果你的 SQL 没走索引（全表扫描），Next-Key Lock 会退化为对整个表的间隙锁——并发能力急剧下降。</p>

<h3 id="误区2：“默认级别就是最好的”"><a href="#误区2：“默认级别就是最好的”" class="headerlink" title="误区2：“默认级别就是最好的”"></a>误区 2："默认级别就是最好的"</h3>

<p><strong>真相</strong>：MySQL 默认 RR 是为了兼容性和安全性做的保守选择。很多互联网公司（阿里、字节等）在生产环境中会将核心业务的隔离级别<strong>降级为 RC</strong>，配合<strong>乐观锁</strong>来解决并发问题。原因很简单：RC 下死锁少、锁开销小、吞吐更高。</p>

<h3 id="误区3：“SET-SESSION-就能全局生效”"><a href="#误区3：“SET-SESSION-就能全局生效”" class="headerlink" title="误区3：“SET SESSION 就能全局生效”"></a>误区 3："SET SESSION 就能全局生效"</h3>

<p><strong>真相</strong>：<code>SET SESSION</code> 只影响<strong>当前连接</strong>。如果要修改全局默认值，需要 <code>SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;</code> 并且新连接才会生效。在 Spring Boot + HikariCP 场景下，连接池里的每个连接都是独立的 session，所以要么在 JDBC URL 加参数 <code>?transactionIsolation=READ_COMMITTED</code>，要么在代码层面控制。</p>

<h3 id="误区4：“autocommit=1-就没有事务问题了”"><a href="#误区4：“autocommit=1-就没有事务问题了”" class="headerlink" title="误区4：“autocommit=1 就没有事务问题了”"></a>误区 4："autocommit=1 就没有事务问题了"</h3>

<p><strong>真相</strong>：<code>autocommit=1</code> 只是说每条 SQL 自动包裹在一个独立事务里，并不是"没有事务"。每条 <code>UPDATE</code> 仍然有自己的隔离级别、自己的 MVCC Read View。而且多条 SQL 之间的原子性完全没有保障——第一条成功第二条失败怎么办？</p>

<h3 id="误区5：“SERIALIZABLE-最安全所以应该用它”"><a href="#误区5：“SERIALIZABLE-最安全所以应该用它”" class="headerlink" title="误区5：“SERIALIZABLE 最安全所以应该用它”"></a>误区 5："SERIALIZABLE 最安全所以应该用它"</h3>

<p><strong>真相</strong>：SERIALIZABLE 在 InnoDB 中的实现是对所有 <code>SELECT</code> 隐式加 <code>SHARE MODE</strong>（共享锁），基本上退化为串行执行。除非你的系统 QPS 极低且一致性要求极高（如金融核心账务），否则用 SERIALIZABLE 等于自废武功。</p>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>

<p>我们用 6 个实验覆盖了 MySQL 4 种事务隔离级别的核心行为：</p>

<table>
<thead>
<tr>
<th>实验</th>
<th>内容</th>
<th>关键结论</th>
</tr>
</thead>
<tbody>
<tr>
<td>实验一</td>
<td>READ UNCOMMITTED 脏读</td>
<td>能读到未提交数据，生产禁用</td>
</tr>
<tr>
<td>实验二</td>
<td>READ COMMITTED 不可重复读</td>
<td>每次 SELECT 新快照，同事务内读可能不一致</td>
</tr>
<tr>
<td>实验三</td>
<td>REPEATABLE READ MVCC</td>
<td>Read View 复用实现可重复读</td>
</tr>
<tr>
<td>实验四</td>
<td>幻读与 Next-Key Lock</td>
<td>快照读靠 MVCC，当前读靠 Next-Key Lock</td>
</tr>
<tr>
<td>实验五</td>
<td>RC vs RR 性能对比</td>
<td>RR 因 Gap Lock 吞吐略低 ~10-15%，死锁略多</td>
</tr>
<tr>
<td>实验六</td>
<td>死锁复现与分析</td>
<td>Gap Lock 是双刃剑，可用降级到 RC 或统一顺序缓解</td>
</tr>
</tbody>
</table>

<p>记住一句话：<strong>没有银弹隔离级别，只有最适合你业务场景的选择</strong>。理解底层机制（MVCC / Read View / Next-Key Lock / Gap Lock），才能在出问题时快速定位根因，而不是盲目调参。</p>
