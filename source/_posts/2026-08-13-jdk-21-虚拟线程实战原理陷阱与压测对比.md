<blockquote><p>**虚拟线程（Virtual Thread）** 是 JDK 21 正式引入的轻量级线程实现，由 JVM 调度而非操作系统。<br>它解决的核心问题是：<strong>平台线程（Platform Thread，即我们用了多年的 <code>new Thread()</code>）太重了</strong>——栈内存默认 1MB、调度依赖 OS 上下文切换、数量上不去。<br>虚拟线程把"线程"这个概念重新做了一遍：创建几乎零成本、百万级并发不再是梦、但有一堆隐藏陷阱等着你踩。</p></blockquote>

<!-- more -->

<h1 id="背景：为什么需要虚拟线程"><a href="#背景：为什么需要虚拟线程" class="headerlink" title="背景：为什么需要虚拟线程"></a>背景：为什么需要虚拟线程</h1>

<p>在聊虚拟线程之前，我们先回顾一下老朋友——<strong>平台线程（Platform Thread）</strong>的痛点。</p>

<p><strong>平台线程</strong>就是 JDK 21 之前我们一直用的线程，底层直接映射到操作系统的内核线程（Kernel Thread）。它的几个硬伤：</p>

<table>
<thead>
<tr><th>问题</th><th>具体表现</th><th>影响</th></tr>
</thead>
<tbody>
<tr><td>栈内存重</td><td>默认每个线程栈 <code>-Xss1m</code>（1MB）</td><td>1000 个线程 ≈ 1GB 内存</td></tr>
<tr><td>创建成本高</td><td>需要系统调用、OS 调度器参与</td><td>频繁创建/销毁开销大</td></tr>
<tr><td>调度不可控</td><td>OS 抢占式调度，时间片不透明</td><td>无法针对业务优先级精细控制</td></tr>
<tr><td>数量天花板低</td><td>受限于内存和 CPU 上下文切换开销</td><td>单机几千个就是极限</td></tr>
</tbody>
</table>

<p>所以过去十几年，我们发明了<strong>线程池（ThreadPoolExecutor）</strong>来复用线程，又搞出了<strong>异步非阻塞（CompletableFuture / Reactor）</strong>来绕过线程数限制。但这两套方案都有代价：</p>

<ul>
<li><strong>线程池</strong>：本质上是"用空间换时间"，线程还是那么多，只是复用了；而且线程池参数调优本身就是一门玄学（核心线程数设多少？队列选哪种？拒绝策略怎么配？）。</li>
<li><strong>异步编程</strong>：性能确实好，但代码写成"回调地狱"，或者被 <code>thenCompose</code>/<code>flatMap</code> 嵌套到怀疑人生，调试困难度直线上升。</li>
</ul>

<p><strong>虚拟线程</strong>的思路完全不同：它不试图优化平台线程，而是<strong>重新定义"线程"</strong>——让线程变得像对象一样廉价。</p>

<h2 id="虚拟线程核心原理"><a href="#虚拟线程核心原理" class="headerlink" title="虚拟线程核心原理"></a>虚拟线程核心原理</h2>

<p>虚拟线程的设计哲学可以用一句话概括：</p>

<blockquote><p><strong>"用户态调度 + 载体线程挂载（Mount/Unmount）"</strong></p></blockquote>

<p>关键概念拆解：</p>

<ul>
<li><strong>虚拟线程（Virtual Thread）</strong>：JVM 层面的轻量级线程，由 <code>java.lang.VirtualThread</code> 实现。创建它不需要 OS 参与就像 new 一个普通对象一样快。</li>
<li><strong>载体线程（Carrier Thread）</strong>：实际干活的平台线程（ForkJoinPool 中的工人线程）。虚拟线程会被"挂载（Mount）"到载体线程上执行 CPU 操作。</li>
<li><strong>Continuation（续体）</strong>：虚拟线程的核心魔法。当虚拟线程执行阻塞 I/O 操作（比如 <code>socket.read()</code>）时，JVM 会把它的调用栈<strong>拷贝下来存到堆内存里</strong>，然后把虚拟线程从载体线程上"卸载（Unmount）"掉，让载体线程去跑别的虚拟线程。等 I/O 完成了，再找个载体线程把栈恢复回来继续执行。</li>
</ul>

<pre><code>注：这个过程对开发者完全透明。你写的代码看起来和以前一样是同步的，
但运行时 JVM 在背后帮你做了"挂起→保存状态→恢复"的全套操作。
这就是虚拟线程最厉害的地方——<strong>同步的写法，异步的性能</strong>。
</code></pre>

<p>用一个类比帮助理解：</p>

<ul>
<li><strong>平台线程</strong> = 公司正式员工，每人一个工位（栈内存），招人/辞退要走 HR 流程（OS 调度），工位有限所以人数有限。</li>
<li><strong>虚拟线程</strong> = 外包任务，公司只有几十个正式员工（载体线程），但可以接几万个外包任务。正式员工忙不过来时就把手头的任务先放一边（Unmount），去处理别的任务；等之前的任务有反馈了（I/O 完成），再捡起来继续做。</li>
</ul>

<h3 id="数据解读"><a href="#数据解读" class="headerlink" title="数据解读"></a>数据解读</h3>

<ol>
<li><strong>小线程池（200+队列）惨败</strong>：因为只有 200 个线程在干活，2000 个任务中大部分在排队等待，吞吐量只有虚拟线程的 <strong>1/10</strong>。这是生产环境最常见的瓶颈——线程池不够大但又不敢开太大。</li>

<li><strong>大线程池（2000）和虚拟线程吞吐接近</strong>：在纯 I/O 密集场景下两者都能打满并发，毕竟瓶颈在网络等待而不是 CPU。</li>

<li><strong>内存差距惊人</strong>：2000 个平台线程吃掉了 <strong>2.1 GB</strong> 内存（每个线程栈 ~1MB），而 2000 个虚拟线程只用了 <strong>45 MB</strong>。如果并发涨到 10000？平台线程直接 OOM，虚拟线程依然淡定。</li>

<li><strong>P99 延迟更稳</strong>：虚拟线程的 P99（58ms）比大线程池（68ms）更低且更稳定，因为载体线程的调度策略针对 I/O 等待做了优化。</li>
</ol>

<pre><code>关键结论：
✅ I/O 密集型场景 → 虚拟线程完胜（高吞吐 + 低内存 + 低延迟）
⚠️ CPU 密集型场景 → 两者接近（瓶颈在 CPU 核心数）
❌ 不要在虚拟线程上跑 synchronized 重计算（后面细说为什么）
</code></pre>

<h1 id="常见坑与误区（重点）"><a href="#常见坑与误区（重点）" class="headerlink" title="常见坑与误区（重点）"></a>常见坑与误区（重点）</h1>

<p>虚拟线程虽好，但不是银弹。以下是我整理的 <strong>6 个高频踩坑点</strong>，每一个都在生产环境见过翻车案例。</p>

<h2 id="坑-1：synchronized-导致-Pinning（线程钉住）"><a href="#坑-1：synchronized-导致-Pinning（线程钉住）" class="headerlink" title="坑 1：synchronized 导致 Pinning（线程钉住）"></a>坑 1：<code>synchronized</code> 导致 <strong>Pinning</strong>（线程钉住）</h2>

<p><strong>这是虚拟线程的头号杀手。</strong></p>

<p>当虚拟线程进入 <code>synchronized</code> 块或调用 <code>synchronized</code> 方法时，JVM 会把这个虚拟线程<strong>钉（Pin）</strong>在当前的载体线程上，直到退出 <code>synchronized</code> 才能卸载。原因很简单：<code>synchronized</code> 的 monitor 机制绑定到了平台线程，JVM 无法安全地把虚拟线程的状态从 synchronized 块中间"抠出来"。</p>

<h2 id="坑-3：线程池思维惯性——试图限制虚拟线程数量"><a href="#坑-3：线程池思维惯性——试图限制虚拟线程数量" class="headerlink" title="坑 3：线程池思维惯性——试图限制虚拟线程数量"></a>坑 3：线程池思维惯性——试图限制虚拟线程数量</h2>

<p>很多人看到 <code>Executors.newVirtualThreadPerTaskExecutor()</code> 第一反应是："这岂不是无限创建线程？要不要加个 Semaphore 限流？"</p>

<p><strong>答案是不需要。虚拟线程的设计初衷就是让你不用再操心线程数量。</strong></p>

<p>JVM 内部的 ForkJoinPool 默认并行度是 CPU 核心数（<code>ForkJoinPool.getCommonPoolParallelism()</code>），这意味着同时运行的载体线程数是有限的。虚拟线程再多，也只是在 I/O 等待时"挂起"而已，不会撑爆 CPU。</p>

<h2 id="坑-4：虚拟线程不适合-CPU-密集型任务"><a href="#坑-4：虚拟线程不适合-CPU-密集型任务" class="headerlink" title="坑 4：虚拟线程不适合 CPU 密集型任务"></a>坑 4：虚拟线程不适合 CPU 密集型任务</h2>

<p>虚拟线程的优势在于 <strong>I/O 等待时的自动卸载</strong>。如果你的任务是纯 CPU 计算（比如图像处理、加密解密、复杂算法），虚拟线程不仅不会更快，反而因为调度开销略低于平台线程。</p>

<blockquote><p><strong>简单判断标准</strong>：如果你的任务里有 <code>Thread.sleep()</code>、<code>socket.read()</code>、<code>connection.executeQuery()</code> 这类阻塞操作 → 虚拟线程适合。如果是纯数学运算/内存数据处理 → 用普通线程池就行。</p></blockquote>

<h2 id="坑-5：修改守护线程属性无效"><a href="#坑-5：修改守护线程属性无效" class="headerlink" title="坑 5：修改守护线程属性无效"></a>坑 5：修改守护线程属性无效</h2>

<p>虚拟线程永远是<strong>守护线程（daemon = true）</strong>，你不能把它改成非守护线程。如果你尝试调用 <code>setDaemon(false)</code> 会直接抛出 <code>IllegalThreadStateException</code>。</p>

<p>这意味着：如果主线程结束了，残留的虚拟线程不会阻止 JVM 退出（这点其实比平台线程更好——不用担心线程池忘记 shutdown 导致进程挂住）。</p>

<h2 id="坑-6：连接池需要适配（重要！）"><a href="#坑-6：连接池需要适配（重要！）" class="headerlink" title="坑 6：连接池需要适配（重要！）"></a>坑 6：连接池需要适配（重要！）</h2>

<p>这是一个<strong>非常容易忽视但影响极大</strong>的问题。</p>

<p>以前我们配置 HikariCP 连接池大小，公式大概是 <code>连接数 = CPU核心数 * 2 + 磁盘数</strong>（或者 PG 的官方建议 <code>连接数 = 核心数 * 4</strong>）。这个公式的假设前提是：<strong>线程数有限（几百个），每个线程持有一个连接在等待 DB 返回</strong>。</p>

<p>但虚拟线程时代，你可能同时有 <strong>10000 个虚拟线程</strong>在等数据库返回。如果连接池还按旧公式配 20 个连接……那 9980 个虚拟线程都在排队等连接，虚拟线程的优势荡然无存。</p>

<p><strong>新规则：虚拟线程环境下，连接池应该适当放大</strong>（但也不是无限大，毕竟数据库那边也有连接上限）。一般建议：</p>

<ul>
<li>HikariCP：从原来的 <code>核心数 * 2 + 1</code> 提升到 <code>核心数 * 4 ~ 核心数 * 8</code></li>
<li>配合数据库端的 <code>max_connections</code> 同步调整</li>
<li>监控连接池等待指标（<code>HikariPool-1.Wait</code>）作为调整依据</li>
</ul>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>

<p>虚拟线程是 Java 并发编程史上<strong>最具革命性的特性之一</strong>——它不是小修小补，而是从根本上重新定义了"线程"这个概念。让我们快速回顾要点：</p>

<ul>
<li><strong>核心价值</strong>：以极低的内存成本实现高并发 I/O，<strong>同步写法，异步性能</strong>。</li>
<li><strong>最佳场景</strong>：I/O 密集型任务（RPC 调用、DB 查询、HTTP 请求、消息发送）。</li>
<li><strong>最大陷阱</strong>：<code>synchronized</code> 导致 Pinning（用 <code>ReentrantLock</code> 替代）、<code>ThreadLocal</code> 内存膨胀（迁移到 <code>ScopedValue</code>）、连接池大小需要重新评估。</li>
<li><strong>不适用场景</strong>：CPU 密集型计算（用传统线程池即可）。</li>
<li><strong>迁移建议</strong>：新项目直接上（Spring Boot 3.2+ 一行配置搞定）；老项目渐进式替换，从 I/O 密集的模块开始。</li>
</ul>

<p>虚拟线程不是要消灭平台线程，而是给了我们一个<strong>更好的工具选择</strong>。就像有了电钻之后锤子依然有用——关键是知道什么时候用什么。</p>
