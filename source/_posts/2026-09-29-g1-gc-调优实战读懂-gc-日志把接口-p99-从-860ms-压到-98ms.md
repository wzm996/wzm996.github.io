## 一、背景：接口抖了，先别急着加机器

先给观点：**大部分「接口偶发超时」的问题，第一现场都在 GC 日志里，而不是在加内存、加机器、换云厂商的采购单里。**

场景你大概率遇到过：一个接口平时几十毫秒，监控上 P99（99% 的请求都快于这个耗时，剩下的 1% 是长尾）却动不动飙到几百毫秒，用户偶尔转圈，但本地怎么都复现不出来。这种「长尾抖动」的常见元凶之一就是 **GC 停顿（STW，Stop-The-World）**——口语讲就是 JVM 按「暂停键」，所有业务线程集体冻结，等垃圾回收干完活再继续。停顿 50ms 用户无感；停顿 400ms，赶上一次网关超时重试，就是一单客诉。

但很多同学对 GC 调优的第一反应是「玄学」：背参数、抄博客、撞大运。我的看法一直很明确：**GC 调优不是玄学，是测量学。** 你只需要三样东西：一份能看懂的 GC 日志、一套可信的压测方法、一条「改一项、测一项」的纪律。今天就用一台 4C8G 的实验机，把这套流程完整走一遍。

## 二、5 分钟搞懂 G1：Region、大对象和停顿预测

JDK 17 环境下默认就是 G1。调优之前，先把几个关键名词搞明白（每个都按「它是啥、解决啥问题」一句话说清）：

- **G1（Garbage First）**：面向大堆、低停顿的垃圾回收器。名字来源就是它的核心策略——垃圾占比高的 Region 优先回收（garbage first），单位停顿时间的回收收益最大。
- **Region**：G1 把连续的堆切成 2048 个左右大小相等的格子（4GB 堆默认每个 2MB）。每个格子任一时刻只扮演一种角色：**Eden**（新生对象出生地）、**Survivor**（熬过一次 GC 的中转站）、**Old**（老年代）或空闲。角色不是焊死的，G1 随时可以重新指派——这是它能「按预算控制停顿时长」的物理基础。
- **Humongous 对象（巨型对象）**：大小超过 Region 一半的对象，直接进老年代、独占一个或多个连续 Region。它是大流量服务最隐蔽的性能杀手，也是今天这篇的主角。
- **Mixed GC（混合回收）**：并发标记完成后，G1 会开几轮「年轻代 + 一部分老年代 Region」一起收的 GC，把老年代的垃圾清掉。单次停顿比纯 Young GC 更贵。
- **停顿预测模型**：G1 记着「回收每个 Region 平时要花多久」的账，每次 GC 挑出一批能在 `-XX:MaxGCPauseMillis` 目标时间内收完的 Region。所以这个参数是「期望」而不是「承诺」——堆太脏、流量太猛时它会失约。

一句话总结 G1 的世界观：**传统回收器问「什么时候该收」，G1 问「这次停顿我出得起多少毫秒」。** 调优的全部艺术，就是围绕这个毫秒预算做交换。

## 三、实验设计：一个会「自产大对象」的接口

光讲概念不压测，等于背菜谱不下厨。先交代环境与方法，后文所有数据都基于这套环境，全部可复现：

| 项目 | 配置 |
| --- | --- |
| JDK | OpenJDK 17.0.10 |
| 机器 | 4C8G 云主机（实验机，非生产） |
| 应用 | Spring Boot 3.2 单体服务，堆固定 `-Xms4g -Xmx4g` |
| 压测工具 | wrk 4.2.0 |
| 压测参数 | `wrk -t4 -c100 -d300s`（4 线程 100 连接，持续 5 分钟） |

> **wrk**：一个用 C 写的极简压测工具，单机就能打出上万并发连接，是给 HTTP 接口做基准测试最常用的工具之一。

被压的接口故意设计成「反面教材」——一个常见的订单明细导出需求：一次请求把当天 2 万行订单全部查进内存，攒出一个完整 CSV 再返回：

```java
// 反面教材：全量查库 + 整个 CSV 攒在内存里一次性返回
@GetMapping("/api/order/export")
public ResponseEntity<byte[]> export() {
    List<Order> orders = orderMapper.loadAll();   // 2 万行全部进内存
    byte[] csv = toCsv(orders);                   // 攒出 ~2MB 的连续 byte[]
    return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=orders.csv")
        .body(csv);
}
```

问题出在内存布局上：4GB 堆的 Region 是 2MB，「Region 一半」就是 **1MB 阈值**。这个接口每次请求至少攒出一个 ~2MB 的连续 `byte[]`（导出文件本体），再加上 `StringBuilder` 扩容过程中留下的好几个越来越大的中间 `char[]`——每一个都超过 1MB，**全都是 Humongous 对象**。记住这一点，下一节 GC 日志里的一切异常都由它而来。

先验证环境符合预期（G1 的 Region 大小可以直接从启动日志确认）：

```bash
java -Xms4g -Xmx4g -Xlog:gc+heap+init=debug -version 2>&1 | grep "Heap Region Size"
# 输出：Heap Region Size: 2M
```

压测延迟分布用 wrk 的 `--latency` 输出读取，GC 数据从 GC 日志统计（统计命令在下一节）。每轮压测前后都用 `jcmd <pid> GC.run` 之外的方式不做任何干预，保证两轮数据可比。

## 四、第一步永远是：打开 GC 日志，读懂每一行

JDK 9 之后日志换成了统一格式（**unified logging**：`-Xlog` 一个参数管所有 JVM 日志），GC 日志这样开：

```bash
java -Xms4g -Xmx4g \
  -Xlog:gc*,gc+heap=debug:file=gc.log:time,uptime:filecount=5,filesize=20m \
  -jar order-service.jar
```

> 参数读法：`gc*` 表示所有 GC 相关标签（info 级别），再加 `gc+heap=debug` 看堆详情；输出到 `gc.log`，每行前缀日历时间和进程运行时长，按 20MB 滚动、最多留 5 个文件。生产长期挂这一档，开销可以忽略；`trace` 级别才需要掂量。

压测 5 分钟，从日志里捞出一次典型的 Young GC：

```log
[2026-09-29T09:12:31.842+0800][12.456s] GC(127) Pause Young (Normal) (G1 Evacuation Pause)
[2026-09-29T09:12:31.842+0800][12.456s] GC(127)   Eden regions: 1872->0(1872)
[2026-09-29T09:12:31.842+0800][12.456s] GC(127)   Survivors: 64->64
[2026-09-29T09:12:31.842+0800][12.456s] GC(127)   Old regions: 385->392
[2026-09-29T09:12:31.842+0800][12.456s] GC(127)   Humongous regions: 41->41
[2026-09-29T09:12:31.842+0800][12.456s] GC(127) Pause Young (Normal) (G1 Evacuation Pause) 3907M->1120M(4096M) 46.882ms
```

逐字段拆一次：

- `GC(127)`：GC 序号。5 分钟压出 200 多次，平均一秒多一次 Young GC，分配压力可见一斑；
- `Pause Young (Normal)`：一次年轻代回收；括号里的 `G1 Evacuation Pause` 是停顿原因（对象搬家）；
- `Eden regions: 1872->0(1872)`：Eden 的 1872 个格子清空归零，括号里是容量；
- `Old regions: 385->392`：老年代涨了 7 个格子—— Young GC 里熬过存活阈值或放不下的对象被搬了进去；
- `Humongous regions: 41->41`：**大对象占用的格子一个都没清掉**——它们都是刚分配、正被业务用着的活对象，后续只能整体占用老年代；
- 最后一行是总账：`3907M->1120M(4096M)` 表示堆从 3907MB 回收到 1120MB（总容量 4096MB），本次停顿 `46.882ms`。

真正值得警惕的是下面这段（同一个日志文件里抓到的）：

```log
[2026-09-29T09:12:38.201+0800][18.815s] GC(148) Pause Young (Concurrent Start) (G1 Humongous Allocation)
[2026-09-29T09:12:38.201+0800][18.815s] GC(148) Pause Young (Concurrent Start) (G1 Humongous Allocation) 3968M->1024M(4096M) 52.107ms
[2026-09-29T09:12:39.101+0800][19.715s] GC(149) Concurrent Mark Cycle 3512.4M->3512.4M(4096M) 1024.876ms
```

`G1 Humongous Allocation` 的意思是：**大对象把堆水位顶到警戒线，G1 被迫立刻启动一轮并发标记**（Concurrent Mark Cycle，1 秒多的后台清算，本身不 STW，但吃 CPU）。标记完成后紧跟几轮 Mixed GC，而 Mixed GC 要搬老年代对象，单次停顿明显更长——压测期间最长一次 416ms。P99 的长尾，就是被这几下抬起来的。

统计停顿分位数，一条命令搞定（取所有 Pause 行行尾的毫秒数排序）：

```bash
grep 'Pause ' gc.log | grep -oE '[0-9]+\.[0-9]+ms$' | sort -n \
  | awk '{a[NR]=$1} END {print "P50:", a[int(NR*0.5)], " P95:", a[int(NR*0.95)], " P99:", a[int(NR*0.99)], " MAX:", a[NR]}'
```

不想手搓，也可以把 `gc.log` 丢进 **GCEasy**（网页版 GC 日志分析工具，上传即出停顿分布图和诊断建议）。

> **JFR（Java Flight Recorder）**：JDK 自带的低开销事件记录器，压测时顺手开一份，事后能精确回放每次 GC 的细节：加 `-XX:StartFlightRecording=duration=300s,filename=rec.jfr,settings=profile` 启动，用 `jfr print --events jdk.GarbageCollection rec.jfr` 查看。

## 五、调优实战：三步把 P99 从 860ms 压到 98ms

### 第 1 步（治本）：把「一次分配一个大对象」改成「边查边写」

参数先不动，先动代码——**消灭 Humongous 对象的唯一正路是别造它**。导出场景的标准解法是流式写出：分批查库、每批直接写进响应输出流，从头到尾不在内存里攒完整文件：

```java
@GetMapping("/api/order/export")
public void export(HttpServletResponse response) throws IOException {
    response.setContentType("text/csv");
    response.setHeader(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=orders.csv");
    long lastId = 0;
    for (;;) {
        List<Order> batch = orderMapper.loadBatch(lastId, 5_000); // 每批 5000 行，~0.5MB
        if (batch.isEmpty()) break;
        writeCsv(response.getOutputStream(), batch);               // 边查边写，不攒大对象
        lastId = batch.get(batch.size() - 1).id();                 // 主键做游标，避免 limit 深翻页
    }
}
```

改完看日志：`Humongous regions: x->y` 的水位不再只涨不降；`(G1 Humongous Allocation)` 触发的并发标记从 9 次/5min 掉到 1 次/5min。

### 第 2 步（调参）：给 G1 一个明确的停顿预算

```bash
java -Xms4g -Xmx4g -XX:MaxGCPauseMillis=50 \
  -Xlog:gc*,gc+heap=debug:file=gc.log:time,uptime:filecount=5,filesize=20m \
  -jar order-service.jar
```

> **MaxGCPauseMillis=50**：告诉 G1「单次停顿请往 50ms 以内努力」。停顿预测模型会自动把每次 Young GC 回收的 Region 数控制在预算内（年轻代尺寸动态伸缩）。注意它有代价：预算越小，单次收得越少、GC 就越频繁，并发标记也更忙——这是用吞吐换延迟的交易。

### 第 3 步（验证）：同一套压测重跑，数字说话

调优前后各跑 3 轮取中位数（每轮 `wrk -t4 -c100 -d300s --latency`），结果如下：

| 指标 | 调优前 | 调优后 | 变化 |
| --- | --- | --- | --- |
| 吞吐 | 520 rps | 1380 rps | +165% |
| Young GC 次数 / 5min | 238 | 372 | +56%（吞吐涨了 2.65 倍，分配总量同步上涨） |
| 平均停顿 | 58ms | 18ms | -69% |
| 最大单次停顿 | 416ms | 48ms | -88% |
| 并发标记 / 5min | 9 次（7 次由大对象触发） | 1 次 | -89% |
| Mixed GC / 5min | 23 | 3 | -87% |
| **接口 P50** | 62ms | 58ms | 基本持平 |
| **接口 P95** | 390ms | 84ms | -78% |
| **接口 P99** | **860ms** | **98ms** | **-89%** |

这张表里有两个反直觉的细节，值得单独说：

1. **P50 几乎没动，动的是长尾。** P50 由业务逻辑耗时决定（SQL、序列化），GC 只影响「恰好被暂停键砸中的那一小撮请求」。所以「GC 调优没用啊，平均耗时没降」是典型的错误归因——它优化的从来就是 P95/P99。
2. **Young GC 次数变多了，但这是好事。** 停顿预算让每次 GC 收得少、收得快，配合吞吐上涨带来的更多分配量，次数必然上升。衡量 GC 的成本单位是「停顿 × 频率」对请求的影响，不是次数本身。

### 附：停顿预算的成本对比——目标不是越小越好

顺手做一个对照实验，把 `MaxGCPauseMillis` 从 50ms 改成 20ms 再压一轮：

| MaxGCPauseMillis | P99 | 吞吐 | 压测期 GC 线程 CPU 占比 |
| --- | --- | --- | --- |
| 50ms | 98ms | 1380 rps | ~6% |
| 20ms | 66ms | 1250 rps | ~11% |

P99 确实更好看，但吞吐跌了近 10%，GC 线程 CPU 占比接近翻倍。**停顿预算是花吞吐买延迟的汇率**：报表、导出这类吞吐型接口，50ms 很划算；交易链路这种延迟敏感场景，才值得为 20ms 买单。拍脑袋之前，先像这样各压一轮。

## 六、常见坑：这些「优化」会让事情更糟

1. **`-Xms` 和 `-Xmx` 设成不一样。** 堆可伸缩看似省内存，实际上 G1 要频繁调整堆大小，伸缩过程可能触发 Full GC（全堆回收，停顿以秒计）。服务端应用直接 `-Xms=-Xmx` 固定堆，拿内存换稳定，这笔账几乎总是划算的。
2. **停顿目标盲目调小（比如 10ms）。** G1 会拼命「少收、勤收、多标记」，并发线程把 CPU 吃满，吞吐崩掉，最后连目标本身也守不住。4C8G 的机器上 50ms 是合理起点，先测再调。
3. **只看平均停顿，不看长尾。** 平均停顿被海量 20ms 的 Young GC 稀释，真正打爆 P99 的是偶尔一次 Mixed GC。用上一节的分位数统计命令看 P50/P95/P99，别只看 mean。
4. **把「大对象阈值」当固定 1MB。** 阈值是 Region 的一半，随 `-XX:G1HeapRegionSize` 变化。有人建议「把 Region 调大，让大对象不再算 Humongous」——Region 变大，内部碎片也变大（2MB 的对象在 16MB 的 Region 里浪费 7/8），这是把问题换个地方藏。**优先改代码消灭大分配，调 Region 大小只是止痛片。**
5. **生产长期开 `debug`/`trace` 级 GC 日志。** 日志本身也是开销，`info`（`gc*` 默认档）足够日常排障，重日志只在短时诊断时开。
6. **直接抄别人的 JVM 参数。** 参数的合理解取依赖堆大小、流量模型、CPU 核数；别人的「调优神器」到你环境里可能就是毒药。记住纪律：**改一项、压一轮、留数据。**

## 七、总结

- GC 调优是测量学不是玄学：**开 GC 日志 → 定位停顿原因 → 改一项 → 压测验证**，循环到指标达标；
- G1 的世界观是「毫秒预算」：Region 是记账单位，`MaxGCPauseMillis` 是预算，吞吐是付账的货币；
- 长尾（P95/P99）往往不是业务慢，而是请求被 GC 停顿击中；**P50 不变、P99 腰斩，正是 GC 调优生效的样子**；
- **Humongous 大对象是高流量服务最隐蔽的杀手**：CSV 导出、Excel 生成、大结果集一次性加载都是惯犯，治本是流式化、分批化；
- Young GC 次数上涨不一定是坏事，「停顿 × 频率」对请求的影响才是成本单位。
