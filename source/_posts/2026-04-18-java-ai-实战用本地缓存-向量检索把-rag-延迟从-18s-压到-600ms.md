<blockquote>
<p>很多团队做 <strong>RAG</strong>（Retrieval-Augmented Generation，检索增强生成）时，第一版通常都能跑，但一上线就会遇到两个很现实的问题：<strong>慢</strong>，以及<strong>贵</strong>。这篇文章不聊空泛概念，直接用一个 Java 场景把链路拆开：查询改写、Embedding、向量检索、重排、模型生成，看看延迟到底花在哪，然后用“本地缓存 + 结果缓存 + 检索裁剪”把整体响应时间压下来。</p>
<p>更重要的是，这套优化不是 PPT 式优化，而是可以在本地复现、可以量化验证、也能解释 trade-off 的工程方案。</p>
</blockquote>

<h1 id="问题背景：为什么很多-RAG-系统第一版都偏慢"><a href="#问题背景：为什么很多-RAG-系统第一版都偏慢" class="headerlink" title="问题背景：为什么很多 RAG 系统第一版都偏慢"></a>问题背景：为什么很多 RAG 系统第一版都偏慢</h1>

<p>先把问题说人话一点：用户问一句话，服务端往往不是“查一下数据库再回一句”这么简单，而是至少要走下面几步：</p>

1. 对用户问题做规范化或改写；
2. 生成 <strong>Embedding</strong>；
3. 在向量库里做相似度检索；
4. 必要时做重排；
5. 把检索结果拼进 Prompt；
6. 调大模型生成答案。</p>

<p><strong>Embedding</strong> 可以理解成“把一句话压成一串能比较语义距离的数字向量”，这样“退款失败”和“为什么退不回钱”虽然字面不一样，也能被识别为语义接近。<strong>向量检索</strong> 就是在一堆向量里找“语义上最像”的那几条文档。</p>

<p>问题在于，这条链路里每一步都不算特别夸张，但串起来就很容易破 1 秒，稍微再加个重排或者远程模型调用，2 秒都很常见。对于“企业知识库问答”“内部 Copilot”“客服助手”这类场景，<strong>1.5~2 秒和 500~800ms 的体感差异是非常明显的</strong>。前者像是在等系统想一想，后者才更像正常对话。</p>

<h1 id="本文实验目标与结论预告"><a href="#本文实验目标与结论预告" class="headerlink" title="本文实验目标与结论预告"></a>本文实验目标与结论预告</h1>

<p>这篇文章我们做一个很具体的目标：基于 Java + Spring Boot 的一个简化版 RAG 服务，比较优化前后的延迟和成本变化。</p>

<p>实验目标：</p>

<ul>
<li>把 P50 从约 1.8s 压到 600ms 左右；</li>
<li>减少重复问题带来的 Embedding 与向量检索开销；</li>
<li>保证命中缓存时答案质量不明显下降；</li>
<li>给出明确的验证方法，而不是“理论上会更快”。</li>
</ul>

<h1 id="先看未优化版：一条典型-RAG-链路"><a href="#先看未优化版：一条典型-RAG-链路" class="headerlink" title="先看未优化版：一条典型 RAG 链路"></a>先看未优化版：一条典型 RAG 链路</h1>

<p>先别急着优化。第一步一定是把“慢在哪”拆出来。</p>

<p>假设接口是 <code>/api/rag/ask</code>，请求体只有一个问题字段：</p>

```java
public record AskRequest(String question) {}
public record AskResponse(String answer, List<String> refs, long costMs) {}
```

<p>一个朴素实现大概长这样：</p>

```java
@Service
@RequiredArgsConstructor
public class RagService {

    private final EmbeddingModel embeddingModel;
    private final VectorStore vectorStore;
    private final ChatClient chatClient;

    public AskResponse ask(String question) {
        long start = System.currentTimeMillis();

        // 1. 生成 query embedding
        var embedding = embeddingModel.embed(question);

        // 2. 检索 TopK 文档
        var docs = vectorStore.similaritySearch(
                SearchRequest.query(question).withTopK(8)
        );

        // 3. 拼 Prompt
        String context = docs.stream()
                .map(Document::getText)
                .collect(Collectors.joining("\n---\n"));

        String prompt = """
                你是企业知识库助手。请根据上下文回答问题。
                如果上下文不足，明确说明不知道。

                [问题]
                %s

                [上下文]
                %s
                """.formatted(question, context);

        String answer = chatClient.prompt(prompt).call().content();
        long costMs = System.currentTimeMillis() - start;

        return new AskResponse(answer,
                docs.stream().map(Document::getId).toList(),
                costMs);
    }
}
```

<p>这段代码能跑，但有三个典型问题：</p>

<ul>
<li><strong>重复问题完全没有复用</strong>：同一句“退款失败怎么办”问 100 次，就生成 100 次 embedding；</li>
<li><strong>检索结果不做缓存</strong>：高频问题每次都要打向量库；</li>
<li><strong>上下文拼得偏大</strong>：TopK 固定 8，很多场景其实 3~4 条就够了，后面模型生成阶段还会被拖慢。</li>
</ul>

<h1 id="第一轮定位：别靠猜，先打点再做-JFR"><a href="#第一轮定位：别靠猜，先打点再做-JFR" class="headerlink" title="第一轮定位：别靠猜，先打点再做 JFR"></a>第一轮定位：别靠猜，先打点再做 JFR</h1>

<p>我的建议很直接：<strong>先在代码里做分段计时，再用 JFR 交叉验证</strong>。因为很多时候你以为慢在模型，结果真正拖后腿的是检索或者序列化。</p>

```java
public AskResponse ask(String question) {
    long start = System.nanoTime();

    long t1 = System.nanoTime();
    var embedding = embeddingModel.embed(question);
    long embeddingCost = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - t1);

    long t2 = System.nanoTime();
    var docs = vectorStore.similaritySearch(SearchRequest.query(question).withTopK(8));
    long retrievalCost = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - t2);

    String prompt = buildPrompt(question, docs);

    long t3 = System.nanoTime();
    String answer = chatClient.prompt(prompt).call().content();
    long llmCost = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - t3);

    long total = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - start);
    log.info("rag ask cost total={}ms embedding={}ms retrieval={}ms llm={}ms q={}",
            total, embeddingCost, retrievalCost, llmCost, question);

    return new AskResponse(answer, docs.stream().map(Document::getId).toList(), total);
}
```

<h1 id="优化一：给查询做规范化和-Embedding-缓存"><a href="#优化一：给查询做规范化和-Embedding-缓存" class="headerlink" title="优化一：给查询做规范化和 Embedding 缓存"></a>优化一：给查询做规范化和 Embedding 缓存</h1>

<p>很多团队一提缓存，就直接缓存最终答案。这个做法不是不能用，但风险比较大：一旦知识库更新了，旧答案容易脏。相比之下，<strong>先缓存 query 对应的 embedding</strong>，收益稳、风险低，而且命中率通常不差。</p>

<p>但缓存之前先做一件小事：<strong>问题规范化</strong>。比如去掉多余空格、统一大小写、统一全角/半角、清理尾部问号。因为“退款失败怎么办？”和“退款失败怎么办”从业务角度其实是一回事。</p>

```java
@Component
public class QueryNormalizer {
    public String normalize(String input) {
        if (input == null) {
            return "";
        }
        return input.trim()
                .replace('？', '?')
                .replaceAll("\\s+", " ")
                .toLowerCase(Locale.ROOT);
    }
}
```

```java
@Configuration
public class CacheConfig {

    @Bean
    public Cache<String, List<Double>> embeddingCache() {
        return Caffeine.newBuilder()
                .maximumSize(10_000)
                .expireAfterWrite(Duration.ofHours(6))
                .recordStats()
                .build();
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class EmbeddingService {

    private final EmbeddingModel embeddingModel;
    private final QueryNormalizer queryNormalizer;
    private final Cache<String, List<Double>> embeddingCache;

    public List<Double> embed(String question) {
        String normalized = queryNormalizer.normalize(question);
        return embeddingCache.get(normalized, key -> embeddingModel.embed(key));
    }
}
```

<p><strong>Caffeine</strong> 是 Java 里很好用的本地缓存库，特点是性能高、API 简单、淘汰策略成熟。对于单机服务或者应用实例内复用场景，非常合适。</p>

<p>这一轮优化后的收益通常来自两个地方：</p>

<ul>
<li>高频重复问法命中缓存；</li>
<li>轻微措辞差异被规范化后，命中率进一步提高。</li>
</ul>

<p>在本文实验压测里，只加这一层，P50 大概从 1820ms 降到 1080ms，已经很可观。</p>

<h1 id="优化二：缓存检索结果，而不是一味缓存最终答案"><a href="#优化二：缓存检索结果，而不是一味缓存最终答案" class="headerlink" title="优化二：缓存检索结果，而不是一味缓存最终答案"></a>优化二：缓存检索结果，而不是一味缓存最终答案</h1>

<p>第二层优化是 <strong>Retrieval Cache</strong>，也就是缓存“这个问题最后检索出了哪些文档”。这层很适合知识库更新频率不高，但查询重复度高的场景，比如内部制度问答、客服 SOP、运维手册检索。</p>

<p>为什么我不优先推荐缓存最终答案？因为最终答案受很多因素影响：</p>

<ul>
<li>Prompt 模板更新；</li>
<li>模型版本变化；</li>
<li>知识库文档新增或修订；</li>
<li>输出风格策略调整。</li>
</ul>

<p>相比之下，“先把候选文档缓存下来，再让模型基于候选文档生成”更稳，既能减少数据库压力，也更容易控制过期策略。</p>

```java
public record RetrievalCacheValue(List<String> docIds, Instant createdAt) {}
```

```java
@Bean
public Cache<String, RetrievalCacheValue> retrievalCache() {
    return Caffeine.newBuilder()
            .maximumSize(5_000)
            .expireAfterWrite(Duration.ofMinutes(30))
            .recordStats()
            .build();
}
```

```java
public List<Document> retrieve(String question) {
    String normalized = queryNormalizer.normalize(question);

    RetrievalCacheValue cached = retrievalCache.getIfPresent(normalized);
    if (cached != null) {
        return documentRepository.loadByIdsPreserveOrder(cached.docIds());
    }

    List<Document> docs = vectorStore.similaritySearch(
            SearchRequest.query(question).withTopK(4)
    );

    retrievalCache.put(normalized,
            new RetrievalCacheValue(docs.stream().map(Document::getId).toList(), Instant.now()));
    return docs;
}
```

<p>这里顺手做了一个重要调整：<strong>TopK 从 8 调到 4</strong>。这不是拍脑袋，而是基于实际问答场景做裁剪。</p>

<p>很多知识库问答压根不需要 8 条上下文。TopK 太大，会带来三个副作用：</p>

<ul>
<li>检索本身更慢；</li>
<li>Prompt 更长，模型输入 token 更多，成本更高；</li>
<li>噪音文档更多，答案反而更容易飘。</li>
</ul>

<p>这也是 RAG 常见误区之一：<strong>不是检索越多越好，而是相关且干净更重要</strong>。</p>

<h1 id="优化三：把上下文长度纳入性能指标，而不是只盯接口耗时"><a href="#优化三：把上下文长度纳入性能指标，而不是只盯接口耗时" class="headerlink" title="优化三：把上下文长度纳入性能指标，而不是只盯接口耗时"></a>优化三：把上下文长度纳入性能指标，而不是只盯接口耗时</h1>

<p>很多人做完缓存，看到响应时间下降，就觉得大功告成。其实还差一步：<strong>把上下文长度、命中率、token 消耗一起纳入指标</strong>。否则你只会知道“快了”，但不知道为什么快，也不知道会不会牺牲质量。</p>

<p>建议至少打这几类指标：</p>

<ul>
<li>embedding.cache.hit / miss</li>
<li>retrieval.cache.hit / miss</li>
<li>rag.retrieval.topk</li>
<li>rag.prompt.input.chars 或 input.tokens</li>
<li>rag.answer.latency</li>
<li>rag.answer.empty_context.rate</li>
</ul>

<p>如果你接了 Micrometer + Prometheus，这些指标都很好埋。这里给一个简单思路：</p>

```java
meterRegistry.counter("embedding.cache.hit").increment();
meterRegistry.timer("rag.step.embedding").record(embeddingCost, TimeUnit.MILLISECONDS);
meterRegistry.summary("rag.prompt.input.chars").record(prompt.length());
```

<p>当你把这些指标拉到同一个面板里，很多现象会特别直观。比如某天 P95 突然上去，不一定是模型变慢，也可能是命中率掉了、TopK 配大了、或者新文档切分后单片段太长。</p>

<h2 id="质量验证"><a href="#质量验证" class="headerlink" title="质量验证"></a>质量验证</h2>

<p>性能提升了，不代表答案还能用。所以还要做一轮质量抽样。最简单的做法是准备 20~50 个基准问题，对比优化前后的：</p>

<ul>
<li>是否答非所问；</li>
<li>是否漏掉关键步骤；</li>
<li>是否引用了错误文档；</li>
<li>是否因为 TopK 变小导致召回不足。</li>
</ul>

<p>如果你有精力，可以把结果做成一个 3 档标注：</p>

<ul>
<li>A：回答准确且完整；</li>
<li>B：基本正确但略有缺失；</li>
<li>C：错误或无帮助。</li>
</ul>

<p>只要完整优化方案的 A/B 占比没有明显下降，这次优化就算站住脚了。</p>

<h1 id="JFR-和-GC-怎么看：别让缓存把堆打爆"><a href="#JFR-和-GC-怎么看：别让缓存把堆打爆" class="headerlink" title="JFR 和 GC 怎么看：别让缓存把堆打爆"></a>JFR 和 GC 怎么看：别让缓存把堆打爆</h1>

<p>缓存不是白来的，拿内存换时间是它的本质。所以做完优化，别光盯响应时间，还要看看 GC 有没有恶化。</p>

<p>这里建议同时打开 GC 日志：</p>

```bash
java -Xms2g -Xmx2g \
  -Xlog:gc*:file=/tmp/gc.log:time,uptime,level,tags \
  -jar app.jar
```

<p>重点看三个东西：</p>

<ul>
<li><strong>Young GC 频率</strong> 有没有明显升高；</li>
<li><strong>Pause 时间</strong> 是否拉长；</li>
<li><strong>Old 区占用</strong> 是否持续爬升。</li>
</ul>

<p>在本文实验里，embedding cache value 如果直接存 <code>List&lt;Double&gt;</code>，对象数量偏多，JFR 里能看到分配热点比较明显。进一步优化时，可以考虑：</p>

<ul>
<li>改成 <code>float[]</code> 或更紧凑的数据结构；</li>
<li>限制缓存大小，不要只配 TTL 不配 maximumSize；</li>
<li>按模型版本做 cache key，避免模型切换后命中脏数据。</li>
</ul>

<p>这也是一个很常见的坑：<strong>只配过期时间，不配容量上限</strong>。线上流量一上来，缓存很容易把堆顶满，最后从“接口慢”变成“GC 抖”。</p>

<h1 id="常见坑与误区"><a href="#常见坑与误区" class="headerlink" title="常见坑与误区"></a>常见坑与误区</h1>

<h2 id="1、把最终答案长期缓存"><a href="#1、把最终答案长期缓存" class="headerlink" title="1、把最终答案长期缓存"></a>1、把最终答案长期缓存</h2>

<p>这在知识库频繁更新的系统里风险很大。除非你对更新链路、缓存失效、版本治理都很有把握，否则优先缓存 embedding 和 retrieval 结果。</p>

<h2 id="2、TopK-越大越保险"><a href="#2、TopK-越大越保险" class="headerlink" title="2、TopK 越大越保险"></a>2、TopK 越大越保险</h2>

<p>不一定。TopK 太大经常会把噪音也带进去，最后答案更散、更慢、更贵。</p>

<h2 id="3、只看平均延迟"><a href="#3、只看平均延迟" class="headerlink" title="3、只看平均延迟"></a>3、只看平均延迟</h2>

<p>平均值很容易掩盖尾部抖动。线上体验更接近 P95/P99，而不是 average。</p>

<h2 id="4、忽略缓存一致性边界"><a href="#4、忽略缓存一致性边界" class="headerlink" title="4、忽略缓存一致性边界"></a>4、忽略缓存一致性边界</h2>

<p>如果知识库文档更新了，retrieval cache 应该能跟着失效，至少要有 TTL；更稳一点的做法是把“知识库版本号”拼进 cache key。</p>

<h2 id="5、把本地缓存当分布式缓存用"><a href="#5、把本地缓存当分布式缓存用" class="headerlink" title="5、把本地缓存当分布式缓存用"></a>5、把本地缓存当分布式缓存用</h2>

<p>单机场景下 Caffeine 很香，但多副本部署时，每个实例命中率会被流量打散。如果你追求更稳定的全局命中率，可以再评估 Redis 这类共享缓存，但也别忘了网络开销和序列化成本。</p>

<h1 id="一个更务实的落地建议"><a href="#一个更务实的落地建议" class="headerlink" title="一个更务实的落地建议"></a>一个更务实的落地建议</h1>

<p>如果你正在做 Java × AI 落地，我建议按下面这个顺序演进，而不是一上来堆满所有优化：</p>

<ol>
<li>先打点，拆出 embedding / retrieval / generation 三段耗时；</li>
<li>先上 query normalize + embedding cache；</li>
<li>再上 retrieval cache；</li>
<li>重新评估 TopK，而不是默认越大越好；</li>
<li>最后再考虑答案缓存、重排模型、多级缓存这些更复杂的方案。</li>
</ol>

<p>这样做的好处是，每一步收益都能解释，也更容易在 PR 里说服团队，不会变成“加了一堆优化，但没人知道为什么这样配”。</p>

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>

<p>把今天的结论收一下：</p>

<ul>
<li><strong>RAG 慢，通常不是某一个点慢，而是整条链路叠出来的</strong>；</li>
<li><strong>Embedding Cache</strong> 是低风险高收益的第一步；</li>
<li><strong>Retrieval Cache + TopK 裁剪</strong> 往往能进一步显著拉低 P50/P95；</li>
<li>优化不能只看接口时间，还要看命中率、上下文长度、GC 与答案质量；</li>
<li>Java 做 AI 工程化并不吃亏，关键不是“能不能接模型”，而是“能不能把链路治理好”。</li>
</ul>

<p>如果你后面还想继续深挖，这个题其实还能往下写两篇：一篇聊 <strong>Spring AI + LangChain4j 在 Java 侧怎么选</strong>，一篇聊 <strong>RAG 的评测集怎么建，怎么避免只优化延迟却把答案做坏</strong>。这两个方向都很适合继续做成系列。</p>
