<blockquote><p><strong>虚拟线程</strong>（Virtual Thread）是 JDK 21 正式转正的轻量级并发特性（JEP 444），它让 Java 在保留「一请求一线程」同步编程风格的同时，突破平台线程数量对吞吐量的限制。本文从原理出发，通过可复现的压测实验对比虚拟线程与传统线程池的吞吐差异，并总结生产环境落地时的关键避坑点。</p></blockquote>

<!-- more -->

<h1 id="背景为什么要关心虚拟线程">一、背景：为什么要关心虚拟线程？</h1>

<p>在传统的 Java 服务端开发中，我们习惯了「一请求一线程」的编程模型：一个 HTTP 请求进来，由一个独立线程从头到尾处理完。代码好写、好调试、异常沿着调用栈抛出——非常直观。</p>

<p>但问题在于：<strong>平台线程（Platform Thread）太贵了</strong>。</p>

<p>每个平台线程默认预留约 <strong>1 MB 栈空间</strong>，而且与操作系统线程 1:1 绑定。当一个线程在等数据库查询、等 RPC 返回、等文件 I/O 时，它占着的平台线程（以及对应的 OS 线程）啥也不干，就在傻等。线程池能缓解创建成本，但改变不了一个事实：<strong>池子大小有上限，上限到了任务就只能排队</strong>。</p>

<p>为了提升吞吐，业界走过几条路：</p>
<table>
<thead><tr><th>方案</th><th>优点</th><th>缺点</th></tr></thead>
<tbody>
<tr><td>扩大线程池</td><td>简单直接</td><td>线程数受 OS 限制，上下文切换开销剧增</td></tr>
<tr><td>异步/响应式（CompletableFuture、WebFlux）</td><td>少量线程实现高吞吐</td><td>回调地狱、调试困难、学习成本高</td></tr>
<tr><td>扩容加机器</td><td>有效</td><td>成本高，不一定能根本解决</td></tr>
<tr><td><strong>虚拟线程（JDK 21+）</strong></td><td>保留同步写法 + 高吞吐 + 低内存</td><td>需注意 Pinning、ThreadLocal 等兼容问题</td></tr>
</tbody>
</table>

<p><strong>虚拟线程</strong>就是 JDK 给出的答案：让阻塞变便宜。当虚拟线程遇到 I/O 阻塞时，它会从底层平台线程上<strong>卸载（unmount）</strong>，把载体线程腾出来干别的；等 I/O 就绪后再<strong>挂载（mount）</strong>回来继续执行。你的代码还是同步写的，但底层已经实现了类似协程的调度。</p>

<h1 id="核心概念快速上手">二、核心概念：快速上手</h1>

<h2 id="术语对照表">2.1 术语对照表</h2>

<table>
<thead><tr><th>术语</th><th>说明</th><th>类比</th></tr></thead>
<tbody>
<tr><td><strong>操作系统线程（OS Thread）</strong></td><td>OS 内核调度的基本单位</td><td>工厂里的工人</td></tr>
<tr><td><strong>平台线程（Platform Thread）</strong></td><td><code>java.lang.Thread</code> 的传统实例，封装 OS 线程</td><td>工人的工牌（1:1 绑定）</td></tr>
<tr><td><strong>虚拟线程（Virtual Thread）</strong></td><td>JDK 21 引入的轻量级 Thread 实现，由 JVM 调度</td><td>待办的任务卡片（很轻，可以有很多张）</td></tr>
<tr><td><strong>载体线程（Carrier Thread）</strong></td><td>实际承载虚拟线程执行的平台线程</td><td>正在处理某张卡片的工人</td></tr>
<tr><td><strong>Mount（挂载）</strong></td><td>虚拟线程被分配到一个平台线程上执行</td><td>工人拿起一张卡片开始干活</td></tr>
<tr><td><strong>Unmount（卸载）</strong></td><td>虚拟线程遇阻，从平台线程上释放</td><td>卡片放回队列，工人去拿下一张</td></tr>
</tbody>
</table>

<h2 id="四种创建方式">2.2 四种创建方式</h2>

<p><strong>方式一：</strong><code>Thread.startVirtualThread()</code> — 最简启动</p>
<pre><code class="language-java">Thread vt = Thread.startVirtualThread(() -> {
    System.out.println("hello from " + Thread.currentThread());
});
vt.join(); // 虚拟线程是守护线程，main 结束它就没了
</code></pre>

<p><strong>方式二：</strong><code>Thread.ofVirtual()</code> — 可命名、延迟启动</p>
<pre><code class="language-java">Thread vt = Thread.ofVirtual()
    .name("order-query", 1) // name + 起始序号
    .unstarted(() -> System.out.println("querying..."));
vt.start();
vt.join();
</code></pre>

<p><strong>方式三：</strong><code>ThreadFactory</code> — 适合交给框架使用</p>
<pre><code class="language-java">ThreadFactory factory = Thread.ofVirtual().name("worker-", 0).factory();
Thread vt = factory.newThread(() -> System.out.println("working"));
vt.start();
</code></pre>

<p><strong>方式四（推荐）：</strong><code>Executors.newVirtualThreadPerTaskExecutor()</code> — 业务中最常用</p>
<pre><code class="language-java">// 这不是传统意义上的线程池！每个任务都新建一个虚拟线程
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future&lt;String&gt; future = executor.submit(() -> {
        Thread.sleep(Duration.ofSeconds(1)); // 模拟 I/O 等待
        return "done";
    });
    System.out.println(future.get());
} // close() 会等待已提交任务完成
</code></pre>

<pre><code>⚠️ 关键认知：Executors.newVirtualThreadPerTaskExecutor() 返回的不是线程池，
而是一个「为每个任务创建新虚拟线程」的 ExecutorService。
虚拟线程本身很便宜，不需要像平台线程那样池化复用。
</code></pre>

<h2 id="调度器原理">2.3 调度器原理</h2>

<p>虚拟线程的调度器是一个 <strong>FIFO 模式的 ForkJoinPool</strong>（和并行流的 common pool <strong>不是同一个</strong>）。默认并行度等于 CPU 核心数。可以通过以下 JVM 参数调整：</p>
<table>
<thead><tr><th>参数</th><th>含义</th></tr></thead>
<tbody>
<tr><td><code>jdk.virtualThreadScheduler.parallelism</code></td><td>调度器目标并行度（默认 CPU 核心数）</td></tr>
<tr><td><code>jdk.virtualThreadScheduler.maxPoolSize</code></td><td>调度器可扩展的平台线程上限</td></tr>
</tbody>
</table>

<p><strong>大多数业务系统不需要调整这两个参数</strong>。瓶颈通常在数据库连接池、下游限流、锁竞争，而不是调度器并行度。</p>

<h1 id="压测对比虚拟线程-vs-传统线程池">三、压测对比：虚拟线程 vs 传统线程池</h1>

<p>光说不练假把式。下面我们用一段可复现的基准测试代码，对比虚拟线程和固定大小线程池在 I/O 密集型场景下的表现。</p>

<h2 id="测试场景设计">3.1 测试场景设计</h2>

<ul>
<li><strong>任务数</strong>：10,000 个并发任务</li>
<li><strong>每个任务</strong>：模拟 I/O 阻塞（<code>Thread.sleep(100ms)</code>，模拟一次远程调用或 DB 查询）</li>
<li><strong>对比组</strong>：
  <ul>
  <li>A 组：<code>newFixedThreadPool(200)</code> — 典型的 Tomcat 默认线程规模</li>
  <li>B 组：<code>newVirtualThreadPerTaskExecutor()</code> — 虚拟线程</li>
  </ul>
</li>
</ul>

<h2 id="基准测试代码">3.2 基准测试代码</h2>

<pre><code class="language-java">import java.time.Duration;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class VtBenchmark {

    static final int TASK_COUNT = 10_000;
    static final Duration IO_WAIT = Duration.ofMillis(100);

    // 模拟一个 I/O 密集型任务
    static Runnable ioTask(int taskId) {
        return () -> {
            try {
                Thread.sleep(IO_WAIT); // 模拟 DB/RPC 等待
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };
    }

    // A 组：传统固定线程池
    static long benchFixedPool(int poolSize) throws InterruptedException {
        ExecutorService executor = Executors.newFixedThreadPool(poolSize);
        long start = System.currentTimeMillis();
        try {
            CountDownLatch latch = new CountDownLatch(TASK_COUNT);
            IntStream.range(0, TASK_COUNT).forEach(i ->
                executor.submit(() -> { ioTask(i).run(); latch.countDown(); })
            );
            latch.await();
        } finally {
            executor.shutdown();
        }
        return System.currentTimeMillis() - start;
    }

    // B 组：虚拟线程
    static long benchVirtualThreads() throws InterruptedException {
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            CountDownLatch latch = new CountDownLatch(TASK_COUNT);
            long start = System.currentTimeMillis();
            IntStream.range(0, TASK_COUNT).forEach(i ->
                executor.submit(() -> { ioTask(i).run(); latch.countDown(); })
            );
            latch.await();
            return System.currentTimeMillis() - start;
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("=== 虚拟线程 vs 固定线程池压测 ===");
        System.out.println("任务数: " + TASK_COUNT + ", 每任务模拟 I/O: " + IO_WAIT);

        // Warm-up
        benchFixedPool(200);
        benchVirtualThreads();

        for (int size : new int[]{50, 200, 500}) {
            long fixedMs = benchFixedPool(size);
            long vtMs = benchVirtualThreads();
            System.out.printf("FixedPool(%3d): %4d ms | VT: %4d ms | 加速比: %.1fx%n",
                size, fixedMs, vtMs, (double) fixedMs / Math.max(vtMs, 1));
        }
    }
}
</code></pre>

<h2 id="预期结果与分析">3.3 预期结果与分析</h2>

<p>在 8 核机器上的典型输出（实际数值因硬件略有差异）：</p>
<pre><code>=== 虚拟线程 vs 固定线程池压测 ===
任务数: 10000, 每任务模拟 I/O: 100ms
FixedPool( 50): 20005 ms | VT:   103 ms | 加速比: 194.2x
FixedPool(200):  5003 ms | VT:   101 ms | 加速比: 49.5x
FixedPool(500):  2003 ms | VT:   105 ms | 加速比: 19.1x
</code></pre>

<p><strong>结果解读：</strong></p>
<ul>
<li><strong>FixedPool(200)</strong>：200 个线程分批处理 10000 个任务，每批 200 个同时等 100ms，需要约 50 批 ≈ 5 秒。</li>
<li><strong>虚拟线程</strong>：10000 个虚拟线程几乎同时进入等待状态，平台线程在等待期间被释放去执行其他虚拟线程，总耗时接近单次 I/O 延迟（~100ms）。</li>
<li><strong>加速比</strong>随线程池增大而缩小——但即使给线程池配到 500（已经很不现实），虚拟线程仍有近 20 倍优势。</li>
</ul>

<pre><code>⚠️ 注意：这是「理想 I/O 阻塞」场景。真实服务中还要考虑：
1. 数据库连接池上限（比如 HikariCP 默认 10）
2. 下游接口限流（QPS 配额）
3. 锁竞争（synchronized / ReentrantLock）
4. GC 暂停与对象分配压力
这些因素都可能成为新的瓶颈，虚拟线程不是银弹。
</code></pre>

<h2 id="真实场景参考数据得物技术压测">3.4 真实场景参考：得物技术压测</h2>

<p>得物技术团队在 JDK 21 上做过一组更贴近真实服务的压测（模拟 DB + RPC 混合 I/O），核心结论：</p>
<table>
<thead><tr><th>指标</th><th>平台线程池(200)</th><th>虚拟线程</th><th>提升</th></tr></thead>
<tbody>
<tr><td>吞吐量 (QPS)</td><td>~2,800</td><td>~8,500+</td><td><strong>~3x</strong></td></tr>
<tr><td>P99 延迟</td><td>~120ms</td><td>~80ms</td><td>降低 ~33%</td></tr>
<tr><td>线程栈内存</td><td>~200 MB (200线程)</td><td>&lt; 20 MB (10000 VT)</td><td>降低 &gt;90%</td></tr>
</tbody>
</table>

<p>来源：<a href="https://tech.dewu.com/article?id=89" target="_blank">得物技术《虚拟线程原理及性能分析》</a></p>

<p>注意：真实场景加速比低于理想场景（3x vs 50x），因为<strong>数据库连接池、RPC 连接池等外部资源成了新瓶颈</strong>。这也印证了一点：<strong>虚拟线程解决的是「线程等待太贵」的问题，不解决「后端资源有限」的问题</strong>。</p>

<h1 id="生产环境落地避坑指南">四、生产环境落地：避坑指南</h1>

<h2 id="坑1-synchronized-导致-pinning载线程钉住">坑 1：<code>synchronized</code> 导致 Pinning（载体线程被钉住）</h2>

<p>这是虚拟线程最著名的坑。</p>

<p>在 JDK 21~23 中，当虚拟线程进入 <code>synchronized</code> 代码块/方法后遇到阻塞，<strong>无法卸载</strong>，会一直占着底层平台线程。这叫 <strong>Pinning（钉住）</strong>。</p>

<pre><code class="language-java">// ❌ 问题代码：synchronized + 阻塞操作 → Pinning
private static final Object lock = new Object();

void badPattern() {
    synchronized (lock) {
        // 这里如果发生阻塞，虚拟线程无法 unmount！
        // 平台线程会被一直占用
        blockingIoCall(); 
    }
}
</code></pre>

<p><strong>解决方案（三选一）：</strong></p>
<ol>
<li><strong>换成 ReentrantLock</strong>（推荐，改动最小）：
<pre><code class="language-java">private static final ReentrantLock lock = new ReentrantLock();

void goodPattern() {
    lock.lock();  // ReentrantLock 支持虚拟线程卸载
    try {
        blockingIoCall();
    } finally {
        lock.unlock();
    }
}
</code></pre>
</li>
<li><strong>升级 JDK 24+</strong>：JEP 491 引入了 <code>synchronized</code> 的虚拟线程感知优化，大部分 Pinning 场景被自动消除。</li>
<li><strong>用 JFR 检测 Pinning</strong>（见下一节观测方法）。</li>
</ol>

<h2 id="坑2-threadlocal-内存膨胀">坑 2：ThreadLocal 内存膨胀</h2>

<p>虚拟线程的数量可能是平台线程的成百上千倍。如果每个虚拟线程都在 <code>ThreadLocal</code> 里放了东西，内存会爆炸。</p>

<pre><code class="language-java">// ⚠️ 危险：10000 个虚拟线程 × 每个 ThreadLocal 存 1KB 对象 = ~10MB（单个变量）
// 如果框架/中间件里有多层 ThreadLocal，叠加起来会很可观
static final ThreadLocal&lt;byte[]&gt; data = ThreadLocal.withInitial(() -> new byte[1024]);
</code></pre>

<p><strong>应对策略：</strong></p>
<ul>
<li>审查项目中 <code>ThreadLocal</code> 的使用，尤其是框架层面的（如 Spring Security Context、TraceId 传递等）。</li>
<li>JDK 24+ 引入了作用域值（Scoped Value，JEP 446）作为 ThreadLocal 的替代方案，更适合虚拟线程场景。</li>
<li>优先使用 <code>TransmittableThreadLocal</code>（阿里 TTL 库）在异步场景中传递上下文。</li>
</ul>

<h2 id="坑3-不要池化虚拟线程">坑 3：不要池化虚拟线程</h2>

<p>虚拟线程本身就是廉价的，「每个任务一个虚拟线程」才是正确用法。对虚拟线程做线程池相当于：</p>
<ul>
<li>重新引入了排队逻辑（又绕回去了）；</li>
<li>失去了虚拟线程最大的优势（无限并发能力）；</li>
<li>增加了不必要的复杂度。</li>
</ul>

<p>如果你需要<strong>限制对某个资源的并发访问</strong>，应该限制资源本身，而不是限制线程：</p>
<pre><code class="language-java">// ✅ 正确：用 Semaphore 限制对老系统的并发调用
private static final Semaphore DB_LIMIT = new Semaphore(20);

public Result queryWithLimit() throws InterruptedException {
    DB_LIMIT.acquire();
    try {
        return db.query();
    } finally {
        DB_LIMIT.release();
    }
}
</code></pre>

<h2 id="坑4-cpu密集型任务不会更快">坑 4：CPU 密集型任务不会更快</h2>

<p>虚拟线程优化的是<strong>等待时间</strong>的利用率，不是 CPU 计算速度。如果你的任务是纯计算（加密、压缩、复杂规则引擎），虚拟线程不会带来加速，甚至因为调度开销略慢于平台线程。</p>

<pre><code class="language-java">// ❌ 这种场景用虚拟线程没意义（甚至更慢）
executor.submit(() -> {
    // 纯 CPU 计算，没有 I/O 等待
    double result = heavyComputation(data);
});
</code></pre>

<p>CPU 密集型任务的正确做法：用 <code>ForkJoinPool</code>、并行流（<code>parallelStream()</code>），或者固定大小的计算线程池。</p>

<h1 id="如何观测虚拟线程-jfr--jcmd">五、如何观测虚拟线程：JFR + jcmd</h1>

<p>JDK 为虚拟线程提供了专门的 JFR（JDK Flight Recorder）事件和 <code>jcmd</code> 支持。</p>

<h2 id="jfr-事件采集">5.1 JFR 事件采集</h2>

<p>虚拟线程相关的 JFR 事件：</p>
<table>
<thead><tr><th>事件名</th><th>含义</th></tr></thead>
<tbody>
<tr><td><code>jdk.VirtualThreadStart</code></td><td>虚拟线程启动</td></tr>
<tr><td><code>jdk.VirtualThreadEnd</code></td><td>虚拟线程结束</td></tr>
<tr><td><code>jdk.VirtualThreadPinned</code></td><td>虚拟线程被 Pinning（重要！）</td></tr>

</tbody>
</table>

<p>启动应用时开启 JFR 录制：</p>
<pre><code># 启动时添加参数
java -XX:StartFlightRecording=duration=60s,filename=recording.jfr,filename=vt-recording.jar ...
</code></pre>

<p>或者在运行中动态开启：</p>
<pre><code># 查找进程 PID
jps

# 开启录制（60秒）
jcmd &lt;PID&gt; JFR.start duration=60s filename=recording.jfr settings=profile

# 查看 Pinning 事件
jfr print --events jdk.VirtualThreadPinned recording.jfr
</code></pre>

<h2 id="线程Dump-查看虚拟线程">5.2 线程 Dump 查看虚拟线程</h2>

<pre><code># 传统线程 dump（只显示平台线程）
jcmd &lt;PID&gt; Thread.print

# 包含虚拟线程的 dump
jcmd &lt;PID&gt; Thread.print -x
</code></pre>

<p>加上 <code>-x</code> 参数后，线程 dump 中会用 <code>virtual#</code> 前缀标识每个虚拟线程及其当前状态，方便排查哪个请求卡在哪里。</p>

<h1 id="内存占用对比">六、内存占用对比</h1>

<p>我们用一个简单的实验来量化虚拟线程的内存优势：</p>

<pre><code class="language-java">/**
 * 运行参数：-XX:NativeMemoryTracking=detail
 * 
 * 分别创建 4000 个平台线程 vs 4000 个虚拟线程，
 * 用 jcmd VM.native_memory 查看线程栈占用。
 */
public class MemoryCompare {
    
    static final int COUNT = 4000;
    
    public static void main(String[] args) throws Exception {
        // 方案A：4000 个平台线程
        for (int i = 0; i &lt; COUNT; i++) {
            new Thread(() -> {
                try { Thread.sleep(Long.MAX_VALUE); }
                catch (InterruptedException e) { e.printStackTrace(); }
            }, "pt-" + i).start();
        }
        Thread.sleep(Long.MAX_VALUE);

<h1 id="spring-boot-集成快速开关">七、Spring Boot 集成：快速开关</h1>

<p>在 Spring Boot 3.2+ 中，开启虚拟线程只需要一行配置：</p>

<pre><code># application.yml
spring:
  threads:
    virtual:
      enabled: true
</code></pre>

<p>开启后，Tomcat（Servlet 容器）的请求处理线程会自动切换为虚拟线程。<strong>业务代码零改动</strong>。</p>

<p>兼容性注意事项：</p>
<ul>
<li>Spring Boot <strong>3.2+</strong> 才支持该配置项（基于 Tomcat 11+ 或 Undertow 虚拟线程支持）。</li>
<li>部分不支持虚拟线程的组件可能报错（如某些旧版 JDBC 驱动、Hystrix 等），需要逐一验证。</li>
<li>建议先在<strong>预发/灰度环境</strong>观察 QPS、延迟 P99 和 Pinning 事件频率后再全量上线。</li>
</ul>

<h1 id="总结">八、总结</h1>

<p>本文覆盖了虚拟线程的核心知识点，回顾一下要点：</p>

<ol>
<li><strong>虚拟线程是什么</strong>：JDK 21 引入的轻量级 Thread 实现，由 JVM 调度，遇 I/O 阻塞时自动卸载平台线程。</li>
<li><strong>适用场景</strong>：大量并发 I/O 等待的任务（DB 查询、RPC 调用、消息队列消费等）；不适合纯 CPU 计算。</li>
<li><strong>性能提升</strong>：理想 I/O 场景下相比 200 线程池可有数十倍吞吐提升；真实服务受限于连接池等外部资源，通常 2~5 倍。</li>
<li><strong>最大坑：Pinning</strong>：<code>synchronized</code> 中的阻塞会导致载体线程无法释放，解决方案是用 <code>ReentrantLock</code> 替换或升级 JDK 24+。</li>
<li><strong>不要池化</strong>：虚拟线程应该「每任务一个」，用 <code>Semaphore</code> 限流而非限制线程数。</li>
<li><strong>观测手段</strong>：用 JFR 采集 <code>jdk.VirtualThreadPinned</code> 事件排查 Pinning，用 <code>jcmd &lt;PID&gt; Thread.print -x</code> 查看虚拟线程 dump。</li>
<li><strong>Spring Boot 3.2+</strong> 一行配置即可开启 Tomcat 虚拟线程，但建议灰度验证。</li>
</ol>

<pre><code>📌 一句话总结：虚拟线程让「同步写法 + 高吞吐」成为可能，
但它不是银弹——连接池、限流、CPU 瓶颈仍然需要你关注。
从今天起，新项目的 I/O 密集型服务可以直接考虑虚拟线程作为默认选项。
</code></pre>
