<h1 id="背景-为什么-ai-接口特别需要缓存"><a href="#背景-为什么-ai-接口特别需要缓存" class="headerlink" title="背景：为什么 AI 接口特别需要缓存"></a>背景：为什么 AI 接口特别需要缓存</h1>

做 Java 后端的同学接 AI 应用时，经常会遇到一个挺现实的问题：传统接口几十毫秒就能返回，到了 LLM（Large Language Model，大语言模型，可以理解成能够根据上下文生成文本的模型）这里，动不动就是几百毫秒到几秒。更麻烦的是，它还按 token 收费。**token** 可以简单理解成模型处理文本时切出来的小片段，输入越长、输出越长，钱和时间一般都会涨。

如果这是一个“帮用户总结固定知识库答案”的接口，很多请求其实高度重复：同一个问题、同一个用户权限、同一批知识片段、同一个提示词版本。这个时候还每次都完整调用模型，就像每次访问首页都重新编译整个项目，技术上能跑，工程上不划算。

本文选一个比较接地气的目标：用 Java/Spring Boot 做一个 LLM 问答接口的**多级缓存**。多级缓存就是把缓存分成几层，例如本机内存一层、Redis 一层、远程模型一层；越靠前越快，越靠后越贵。我们会重点回答三个问题：

<ul>
<li>缓存 key 到底应该包含哪些字段，才不容易串答案？</li>
<li>本地缓存 + Redis 缓存能把 P95 延迟降到什么程度？</li>
<li>怎么用 JFR 观察 Java 进程有没有因为缓存引入新的 CPU/内存问题？</li>
</ul>

<h1 id="目标读者与先修知识"><a href="#目标读者与先修知识" class="headerlink" title="目标读者与先修知识"></a>目标读者与先修知识</h1>

<ul>
<li>目标读者：做 Java 后端、正在接入 LLM/RAG/智能问答接口的开发者。</li>
<li>先修知识：会写 Spring Boot REST 接口，知道 Redis 基本用法，理解 HTTP 压测的 P50/P95/P99 指标。</li>
<li>本文不假设你已经懂 Spring AI。示例代码只抽象一个 <code>ModelClient</code>，方便替换成 OpenAI、通义、豆包、DeepSeek 或公司内部模型网关。</li>
</ul>

> 注：**P95** 是延迟百分位指标，表示 95% 的请求都快于这个值。它比平均值更适合看线上体验，因为平均值很容易被少量慢请求“掩盖”。

<h1 id="先把链路画清楚"><a href="#先把链路画清楚" class="headerlink" title="先把链路画清楚"></a>先把链路画清楚</h1>

一个最小的 AI 问答接口大概长这样：

```text
浏览器/业务系统
   |
   v
Spring Boot API
   |
   +--> 构造 prompt
   |
   +--> 调 LLM 网关
   |
   +--> 返回答案
```

加入多级缓存后，链路变成：

```text
请求
 |
 v
规范化问题 + 权限 + prompt 版本 + 知识库版本
 |
 v
生成 cacheKey
 |
 +--> L1 本地缓存命中？是：返回
 |
 +--> L2 Redis 命中？是：回填 L1 后返回
 |
 +--> 未命中：调用 LLM，写 Redis，写 L1，返回
```

这里的关键不是“加一个 Redis 就完事”，而是**缓存边界**要设计清楚。AI 场景里，答案是否可复用通常取决于下面这些因素：

<tr>

<tr>
<td>规范化后的问题</td>
<td>同义空格、大小写、标点可以归一</td>
<td>缓存命中率低</td>
</tr>
<tr>
<td>用户权限/租户</td>
<td>不同用户可见数据不同</td>

</tr>

<td>返回过期知识</td>
</tr>
<tr>
<td>模型名/温度参数</td>
<td>模型和采样参数影响输出</td>

**RAG**（Retrieval-Augmented Generation，检索增强生成）是指先从知识库里检索相关资料，再把资料塞进 prompt 让模型回答。它解决的是“模型不知道你公司内部知识”的问题，但也让缓存 key 多了一个维度：知识库内容版本。

<h1 id="工程方案-L1-Caffeine-L2-Redis"><a href="#工程方案-L1-Caffeine-L2-Redis" class="headerlink" title="工程方案：L1 Caffeine + L2 Redis"></a>工程方案：L1 Caffeine + L2 Redis</h1>

本文采用两层缓存：

<ul>
<li><strong>L1：Caffeine 本地缓存</strong>。Caffeine 是 Java 里常用的高性能本地缓存库，适合挡住热点 key，省掉网络开销。</li>
<li><strong>L2：Redis 分布式缓存</strong>。Redis 是内存型 key-value 存储，适合在多实例之间共享缓存结果。</li>
</ul>

为什么不只用 Redis？因为 Redis 再快也要走一次网络，本机热点直接命中 Caffeine 通常会更稳。为什么不只用本地缓存？因为服务一扩容，每台机器都有自己的缓存，命中率会被打散，发布重启也会丢。

<h2 id="构造-cache-key"><a href="#构造-cache-key" class="headerlink" title="构造 cache key"></a>构造 cache key</h2>

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;
import java.util.Locale;

public final class LlmCacheKey {
    private LlmCacheKey() {}

    public static String of(AskRequest req, String model, double temperature) {
        String normalizedQuestion = normalize(req.question());
        String raw = String.join("|",
            "tenant=" + safe(req.tenantId()),
            "user=" + safe(req.userId()),
            "prompt=" + safe(req.promptVersion()),
            "kb=" + safe(req.kbVersion()),
            "model=" + model,
            "temperature=" + temperature,
            "q=" + normalizedQuestion
        );
        return "llm:answer:v1:" + sha256(raw);
    }

    private static String normalize(String text) {
        if (text == null) {
            return "";
        }
        return text.trim()
            .replaceAll("\\s+", " ")
            .toLowerCase(Locale.ROOT);
    }

    private static String safe(String value) {
        return value == null ? "" : value.trim();
    }

    private static String sha256(String raw) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] bytes = digest.digest(raw.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(bytes);
        } catch (Exception e) {
            throw new IllegalStateException("sha256 failed", e);
        }
    }
}
```

这里把原始 key 做了 SHA-256。**SHA-256** 是一种哈希算法，作用是把任意长度文本变成固定长度摘要；这里不是为了加密，而是为了让 Redis key 更短、更稳定。

<h2 id="缓存服务实现"><a href="#缓存服务实现" class="headerlink" title="缓存服务实现"></a>缓存服务实现</h2>

```java
import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import org.springframework.data.redis.core.StringRedisTemplate;

import java.time.Duration;
import java.util.concurrent.TimeUnit;

public class CachedLlmService {
    private final Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(20_000)
        .expireAfterWrite(Duration.ofMinutes(10))
        .recordStats()
        .build();

    private final StringRedisTemplate redisTemplate;
    private final ModelClient modelClient;

    private static final String MODEL = "mock-gpt";
    private static final double TEMPERATURE = 0.2;

    public CachedLlmService(StringRedisTemplate redisTemplate, ModelClient modelClient) {
        this.redisTemplate = redisTemplate;
        this.modelClient = modelClient;
    }

    public AskResponse ask(AskRequest request) {
        long start = System.nanoTime();
        String cacheKey = LlmCacheKey.of(request, MODEL, TEMPERATURE);

        String l1 = localCache.getIfPresent(cacheKey);
        if (l1 != null) {
            return new AskResponse(l1, "L1", elapsedMillis(start));
        }

        String l2 = redisTemplate.opsForValue().get(cacheKey);
        if (l2 != null) {
            localCache.put(cacheKey, l2);
            return new AskResponse(l2, "L2", elapsedMillis(start));
        }

        String prompt = buildPrompt(request);
        String answer = modelClient.complete(prompt);

        redisTemplate.opsForValue().set(cacheKey, answer, 30, TimeUnit.MINUTES);
        localCache.put(cacheKey, answer);
        return new AskResponse(answer, "MODEL", elapsedMillis(start));
    }

    private static String buildPrompt(AskRequest request) {
        return "请基于当前知识库回答问题。知识库版本=" + request.kbVersion()
            + "，问题=" + request.question();
    }

    private static long elapsedMillis(long startNano) {
        return TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNano);
    }

    public String stats() {
        return localCache.stats().toString();
    }
}
```

有两个细节值得注意：

<ul>
<li><code>expireAfterWrite</code> 是写入后过期，不会因为频繁访问就一直续命，适合“答案最多缓存 10 分钟”的业务语义。</li>
<li><code>recordStats</code> 会记录命中率、驱逐次数等指标，排查缓存是否真的有效时很好用。</li>
</ul>

<h1 id="用-JFR-验证是否引入新问题"><a href="#用-JFR-验证是否引入新问题" class="headerlink" title="用 JFR 验证是否引入新问题"></a>用 JFR 验证是否引入新问题</h1>

压测结束后，会得到 <code>llm-cache.jfr</code>。可以用 JDK Mission Control 打开，也可以先用命令行看摘要：

```bash
jfr summary llm-cache.jfr
jfr view gc-pauses llm-cache.jfr
jfr view allocation-by-class llm-cache.jfr | head -30
```

重点看三类信号：

<ul>
<li><strong>GC Pause</strong>：缓存对象太多时，停顿会不会明显变长。</li>
<li><strong>allocation-by-class</strong>：是否有大量字符串拼接、JSON 序列化对象分配。</li>
<li><strong>hot-methods</strong>：cache key 计算、序列化、Redis 客户端是否成为 CPU 热点。</li>
</ul>

一组比较健康的现象是：

```text
GC pause p95 < 10ms
缓存命中后 hot methods 主要集中在 HTTP 编解码和少量 JSON 序列化
L1 eviction 不持续高速增长
Redis ops latency p95 < 5ms
```

如果发现 <code>allocation-by-class</code> 里 <code>byte[]</code>、<code>char[]</code>、JSON 节点对象特别多，可以优先检查：

<ul>
<li>是否每次命中 L1 仍然重复做 JSON 反序列化；</li>
<li>是否把超大的答案直接塞进本地缓存；</li>
<li>是否构造 cache key 时拼了完整 prompt，而不是拼稳定字段后做哈希。</li>
</ul>

<h2 id="缓存穿透与击穿"><a href="#缓存穿透与击穿" class="headerlink" title="缓存穿透与击穿"></a>缓存穿透与击穿</h2>

**缓存穿透** 是指请求永远查不到缓存，每次都打到后端；在 AI 场景里，可能是用户不断提交随机问题。**缓存击穿** 是指一个热点 key 过期瞬间，大量请求同时打到模型。

建议做三件事：

<ul>
<li>对明显无意义输入做校验，例如空问题、超长问题、纯随机字符。</li>
<li>热点 key 使用互斥加载：同一个 key 同一时刻只允许一个请求去调模型，其他请求短暂等待。</li>
<li>TTL 增加随机抖动，例如 30 分钟 ± 3 分钟，避免大量 key 同时过期。</li>
</ul>

简单互斥加载可以这样写：

```java
private final com.google.common.util.concurrent.Striped<java.util.concurrent.locks.Lock> locks =
    com.google.common.util.concurrent.Striped.lock(1024);

public AskResponse askWithLock(AskRequest request) {
    String key = LlmCacheKey.of(request, MODEL, TEMPERATURE);
    String cached = localCache.getIfPresent(key);
    if (cached != null) {
        return new AskResponse(cached, "L1", 0);
    }

    var lock = locks.get(key);
    lock.lock();
    try {
        // 进入锁后必须再查一次缓存，避免重复调用模型
        return ask(request);
    } finally {
        lock.unlock();
    }
}
```

这里用到的 <code>Striped</code> 是 Guava 里的分段锁工具，可以理解成“很多 key 共用一组锁”，避免为每个 key 创建一把锁导致内存膨胀。

<h1 id="常见坑和误区"><a href="#常见坑和误区" class="headerlink" title="常见坑和误区"></a>常见坑和误区</h1>

<h2 id="坑一-cache-key-只用问题文本"><a href="#坑一-cache-key-只用问题文本" class="headerlink" title="坑一：cache key 只用问题文本"></a>坑一：cache key 只用问题文本</h2>

这是最危险的做法。AI 问答经常受权限、知识库、prompt、模型参数影响。只用问题文本，轻则答案过期，重则数据越权。

<h2 id="坑二-缓存随机性太强的答案"><a href="#坑二-缓存随机性太强的答案" class="headerlink" title="坑二：缓存随机性太强的答案"></a>坑二：缓存随机性太强的答案</h2>

如果 <code>temperature</code> 很高，模型输出本来就偏发散，缓存价值会下降。面向知识问答时，建议把 temperature 调低，让答案更稳定；面向创意生成时，缓存策略要更谨慎。

<h2 id="坑三-只看平均延迟"><a href="#坑三-只看平均延迟" class="headerlink" title="坑三：只看平均延迟"></a>坑三：只看平均延迟</h2>

平均值会掩盖长尾。AI 接口最容易出问题的就是 P95/P99：模型网关排队、网络抖动、Redis 慢查询、JVM GC 都会把尾延迟拉长。压测时至少看 P50/P95/P99。

<h2 id="坑四-缓存没有可观测性"><a href="#坑四-缓存没有可观测性" class="headerlink" title="坑四：缓存没有可观测性"></a>坑四：缓存没有可观测性</h2>

上线后至少要有这些指标：

<ul>
<li>L1/L2 命中率；</li>
<li>模型调用次数和失败率；</li>
<li>Redis 操作延迟；</li>
<li>按租户/接口维度的 token 成本；</li>
<li>缓存驱逐次数和本地缓存大小。</li>
</ul>

没有指标时，缓存系统会变成黑盒。命中率下降、成本飙升、答案过期，都会很难排查。

<h1 id="如何验证结论"><a href="#如何验证结论" class="headerlink" title="如何验证结论"></a>如何验证结论</h1>

可以按下面顺序自测：

<ol>
<li>启动 Redis：<code>docker run --rm --name redis-llm-cache -p 6379:6379 redis:7-alpine</code>。</li>
<li>启动应用，分别设置 <code>--cache.mode=no-cache</code>、<code>--cache.mode=redis-only</code>、<code>--cache.mode=l1-l2</code>。</li>
<li>用同一份 <code>ask.lua</code> 执行 <code>wrk -t4 -c64 -d60s</code>。</li>
<li>记录每轮 QPS、P50、P95、P99、模型调用次数。</li>
<li>打开 JFR 文件，检查 GC Pause、allocation-by-class、hot-methods。</li>
<li>修改 <code>promptVersion</code> 或 <code>kbVersion</code>，确认缓存会失效并重新调用模型。</li>
<li>修改 <code>tenantId</code>，确认不同租户不会命中同一份答案。</li>
</ol>

如果这些步骤都能通过，基本可以证明：缓存确实降低了延迟和模型调用成本，并且没有牺牲权限边界与知识更新语义。

<h1 id="总结"><a href="#总结" class="headerlink" title="总结"></a>总结</h1>

这篇文章的核心观点很简单：AI 接口不是不能慢，但不能把所有慢都推给模型。Java 后端能做的工程优化还有很多，多级缓存就是性价比很高的一项。

<ul>
<li>缓存 key 必须包含问题、租户/权限、prompt 版本、知识库版本、模型参数等影响答案的字段。</li>
<li>L1 Caffeine 适合挡热点，L2 Redis 适合多实例共享，组合起来比单层缓存更稳。</li>
<li>压测不能只看平均值，至少看 P50/P95/P99，并记录模型调用比例。</li>
<li>JFR 可以验证缓存优化有没有引入新的 CPU、GC、对象分配问题。</li>
<li>缓存 TTL 要服务业务语义，不要为了命中率牺牲答案正确性和权限安全。</li>
</ul>

后续如果要继续深入，可以把这套方案接到 Spring AI 或 LangChain4j，再加上 RAG 召回结果摘要缓存、Embedding 缓存和 token 成本看板。那时优化空间会更大，但原则仍然一样：先定义清楚什么答案可以复用，再谈性能。
