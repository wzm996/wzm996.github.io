<p>很多团队把 <strong>Spring AI</strong> 接进项目后，功能很快能跑通，但一上并发就开始出现一种很烦的现象：平均耗时看起来还行，<strong>P95/P99</strong> 却抖得很厉害。<br>这类问题通常不是“模型突然变慢”这么简单，更常见的是 <strong>HTTP 连接池不够、并发度失控、重试策略放大抖动</strong> 叠在一起，最后把尾延迟拖爆。</p>
</blockquote>

<!-- more -->

<h1 id="一、这篇文章要解决什么问题"><a href="#一、这篇文章要解决什么问题" class="headerlink" title="一、这篇文章要解决什么问题"></a>一、这篇文章要解决什么问题</h1>
<p>这篇文章我们不聊“Prompt 怎么写得更优雅”，也不聊“RAG 架构怎么设计得更大”。我们只盯一个特别工程化、但又特别容易被忽略的问题：<strong>Java 服务通过 Spring AI 调用大模型接口时，为什么尾延迟会抖</strong>。</p>
<p>先把几个新名词讲人话：</p>
<ul>
<li><strong>P50/P95/P99</strong>：就是延迟分位数。P50 可以理解成“中位数”，P95 表示 95% 的请求都比这个值快，P99 表示最慢的那 1% 请求大概有多慢。线上体验差，很多时候不是平均值差，而是 <strong>P95/P99 太难看</strong>。</li>
<li><strong>尾延迟（Tail Latency）</strong>：不是平均慢，而是少部分请求特别慢。用户最容易骂的，往往就是这部分。</li>
<li><strong>JFR</strong>：全称 <strong>Java Flight Recorder</strong>，是 JDK 自带的性能诊断工具。你可以把它理解成“JVM 自带的黑匣子”，能录线程、锁、GC、方法热点、网络等待等信息。</li>
<li><strong>连接池</strong>：不是数据库专属，大模型 HTTP 调用同样有连接池。它解决的是“别每次都重新建 TCP/TLS 连接”，不然握手成本会把延迟白白抬高。</li>
<li><strong>重试</strong>：请求失败后再来一次。它本来是为了提升成功率，但如果没有边界，<strong>失败时的重试会放大拥塞</strong>，把系统拖进雪崩。</li>
</ul>
<p>本文会给出一套可复现的实验：同一套 Spring Boot + Spring AI 服务，只改 <strong>连接池大小、调用并发度、重试参数</strong>，观察吞吐、P95/P99、JFR 采样结果如何变化。最后你会得到一套比较稳的调参思路。</p>

<h1 id="二、为什么-LLM-调用特别容易出现尾延迟问题"><a href="#二、为什么-LLM-调用特别容易出现尾延迟问题" class="headerlink" title="二、为什么 LLM 调用特别容易出现尾延迟问题"></a>二、为什么 LLM 调用特别容易出现尾延迟问题</h1>
<p>传统 CRUD 接口里，很多请求是“本地 CPU + 数据库查询 + 缓存命中”。而 LLM 调用天然带两个特点：</p>
<blockquote>
<p>1、它是远程网络调用；<br>2、它的响应时间本身就比普通接口大一个数量级。</p>
</blockquote>
<p>比如你一个普通查询接口平时 20ms，偶发到 100ms，用户未必能明显感知。但大模型接口平时如果就是 900ms~1500ms，再叠加排队、重试、连接争抢，P95 很容易冲到 3s 甚至 5s 以上。</p>
<p>更要命的是，很多项目刚接入时只做了“能调通”这一步，下面这些问题一个没收：</p>
<ul>
<li>HTTP 客户端默认连接池太小</li>
<li>业务线程池把下游模型接口打满了</li>
<li>超时时间和重试策略互相打架</li>
<li>失败请求重试后继续占用线程，导致排队时间变长</li>
<li>流式与非流式接口混用，但连接预算没有分开</li>
</ul>
<p>这就像饭馆只有 10 张桌子，你却一次放了 200 个顾客进来。前台没崩，不代表体验没崩。</p>

<h2 id="4-2-应用配置"><a href="#4-2-应用配置" class="headerlink" title="4.2 应用配置"></a>4.2 应用配置</h2>
<pre><code class="language-yaml">server:
  port: 8080

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY:test-key}
      base-url: ${OPENAI_BASE_URL:http://localhost:11434}
      chat:
        options:
          model: ${OPENAI_MODEL:gpt-4o-mini}

app:

    read-timeout-ms: 10000
    max-connections: 64
    pending-acquire-timeout-ms: 200
    retry-times: 1
    retry-wait-ms: 150</code></pre>
<p><strong>pending-acquire-timeout</strong> 第一次看到可能有点陌生。它的意思很简单：当连接池里没有空闲连接时，一个请求最多愿意等多久去抢连接。这个值太大，会把请求悄悄堆在客户端；太小，会更早失败。它本质上是“排队容忍度”。</p>

<h2 id="4-3-并发闸门实现"><a href="#4-3-并发闸门实现" class="headerlink" title="4.3 并发闸门实现"></a>4.3 并发闸门实现</h2>
<pre><code class="language-java">@Component
public class AiConcurrencyLimiter {

    private final Semaphore semaphore;

    public AiConcurrencyLimiter(@Value("${app.ai.concurrency:32}") int concurrency) {
        this.semaphore = new Semaphore(concurrency);
    }

    public &lt;T&gt; T execute(Callable&lt;T&gt; task) {
        boolean acquired = semaphore.tryAcquire();
        if (!acquired) {
            throw new IllegalStateException("ai concurrency limit reached");
        }
        try {
            return task.call();
        } catch (Exception e) {
            throw new RuntimeException(e);
        } finally {
            semaphore.release();
        }
    }
}</code></pre>
<p>为什么这里要显式加一个并发闸门？因为很多系统的问题不是“机器不够强”，而是 <strong>你没有给下游设预算</strong>。如果应用线程池能无限把请求往外怼，LLM 一旦稍慢一点，所有请求都会在应用内堆积。</p>

<h2 id="4-4-服务层调用"><a href="#4-4-服务层调用" class="headerlink" title="4.4 服务层调用"></a>4.4 服务层调用</h2>
<pre><code class="language-java">@Service
public class AiChatService {

    private final ChatClient chatClient;
    private final AiConcurrencyLimiter limiter;

    public AiChatService(ChatClient.Builder builder, AiConcurrencyLimiter limiter) {
        this.chatClient = builder.build();
        this.limiter = limiter;
    }

    public String chat(String prompt) {
        return limiter.execute(() -&gt;
            chatClient.prompt()
                .user(prompt)
                .call()
                .content()
        );
    }
}</code></pre>

@RequestMapping("/ai")
public class AiController {

    private final AiChatService aiChatService;

    public AiController(AiChatService aiChatService) {

<h2 id="4-6-Mock-Server-模拟模型延迟与失败"><a href="#4-6-Mock-Server-模拟模型延迟与失败" class="headerlink" title="4.6 Mock Server 模拟模型延迟与失败"></a>4.6 Mock Server 模拟模型延迟与失败</h2>
<p>本地你可以直接用 WireMock、MockWebServer，或者最简单一点，用一个 Node/Python 小服务模拟。下面给个 Python 版本：</p>
<pre><code class="language-python">from flask import Flask, request, jsonify
import random, time

app = Flask(__name__)

@app.route('/v1/chat/completions', methods=['POST'])
def chat():
    r = random.random()
    if r &lt; 0.1:
        time.sleep(2.5)
    else:
        time.sleep(0.8)

    if r &lt; 0.03:
        return jsonify({"error": "upstream busy"}), 503

    return jsonify({
        "choices": [
            {
                "message": {
                    "content": "mock answer"
                }
            }
        ]
    })

app.run(host='0.0.0.0', port=11434)</code></pre>
<p>这个 Mock Server 做了两件事：</p>
<ul>
<li>90% 请求耗时约 800ms</li>
<li>10% 请求耗时约 2500ms，且其中 3% 直接返回 503</li>
</ul>
<p>这个比例很像真实世界里“平时还行，偶发抖一把”的下游服务。</p>

<h2 id="5-1-压测命令"><a href="#5-1-压测命令" class="headerlink" title="5.1 压测命令"></a>5.1 压测命令</h2>
<p>推荐用 <strong>k6</strong>。它是一个现代压测工具，比传统 ab 更适合做带断言和分位数统计的 HTTP 压测。</p>
<pre><code class="language-javascript">// save as script.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 50,
  duration: '2m',
  thresholds: {
    http_req_failed: ['rate&lt;0.05'],
    http_req_duration: ['p(95)&lt;3000']
  }
};

export default function () {
  const res = http.get('http://localhost:8080/ai/chat?q=用一句话解释线程池排队');
  check(res, {
    'status is 200': (r) =&gt; r.status === 200
  });
  sleep(1);
}</code></pre>
<p>执行命令：</p>
<pre><code class="language-bash">k6 run script.js</code></pre>

<h2 id="5-2-JFR-采集命令"><a href="#5-2-JFR-采集命令" class="headerlink" title="5.2 JFR 采集命令"></a>5.2 JFR 采集命令</h2>
<p>启动服务时加上下面参数：</p>
<pre><code class="language-bash">java \
  -XX:StartFlightRecording=filename=llm-latency.jfr,duration=2m,settings=profile \
  -jar target/demo.jar</code></pre>
<p>如果服务已经启动，也可以用 <code>jcmd</code> 动态录制：</p>
<pre><code class="language-bash">jcmd &lt;pid&gt; JFR.start name=llm-profile settings=profile duration=120s filename=llm-latency.jfr</code></pre>
<p>录完后用 JDK Mission Control 打开 <code>llm-latency.jfr</code>，重点看：</p>
<ul>
<li><strong>Threads</strong>：业务线程是不是大量卡在网络读写或连接获取</li>
<li><strong>Socket Read</strong>：是不是大量时间都在等下游响应</li>
<li><strong>Java Monitor Blocked</strong>：有没有锁竞争放大问题</li>
<li><strong>Garbage Collections</strong>：GC 停顿有没有明显抬高请求尾部</li>
</ul>

<h2 id="5-3-如何验证结论"><a href="#5-3-如何验证结论" class="headerlink" title="5.3 如何验证结论"></a>5.3 如何验证结论</h2>
<p>验证方法不要搞太玄学，按下面流程来：</p>
<blockquote>
<p>1、固定压测脚本不变；<br>2、每次只改一个变量；<br>3、每组压测至少跑 2 分钟；<br>4、记录吞吐、P50、P95、P99、错误率；<br>5、同时保留对应的 JFR 文件。</p>
</blockquote>
<p>最后你会得到一张“参数变化 → 指标变化”的表，不是靠感觉调参，而是靠证据调参。</p>

<p>JFR 里会看到明显的 <strong>Socket Read</strong> 和等待连接的时间堆积，业务线程空转时间增多。</p>

<h1 id="七、JFR-怎么看：别只看-GC，线程等待更关键"><a href="#七、JFR-怎么看：别只看-GC，线程等待更关键" class="headerlink" title="七、JFR 怎么看：别只看 GC，线程等待更关键"></a>七、JFR 怎么看：别只看 GC，线程等待更关键</h1>
<p>很多 Java 同学做性能分析时，第一反应就是看 GC。这个方向没错，但在 LLM 调用这种 IO 型场景里，<strong>GC 往往不是第一现场</strong>。</p>
<p>这次实验里更常见的信号有三个：</p>

<h2 id="7-1-Socket-Read-时间很长"><a href="#7-1-Socket-Read-时间很长" class="headerlink" title="7.1 Socket Read 时间很长"></a>7.1 Socket Read 时间很长</h2>
<p>说明线程主要在等下游响应。这种情况下一味加线程没有意义，因为线程不是在“算”，是在“等”。</p>

<h2 id="7-2-线程数变多，但吞吐没明显变高"><a href="#7-2-线程数变多，但吞吐没明显变高" class="headerlink" title="7.2 线程数变多，但吞吐没明显变高"></a>7.2 线程数变多，但吞吐没明显变高</h2>
<p>这通常说明你进入了“排队放大期”。线程、连接、重试都在堆，但真正完成的请求没明显增多。</p>

<h2 id="7-3-GC-有波动，但不是主因"><a href="#7-3-GC-有波动，但不是主因" class="headerlink" title="7.3 GC 有波动，但不是主因"></a>7.3 GC 有波动，但不是主因</h2>
<p>实验里会有一些短暂的 Young GC，但停顿通常不是主要瓶颈。一个典型现象是：</p>
<pre><code class="language-text">GC pause: 8ms ~ 18ms
P95 latency: 2.4s ~ 4.0s</code></pre>
<p>这说明真正把 P95 拉高的不是 GC，而是网络等待、连接争抢、重试叠加的排队效应。</p>
<p>换句话说，不要一看 Java 慢就下意识甩锅给 JVM。很多时候问题根本不在堆里，而在网线上。</p>

<h1 id="八、成本-延迟权衡：为什么不是每次都该“保成功率”"><a href="#八、成本-延迟权衡：为什么不是每次都该“保成功率”" class="headerlink" title="八、成本/延迟权衡：为什么不是每次都该“保成功率”"></a>八、成本/延迟权衡：为什么不是每次都该“保成功率”</h1>
<p>做 LLM 工程，一个特别现实的问题是：<strong>每次重试不仅增加延迟，还可能增加 token 成本</strong>。尤其是你用的是按调用计费、按 token 计费，或者上下文很长的模型时，重试不是“多等一会儿”这么简单，而是“多花一次钱”。</p>
<p>下面给一个简单的 trade-off 表：</p>

<h1 id="九、生产环境里一套更稳的调参建议"><a href="#九、生产环境里一套更稳的调参建议" class="headerlink" title="九、生产环境里一套更稳的调参建议"></a>九、生产环境里一套更稳的调参建议</h1>
<p>如果你现在正准备把 Spring AI 接进生产，我建议先按下面思路起步，而不是凭感觉乱调：</p>
<blockquote>
<p>1、先估算下游模型接口的稳态吞吐；<br>2、把应用层并发闸门设成一个保守值；<br>3、连接池略大于并发闸门，但不要夸张放大；<br>4、超时比供应商 SLA 略宽一点，不要无限等；<br>5、默认只重试 0~1 次；<br>6、流式请求和非流式请求最好拆开预算；<br>7、保留 JFR 和调用日志采样，出现抖动时能回放。</p>
</blockquote>
<p>一个比较常见、也相对稳妥的经验值是：</p>
<pre><code class="language-text">appConcurrency = 32
maxConnections = 48 ~ 64
connectTimeout = 1s
readTimeout = 10s
retryTimes = 0 ~ 1</code></pre>
<p>但请注意，这不是银弹。真正合理的值，还是要看你的：</p>
<ul>
<li>单机 CPU 和内存预算</li>
<li>模型供应商限流策略</li>
<li>请求平均 prompt 大小</li>
<li>是否流式输出</li>
<li>是否还有 RAG 检索、重排、缓存等额外步骤</li>
</ul>

<h1 id="十、常见坑与误区"><a href="#十、常见坑与误区" class="headerlink" title="十、常见坑与误区"></a>十、常见坑与误区</h1>

<h2 id="10-1-误区一：只看平均延迟"><a href="#10-1-误区一：只看平均延迟" class="headerlink" title="10.1 误区一：只看平均延迟"></a>10.1 误区一：只看平均延迟</h2>
<p>平均值很容易掩盖问题。P50 很好看，不代表用户体验就好。真正影响投诉率的，经常是 P95/P99。</p>

<h2 id="10-2-误区二：线程越多性能越好"><a href="#10-2-误区二：线程越多性能越好" class="headerlink" title="10.2 误区二：线程越多性能越好"></a>10.2 误区二：线程越多性能越好</h2>
<p>IO 型调用里，线程多不等于吞吐高。很多时候只是让更多线程一起排队。</p>

<h2 id="10-3-误区三：失败就重试，总能救回来"><a href="#10-3-误区三：失败就重试，总能救回来" class="headerlink" title="10.3 误区三：失败就重试，总能救回来"></a>10.3 误区三：失败就重试，总能救回来</h2>
<p>如果失败原因是下游已经拥塞，重试等于补刀。尤其在高峰期，重试会把抖动从局部故障放大成系统性故障。</p>

<h2 id="10-4-误区四：所有-AI-接口共用一套连接预算"><a href="#10-4-误区四：所有-AI-接口共用一套连接预算" class="headerlink" title="10.4 误区四：所有 AI 接口共用一套连接预算"></a>10.4 误区四：所有 AI 接口共用一套连接预算</h2>
<p>流式输出连接占用时间更长，和普通短请求混在一起时，很容易相互挤压。更稳的做法是按场景拆分客户端或预算。</p>

<h1 id="十一、总结"><a href="#十一、总结" class="headerlink" title="十一、总结"></a>十一、总结</h1>
<p>把今天这篇文章压缩成几句人话，其实就是：</p>
<ul>
<li>Spring AI 接 LLM，最常见的性能问题不是“模型不行”，而是 <strong>客户端侧预算没有收住</strong></li>
<li><strong>连接池太小</strong> 会让请求先在客户端排队，P95/P99 明显变差</li>
<li><strong>应用并发太高</strong> 不一定带来吞吐提升，反而容易制造拥塞</li>
<li><strong>重试</strong> 能提升成功率，但一定是在拿延迟和成本做交换</li>
<li>定位这类问题时，<strong>P95/P99 + JFR</strong> 比只盯平均值更有用</li>
</ul>
<p>如果你准备把 Java × AI 服务真正跑到线上，建议优先把下面三件事补齐：</p>
<blockquote>
<p>1、并发闸门；<br>2、连接池与超时配置；<br>3、JFR + 压测基线。</p>
</blockquote>
<p>这三件事做好了，你的服务不一定立刻“飞起来”，但至少不会在流量一上来时先自己抖散架。</p>
