<blockquote>
<p>很多 Java 服务一遇到高峰流量，第一反应就是把线程池调大、把队列拉长，觉得这样“更稳”。但线上真实情况往往刚好反过来：吞吐没怎么涨，<strong>P99 延迟</strong> 先飙了，GC 也开始变难看。这篇文章就用一个可复现实验，把这个坑拆开讲清楚。</p>
</blockquote>

<h1 id="一、问题是怎么来的"><a href="#一、问题是怎么来的" class="headerlink" title="一、问题是怎么来的"></a>一、问题是怎么来的</h1>
<p>在 Java 服务里，线程池基本是绕不过去的。你写异步任务、批量处理、消息消费、下游调用隔离，最后多半都会落到 <strong>ThreadPoolExecutor</strong> 上。它本质上就是一个“任务分发器”：有空闲线程就直接执行，线程忙不过来就先排队，排队也顶不住了再扩线程，最后彻底扛不住才拒绝。</p>
<p>问题就出在很多项目把“先排队”这件事想得太美好了。队列不是免费的缓冲区，它是把延迟、内存占用、对象存活时间一起往后拖。你看到系统没报错，不代表系统健康；很多时候只是请求还没死，只是在队列里闷着。</p>
<p>这篇文章我想回答 3 个具体问题：</p>
<ul>
<li>为什么线程池队列一旦配得太大，<strong>P99 延迟</strong> 会先恶化？</li>
<li>为什么你把 <code>maxPoolSize</code> 加大了，吞吐未必跟着涨？</li>
<li>怎么用 <strong>JFR</strong> 和 <strong>async-profiler</strong> 把问题抓出来，而不是靠感觉调参数？</li>
</ul>
<pre><code>注：P99 指 99% 的请求都比这个延迟更快，只有最慢的 1% 会落在它后面。线上用户体感经常不是看平均值，而是看这些“尾部延迟”。
注：JFR（Java Flight Recorder）是 JDK 自带的低开销运行时诊断工具，适合抓线程状态、锁竞争、分配热点、GC 行为。
注：async-profiler 是一款常用的 Java 性能剖析工具，能抓 CPU、alloc（对象分配）、lock 等热点，比只看 top/jstack 更接近根因。
</code></pre>

<h1 id="二、先说结论：大队列经常是在隐藏问题，不是在解决问题"><a href="#二、先说结论：大队列经常是在隐藏问题，不是在解决问题" class="headerlink" title="二、先说结论：大队列经常是在隐藏问题，不是在解决问题"></a>二、先说结论：大队列经常是在隐藏问题，不是在解决问题</h1>
<p>先把结论放前面，避免大家一路看到最后还想“那到底怎么配”。</p>
<ul>
<li>如果任务是 <strong>CPU 密集型</strong>，线程数超过 CPU 核数太多，通常不会提高吞吐，只会增加上下文切换。</li>
<li>如果任务是 <strong>I/O 密集型</strong>，线程池可以放宽，但也不能无限排队，否则请求会在队列里白白等待。</li>
<li><strong>队列越大，失败越晚暴露</strong>。这听起来像优点，实际上很危险，因为延迟、内存、超时会一起被拖坏。</li>
<li>生产环境里，线程池更像一个<strong>背压阀门</strong>，不是垃圾桶。背压的意思很简单：系统忙不过来时，要尽快把“忙不过来”暴露出去，而不是把任务越攒越多。</li>
</ul>
<p>所以，线程池参数设计的核心不是“怎么让它永远不拒绝”，而是“怎么让它在容量边界内稳定工作，在越界时尽快失败并可观测”。</p>

<h1 id="三、实验模型：同样的接口，为什么两个线程池表现差这么多"><a href="#三、实验模型：同样的接口，为什么两个线程池表现差这么多" class="headerlink" title="三、实验模型：同样的接口，为什么两个线程池表现差这么多"></a>三、实验模型：同样的接口，为什么两个线程池表现差这么多</h1>
<p>为了把问题讲清楚，我们做一个很接近日常业务的模型：Spring Boot 提供一个 HTTP 接口，收到请求后把任务丢进线程池。任务本身不是纯睡眠，而是“少量 JSON 处理 + 一段可控延迟”，模拟常见的下游 RPC/数据库操作。</p>
<p>下面是核心代码，已经尽量缩到最小可复现：</p>

```java
@RestController
@RequiredArgsConstructor
public class DemoController {

    private final TaskService taskService;

    @GetMapping("/work")
    public Map<String, Object> work(@RequestParam(defaultValue = "80") long costMs) throws Exception {
        long begin = System.nanoTime();
        Map<String, Object> result = taskService.handle(costMs).get(1500, TimeUnit.MILLISECONDS);
        long elapsedMs = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - begin);
        result.put("elapsedMs", elapsedMs);
        return result;
    }
}
```

```java
@Service
public class TaskService {

    private final ThreadPoolTaskExecutor executor;
    private final ObjectMapper objectMapper = new ObjectMapper();

    public TaskService(@Qualifier("bizExecutor") ThreadPoolTaskExecutor executor) {
        this.executor = executor;
    }

    public CompletableFuture<Map<String, Object>> handle(long costMs) {
        return CompletableFuture.supplyAsync(() -> {
            try {
                // 模拟少量 CPU 工作
                String json = "{\"name\":\"jarvis\",\"costMs\":" + costMs + "}";
                JsonNode node = objectMapper.readTree(json);

                // 模拟 I/O 或下游调用耗时
                LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(node.get("costMs").asLong()));

                return new HashMap<>() {{
                    put("thread", Thread.currentThread().getName());
                    put("ok", true);
                }};
            } catch (Exception e) {
                throw new RuntimeException(e);
            }
        }, executor);
    }
}
```

<p>重点看线程池配置。我们对比两组：</p>

```java
@Bean("bizExecutor")
public ThreadPoolTaskExecutor bizExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(8);
    executor.setMaxPoolSize(16);
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("biz-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    // 方案 A：queueCapacity = 1000
    // 方案 B：queueCapacity = 64
    executor.initialize();
    return executor;
}
```

<p>这里有两个容易忽略的点：</p>
<ul>
<li><strong>CallerRunsPolicy</strong> 的意思是，线程池忙不过来时，让提交任务的调用线程自己执行任务。它不是“优雅降级”，本质上是一种反压手段：上游发得越猛，自己越容易被拖慢。</li>
<li><strong>queueCapacity</strong> 指阻塞队列可容纳的任务数。很多人一看到拒绝策略就心慌，顺手把它配成 1000、5000，甚至无界队列。这通常是事故伏笔。</li>
</ul>

<h1 id="四、压测方法与环境"><a href="#四、压测方法与环境" class="headerlink" title="四、压测方法与环境"></a>四、压测方法与环境</h1>
<p>实验环境如下：</p>
<ul>
<li>JDK：OpenJDK 21</li>
<li>Spring Boot：3.3.x</li>
<li>机器：4 vCPU / 8 GB 内存</li>
<li>JVM 参数：<code>-Xms512m -Xmx512m -XX:StartFlightRecording=filename=app.jfr,dumponexit=true</code></li>
<li>压测工具：wrk</li>
</ul>
<p><strong>wrk</strong> 是一个轻量 HTTP 压测工具，适合快速看吞吐和延迟分布；如果你更熟悉 JMeter、hey、ab，也可以替换，但建议保留并发和请求时长一致，方便对比。</p>

<p>压测命令如下：</p>

```bash
wrk -t4 -c128 -d60s --latency 'http://127.0.0.1:8080/work?costMs=80'
```

<p>同时再开一个窗口，每 2 秒抓一次线程池和 GC 侧指标：</p>

```bash
jcmd $(pgrep -f 'demo.*jar') Thread.print > /tmp/thread-dump.txt
jstat -gcutil $(pgrep -f 'demo.*jar') 2s 30
```

<p>如果你装了 async-profiler，可以在压测中段抓 30 秒分配热点：</p>

```bash
./profiler.sh -d 30 -e alloc -f /tmp/alloc.html $(pgrep -f 'demo.*jar')
```

<h1 id="五、实验结果：吞吐差不多，P99 完全不是一个世界"><a href="#五、实验结果：吞吐差不多，P99 完全不是一个世界" class="headerlink" title="五、实验结果：吞吐差不多，P99 完全不是一个世界"></a>五、实验结果：吞吐差不多，P99 完全不是一个世界</h1>
<p>下面是两组典型结果。不要死抠绝对数字，重点看趋势。</p>

| 方案 | core/max | queueCapacity | QPS | Avg | P50 | P95 | P99 | 超时率 | Young GC 次数 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| A：大队列 | 8/16 | 1000 | 182 | 436ms | 118ms | 1210ms | 1684ms | 3.8% | 19 |
| B：小队列 + 反压 | 8/16 | 64 | 176 | 132ms | 96ms | 248ms | 382ms | 0.6% | 7 |

<p>你会发现一个很反直觉的现象：<strong>方案 A 的吞吐并没有明显更高，但尾延迟和超时率明显更差</strong>。</p>
<p>原因并不神秘：</p>
<ol>
<li>请求一旦进了长队列，哪怕真正执行只要 80ms，也会先在队列里等上几百毫秒。</li>
<li>排队任务越多，相关对象活得越久，更容易从 Eden 区熬到 Survivor，甚至进入老年代，GC 压力就会变大。</li>
<li>调用方通常有超时时间，比如 500ms、1s、2s。长队列会把很多“本来能做完”的任务拖到超时边界之外，造成无效计算。</li>
</ol>

<p>这就是为什么我前面说：大队列经常不是把系统救了，而是把问题藏起来了。它让系统看上去还能接请求，但用户体验已经明显变差。</p>

<h1 id="六、JFR-里能看到什么：线程没满，但请求已经堵住了"><a href="#六、JFR-里能看到什么：线程没满，但请求已经堵住了" class="headerlink" title="六、JFR-里能看到什么：线程没满，但请求已经堵住了"></a>六、JFR 里能看到什么：线程没满，但请求已经堵住了</h1>
<p>很多同学排查性能问题时，只会盯着 CPU 使用率。这个场景里，CPU 可能根本不高，但延迟已经非常难看，所以只看 CPU 很容易误判。</p>
<p>在 JFR 里，这个问题通常会表现为：</p>
<ul>
<li><strong>Java Monitor Blocked</strong> 不一定高，因为主要矛盾不是锁。</li>
<li><strong>Thread Park</strong>、<strong>Socket Read</strong>、<strong>Executor</strong> 相关事件会更明显，说明线程经常在等待外部资源或排队调度。</li>
<li><strong>Object Allocation in New TLAB / Outside TLAB</strong> 总量会随着排队任务增多而放大。</li>
<li>GC Pause 虽然不一定长得离谱，但发生频次会上升。</li>
</ul>

<p>一个很典型的观察是：线程池活跃线程数并没有一直打满到 16，但是接口 P99 已经很高。为什么？因为瓶颈不一定是“线程不够”，而是<strong>任务完成时间 = 排队时间 + 执行时间</strong>。当排队时间开始占大头时，你看到的就不是执行慢，而是系统调度策略有问题。</p>

<p>抓 JFR 的命令可以这样写：</p>

```bash
jcmd $(pgrep -f 'demo.*jar') JFR.start \
  name=queue-test \
  settings=profile \
  filename=/tmp/queue-test.jfr

# 压测 60 秒后停止
jcmd $(pgrep -f 'demo.*jar') JFR.stop name=queue-test
```

<p>然后用 JDK Mission Control 打开，重点看这些页签：</p>
<ul>
<li>Threads：线程状态分布、活跃时间</li>
<li>Method Profiling：热点方法</li>
<li>Allocation：对象分配速率</li>
<li>Garbage Collections：GC 次数和停顿</li>
</ul>

<h1 id="七、async-profiler-怎么看：问题不总在-CPU，而在分配和等待"><a href="#七、async-profiler-怎么看：问题不总在-CPU，而在分配和等待" class="headerlink" title="七、async-profiler-怎么看：问题不总在 CPU，而在分配和等待"></a>七、async-profiler 怎么看：问题不总在 CPU，而在分配和等待</h1>
<p>如果你只抓 CPU flame graph，可能看到的热点并不夸张，因为这个实验本身不是 CPU 被打爆，而是排队和对象存活时间出了问题。所以这里更推荐抓 <strong>alloc</strong> 事件，也就是对象分配火焰图。</p>
<p>在大队列方案里，通常会看到这些热点更显眼：</p>
<ul>
<li><code>LinkedBlockingQueue$Node</code>：队列节点对象增多</li>
<li><code>CompletableFuture</code> 相关对象：异步编排对象增多</li>
<li>业务 DTO / JSON 解析对象：随着积压任务增加，存活时间变长</li>
</ul>
<p>这类问题的危险点在于，它不是某一行代码“特别慢”，而是整条请求链路上多了大量“该早点失败却没失败”的任务。最终效果就是内存更忙、GC 更频繁、延迟更差。</p>

<h1 id="八、怎么设计更靠谱的线程池参数"><a href="#八、怎么设计更靠谱的线程池参数" class="headerlink" title="八、怎么设计更靠谱的线程池参数"></a>八、怎么设计更靠谱的线程池参数</h1>
<p>线程池没有银弹参数，但有一套相对靠谱的工程化思路。</p>

<h2 id="1-先判断任务类型"><a href="#1-先判断任务类型" class="headerlink" title="1. 先判断任务类型"></a>1. 先判断任务类型</h2>
<ul>
<li><strong>CPU 密集型</strong>：比如加解密、压缩、复杂 JSON 计算、规则引擎。线程数通常以 CPU 核数附近为起点，别一上来开几十上百。</li>
<li><strong>I/O 密集型</strong>：比如查库、RPC、HTTP 调用、消息发送。线程数可以适当放大，但前提是你知道等待时间和超时上限。</li>
</ul>

<h2 id="2-队列别一上来就配很大"><a href="#2-队列别一上来就配很大" class="headerlink" title="2. 队列别一上来就配很大"></a>2. 队列别一上来就配很大</h2>
<p>我的建议是：先从一个<strong>小而可观测</strong>的队列开始，比如 32、64、128，再结合压测和生产指标调整。你要先知道系统什么时候开始吃紧，而不是用一个大队列把这个边界糊掉。</p>

<h2 id="3-优先定义超时、拒绝和降级策略"><a href="#3-优先定义超时、拒绝和降级策略" class="headerlink" title="3. 优先定义超时、拒绝和降级策略"></a>3. 优先定义超时、拒绝和降级策略</h2>
<p>很多项目只配线程数，不配超时和拒绝策略，这其实是不完整的。更合理的组合通常是：</p>
<ul>
<li>明确接口超时</li>
<li>明确下游调用超时</li>
<li>明确线程池拒绝后的处理方式</li>
<li>明确熔断/限流/降级策略</li>
</ul>
<p>如果这些都没有，大队列只会让事故来得更晚，但更大。</p>

<h2 id="4-把线程池指标接进监控"><a href="#4-把线程池指标接进监控" class="headerlink" title="4. 把线程池指标接进监控"></a>4. 把线程池指标接进监控</h2>
<p>线上至少要监控这些指标：</p>
<ul>
<li><code>activeCount</code>：活跃线程数</li>
<li><code>poolSize</code>：当前线程数</li>
<li><code>queueSize</code>：排队任务数</li>
<li><code>taskCount</code> / <code>completedTaskCount</code></li>
<li>拒绝次数</li>
<li>接口 RT（尤其 P95 / P99）</li>
</ul>
<p>如果你只监控平均延迟，那这个问题很容易漏掉。平均值会掩盖很多尾部请求的痛感。</p>

<h1 id="九、可复现步骤：你可以在自己机器上跑一遍"><a href="#九、可复现步骤：你可以在自己机器上跑一遍" class="headerlink" title="九、可复现步骤：你可以在自己机器上跑一遍"></a>九、可复现步骤：你可以在自己机器上跑一遍</h1>
<p>把实验步骤整理成最短路径，方便你自己复现：</p>
<ol>
<li>新建一个 Spring Boot 3 项目，引入 <code>spring-boot-starter-web</code>。</li>
<li>按上面的代码创建接口和线程池配置。</li>
<li>先把 <code>queueCapacity</code> 设为 <code>1000</code>，启动服务。</li>
<li>执行压测命令：<code>wrk -t4 -c128 -d60s --latency 'http://127.0.0.1:8080/work?costMs=80'</code>。</li>
<li>记录吞吐、P50/P95/P99、超时率、GC 次数。</li>

<li>对比两组结果，并打开 JFR / async-profiler 输出文件。</li>
</ol>

<h2 id="如何验证结论"><a href="#如何验证结论" class="headerlink" title="如何验证结论"></a>如何验证结论</h2>
<ul>
<li>如果大队列方案的 QPS 没明显上升，但 P99 明显变差，说明“靠排队换吞吐”没有成立。</li>
<li>如果大队列方案的 GC 次数更多、分配热点更集中在队列节点和异步对象，说明积压任务确实加重了内存压力。</li>
<li>如果小队列方案出现少量拒绝或调用线程被拖慢，但整体 P99 更稳，说明反压比“无限积压”更健康。</li>
</ul>

<h1 id="十、常见坑与误区"><a href="#十、常见坑与误区" class="headerlink" title="十、常见坑与误区"></a>十、常见坑与误区</h1>
<ul>
<li><strong>误区 1：队列越大越安全。</strong><br>错。队列越大，只是越不容易立刻拒绝，不代表整体稳定性更好。</li>
<li><strong>误区 2：只要 maxPoolSize 足够大，吞吐就会上去。</strong><br>错。如果瓶颈在数据库、下游接口、网络或者锁竞争，盲目扩线程只会制造更多等待。</li>
<li><strong>误区 3：平均延迟还行，就说明线程池没问题。</strong><br>错。线程池问题最容易先体现在 P95/P99，而不是平均值。</li>
<li><strong>误区 4：CallerRunsPolicy 一定是好策略。</strong><br>也不绝对。它适合做反压，但如果调用线程本身是 Tomcat/Netty 工作线程，拖慢过头也可能影响入口层吞吐，所以要结合网关超时、隔离设计一起看。</li>
<li><strong>误区 5：线程池参数可以拍脑袋套模板。</strong><br>错。线程池一定要结合任务类型、超时、容量目标、压测数据和监控结果一起定。</li>
</ul>

<h1 id="十一、一个更实用的落地建议"><a href="#十一、一个更实用的落地建议" class="headerlink" title="十一、一个更实用的落地建议"></a>十一、一个更实用的落地建议</h1>
<p>如果你现在就要去改生产参数，我更建议按这个顺序做：</p>
<ol>
<li>先补监控：线程池活跃数、队列长度、拒绝数、P95/P99。</li>
<li>再补超时：入口超时、下游超时、Future 超时。</li>
<li>然后缩队列，不要一口气缩到很激进，先从 1000 → 256 → 128 → 64 逐步验证。</li>
<li>最后结合压测和 JFR/async-profiler 结果，决定要不要继续调大线程数，或者干脆改异步模型。</li>
</ol>
<p>说白了，线程池参数不是“配完就忘”的 YAML，它是容量治理的一部分。你得把它当成生产系统行为的一部分来观测，而不是只当成一个默认配置。</p>

<h1 id="十二、总结"><a href="#十二、总结" class="headerlink" title="十二、总结"></a>十二、总结</h1>
<ul>
<li>线程池大队列最常见的问题，不是报错太多，而是<strong>尾延迟被悄悄拖坏</strong>。</li>
<li>吞吐没有明显提升时，继续放大队列通常没有意义，反而会加重对象存活和 GC 压力。</li>
<li>看线程池不能只看线程数和 CPU，还要看队列长度、拒绝次数、P95/P99、GC 和分配热点。</li>
<li>JFR 适合看线程状态、分配和 GC；async-profiler 适合看 CPU / alloc 热点，两者结合比拍脑袋调参靠谱得多。</li>
<li>生产环境里，合理反压通常比“无限积压”更健康。</li>
</ul>
